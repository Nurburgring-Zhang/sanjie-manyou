# D1 引擎与几何管线

> **本卷服从 D0《重建纲领》的 ADR-2（几何管线分层：烘焙是基底，运行时只能追加）。**
> 同时受 ADR-1（坐标唯一真相源）、ADR-4（热更新只有资产热替换）、ADR-7（性能预算前置）、
> ADR-9（本体必须改动，`LodManager` 加 `unregister`、`ensureWalkSurface` 加局部失效）约束；
> 凡与 ADR 冲突之处，以 ADR 为准，本卷只做细化，不改裁决。
>
> **本卷不复述 ADR-5／ADR-6 的内容**：那两条管的是「代码在哪执行」与「议会怎么开」，
> 与本卷的几何管线只在 `CreationBundle` 的接收端相接，接口面写在 §2.2，机制由 D5／D6 持有。
>
> **行号基线**：工作树 `806fa79`（v93 提交）+ v96 未提交改动，**未锁 commit**；
> 实施前须按《勘误》整卷重锚。所有 `文件:行号` 均指该基线，不指 release 包内压缩后的代码。

## 0. 两个口径的基线，不许混用

D0 §0 给的是**打包态**（`release-v96` 的 `win-unpacked`，`file://` 加载，真 GPU）的数字。
本卷为了拿到「逐段」而不是「总和」的耗时，另跑了一次**同一份 `dist/` 走本地 HTTP + headless SwiftShader** 的复测。
两次数值不同，原因不是代码变了，而是环境变了。**本卷所有「逐段耗时」来自复测，所有「红线与余量」来自 D0。**

| 项 | D0 打包态（v96） | 本卷复测（dist + http + headless） | 说明 |
|---|---|---|---|
| `navToEngineMs` | 297（= 11,926 − 11,629） | **400** | 导航→引擎开始生成 |
| `engineMs` | **11,629** | **10,289** | 引擎内世界生成 |
| `flushMs`（内含） | **918** | **999** | 每步 `baker.flush` 累计 |
| 两步之和 | 11,926 / 红线 12,000 ⇒ **余量 74ms** | 10,689 | 复测更快不等于余量变大 |
| `__heapPre` → `__heapPost` | 未采 | **2,458 → 1,817MB**（−641MB） | 合批释放量 |
| 加载步数 | 33（D0 口径） | **35**（`__loadTimings.length`） | 复测把两段拆成了独立步 |
| 步自报合计（**含 flush**） | 约 14,000（D0 注释的历史值） | **9,288ms** | 见 §1.1 表与 §1.7 |

三个必须写死的口径纪律：

1. **`engineMs` 是载入期指标**，起点是 `window.__loadStartAt`（`src/world.ts:697`），
   终点是 `window.__loadEndAt`（`src/world.ts:834`）。运行时发生的任何事情都**不进这个数**。
   本卷 §3 的热替换之所以敢说「不影响 `engineMs`」，依据就是这两个赋值点的位置，不是推测。
2. **面数必须带口径**。D0 §0 的四个数：`T_static` 18,959,342（烘焙期逐组求和）、
   `T_scene` 19,873,969（Mesh 单份几何）、`T_frame` 45,911,485（单帧提交，含实例展开与多 pass）。
   本卷只新增 `rt_` 对象，它们只进 `T_scene` 与 `T_frame`，**永不进 `T_static`**。
3. **draw call 与机位强相关**。同一份 `dist/`、同一台机，两次加载后 `renderer.info.render.calls`
   分别读到 **378**（对应 `T_frame` 45,905,081）与 **240**（对应 25,832,161）。差异来自开场运镜机位与视锥剔除，不是代码差异。
   **结论：draw 额度只能按「绝对增量」记**，按百分比记换个机位基线就漂；§4.3 因此写 `+36 calls` 而非 `+9.5%`。

## 1. 载入期烘焙链：逐段的输入、输出、实测与失败模式

### 1.0 链的真实拓扑（先纠正 D0 的一处措辞）

D0 的 ADR-2 把链写成「`Baker` 累积 → `flush` → `compactStatic` → `scaleHeavenGeometry` → `enlargeLingxiao` → LOD 注册」。
这段顺序在**几何变换**上完全正确，但在**代码位置上**有两处偏差，必须在本卷写清，否则实现者会去错文件里加埋点：

| 段 | 真实调用点 | 与 ADR-2 的差异 |
|---|---|---|
| `Baker` 累积 | 各 builder 内部调 `b.box/cyl/...`；`Baker` 类在 `src/city/bake.ts:677` | 一致 |
| `flush` | `src/world.ts:783` 的 `await baker.flush(scene)`，实现在 `src/city/bake.ts:1297` | 一致，但它是**每步一次**，共 35 次 |
| `compactStatic` | `src/world.ts:710` 定义、`:821` 调用 | 一致 |
| `scaleHeavenGeometry` | `src/sky/expansion.ts:294` 定义，`:1027` 在 `buildCloudSeaView()` 的 `bind()` 内调用；`buildCloudSeaView` 由 `src/world.ts:830` 调用 | **不在 `world.ts`**；且排在 `compactStatic` **之后**、云海切分**之前** |
| `enlargeLingxiao` | `src/sky/expansion.ts:343` 定义，`:1033` 调用（`palaceScaled` 守卫） | 同上 |
| LOD 注册 | `src/core/engine.ts:189` 的 `LodManager.register`；接线在 `:506` 的 `setLodSink(this.lod)`；唯一注册调用点是 `src/city/infill.ts:3351` | **不在链尾**，而是**穿插在烘焙过程中**（WardInfill 建一个单元注册一组） |

这条纠正有实际后果：ADR-2 写「链尾注册 LOD」，会让实现者以为「运行时新增对象要等一个统一的注册阶段」。
实测不是：注册是**随建随注册**的，`register()` 单次开销低到测不出（§1.6）。
真正需要「统一阶段」的是 `compactStatic`——它把 273 个网格并成 36 个，**此后对象身份消失**。

**这对全卷最重要的一句话**：合并之后，场景里不再有「某一栋楼」这个对象，只有「某一材质的第几批」。
任何需要按对象寻址的功能（LOD 分组、碰撞体、热替换、插入空域判定）都必须在合并**之前**把身份落到旁路数据结构里。

### 1.1 ① `Baker` 累积：35 步、9,288ms、四步超预算

**输入**：各 builder 的过程化图元调用（`b.box` / `b.cyl` / `b.sphere` / `b.roof` / `b.lathe` …）。
**输出**：14 个 `BGroup` 各自的四段缓冲（`pos` Float32×3、`normal` Int16×3 normalized、`color` Uint16×3 normalized、`uv` Float32×2）。
**实测**（复测，35 步自报合计 **9,288ms**）：

| 步 | ms | 累计 tris | 备注 |
|---|---:|---:|---|
| 山河·地形 | **1,714** | 2,792k | 超 1,200ms 预算线（`:804`） |
| 皇城·里坊民居 | **1,633** | 9,736k | 超线 |
| 皇城·宫城 | **1,519** | 9,736k | 超线；与里坊合计 3.15s |
| 云海·宫阙群 | **1,277** | 17,468k | 超线；**天宫缩放就在这一步的 bind 里** |
| 皇城·街巷铺装 | 890 | 13,335k | |
| 筑城·街屋群 | 610 | 4,996k | |
| 开天辟地 | 370 | 0k | 灯光/人群池 |
| 云起天宫 | 259 | 14,225k | |
| 幽冥·丰都街 | 216 | 18,840k | |
| 名牌图鉴 | 206 | 18,959k | 建 165 个英雄名牌 |
| 其余 25 步 | ≤176 | | 合计约 600ms |

**失败模式**（按发生概率排序）：

1. **单步超 1,200ms 只告警、不阻断**。`src/world.ts:804` 是 `console.warn`，不是 `throw`。
   复测有 4 步超线（1,714 / 1,633 / 1,519 / 1,277），最坏一步占 `engineMs` 的 16.7%。
   这意味着「加载卡一下」是**结构性的**，不是偶发 GC；任何新增几何都要先问「挂在哪个步上、该步还有多少余量」。
2. **`flush` 让帧策略**：`src/city/bake.ts:1309` 是「累计装配量超 8ms 才让一帧」。
   注释记录了旧实现「每装一组让一帧，271 次让帧等掉 4.6s」的历史。这条参数不能随手调小——
   调小会让帧次数回升，把 0.63s 的装配变成数秒的等待。
3. **共享 RNG 消耗顺序**。`src/world.ts:277` 的 `new RNG(20260905)` 被所有步共享，
   拆分步「只按调用点切，顺序逐字不变」（`:323-324` 注释）。任何新增的 `rng.next()` 插在中间，
   都会让下游全部几何**逐值改变**——不是「略有不同」，是整座城重排。
   这条是本项目最容易被忽视的确定性约束，写在这里是为了让后续卷的「新撒点」先报备。

### 1.2 ② `flush`：35 次、999ms、每步落盘

**输入**：`Baker` 当前的四个 `QBuf`。
**输出**：`city_<group>` 或 `city_<group>_<batch>` 命名的 `THREE.Mesh`，材质取自 `materialSet()` 缓存。
**实测**：`__flushMs` 累计 **999ms**（D0 打包态 918ms），占 `engineMs` 的 9.7%。
按 35 次摊，单次中位数约 **28ms**；最重的一次落在「皇城·宫城」之后（该步 tris 从 5,171k 跳到 9,736k，
单批新增 4.57M 面）。

**为什么必须每步 flush**：`src/city/bake.ts:1292-1295` 的注释给了实测依据——
「全城累积要 10M 面 / 3GB 堆，V8 在 3GB 附近进 GC 悬崖」。
复测的 `__heapPre` 2,458MB 是这个策略的产物：它记的是**合批前**水位，而单步峰值从未超过它，
说明分步落盘确实把峰值钉在「一步的量」而不是「全城的量」。

**失败模式**：

1. **`take()` 后的缓冲重建**。`QBuf.take()` 把 `n` 归零，但底层 `Float32Array` 会重新分配（`reset()` 里 `new Float32Array(4096)`）。
   单步几何量突增时这里会有一次大数组分配 + 一次拷贝，它是 `flushMs` 的主要构成，也是「同一份代码换台机器差 80ms」的来源。
2. **命名冲突**。`city_<group>_<batch>` 的 batch 号自增，与 `compactStatic` 的 `taken`（`src/world.ts:712`）是两套去重。
   将来若有代码手写 `city_wood_3`，合批时会静默改名（`:754`），探针按名字取证就取错对象。
   这是「禁止 `city_*` 命名空间」被写成硬规则的技术理由之一。

### 1.3 ③ `compactStatic`：273 → 36、−641MB、48MB 批预算

**输入**：场景里所有 `name.startsWith('city_')` 的 Mesh（`src/world.ts:716`）。
**输出**：合并后的 `city_<base>[_<n>]`，`matrixAutoUpdate = false`，`computeBoundingSphere()` 已算。
**实测**（复测，控制台原文）：

```
[加载] 静态合批：273 个网格 → 36 个（合并 22，保留单块 14，单批 ≤48MB）
```

配套的两个数字：`__heapPre` **2,458MB** → `__heapPost` **1,817MB**，净释放 **641MB**。
合并后 `city_*` 网格 **37 个**（36 个合批产物 + 1 个在合批之后由 `buildCloudSeaView` 切分出来的 `city_fabric`），
共 **56,696,487** 个 position 顶点——这个顶点数是 §1.4／§1.5 两段耗时的分母。

**耗时为什么没有直接读数**：`compactStatic` 前后只有 `__heapPre/__heapPost` 两个堆采样（`src/world.ts:815-827`），
中间没有 `performance.now()`。这是本次复测暴露的**埋点缺口**，本卷如实登记，不拿估计冒充实测。
可给的上界推算：复测测得**字节拷贝吞吐 6.74GB/s**（68.7MB / 10.2ms，`Float32Array.set`，同机同页），
城市几何按 32B/顶点（`src/city/bake.ts:455` 的实际值；该行注释写 28B 是笔误，D3 §0.3 已纠正）估
`56.7M × 32 ≈ 1.81GB`，纯拷贝下界约 **269ms**；真实合批还要加上逐块解引用、`transfer(0)` 与 22 次 `raf()` 让帧，
所以**合批段落在 300–600ms 区间**。区间不是实测，仅用于预算；要变成实测，必须加埋点（§5 A2）。

**失败模式**：

1. **单块批跳过**（`src/world.ts:746`）。`batch.length < 2` 时不合并，名字也不动。
   实测保留 14 块单块批，注释记录「这类纯拷贝有 12 块 / 554MB，最大一块 163MB」。
   保留是对的（合并 1 块没有 draw 收益），但它让「网格数」与「draw 数」不再一一对应，
   任何「合并后 mesh 数 = draw 数」的假设都会错。
2. **源与目标双份驻留**。`mergeExact` 的旧实现会同时持有源全集与目标全集；
   `releaseGeometry`（`src/world.ts:86`）改为「每拷完一块立刻 `dispose()` + `transfer(0)`」。
   复测的 −641MB 就是这条修复的直接证据。**新增任何合批逻辑必须沿用这条纪律**，
   否则峰值会回到 3.4GB（`src/world.ts:701` 的历史值）。
3. **材质是合批的键**。`byMat` 以 `material` 对象为键（`:711`），不是材质名。
   因此同一 `BGroup` 若因参数不同被建出两个材质实例，会被分成两批，draw 翻倍。
   D3 §1.5 的「不许新建材质组」在引擎侧的真实代价就在这里。
### 1.4 ④ `scaleHeavenGeometry`：56.7M 顶点、一遍 220ms

**输入**：合并后的 `city_*` 与 `sky_cloudSheets` 网格（`src/sky/expansion.ts:300`）。
**判据**（`:307-309`）：顶点 `y ≥ HEAVEN_Y_MIN(150)` 且 `|x| ≤ 1500` 且 `|z| ≤ 1500`。
**变换**（`:312`）：`x' = 2.2x`，`y' = HEAVEN_BASE_LIFTED + (y − 196) × 2.2`，`z' = 2.2z`；
与 `heavenY()` 逐字一致（这正是 ADR-1 要求「换算只有一份」的由来）。

**实测三个数**（复测，页面内对真实 `position` 属性逐点遍历）：

| 量 | 值 | 取法 |
|---|---:|---|
| 城市 `city_*` 顶点总数 | **56,696,487** | 37 个网格的 `position.count` 求和 |
| 满足 `y ≥ 150` | **13,965,449** | 24.6% |
| 再满足 `|x|,|z| ≤ 1500` | **11,488,159** | 20.3%，即真正被变换的顶点 |
| 谓词整趟（只读，含全部 56.7M 次 `getY`） | **158.2ms** | 同页 `performance.now()` |
| 写入成本（`setXYZ`，同值回写 200 万顶点） | **10.7ms** → **5.35ms/百万** | 线性外推 |

**推算该段耗时**：`158.2ms`（谓词 + 分支）+ `11,488,159 × 5.35ms/M ≈ 61.5ms`（写入）
+ 13 个 mesh 的 `computeBoundingSphere()`（实测单次 0.5ms 量级，合计 <7ms）
⇒ **约 220ms**，占复测 `engineMs` 的 **2.1%**。

这是本卷唯一一处「用吞吐 × 顶点数」得到的数字。它之所以可信，是因为**谓词那趟是在真实属性上整趟跑完的**，
不是抽样外推；只有写入那部分用了每百万顶点的线性系数。**标注为推算，不标为实测**。

**失败模式**：

1. **漏序即错位，且不会报错**。这段跑在 `buildCloudSeaView` 的 `bind()` 里（`:1027`），
   而 `bind()` 由 `src/world.ts:830` 调用。也就是说：**任何在 `cloudSea` 之后才加入的 `city_*` 天宫几何都不会被缩放**。
   现状之所以没出问题，是因为所有天宫 builder 都在 `云海·宫阙群`（含）之前的 20 步里跑完了。
   这条顺序没有断言保护——只要有人把某个天宫构件挪到「幽冥·丰都街」之后，它就会以「未缩放尺寸」直接落在 2153m 高空，
   表现为「天宫地上趴着一间 1/2.2 的小屋」。**这是本卷认为最危险的一条隐式依赖**，验收断言 A5 就为它而设。
2. **`|x|,|z| > 1500` 的静默豁免**。`:309` 跳过远处剪影（r 7.9–15km 的宫阙），避免被推出雾外。
   代价是：任何放在 ±1500m 之外的、本该属于天宫的东西不会被抬升。新内容不要往那个环带放。
3. **Float32 精度**。位置是 `Float32Array`（`src/city/bake.ts:1315`），天宫 y 已到 2100+，
   Float32 在该量级的间隔约 **0.000244m**（2⁻¹² 量级），足以支撑 1mm 级断言，但不是「无限精确」。
   §5 的 A6 断言因此把容差定在 0.001m，而不是 1e-6。

### 1.5 ⑤ `enlargeLingxiao`：13 个 mesh、137,466 顶点、一遍 136ms

**输入**：`city_*` 网格（`:349` 只挑 `city_`，不含 `sky_cloudSheets`）。
**判据**（`:356-358`）：`y ≥ LINGXIAO_Y_MIN_PRESCALE + HEAVEN_LIFT = 230 + 1935 = 2165`
且 `|x − 0| ≤ 60` 且 `|z − 209| ≤ 62`。
**变换**（`:359`）：绕锚点 `(0, 233+1935, 209)` 三轴等比 `k = 2.7273`。

**实测**：

| 量 | 值 |
|---|---:|
| 被命中的网格数（`window.__lxScaled`） | **13** |
| 命中顶点数 | **137,466** |
| 谓词整趟（56.7M 次 `getY` + 分支） | **135.1ms** |
| 推算总耗时 | `135.1 + 0.137M × 5.35 ≈ **136ms**` |

命中顶点只有 13.7 万，却要付 135ms 的谓词成本——因为**判据的第一关 `y < 2165` 对 99.76% 的顶点都要算一次**。
这是一个可以直接优化的点（倒排：先把 mesh 的 `boundingBox` 与选区求交，只对相交的 mesh 逐顶点），
但本卷**不建议现在改**：这段只跑一次、占 `engineMs` 1.3%，优化的收益远小于改坏的风险。

**失败模式**：

1. **重入 = 二次放大**。`palaceScaled` 布尔守卫（`:963`、`:1031`）只在模块作用域，
   若热重载或重复 `bind()` 把守卫绕过，台基会被放大 2.7273² ≈ 7.44 倍。
   注释已写明「bind() 若被重入（loadingDone 竞态）会把台基放大两次」。**这条守卫不能被删除，也不能被「重构掉」**。
2. **阈值口径混用（已修，留档）**。历史事故：`palace.ts` 用 233、`expansion.ts` 用 230，
   差 3m 的选区让「落在 [230,233) 的构件几何被放大、灯没被放大」，最多错位 `2.7273 × 3 ≈ 8.18m`。
   现在两处都从 `src/sky/heavenFrame.ts` import，`scripts/probe-heaven-transform-consistency.mjs` 做静态机检。
   **该门只证明常量单源，不证明运行时逐值一致**（探针原文的诚实边界）——所以 D2 §5 还要补一条运行时断言。
3. **锚点的 pre-lift 口径**。`LINGXIAO_ANCHOR_PRESCALE.y = 233` 是「已 ×2.2、尚未 +LIFT」的口径，
   代码里只 `+ HEAVEN_LIFT`、**不再乘 2.2**（`:334` 注释：「否则台基会再飞 81m」）。
   这句注释的 81 可复算：`heavenY(233) = 2131 + (233 − 196) × 2.2 = 2212.4`，
   相对云海顶面 2131 高 **81.4m**；而正确的锚点只比顶面高 `233 + 1935 − 2131 = 37m`。
   也就是说，把 233 当设计坐标再过一次 `heavenY`，锚点会从 2168 抬到 2212.4，**多抬 44.4m**，
   而「相对云海 81.4m」是另一个口径的同一错误。**两个数都对，指的却不是同一个量**——
   这正是本卷反复强调「口径必须写全」的原因。
   新人最容易在这里写错一次，且写错后画面是「殿飞了」而不是「报错」。

### 1.6 ⑥ LOD 注册：54 组、单次 0ms、**没有反注册接口**

**输入**：`LodGroupSpec`（`src/city/infill.ts:21`）：`id`、中心 `cx/cy/cz`、半跨 `hx/hy/hz`、
四档可见网格 `tiers`、极远剪影卡 `card`。
**输出**：`LodManager.groups` 里的一组，以及 `view.groups` 里的一份快照（`src/core/engine.ts:222-223`）。
**实测**：加载完成后 `__lod.view.groups.length = **54**`；`register()` 单次耗时在微基准里 **< 0.001ms**（12 次调用测不出非零中位数）。

**四档语义（容易误解，必须写清）**：`near / mid / far / impostor` **不是四份几何**，
而是「同一批对象」的可见子集——换档只改 `visible`，几何与实例数据零复制（`infill.ts:18-19` 注释）。
阈值是 `LOD_ENTER = [120, 400, 1200]`、`LOD_EXIT = [150, 470, 1350]`（`engine.ts:38`、`:40`），
滞回带 25%，防抖靠滞回而不是冷却计时。

**失败模式**：

1. **空档 = 永不隐藏**。`isReady()`（`engine.ts:316`）要求 `mid.size > 0`；
   若某组只注册 `near`、`mid` 传空数组，`firstReady` 会永远落回 `near`，整组在 1,200m 外仍然可见。
   D3 §1.8 已踩过这个坑并给出 `setReady(id, 2, false)` 的折中。本卷确认：**该折中有效，但它是绕过，不是修复**。
2. **没有 `unregister`**。`LodManager` 只有 `register` 与 `setReady`（`engine.ts:189`、`:228`），
   没有删除组的接口。复测里我连续 `register` 了 12 个基准组，`groups` 从 54 涨到 **66**，且无法回退——
   这不是探针写错，是接口缺失的实证。**热替换（§3）必须先补 `unregister(id)`，否则每次换装都会泄漏一个组**。
3. **组的距离是「到外沿包围盒」**（`engine.ts:308-313`）：相机在盒内时距离为 0。
   新对象的盒填小了 → 远看被判成近档，白画；填大了 → 近看被判成远档，糊。
   半跨必须按 `rt_` 对象的真实 AABB + 2m 余量填，不能照抄邻近组。

### 1.7 链的总账：一处对不上的账，照实写

**先纠正一个很容易犯的读表错误**：`timings` 里的 `dt` 是从「步开始」量到「flush 结束」
（`src/world.ts:778` 的 `t0` 在 task 前，`:790` 的 `dt` 在 flush 后），
**所以 35 步的 9,288ms 已经包含 flush 的 999ms**，两者不能相加。

| 段 | 实测/推算 ms | 占复测 `engineMs` 10,289ms | 数据性质 |
|---|---:|---:|---|
| 35 步自报合计（**含 flush**） | **9,288** | 90.3% | 实测，逐步 |
| ├ 其中 `flush`（35 次） | **999** | 9.7%（含在上面之内） | 实测，累计 |
| └ 其中步本体 | 8,289 | 80.6% | 相减得到 |
| 链尾 `settle`（`idle(800)` + 400ms 兜底） | ≤800 | ≤7.8% | 代码可读，实际值未测 |
| `compactStatic` | 300–600（区间） | 2.9–5.8% | **推算**（无埋点） |
| `buildCloudSeaView`：scale + enlarge | **~356**（220 + 136） | 3.5% | 谓词实测 + 写入推算 |
| `buildCloudSeaView`：云海切分/塑形/雾 | 未测 | — | 无埋点 |
| `liftHeavenResiduals` | 未测（遍历 4,494 个演员 + POI 表） | — | 无埋点 |
| LOD 注册 | < 1 | ~0% | 实测（微基准） |

**这张表对不上，而且差得很明显**：`engineMs − 步合计 = 10,289 − 9,288 = 1,001ms`，
要装下 `settle`（≤800）+ `compactStatic`（300–600）+ 两段顶点变换（≈356）+ 云海塑形 + `liftHeavenResiduals`。
**这些项的下界之和（400 + 300 + 356 = 1,056ms）已经超过 1,001ms。**

三种可能，本卷不替读者选：

1. `settle` 的 `idle(800)` 远没有跑满（`Promise.all` 里还有一个 400ms 定时器，谁先到算谁）；
2. `compactStatic` 比我推算的 300ms 更快（复测的 −641MB 只说明释放量，不说明耗时）；
3. 两段顶点变换的推算偏高（谓词那趟是在**加载完成后**跑的，V8 已 JIT 优化过一遍；真实首跑可能更慢，也可能因缓存热而更快，方向不确定）。

**这条「账对不上」本身就是本卷最有价值的实测结论之一**：
它证明 `engineMs` 的 1,001ms 尾段里有一块**没有任何埋点覆盖的黑区**，
而这正是 D1-2／D1-3 两个依赖项要补的东西。在补齐之前，任何「新增内容只花 Xms」的估算都不可靠——
因为你连现有的 1,001ms 花在哪都不知道。

**一条给后续卷的结论**：`engineMs` 里真正「可被新内容挤占」的空间不是 74ms 全部。
35 步中已有 4 步超 1,200ms 预算线，说明**单步预算已经透支**；新增几何要么挂到轻步（≤176ms 那 25 步）上，
要么必须先拆步。这条约束比「总余量 74ms」更硬。

## 2. 运行时追加路径（ADR-2）

### 2.1 为什么不能走载入期链：三条可验证的理由

**理由一：成本量级差三个数量级。**
载入期链的每一段都是「全场景遍历」：`scaleHeavenGeometry` 要读 5,667 万次 `getY`，`enlargeLingxiao` 再读一遍，
`compactStatic` 要重排 273 个网格。若运行时新增一个 2 万面的物件也走这条链，等于为了一个物件重算全城：
按 §1.4 的 158.2ms 谓词成本，单次追加就要付 **158ms 起步**，帧预算 16.7ms 直接被击穿 10 倍。

**理由二：合并之后没有对象身份。**
`compactStatic` 把 273 个网格并成 36 个（§1.3）。合并体的 `geometry` 是一整块 `BufferAttribute`，
没有「第几个三角属于哪栋楼」的索引。要让运行时对象进入合并体，就必须重新拆解—追加—再合并，
而 `mergeExact` 的峰值纪律（源与目标双份驻留）会让每次追加都付一次「目标全集拷贝」——
按 1.81GB 的城市几何算，一次就是数百 MB 的瞬时分配。这在 GC 悬崖附近是致命的。

**理由三：命名空间会污染下一次合并。**
`compactStatic` 的筛选条件是 `name.startsWith('city_')`（`src/world.ts:716`），`scaleHeavenGeometry` 是
`startsWith('city_') || startsWith('sky_cloudSheets')`（`expansion.ts:300`），`enlargeLingxiao` 是 `startsWith('city_')`（`:349`）。
三处筛选都按名字前缀。运行时对象一旦叫 `city_*`，它就自动成为**下一次**这些遍历的目标：
- 若它在人间且 y≥150，会被 `scaleHeavenGeometry` 抬到 2,100m 高空；
- 若它落在凌霄选区内，会被放大 2.7273 倍；
- 若它在下次 `compactStatic` 时还在，会被并入合并体，从此不能被单独卸载。

三条里任何一条发生，都是「不可回滚的静默变形」。**这就是 ADR-2 要求 `rt_` 前缀的全部理由**：
它不是命名风格，是**三道前缀筛选的豁免标记**。

### 2.2 接口定义

本卷给出的接口是**契约**，不是已实现代码。落点建议 `src/world/runtimeAssets.ts`（新文件，约 220 行）。

```ts
/** 运行时追加对象的唯一描述子。字段全部必填，缺一即拒收。 */
export interface RuntimeAsset {
  /** 必须匹配 /^rt_[a-z0-9_]+$/，且全局唯一 */
  id: string;
  /** 根节点。position/quaternion/scale 均为**世界值**，matrixAutoUpdate = false */
  root: THREE.Object3D;
  /** 世界 AABB（构建时算一次，之后只读） */
  aabb: THREE.Box3;
  /** 包围球：中心 + 半径，手填，不用 computeBoundingSphere 的默认值 */
  sphere: { c: [number, number, number]; r: number };
  /** 四档可见集合。至少 near 非空；mid/far 可为空数组，但必须显式给 */
  lod: { near: THREE.Object3D[]; mid: THREE.Object3D[]; far: THREE.Object3D[]; impostor: THREE.Object3D | null };
  /** 剪影卡尺寸；null = 不出卡 */
  card: { w: number; h: number } | null;
  /** 碰撞。'none' 表示可穿过的装饰物（ADR-8 §8.3 的语义） */
  collider:
    | { kind: 'none' }
    | { kind: 'box'; half: [number, number, number]; center: [number, number, number] }
    | { kind: 'sphere'; r: number; center: [number, number, number] }
    | { kind: 'capsule'; r: number; h: number; center: [number, number, number] };
  /** 释放钩子：必须幂等，且必须把 geometry/material 一并 dispose */
  dispose: () => void;
}

export interface MountResult {
  ok: boolean;
  code?: 'E_PREFIX' | 'E_DUP_ID' | 'E_NO_SPHERE' | 'E_NO_LOD' | 'E_BUDGET_CALLS' | 'E_NOT_WORLD';
  calls: number;   // 挂载后的 renderer.info.render.calls 快照
}

export function mountRuntime(a: RuntimeAsset): MountResult;
export function unmountRuntime(id: string): boolean;   // 依赖 LodManager.unregister（待补）
```

**五条硬规则，逐条对应 ADR-2**：

| ADR-2 要求 | 接口落点 | 机检方式 |
|---|---|---|
| 世界坐标构建，不走载入期变换链 | `root.matrixAutoUpdate = false`；`root.position` 直接写世界值；**禁止**把 `root` 挂到任何会带缩放的父节点下 | A6：`getWorldPosition()` 与设计值逐值比，容差 0.001m |
| 自带包围球 | `sphere` 必填；`mountRuntime` 在 `sphere.r <= 0` 时返回 `E_NO_SPHERE` | A7：每个 `rt_` 对象的 `geometry.boundingSphere.radius` 与登记值一致 |
| 显式注册 LOD | `lod.near` 非空；`register({id, …})` 后立刻 `setReady(id,'far',false)`（若 far 为空） | A8：`__lod.view.groups` 里存在该 id，且 `isReady(id,1)===false` |
| 不进 `city_*` 命名空间 | `id` 正则 + 遍历 `root` 的每个后代检查 `name` 不以 `city_` 开头 | A9：场景内不存在 `city_rt*`；`rt_` 对象数 = 登记表大小 |
| 可回滚 | `dispose()` 幂等；`unmountRuntime` 先摘 LOD 组再 `scene.remove` | A10：挂载→卸载 20 轮后 `groups` 数与 `memory.geometries` 均回到初值 |

**「世界坐标」这条要写成断言而不是口号**：最容易犯的错是把 `root` 挂进某个带 `scale` 的 `Group`
（比如 `cloudSeaGroup` 或未来的沙盒组）。一旦父节点有缩放，`position` 的世界值就被父变换乘掉了。
`mountRuntime` 应当只允许挂到 `scene` 或**明确标记为 `scale=1`** 的容器下，并在挂载后立刻做一次
`getWorldPosition()` 回读比对。

### 2.3 前缀机检的实现细节

正则不能只写 `/^rt_/`。三个必须挡住的变体：

1. `rt_` 后面直接跟大写（`rt_Foo`）——与体素侧 `rt_vox_*` 的命名约定不一致，检索会漏；
2. `rt_` 出现在名字中段（`city_rt_1`）——前缀筛选按 `startsWith`，这个名字仍会被 `city_` 命中；
3. 名字为空串（Three.js 允许匿名对象）。

因此断言是三条同时成立：
`/^rt_[a-z0-9]+(_[a-z0-9]+)*$/.test(id)`、`!id.includes('city_')`、`id.length >= 4`。

### 2.4 与 D3 体素侧的关系

D3 §1.8 已经给出 `rt_vox_<sandbox>_<chunk>` 的命名与「局部坐标 + 父变换」的构建方式。
本卷确认这两者**不冲突**，但要把边界写清：

- D3 的区块网格用**局部坐标**（0–16m）+ `mesh.position = 沙盒原点`，
  这在 ADR-2 的字面上是「不以世界坐标构建」，但**等价**：局部坐标 + 单一平移父变换 = 世界坐标，
  且不经过任何缩放。本卷接受这种等价形式，条件是**父变换只允许平移**（`scale=1`、`quaternion=identity`）。
- 因此 §2.2 的 `E_NOT_WORLD` 判定要放宽为「父链上所有变换的 scale 均为 1」，
  而不是「`position` 必须等于世界坐标」。

这条放宽不是妥协，是因为 16m×16m 的区块若用世界坐标写 Float32，在 x≈±5,000 处的精度损失约 0.0005m，
而用局部坐标可以把误差压到 1e-7 量级。**精度理由优先于字面理由**，这一条建议回写进 D0 的 ADR-2 释义。

## 3. 85ms 级的热替换（ADR-4）

### 3.1 时序：五个阶段、四个回滚点

ADR-4 允许的唯一热更新形态是「资产清单 + 动态加载 + 场景图替换」。本卷把它固化成一条五段流水线，
每段都有明确的输入、输出与失败处置。**回滚点用 R0–R4 编号，失败即回退到最近一个 R 点，不允许「部分成功」。**

```
R0 ── unmount ──▶ R1 ── validate ──▶ R2 ── mount ──▶ R3 ── registerLod ──▶ R4 ── updateCollider ──▶ 完成
      (摘旧)            (校验)            (挂新)             (注册LOD)             (刷碰撞)
```

| 段 | 动作 | 预算 ms | 实测/依据 | 失败处置 |
|---|---|---:|---|---|
| `unmount` | `lod.unregister(id)` → `scene.remove(root)` → 保留 `dispose` 不调用 | 0.2 | `scene.remove` 微基准中位数 **0.0ms**；`unregister` 待补（§1.6） | 失败：直接 R0 终止，旧对象仍在 |
| `validate` | `schema` 版本 + `hash` 比对 + 预算四关（面数/包围盒/内存/确定性，ADR-8 §8.2） | 5–10（**未测**） | 8MB 上限用 `crypto.subtle.digest('SHA-256')` 估；**这是预算不是实测** | 失败：**不卸旧对象**，回到 R0 |
| `mount` | 建 `BufferGeometry` → `scene.add(root)` → `computeBoundingSphere()` | 1.6 | 微基准 12 轮中位数：建几何 0.0 + `add` 0.0 + 包围球 **0.5** | 失败：`root.dispose()`，回 R0（旧对象从未被摘，因为 `unmount` 只摘不销毁） |
| `registerLod` | `LodManager.register({id, cx…hz, tiers, card})` + 空档 `setReady(id,'mid',false)` | 0.0 | 12 次调用测不出非零中位数（§1.6） | 失败：回 R2，摘掉新对象 |
| `updateCollider` | 用新 AABB 刷新碰撞代理；若 `collider.kind !== 'none'` 做一次自相交/落地校验 | 1.1 | 对 2 万面网格做一次垂直射线 **1.1ms**（中位数） | 失败：**保留旧碰撞体**并告警，不阻断视觉（宁可穿模，不可卡死） |
| GPU 上传 | 首帧渲染时由驱动分配 | ≤16.7（一帧） | **未测**；按一帧预算 | 不阻断 |
| **合计** | | **≈ 8–13（不含上传）/ ≈ 25–30（含一帧上传）** | | 距 85ms 还有 55–60ms 余量 |

**关于「85ms」这个数必须说清楚**：本卷实测到的 JS 侧总成本只有 **1.6ms**（2 万面、6 万顶点、`MeshLambertMaterial`；
`renderer.info.memory.geometries` 在 12 轮挂载/卸载前后保持 **213 → 213**，无泄漏）。
85ms 不是「测出来的」，而是**给这条流水线设的预算上限**：它覆盖了三件本机没有测到的事——
① 从磁盘/asar 读 GLB 并 `parse`（未测，取决于包体与解压）；
② `crypto.subtle` 哈希 8MB（未测）；
③ 首帧的 GPU 缓冲分配与着色器变体编译（未测，最坏可能触发一次 `program` 编译，本项目在同一台机上首帧编译曾达到数百毫秒）。
**所以 §5 的 A11 断言只断言「JS 侧 ≤15ms」，不断言 85ms**——85ms 是设计预算，不是可机检的事实。
把预算当实测是本项目已经踩过的坑（`flushMs` 从前一直是黑账，见 `src/world.ts:785-786` 的注释），这里不重复。

**这里有一个会直接把 85ms 打穿的坑，必须先说**：表里的 `updateCollider` 1.1ms 只是「对 2 万面网格打一次射线」，
它**不是**「把新物体接进可行走面」。后者走的是 `ensureWalkSurface()`（`src/actors/behaviors.ts:127`），
而它按 ADR-9 §9.1③ 的实测是**无参、一次性**构建 4m 空间哈希——新增可站立物体只能全量重建，
代价 80ms+。也就是说：**若 `updateCollider` 落到全量重建，85ms 预算当场破产**（1.1 + 80 ≈ 81ms 只剩 4ms 余量给其余四段）。
因此本卷的 `updateCollider` **明确限定为「动态 collider 集合的增删」**（改一个数组，不动空间哈希），
可行走面只在「造物声明了 `interact.verb === '骑'` 或可登」时才需要，且必须走 ADR-9 §9.2 序 4 的局部失效入口。
这条限定写进 §6 的 D1-8。

### 3.2 为什么它不影响 `engineMs`

三条依据，全部是代码位置而不是推测：

1. **测量区间不重叠**。`engineMs = __loadEndAt − __loadStartAt`（`scripts/verify-packaged.mjs:100`），
   `__loadEndAt` 在 `src/world.ts:834` 写入，之后 `init()` 只剩 `applyDensity / buildCinema / applyQuality` 三件收尾。
   热替换发生在 `engine.start()` 之后（`src/main.ts:45`），此时 `__loadEndAt` 早已固定。
   **即使热替换跑 10 秒，`engineMs` 也一个字节不变。**
2. **代码路径不重叠**。热替换只碰 `scene.add/remove`、`LodManager.register`、碰撞代理，
   不碰 `Baker`、不碰 `baker.flush`、不碰 `compactStatic`、不碰 `scaleHeavenGeometry/enlargeLingxiao`。
   这四段是 `engineMs` 的全部构成（§1.7 表），它们对新对象完全无感。
3. **`engineMs` 是「载入期」指标，不是「每次加载」指标**。D0 把它与 `navToEngineMs` 相加去对 12,000ms 红线，
   比的是「从导航到可玩」。热替换发生在「已可玩」之后，属于交互期，用的是帧预算（16.7ms）与 §3.1 的 85ms 预算，
   **两套预算不能互相抵扣**：不能因为热替换很快，就认为可以多加载 85ms 的东西。

**反过来说一条风险**：如果实现者把「热替换」写成「重新触发一次 `buildCloudSeaView().bind()`」，
那就会真的碰到 `engineMs` 的构成段（`scaleHeavenGeometry` 220ms + `enlargeLingxiao` 136ms），
而且 `palaceScaled` 守卫会让第二次调用**静默不放大**——结果是「一半天宫被缩放两次、一半没被缩放」。
这是本卷明确禁止的实现方式，写进 A12 断言。

### 3.3 回滚的四个不变量

回滚不是「把旧对象塞回去」那么简单，必须同时满足四条不变量，否则会出现「看起来回去了、实际泄漏了」：

| 不变量 | 判据 | 违反后果 |
|---|---|---|
| I1 对象数守恒 | 挂载失败后 `scene.children.length` 与操作前相等 | 场景图缓慢膨胀 |
| I2 LOD 组数守恒 | `__lod.view.groups.length` 回到操作前 | 每次失败泄漏一组，`update()` 的 O(n) 扫描变慢 |
| I3 几何数守恒 | `renderer.info.memory.geometries` 回到操作前 | GPU 显存泄漏（CPU 侧看不出） |
| I4 旧对象仍可渲染 | 回滚后旧 `root.visible === true` 且不在 LOD 的隐藏集合里 | 「热替换失败 → 东西消失了」 |

**I4 是最容易漏的一条**：`unmount` 若把旧对象的 `visible` 置 false，而 `mount` 又失败，玩家看到的就是「东西没了」。
正确顺序是**先挂新的、再摘旧的**（copy-on-write）：`unmount` 只把旧对象从 LOD 的可见集合里摘出，
真正的 `scene.remove` 放到 `mount` 成功之后。**§3.1 的图在这点上是错的**（图上 `unmount` 在最前），
实现必须按 `validate → mount → registerLod → 成功 → unmount 旧 → updateCollider`。
图保留是为让读者看到「意图顺序」，这段文字才是实现顺序——自我矛盾在此显式登记，不藏脚注。

## 4. LOD 与合批的冲突：独立 Mesh / BatchedMesh / InstancedMesh 三选一

### 4.1 冲突的账

合批的收益是「draw call 按材质收敛」：273 个网格并成 22 个合并体 + 14 个保留单块。
运行时新增对象**不能进这个合并体**（§2.1 理由二），所以它天然是「一个对象一次 draw」。
这就是冲突的全部：**合批把 draw 数压到材质数量级，运行时追加把 draw 数拉回对象数量级。**

先把三种选项的账摊开（`three` r180，已确认 `BatchedMesh` 与 `InstancedMesh` 均存在）：

| 选项 | draw 增量 | 适用条件 | 代价 |
|---|---:|---|---|
| 独立 `Mesh` | **+1/对象**（若 `castShadow` 再 +1） | 几何互不相同、数量少、需要单独 LOD/碰撞 | 每对象一次状态切换；无实例化收益 |
| `BatchedMesh` | **+1/材质**（多几何共享一次 draw，逐实例可见性） | 几何不同但材质相同、数量中等（十几到几百） | 需要预分配 `maxInstanceCount` 与 `maxVertexCount`；单几何不能超预算；改一个几何要重建 batch |
| `InstancedMesh` | **+1/材质/几何**（一次 draw 画 N 个同几何） | 几何完全相同、只有变换不同 | 逐实例属性只能靠 `instanceColor` / 自定义 attribute；不能逐实例换拓扑 |

### 4.2 三选一的判据（按顺序问，命中即停）

```
Q1 几何是否完全相同（顶点逐值一致，含拓扑）？
   ├─ 是 → InstancedMesh（1 draw 承载全部）
   └─ 否 → Q2
Q2 材质是否完全相同（同一个 Material 实例，不是「同 BGroup」）？
   ├─ 否 → 独立 Mesh（不同材质本来就要不同 draw，BatchedMesh 也救不了）
   └─ 是 → Q3
Q3 变体数 × 实例数 是否 ≥ 8，且都在同一 LOD 档？
   ├─ 是 → BatchedMesh（1 draw）
   └─ 否 → 独立 Mesh（BatchedMesh 的预分配开销 > 省下的 draw）
```

**Q2 的「同一个 Material 实例」是关键细节**：`compactStatic` 用 `material` 对象做合批键（`src/world.ts:711`），
不是 `BGroup` 名。两个 `MeshLambertMaterial` 即使参数逐字相同，也是两次 draw。
所以 `BatchedMesh` 的前提是**复用同一个材质实例**（`materialSet()` 的缓存，`src/city/bake.ts:1298`），
而不是「都是 `wood`」。

**Q3 的阈值 8 从哪来**：`BatchedMesh` 要为每个几何付一份 `geometry` 元数据 + 一次 `addGeometry` 调用，
并在 `maxVertexCount` 不足时整体重建。按本卷微基准的量级（一次 `add` < 0.01ms、一次 `computeBoundingSphere` 0.5ms），
8 个变体以下用独立 Mesh 的额外 draw 成本（每次 ~5–10µs 的状态切换，按 60fps 摊约 0.3–0.6ms/帧/8 个）
低于 BatchedMesh 的重建风险。**这个 8 是工程判断，不是实测**，登记在 §7 的弱点里。

### 4.3 额度：`+36 calls`，按绝对增量记

**为什么不按百分比**：同一份代码、同一台机，两次加载后 `calls` 分别读到 378 与 240（§0）。
按 378 算「+10%」是 38 个，按 240 算是 24 个——同一个方案在两次数值下会一个通过一个不通过。
**额度必须与机位无关**，所以写成绝对增量。

| 项 | 额度 | 折算 |
|---|---:|---|
| `rt_` 独立 Mesh（含 `castShadow` 的阴影 pass） | **≤ 24 个** | 24 × 1 + 24 × 1（阴影）= **+48 calls**（最坏） |
| `rt_` BatchedMesh 组 | ≤ 6 组 | +6 calls；每组 ≤ 64 个几何 |
| `rt_` InstancedMesh 组 | ≤ 8 组 | +8 calls |
| **P0 总量上限** | | **+36 calls**（常态，仅 1/3 的对象开阴影） |
| **P1 硬上限** | | **+62 calls**（全部开阴影 + 全部组都用满） |

**为什么常态是 +36 而不是 +48**：阴影 pass 只对 `castShadow` 的网格生效，而 `buildLights` 把阴影相机裁到
玩家周围 ±120m（`src/world.ts:856-857`）。运行时对象大多在 100m 生成区内（D2 §4），确实会进阴影相机；
但 ADR-8 §8.2 允许单件 2 万面，24 件全开阴影会让阴影 pass 多画 48 万面——这是 `T_frame` 的 +1.0%，
可接受；draw 的 +48 才是紧的那一头。**因此建议：`rt_` 对象默认不开阴影，只有 `lifecycle.persist === true`
且包围盒最大边 ≥ 3m 的才开**。这条写进 D5 的加载协议，不写在本卷。

### 4.4 LOD 档位与 draw 的关系：换档不减 draw，减的是「画什么」

这一点反复被误解，必须写死：`LOD_TIERS` 的四档是**同一批对象的可见子集**（`infill.ts:18-19`），
`applyVisibility`（`engine.ts:342`）只是把不在当前档的 `visible` 置 false。
**因此：**

- 一个 `rt_` 对象若只在 `near` 注册（`mid/far` 空数组），它在 400m 外**仍然可见**——
  因为 `firstReady` 会落回 `near`（`engine.ts:324-329`）。
- 想让它远看消失，必须给 `far` 一个**非空**的替身（低模或剪影卡），否则它永远以近模渲染。
- 剪影卡是**全局共享**的一个 `InstancedMesh`（`engine.ts:153`、`:302-305`），
  所以「加一张卡」的真实成本是 **+0 draw**（共享卡池），只付一次 `writeCard` 的矩阵写入。

**对 §4.3 的修正**：`rt_` 对象若配「近模 + 剪影卡」而不是「近模 + 空 far」，1,200m 外会切到共享卡池
（`engine.ts:153` 的单个 `InstancedMesh`），**draw 净减少**。所以表里的 `+36` 是「全部常驻近模」的最坏常态，
实际可以把 24 个独立 Mesh 的远场 draw 压到 1。**建议默认给每个 `rt_` 对象配卡**，成本只有一行 `card: {w, h}`。

### 4.5 反例：D3 的 200 座运行时建筑

D3 §2.6 设了「运行时建造 200 座」的上限（`E_BUILD_LIMIT`）。
若每座走独立 Mesh，就是 **+200 calls**，是本节 P1 硬上限的 3.2 倍。
按 §4.2 的判据：这些建筑**几何各不相同**（Q1 否）、**材质相同**（Q2 是，都落 `wood/roof/wall` 三组）、
**变体数 × 实例数 = 200 ≥ 8**（Q3 是）⇒ 必须走 `BatchedMesh`，每材质一组，共 **3 组 = +3 calls**。

代价是 `BatchedMesh` 的 `maxVertexCount` 必须一次预留够：200 座 × 1,608 面（D3 §2.6 的算例）
= 321,600 面；按非索引顶点 3/面、32B/顶点算 ≈ 30.9MB 顶点数据 + 索引。
**这是一次性预分配，不是增量**，所以它必须算进 ADR-7 的 Δ 表，而不是算进 draw 额度。
D3 的 200 座上限在本卷看来是合理的，但**实现方式必须是 BatchedMesh，否则 draw 预算立即破产**。
这条作为依赖项登记在 §6。

## 5. 可执行验收断言

**两类断言，两种跑法，不许混**（沿用 D3 §5 的纪律）：
`S-` 开头是**静态/纯 Node**断言，不需要浏览器，可在 CI 跑；
`R-` 开头是**打包态运行时**断言，必须对着 `release-v96` 的 `file://` 页面跑，
因为它们要读 `renderer.info`、`__lod.view`、真实 `world.getWorldPosition()`。
`vite dev` 下 `R-` 类不成立（HMR 会重建场景，`__loadStartAt` 等全局量会被重置）。

| # | 断言 | 判据 | 落点 | 类型 |
|---|---|---|---|---|
| **A1** | 合批规模与命名 | `compactStatic` 前后：`city_*` 网格数从 N 降到 M，且 `M ≤ 60`；合并后不存在两个同名网格 | `probe-compact`（待建） | R |
| **A2** | 合批埋点存在 | `window.__compactMs` 是数字且 > 0；`__heapPre − __heapPost ≥ 300MB` | 同上 | R |
| **A3** | flush 累计 | `__flushMs` ∈ [600, 1,400]；且 `__flushMs < engineMs` | `verify-packaged.mjs`（已读，加区间判定） | R |
| **A4** | 步预算 | `__loadTimings` 中 `ms > 1200` 的步数 ≤ 4（当前实测恰好 4） | `probe-load-budget.mjs`（已存在，阈值改断言） | R |
| **A5** | 天宫缩放不漏序 | 对每个 `city_*` 网格：若其 `boundingBox` 与 `y ∈ [150, 2100]` 相交且 `|x|,|z| ≤ 1500`，则该网格**不得**出现在缩放后的场景里（即缩放后所有天宫几何 `minY ≥ 2131`） | `probe-heaven-scale.mjs`（已存在，补 minY 断言） | R |
| **A6** | 世界坐标逐值一致 | 每个 `rt_` 对象 `getWorldPosition()` 与登记表设计值逐分量差 ≤ **0.001m** | `probe-runtime-assets.mjs`（待建，D3 A10 同族） | R |

| **A8** | 空档不悬挂 | 对 `rt_` 组：若 `tiers.mid` 为空，则 `lod.isReady(group,1) === false`（防 `mid.size > 0` 陷阱） | 同上 | R |
| **A9** | 命名空间隔离 | 场景中不存在名字匹配 `/^city_.*rt_/` 或 `/^rt_/` 但被 `city_` 前缀命中的对象；`rt_` 对象数 = 登记表大小 | 同上 | R |
| **A10** | 挂载/卸载无泄漏 | 20 轮 `mount → unmount` 后：`groups` 数、`memory.geometries`、`scene.children.length` 三项全部回到初值 | `probe-hotswap.mjs`（待建） | R |
| **A11** | JS 侧热替换耗时 | 2 万面对象：`mount + sphere + register + collider` 的 JS 合计 **≤ 15ms**（实测中位数 1.6ms，留 9× 余量） | 同上 | R |
| **A12** | 禁止重入缩放 | 热替换后 `window.__lxScaled` **不得增加**（第二次 `bind()` 会让它翻倍或保持不变但几何错位） | 同上 | R |
| **A13** | 前缀正则 | `RuntimeAsset.id` 三条正则（§2.3）对 30 个样本（10 合法 / 20 非法）判定全对 | `tests/runtime-asset.test.ts`（待建） | S |
| **A14** | 合批键是材质实例 | 构造两个参数相同但实例不同的 `Material`，`compactStatic` 必须分成两批（证明合批键不是名字） | 同上（纯函数化 `compactStatic` 后可测） | S |

**A5 的判据要写成一个可执行的三元组**，否则容易变成口号：

```
for (const m of cityMeshes) {
  m.geometry.computeBoundingBox();
  const bb = m.geometry.boundingBox;
  const inBand = bb.min.y < 2100 && bb.max.y > 150;      // 与天宫层带相交
  const inRange = Math.abs(bb.min.x) < 1500 && Math.abs(bb.min.z) < 1500;
  assert(!(inBand && inRange) || bb.min.y >= 2131 - 1e-3);  // 要么不在带内，要么已抬升
}
```

这条断言不需要知道哪个 mesh 是天宫，只用「y 落在层带内」这个几何事实判定：
任何漏序的天宫几何都会以 `minY ≈ 200` 留在人间上空。

**A12 为什么重要**：`palaceScaled` 是模块级布尔（`src/sky/expansion.ts:963`）。它一旦为 true，
后续 `bind()` 里的 `enlargeLingxiao` 就被跳过。如果热替换的某条路径重置了这个布尔（例如整模块热重载），
凌霄殿会被放大第二次（2.7273² ≈ 7.44 倍）。这条断言直接读 `__lxScaled` 的**增量**，
是最省事的探针形态。

**A3 的区间为什么是 [600, 1,400]**：D0 打包态 918、本卷复测 999。区间取「实测中位数 ±45%」是为了容忍机器差异，不是为了放水——
若将来涨到 1,500，说明发生了「每步都 flush 大量几何」的结构变化，必须人工看。

**探针最小契约**（与既有 `probe-*.mjs` 同款）：

```
node scripts/probe-runtime-assets.mjs --url file:///.../dist/index.html --expect 24
→ 输出 JSON { pass, rtCount, worldErrMax, lodMissing, cityLeak, groups }
→ 退出码 0=PASS / 1=BLOCK / 2=USAGE_ERROR
```

## 7. 自认最弱的三段

1. **§1.3 的 `compactStatic` 耗时是推算，不是实测。**
   我只有 `heapPre/heapPost` 两个堆采样和一个 6.74GB/s 的拷贝吞吐（68.7MB / 10.2ms），
   据此推出「300–600ms」。这个区间的下界（纯拷贝 269ms）有依据，上界（600ms）是拍的——
   我并不知道 22 次 `raf()` 让帧在里面占多少（一次 16.7ms 的帧等待，22 次就是 367ms）。
   如果下一个人按 300ms 做预算，可能低估一半。**根治只能加埋点（D1-2），靠推算不行。**

2. **§1.4 / §1.5 的「220ms / 136ms」是两段拼起来的。**
   谓词那趟是真跑完的（158.2ms / 135.1ms，真实 `BufferAttribute`、真实 5,667 万顶点），
   但**写入那部分是线性外推**（5.35ms/百万顶点，从 200 万顶点的样本推）。真实写入还包含
   `pos.needsUpdate = true` 的版本号递增与 13 个网格的 `computeBoundingSphere()`，
   后者我只测了单个 2 万面网格的 0.5ms，没有测 1,000 万面网格的包围球（那个是 O(n) 的）。
   所以这两个数是**量级可信、精度可疑**。断言 A5 只判「有没有漏序」，不判耗时，就是为了避开这个弱点。

3. **§4 的三选一判据里，阈值 8 是工程判断。**
   `BatchedMesh` 与独立 Mesh 的真实交叉点取决于驱动的状态切换成本、材质切换成本、
   以及 `BatchedMesh` 的 `maxVertexCount` 是否一次预分配够。我没有做 A/B 实测——
   那需要在打包态里各跑一遍 200 座建筑并读 `calls`，本卷的时间预算不够。
   如果 D3 真的要做到 200 座，这个阈值必须用实测替换；在此之前，「200 座走 BatchedMesh」这个结论
