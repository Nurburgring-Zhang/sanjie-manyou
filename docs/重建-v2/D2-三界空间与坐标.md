> **本卷服从 D0《重建纲领》的 ADR-1（坐标与单位只有一个真相源）。**
> 同时受 ADR-2（运行时只能追加：新对象必须在世界坐标里落位）、ADR-7（性能预算前置：新增栅格要算 Δ）约束。
> ADR-3／4／5／6／8 与本卷只在「新对象落在哪」这一点上相接，机制由各自卷册持有，本卷不越界。
>
> **行号基线**：工作树 `806fa79`（v93）+ v96 未提交改动，**未锁 commit**。
> 所有实测数字标注了取数方式：`[E]` = 本次页面内实测，`[D0]` = 引自 D0 §0 的基线，`[C]` = 由源码常量计算。

## 0. 三句话把坐标系说完

1. **单位是米，右手系，+y 朝上，场景无任何全局缩放**。三界的差别只在 y 基准与几何密度，不在坐标系本身。
2. **天宫不是「另一个场景」，它是同一场景里被抬高 + 放大的一层几何**。
   换算只有两个函数：`heavenY(y)` 与 `heavenPoint(x,y,z)`，定义在 `src/sky/heavenFrame.ts:22` / `:27`。
3. **地府也不是另一个场景**，它是在 `y ≈ −260` 处铺的一层几何，`UNDER = { y: -260, gateZ: -130, bridgeZ: -60 }`
   （`src/sky/underworld.ts:10`）。

三条合起来意味着：**「三界」是同一坐标系里的三个 y 带**，任何跨界移动都只是一次 `position.y` 的赋值或一次传送，
不存在「切换场景」「重载资源」这类动作。这条认知决定了后面所有落位都能用一个三元组写死。

| 层带 | y 区间（世界） | 判据来源 | 典型地面 |
|---|---|---|---|
| 地府 | −320 … −120 | `UNDER.y = -260`，建筑最高约 +40 | **−260.00** `[E]` |
| 人间 | −2 … +40 | `HEAVEN_Y_MIN = 150` 以下全是人间 | **−1.14 … +0.28** `[E]`，水面 **1.0** `[C]` |
| 天宫 | 2131 … 2360（含凌霄二次放大后更高） | `HEAVEN_BASE_LIFTED = 2131` 以上 | **2142.1 … 2196.8** `[E]` |
| 云海顶面 | **2131.0** | `HEAVEN_BASE_Y + HEAVEN_LIFT = 196 + 1935` `[C]` | 云盘，不可站立 |

**这三行是本卷的地基。** 后面每一个坐标都能追溯到其中一行。

## 1. 坐标唯一真相源（ADR-1）

### 1.1 两个函数、五个常量

`src/sky/heavenFrame.ts` 全文只有 44 行，它是 ADR-1 的物理载体：

```ts
export const HEAVEN_SCALE = 2.2;              // :11  等比放大
export const HEAVEN_BASE_Y = 196;             // :13  放大基准面（旧云海顶面）
export const HEAVEN_Y_MIN = 150;              // :15  天庭层下界
export const HEAVEN_LIFT = 1935;              // :17  整层抬升量
export const HEAVEN_BASE_LIFTED = 196 + 1935; // :19  = 2131，云海顶面的世界 y

export function heavenY(y: number): number {                       // :22
  return HEAVEN_BASE_LIFTED + (y - HEAVEN_BASE_Y) * HEAVEN_SCALE;
}
export function heavenPoint(x, y, z): [number, number, number] {   // :27
  return [x * HEAVEN_SCALE, heavenY(y), z * HEAVEN_SCALE];
}
```

**代数性质（本卷后面要反复用）**：

- `heavenY` 是 `y` 的**一次函数**，可逆：`y_pre = (y_world − 2131) / 2.2 + 196`。
  逆函数目前没有导出，本卷建议补一个 `heavenYInv()`，否则任何「从世界点反查设计点」的调试都要手算。
- `heavenPoint` **只缩放 x/z，不缩放 y 的偏移量以外的任何东西**——它是「等比缩放 + 平移」的复合，
  不是仿射矩阵，因此不能用「乘一个 4×4 矩阵」替代，否则会与 `HEAVEN_LIFT` 的加法顺序打架。
- 两个函数都是**纯函数、无副作用、无 THREE 依赖**。这一点很重要：它让坐标换算可以在 Node 里单测，
  不需要起浏览器（见 §5 的 S 类断言）。

### 1.2 凌霄二次放大：五个常量与一个口径陷阱

```ts
export const LINGXIAO_SCALE = 2.7273;                                   // :38
export const LINGXIAO_ANCHOR_PRESCALE = { x: 0, y: 233, z: 209 };       // :40
export const LINGXIAO_HALF_X = 60;                                      // :41
export const LINGXIAO_HALF_Z = 62;                                      // :42
export const LINGXIAO_Y_MIN_PRESCALE = 230;                             // :44
```

**口径陷阱（本卷认为最容易写错的一处）**：`LINGXIAO_ANCHOR_PRESCALE.y = 233` 的名字里带 `PRESCALE`，
但它的语义是「**已 ×2.2、尚未 +1935**」，不是「原始设计坐标」。
证据在 `src/sky/expansion.ts:334`：「锚点 y 用 pre-lift 口径的 233，这里只加抬升量、不再乘 2.2（否则台基会再飞 81m）」。
`81m` 的来源可复算：`233 × (2.2 − 1) = 81.3m`——若把 233 再乘一次 2.2，锚点会飞到 2512.6 而非 2168。

因此 `LINGXIAO_ANCHOR`（世界口径）是：

```
y = 233 + 1935 = 2168
x = 0, z = 209（不缩放，因为锚点的 x/z 在 pre-lift 口径里已经是世界值）
```

**这里有个不对称必须写清**：`heavenPoint(0, 233, 209)` 会给出 `(0, 2212.4, 459.8)`，
而 `LINGXIAO_ANCHOR` 给出 `(0, 2168, 209)`。**两者不相等，且都对**——
前者是「一个天宫设计点 (0,233,209) 的世界位置」，后者是「凌霄选区在顶点变换链里的固定锚」。
它们的 x/z 差 2.2 倍是因为选区的 x/z 判据本来就是世界口径（`|x − 0| ≤ 60`、`|z − 209| ≤ 62`），
而 `heavenPoint` 的 x/z 是设计口径。**这一条如果不讲清，下一个人一定会把锚点也过一遍 `heavenPoint`，
然后凌霄殿整体漂到 z=459.8，与 palace.ts 里建在 z≈209 的殿身错开 250m。**

### 1.3 五次事故，逐条给算式

D0 的 ADR-1 写「已踩过 3 次」，`scripts/probe-heaven-convention.mjs:4-9` 的注释列了四次，
`probe-heaven-transform-consistency.mjs:4-7` 又记了第五次。本卷按「算式可复现」的标准重列，
每一条都能用 §1.1 的两个函数验证：

| # | 事故 | 错误写法 | 误差算式 | 量级 |
|---|---|---|---|---|
| ① | 天宫窗户变 7.6m 黑洞 | 窗户几何随凌霄二次放大一起被 `×2.7273` | `2.79m × 2.7273 = 7.61m` | 单件被放大 2.7 倍 |
| ② | 神像埋进台基（低 21.8m） | `y + HEAVEN_LIFT`（只加不乘） | `Δ = 1.2y − 235.2`，`y = 214.2` 时 `Δ = 21.8m` | 低 21.8m |
| ③ | 活体神佛演员低 21.8m | 读 `SkyCenters` 的混合口径（x/z 未缩放、y 抬了） | 同 ② | 低 21.8m |
| ④ | 天宫 POI 水平偏 96–180m | `POI.pos.set(x, y+1935, z)`，x/z 没过 `×2.2` | `Δx = 1.2x`，`x ∈ [80,150]` ⇒ `Δx ∈ [96,180]` | 偏 96–180m |
| ⑤ | 凌霄阈值差 3m | `palace.ts` 用 233、`expansion.ts` 用 230 | `2.7273 × 3 = 8.18m` | 最多错位 8.18m |

**②③ 的算式展开**（这是本卷唯一需要读者动手核的一段）：

```
正确： y_world = 2131 + (y − 196) × 2.2 = 2.2y + 1699.8
错误： y_wrong = y + 1935
误差： Δ = y_world − y_wrong = 1.2y − 235.2
```

代入 `y = 214.2`（将台/神像所在的设计高度）：`Δ = 257.04 − 235.2 = 21.84m ≈ 21.8m`。
代入 `y = 233`（凌霄锚点）：`Δ = 279.6 − 235.2 = 44.4m`——**误差随 y 线性增长**，
这解释了为什么「同样一段错误写法，在低处错 21m、在高处错 44m」，
也解释了为什么这类 bug 的表现是「有的神像埋了、有的只露个头」，而不是整齐地下沉一个固定值。

**④ 的算式**：`Δx = 2.2x − x = 1.2x`。POI 的 x 落在 80–150 区间（星宿九府两列、将台、凌霄都在这个范围），
所以误差 96–180m。**这条最阴险的地方是「看起来没错」**：y 对了、方向对了、就是横向偏了半条街。

### 1.4 现有两道机检，以及它们的诚实边界

| 探针 | 判据 | 能证明 | **不能**证明 |
|---|---|---|---|
`probe-heaven-convention.mjs` | 扫描 `src/` 全部 `.ts`，`+ HEAVEN_LIFT` 若出现在位置语境（`set(`/`position`/`pos`/`.y =`/`y:`/`px`/`pz`/`translate`）且不在阈值语境（`clamp(`/`Math.min`/`Math.max`/`smoothstep`）→ BLOCK | 「没有把加法当换算用」 | 用了 `heavenPoint` 但传错参数（例如把世界 x 又传进去） |
`probe-heaven-transform-consistency.mjs` | 静态文本：两个文件都 import 五个常量、都不出现字面量 `2.7273`、都不手抄选区下界 | 「常量单源，没有手抄副本」 | 运行时变换逐值一致（探针原文：「本门只证明常量单源，不证明运行时变换真的逐值一致」） |

**本卷补一条运行时断言**（§5 的 R2）：在打包态里对 3 个已知设计点做 `heavenPoint` 计算，
再与场景里对应网格的实际顶点位置比对。这补上了两道静态门共同的盲区。

### 1.5 一条给所有后续卷的纪律

**任何坐标只允许三种写法**：

1. 人间/地府的**世界坐标字面量**（如 `new THREE.Vector3(-800, -0.9, 150)`），直接可用；
2. 天宫的**设计坐标**，必须过 `heavenPoint(x, y, z)`；
3. 从已有常量**派生**（`UNDER.y + 18`、`heavenY(206.12)`）。

**禁止**第四种：手写「部分换算」（只乘 x/z、只加 LIFT、只乘 2.2 之一）。
判定不看意图，看形态：只要出现 `× 2.2` 或 `+ 1935` 的字面量，就是第四种。
`probe-heaven-convention` 只抓 `+ HEAVEN_LIFT`，抓不到 `* 2.2`——这是它的已知缺口，本卷登记，不假装它齐备。

## 2. 三界空间：实测高度与净空

### 2.1 人间 `y ≈ 0`

**地表实测**（本次对 5 块候选沙盒足迹共 15 条垂直射线，`[E]`）：

| 位置 | 命中面 | y 值 | 高差（5 点内 max−min） |
|---|---|---|---|
| (−800, 150) 西郊 | `terrain` | −1.14 … −0.66 | **0.48m** |
| (700, 140) 东门外 | `terrain` | −0.78 … −0.50 | **0.28m** |
| (200, −210) 南岸 | `pave_patch` / `city_ground` | 0.07 … 0.28 | **0.21m** |
| (700, 52) 大街东延 | `city_ground` | 0.13 | 单点 |
| (300, −120) 南岸街南 | `city_ground` | 0.28 | 单点 |

**读法**：人间不是「一块平地」，而是「地形起伏 ±1.2m + 铺装抬高 0.1–0.3m」。
`terrain` 是程序化高度场（`src/world/terrain.ts`），`city_ground` 是铺装（烘焙进 `city_*` 合并体）。
两者差 0.1–1.3m，**落地判定必须用「射线命中面」而不是 `terrainHeight()`**——
否则人站在铺装上会被判成「陷进地面 0.3m」或「悬空 0.3m」。这是 D3 §1.6 强调「碰撞走高度场 + 体素查询」的原因，
本卷补一句：**高度场只覆盖地形，不覆盖铺装**，两者要分开存。

**水面**：`RIVER_WATER_Y = 1.0`（`src/city/riverGeom.ts:19`），全河段恒定。
河半宽城里段 **31m**、城外段 **21m**（`:26-27`），`|x|` 从 900 到 1600 平滑收窄。

### 2.2 天宫：云海 2131，台面 2142–2197，凌霄地坪 2241

**三个层高，各有来源**：

| 面 | y（世界） | 来源 |
|---|---:|---|
| 云海顶面（基准面） | **2131.00** | `HEAVEN_BASE_Y + HEAVEN_LIFT = 196 + 1935` `[C]` |
| 云盘实顶 | 2131.65 | `CLOUD_TOP_WORLD = 196.65 + 1935`（`src/sky/expansion.ts:586`）`[C]` |
| 斗法云台台面 | **2153.26** | `heavenY(206.12)`，`platform()` 台面 = y + 0.12（`src/sky/realm.ts:39`）`[C]` |
| 将台台面（`platform(0,214,20,12)`） | **2170.60** | `heavenY(214)` `[C]`；远射线实测 2170.86（`src/world.ts:298` 注释）`[D]` |
| 凌霄殿地坪（设计 246.2） | **2241.44** | `heavenY(246.2)` `[C]` |
| 星宿九府台面（设计 208–210） | 2157.4 – 2161.8 | `heavenY(208..210)` `[C]` |

**81 点扫描实测**（`[E]`，天宫 x/z ∈ [−600, 600] 步长 150，从天顶 3000m 垂直下射）：

- 命中「天宫实体面」的点共 **29 个**，y 分布 **2142.1 … 2196.8**；
- 其中 y 落在 `[2150, 2170]` 的有 18 个，占 62% ⇒ **「天宫台面 ≈ 2150」这个说法在统计上成立**；
- 命中「人间面」的点共 41 个（y ≤ 8.5），说明天宫是**稀疏岛链**，不是连续地壳——云隙可以直接看穿到人间；
- 其余 11 点无命中（射线打空）。

**这条结论对设计的直接约束**：天宫没有「地面」，只有「云台」。任何要在天宫放的东西，
要么落在某个已有台面上（台面半径 17–46 设计单位，即 37–101m 世界），要么自己造一个台。
**一个 32×32m 的沙盒，在半径 37m 的小台上放不下**（足迹对角线 45.3m > 台径）——这是 §3 里 S4 必须新建云台的实测理由。

### 2.3 地府：−260 的平台，−242 的望乡台

**实测**（`[E]`，两点各 5 条射线）：

| 位置 | 命中 | y | 高差 | 上方第一命中 |
|---|---|---|---|---|
| (−200, −150) | `city_ground` | **−260.00** ×5 | **0.00m** | +125.5m（`city_ash_3`，y≈−134.5） |
| (300, −160) | `city_ground` | **−260.00** ×5 | **0.00m** | +125.5m |

**地府是三层结构里最平的一层**：5 点全在 −260.00，高差 0。这不是巧合——
`UNDER.y = -260` 被当作绝对基准写进 `src/sky/underworld.ts:10`，
`src/sky/fengduGround.ts:39`、`src/sky/flora.ts:33`、`src/sky/expansion.ts:1229` 都用 `const y = -260` 直取。
**这是一处「事实上的唯一真相源，但不是形式上的」**：五个文件各写了一遍 −260 字面量。
`probe-heaven-convention` 的 ALLOW 只豁免了 `heavenFrame.ts` 与 `expansion.ts`，抓不到地府。
本卷建议把 `UNDER.y` 提成唯一入口（§6 依赖 D2-1），但在那之前，**任何新增地府坐标都必须 `import { UNDER }`**。

**望乡台 = −242**：`UNDER.y + 18`（`src/world.ts:306` 的 POI 与 `src/actors/crowd.ts:1691` 的
`key === 'wangxiang' ? p.pos.y - 1.5 : UNDER.y` 都用这个 18m 高差）。
**−242 不是地府地面**，它是地府里唯一一个抬高的台。把它当基准会让所有落地判定高 18m。

**上方 125.5m 的 `city_ash_3`** 是地府的「顶」——不是天空，是岩层/殿顶几何。
这意味着地府的可用净空约 **125m**，一个 24m 高的沙盒完全够用，但不能再往高里堆。

### 2.4 三界怎么连通

**只有两对传送门，都是数据驱动的**（`src/game/player.ts:474-475`）：

```
{ x: 470, y: 0,    z: 24,   to: [0, -260, -130] }   // 人间·阴阳界 → 地府
{ x: 0,   y: -260, z: -124, to: [472, 0, 28] }      // 地府 → 人间·阴阳界
```

**天宫没有传送门**——按 `src/world.ts` 的 POI 表，天宫靠「飞」上去：`POIS['jiangtai']` 的 `sky: true`
标记的落点是 `heavenPoint(0, 206.12, 9.09)`。三条界的可达性因此不对称：

| 界 | 抵达方式 | 落点 | 是否需要新传送 |
|---|---|---|---|
| 人间 | 初始出生 (−20, 0, 58) | 地面 | 否 |
| 地府 | 阴阳界 (470, 2, 24) 走进 → 传送 | (0, −260, −130) | 否（已有） |
| 天宫 | 飞 / 传送 POI | (0, 2153.26, 20) | 视沙盒位置而定（见 §3） |

**这张表是 §3「可达性」一列的依据**：人间与地府的沙盒靠「走 + 一段路」，天宫的沙盒靠「从将台飞/走 150m」。

## 3. 五块沙盒的落位（D3 的阻塞项）

D3 §6.3 把「5 块沙盒落位坐标」列为**阻塞项**：没有坐标，体素系统无法确定网格原点、
无法预生成高度场、也无法判断「进入沙盒要不要传送」。本节按 D3 §1.2 的尺寸（**32m × 32m × 24m**，
即 64×64×48 格）给出五块落位，每块都给中心、尺寸、与既有物的间距、可达性与射线取证。

### 3.1 选位的六条判据（先定规则，再给坐标）

| # | 判据 | 阈值 | 理由 |
|---|---|---|---|
| J1 | 足迹内无建筑 | 5 条垂直射线（中心 + 四角）全部命中 `terrain`/`city_ground`/`pave_*`，且**向上射线**的第一命中距地面 ≥ 24m | 沙盒高 24m，头顶有东西就穿模 |
| J2 | 地面高差 | 5 点 `max − min ≤ 0.6m` | 体素格 0.5m，高差超过一格就要逐格找平，直接吃掉「地形薄壳」的预算 |
| J3 | 避河 | `|z − riverCenterZ(x)| − riverHalfWidth(x) ≥ 40m` | 河宽 62m（城里段），沙盒压在河上要么填河要么悬空 |
| J4 | 不在水面 | 命中面名不含 `river` / `water` | 同上，且水面 y=1.0 是硬基准 |
| J5 | 可达 | 距最近的既有道路端点 ≤ 220m，或已有传送点 ≤ 200m | 超过这个距离玩家不会去，沙盒等于不存在 |
| J6 | 不压 POI | 距任一 POI 中心 ≥ 其 `radius + 16m` | POI 是导引与传送锚，压住会让导引指向沙盒内部 |

**J3 的算式用到 `riverCenterZ` 的分段定义**（`src/city/riverGeom.ts:40-46`）：
`|x| ≤ 620` 时恒为 0；620–2600 之间是 `sign(x) · 3.2 · sin²(π(a−620)/1980)`；2600 以外归零。
所以城南/城北两侧的河心并不在 z=0 上，**用「|z| > 40」做判据在 x=800 处会差 0.25m、在 x=1200 处会差 3.2m**。
本节的间距全部按函数算，不按 `|z|` 拍脑袋。

### 3.3 逐块论证

**S1 西郊农事场（−800, −0.90, 150）——为什么是「农事」**

这块的位置意义来自题材而不是空地：汴京城西是《清明上河图》开卷的田垄与扫墓返城队伍，
`src/world.ts:330` 的「山河·旷野」把 `buildDesertOutpost` 放在 (−16000, −14500)，
而 `scatterVegetation` 撒 1,500 个树点覆盖郊野。−800 这个 x 落在「郊野区（−600…−350）」之**外**，
是城内几何的空白带：5 条射线全部命中 `terrain`，没有一条命中 `city_*`。

高差 0.48m 是五块里最大的，仍在 0.6m 阈值内，但**它是唯一一块需要「先推平一格」的**：
0.48m 接近一个体素格，D3 的 `[3,3,4,3,3]` 量化在台基上会吃 0.2m 残差，叠加后可能到 0.68m。
建议 S1 的体素原点取 **−1.14**（五点的最低值），把 0.48m 的差全部做成「填方」而不是「挖方」——
填方不破坏地形高度场，挖方要改 `terrainHeight()` 的采样。

距河 119m 的算法：`x = −800` 时 `riverCenterZ = −3.2·sin²(π·180/1980) = −3.2 × 0.0794 = −0.254`，
`riverHalfWidth(−800) = 31`（`|x| < 900` 段未收窄），故水线南缘 `z = −0.254 + 31 = 30.75`。
两个口径都要给：**中心口径** `150 − 30.75 = 119.25m`（表里写的 119m），
**边缘口径** `134 − 30.75 = 103.25m`（判据 J3 用的、也是真正该用的那个，因为沙盒有 32m 宽）。
两者都 ≥ 40m，不影响结论；但**表里只写中心值是有误导风险的**，读者会以为边缘也离 119m。
下一版应把表头改成「距河（中心/边缘）」两列。

**S2 东门货场（700, −0.50, 140）——五块里最平、最干净的一块**

高差 0.28m，是五块里最小的；向上射线打到 45,892m 都没有命中，说明这块头顶**连云海都没有**
（云海是环带，东侧外缘之外是空的）。它距城墙 `WALL_X = 462`（`src/city/layout.ts:21`）238m，
距城内大街东端 (620, 52) 96m——`H_STREETS` 的第四条 `{x0: 470, x1: 620, z: 52}` 正好把街修到这里，
再往东就是野地。**这就是「货场」的题材依据**：城门外的货物堆场，紧贴大街东端，不需要新修路。

需要注意的一点：`(700, 52)` 单点射线命中 `city_ground` 0.13，说明**大街的铺装一直铺到 x=700**。
所以 S2 的南缘（z=124）离铺装带（z=52±5.5）还有 66m，不会压街。

**S3 南岸窑场（200, 0.15, −210）——唯一落在既有铺装上的沙盒**

5 点里 3 点命中 `pave_patch`（0.07）、2 点命中 `city_ground`（0.28）。
`pave_patch` 是铺装补丁（不属于 `city_*` 合并体，名字没有前缀），`city_ground` 是合并后的地面组。
两者都在 0.1–0.3m，高差 0.21m，是三块人间沙盒里**唯一「已经有硬底」的**：
这意味着沙盒的体素地面可以直接铺在既有铺装上，不需要额外做「地形过渡」。

题材上它是「南岸窑场」：汴河南岸（z < −31）在宋代是砖瓦窑与货运码头带，
`src/city/layout.ts:12` 的 `LANDMARK_KEEPOUT` 里 `[-272, -202, 34, 41]` 是漕运仓场，
S3 在 (200, −210)，与仓场相距 470m，不冲突。距南岸街（z=−52）142m，
中间没有 `LANDMARK_KEEPOUT` 的阻挡，可以走直线。

**S4 天宫新云台（−150, 2153.00, 0）——唯一一块「必须新建底座」的**

这块是本卷最不情愿、但数据逼出来的结论。我先试了两个「看起来有台面」的位置：

| 候选 | 5 点射线结果 | 结论 |
|---|---|---|
| (−450, 150)（西侧星宿岛外缘） | 4 点命中 `city_ash_3` @ **2159.80–2159.95**，1 点（−434, 134）**穿透到 `pave_patch` @ 0.07** | 台面边缘在 x ∈ [−450, −434] 之间，**32m 足迹放不下** |
| (450, −150)（东侧星宿岛外缘） | 4 点 @ 2157.75–2159.14，1 点（466, −166）命中 `city_metal` @ **2188.47** | 有构筑物，且同样在岛缘 |

两次都说明同一件事：**星宿九府的岛半径（设计 23–25，世界 50.6–55）容得下 32m 足迹的对角线（45.3m），
但容不下「足迹 + 建筑退让」**——岛中心是大殿（射线在 (0,120) 命中 `city_roof_3` @ 2282.5），
岛缘又只剩 10–16m 的环带。这不是「没找对地方」，是「已有天宫台面的尺度就是按 22–26m 岛设计的」。

于是我改用第二种取证：找**空柱**。射线在 (−180, 0) 从 3000m 打下去，命中 `bian_river` @ **y = 1**
——意味着这一柱从 2100m 到 1m **没有任何天宫几何**。再往东 (−150, 0) 同样是空柱（扫描表里 y=1）。
空柱是「可以放新台」的充分证据，但反过来也说明：**那里没有地面，必须自己造**。

因此 S4 的定义是：**中心 (−150, 2153.00, 0)，32×32 足迹，需要新增一个 `rt_heaven_pad` 云台底盘**
（建议做法：`buildIslandKeel` 同款倒锥 + 一层 0.12m 铺装，参照 `src/sky/realm.ts:39` 的 `platform()`）。
**该底盘走 ADR-2 的运行时路径还是载入期路径，是本卷留给 D1 的判断题**：
- 走载入期：需要在 `云海·宫阙群` 步内加，`engineMs` +约 3ms（一个 32×32 台面 ≈ 2,000 面）；
- 走运行时：`rt_heaven_pad`，`+1 draw`，不占 `engineMs`，但要等玩家首次进天宫才建。

本卷建议**走载入期**，理由是「沙盒的底座属于世界，不属于玩家造物」，
而且 §3.5 的落位常量本来就该在载入期确定。这一条不影响 D3 的体素侧（体素仍走 `rt_vox_*`）。

**S5 地府西鬼市（−200, −260.00, −150）——五块里唯一「零高差」的**

5 点全部 `city_ground` @ −260.00，高差 0.00m。这是三界里唯一一处「绝对平地」，
所以它不需要任何找平，体素原点直接取 −260.00 即可。

题材上它是「鬼市」：丰都鬼城在 `x≈540`（POI `fengdu`），十八狱环在 `z≈55`，
而 (−200, −150) 位于地府西侧的空场，距孟婆庄 POI (−40, −132) 约 161m、距望乡台 (−150, −150, −242) 约 50m。
**要注意望乡台**：它是一个抬高 18m 的台，POI 半径 14，沙盒足迹西缘 (−216, −150) 距其中心 66m、
距其台体边缘（假设半径 12m）约 54m，满足 J6 的 `radius + 16 = 30m`。

可达性是最弱的一块：地府抵达点 (0, −260, −130) 到 S5 中心 200m，中间要穿过孟婆庄一带的铺装。
**建议新增一个地府传送点**（`POIS['guishi']`，落在 (−200, −258, −150)，半径 12），
理由不是「走不到」，而是「地府没有天空、没有远景参照，200m 的空白步行会让玩家迷路」——
这是体验判断，不是技术约束，因此标为「建议」而不是「必须」。

### 3.4 五块的空间分布与「为什么是这五块」

把五块画在同一张平面图上（x 向右、z 向上），它们的分布是：

```
        天宫  S4 (−150, 2153, 0)          ← y 基准 2153
                     │
   ── 人间 ──────────┼──────────────────
   S1 (−800,150)     │        S2 (700,140)
```

三块人间沙盒呈「品」字：西、东、南各一块，距离出生点 (−20, 0, 58) 分别是 860m、720m、300m。

沙盒是「补丁」，不是「世界」，一旦超过 1% 就该考虑「整片地形可编辑」，那是另一个量级的工程。

### 3.5 给 D3 的引用契约

D3 需要的不是五个数字，而是**一份可以被 import 的常量表**。本卷建议落点
`src/voxel/sandboxSites.ts`（新文件，约 60 行），由 D3 持有、本卷只给值：

```ts
export interface SandboxSite {
  id: 'S1' | 'S2' | 'S3' | 'S4' | 'S5';
  realm: 'renjian' | 'tiangong' | 'difu';
  /** 沙盒原点 = 足迹的「最小角」，不是中心；体素 (0,0,0) 落在这里 */
  origin: [number, number, number];
  /** 足迹（米）：宽 × 高 × 深 */
  size: [number, number, number];
  /** 中心（米），= origin + size/2，供 LOD/POI/传送使用 */
  center: [number, number, number];
  /** 是否需要额外底座（S4 为 true） */
  needsPad: boolean;
  /** 建议的传送点（null = 不需要） */
  portal: [number, number, number] | null;
}
```

**为什么给 `origin` 而不只给 `center`**：D3 的区块网格用局部坐标（0–16m），
`mesh.position` 必须等于**区块原点**而不是沙盒中心；给中心会让每个区块多一次 `− size/2` 的偏移，
而这个偏移一旦写错，5 块沙盒会集体偏 16m。**给最小角，让偏移只发生一次。**

按上表的中心换算成 origin（`origin = center − (16, 0, 16)`，y 取地面）：

| # | origin (x, y, z) |
|---|---|
| S1 | (−816, −1.14, 134) |
| S2 | (684, −0.78, 124) |
| S3 | (184, 0.07, −226) |
| S4 | (−166, 2153.00, −16) |
| S5 | (−216, −260.00, −166) |

**S1 的 y 取 −1.14 而不是 −0.90**：按 §3.3 的「填方优先」原则，原点压在最低点，
差量用体素填。其余四块取实测最低值，理由相同。**这条规则要写进 D3 的 `sandbox.ts`**，
否则五个原点会各用各的口径（有的取均值、有的取中心），五块沙盒的地面高度就不可比了。

## 4. 100m 生成区：可插入空域的算法与判据

### 4.1 问题定义

用户许愿造物，产物必须出现在玩家周围 **100m 内**——这是 D5 的交互契约（「我看得见我刚许愿的东西」），
也是本卷要解的最后一个几何问题：**给定一个任意尺寸的造物（ADR-8 允许最大边 ≤ 200m，
但 100m 内要放下的实际上是 2–20m 量级的物件），在玩家周围 100m 的环里找一个空地。**

「空地」不是「没东西」，它有三条硬性否定：

1. **不得压既有建筑**（压了就穿模，且建筑在合并体里，事后挪不动）；
2. **不得悬空**（造物底面必须落在实体面上，允许的悬空量为 0，除非 `behavior.kind === 'fly'`）；
3. **不得落在水面中央**（落在河里会随水消失——水没有碰撞体，且 `city_water` 是独立材质组）。

这三条听起来可以用「射线一打就知道」，但实测把这条路堵死了。

### 4.2 为什么不能运行时射线：一条被实测否掉的路

本次复测在打包态场景里对 260 个可见 Mesh 打垂直射线（已过滤云/雾/天穹），得到：

| 场景 | 射线数 | 总耗时 | 单条均耗 |
|---|---:|---:|---:|
| 18 点 × 2（向下 + 净空） | 36 | 29.0s | **0.81s** |
| 16 点 × 2 | 32 | 25.7s | **0.80s** |
| 18 点 × 2（换过滤集） | 36 | 29.0s | 0.81s |
| 81 点单向下 | 81 | 85.8s | **1.06s** |
| 7 块沙盒 × 5 点 | 35 | 47.6s | 1.36s |

**单条射线 0.8–1.4 秒**。原因是射线要对 3,700 万面的合并体做逐三角求交——
`compactStatic` 之后没有 BVH，`THREE.Raycaster` 走的是线性三角形遍历。
一个 60fps 的游戏里，帧预算是 16.7ms，而这里一条射线要 800ms，**差 48 倍**。

**结论（本卷最重要的一条工程判断）**：**运行时禁止用 `Raycaster` 做落地/空域判定。**
不是「尽量少用」，是「一次都不能用」。所有落地信息必须在载入期算好，存成栅格。

这条判断与 D3 §1.6 的「碰撞走高度场 + 体素查询，不依赖网格」是同一个结论的两个面：
D3 说的是「别用网格查碰撞」，本卷补上量化依据（800ms/条），
并把它推广到「别用网格查任何空间关系」。

### 4.3 必须在合并前建索引：`insertionMask`

`compactStatic` 把 273 个网格并成 36 个（D0 与本卷复测一致）。合并之后：

- 场景里没有「某一栋楼」这个对象，只有「`city_wood` 的第 3 批」；
- `geometry.boundingBox` 是整个批的盒子（覆盖半条街），**不能用来判「这一点有没有建筑」**；
- 没有 BVH，射线又太慢。

所以空间索引必须在**合并之前**建。本卷定义三张 `InsertionMask`，每界一张：

```ts
export interface InsertionMask {
  realm: 'renjian' | 'tiangong' | 'difu';
  /** 栅格原点（世界坐标，2m 对齐） */
  ox: number; oz: number;
  /** 每格边长（m），固定 2.0 */
  cell: 2.0;
  /** 格数 */
  w: number; h: number;
  /** 每格一个字节的位域 */
  bits: Uint8Array;
  /** 每格的地面标高（世界 y），Int16，单位 0.25m —— 覆盖 −320…+2360 需要 2680/0.25 = 10,720 档，Int16 够 */
  floorY: Int16Array;
}

// 位域
const B_BUILDING = 1 << 0;   // 有建筑/构筑物（含屋顶投影）
const B_ROAD     = 1 << 1;   // 道路中线 ± w/2
const B_RIVER    = 1 << 2;   // 水域（含驳岸外 6m）
const B_POI      = 1 << 3;   // POI 半径内
const B_STEEP    = 1 << 4;   // 格内高差 > 0.6m
const B_VACANT   = 1 << 5;   // 上述全 0 且 floorY 有效（派生态，构建完成后回填）
```

**尺寸与内存（ADR-7 要求的 Δ 账）**：

| 界 | 域（世界） | 格数 | `bits` | `floorY` | 合计 |
|---|---|---:|---:|---:|---:|
| 人间 | x/z ∈ [−660, 660] | 660 × 660 = 435,600 | 425KB | 851KB | **1.25MB** |
| 天宫 | x/z ∈ [−560, 560] | 560 × 560 = 313,600 | 306KB | 613KB | 0.88MB |
| 地府 | x/z ∈ [−400, 400] | 400 × 400 = 160,000 | 156KB | 313KB | 0.45MB |
| **合计** | | | 887KB | 1.78MB | **2.58MB** |

占 D0 峰值堆 2,615MB 的 **0.099%**。这是可接受的——比 D3 的体素系统（22.8–28.9MB）小一个数量级。

**为什么是 2m 格而不是 1m**：1m 会让格数翻 4 倍（人间 1,742,400 格），内存到 10MB，
而判据的最小尺度是「造物包围盒 + 2m 退让」，2m 的量化误差（±1m）刚好等于退让量的一半，
不改变任何判定的结论。**1m 不带来精度收益，只带来 4 倍内存与 4 倍填充时间。**

**为什么人间域只到 ±660**：`src/city/infrag.ts` 的 `buildGround`/`pavement` 只铺到 ±660，
之外是 `terrain` 高度场（可以用 `terrainHeight()` 直接算，不需要栅格）。
**栅格只覆盖「有铺装、有建筑」的精细城区**，城外退化为「纯地形 + 无建筑」的快速路径。

### 4.4 栅格怎么填：三个数据源

| 位 | 数据源 | 填充时机 | 成本 |
|---|---|---|---|
| `B_BUILDING` | `Baker.box/cyl/...` 调用的 AABB（需新增 `Baker.onPrimitive` 钩子） | 烘焙期，逐图元 | 每个图元 O(足迹格数)，估算 ≤15ms（**未实测，见 §7**） |
| `B_ROAD` | `H_STREETS` / `V_STREETS`（`src/city/layout.ts:28` / `:35`）的线段 + 宽度 | 载入期一次，纯数据 | <1ms |
| `B_RIVER` | `inRiverFootprint(x, z, 6)`（`src/city/riverGeom.ts:52`） | 载入期一次，纯函数 | 435,600 次函数调用，约 2ms |
| `B_POI` | `POIS` 表的 `pos` + `radius + 16` | 载入期一次 | <0.1ms |
| `B_STEEP` | `floorY` 邻域差 | 填完 `floorY` 后一遍 | 435,600 次比较，约 1ms |
| `floorY` | 地形 `terrainHeight()` + 铺装抬高 | 载入期一次 | 435,600 次 `terrainHeight()`，**未实测**（该函数含多层噪声，单次约 1–3µs ⇒ 0.4–1.3s？） |

**这里有一个必须先测的未知数**：`terrainHeight()` 单次调用的成本。若它真是 1–3µs，
435,600 次就是 0.4–1.3 秒——**这会直接吃掉 74ms 余量，方案当场作废**。
备选方案：`floorY` 不预填，改为**首次查询时按需填**（lazy），并用 4m 格做粗查。
本条登记为 D2-2 的阻塞项：**先测 `terrainHeight()` 的真实单次成本，再决定预填还是懒填。**

**`Baker.onPrimitive` 是新增接口**（当前 `Baker` 没有图元回调）。它必须只做「记录 AABB」，
不能改任何几何——否则会破 ADR-3 的确定性（记录顺序若影响 RNG，全城重排）。

### 4.5 选址算法

输入：玩家位置 `p`、造物的 `size`（`[w,h,d]`，来自 `CreationBundle.budget` 或 AABB）、
`behavior.kind`。输出：`{ origin, rotY, score, reason }` 或 `E_NO_SPACE`。

```
1. 候选环采样
   radii  = [40, 55, 70, 85, 100]
   angles = 0°, 15°, …, 345°            // 24 等分
   cands  = 5 × 24 = 120 个候选中心

2. 硬拒（顺序执行，命中即弃）
   R1 距玩家 < 8m                    → 弃（会压在玩家身上）
   R2 mask 在「足迹 + 2m 退让」内命中 B_BUILDING  → 弃
   R3 mask 命中 B_ROAD               → 弃（不占街道）
   R4 mask 命中 B_RIVER              → 弃（不落水面）
   R5 mask 命中 B_POI                → 弃（不压导引锚）
   R6 mask 命中 B_STEEP              → 弃（除非 behavior === 'fly'）
   R7 全部格 floorY 无效（无地面）    → 弃

3. 落地计算
   floor = min(足迹内所有格的 floorY)     // 取最低，填方优先
   if (behavior.kind !== 'fly') {
     require floor ∈ [p.y − 2.5, p.y + 2.5]     // 不跨层：不允许把人引到 20m 高的屋顶
     require max(floorY) − floor ≤ 0.6          // 与 J2 同阈值
   }

4. 打分（只在通过 R1–R7 的候选里比）
   score = 0.50 × (1 − dist/100)        // 越近越好
         + 0.30 × (1 − spread/0.6)      // 越平越好
         + 0.20 × facing                // 在玩家视线前方 ±60° 内加分

5. 输出
   取 score 最大的候选；若全被拒 → 见 §4.7 的降级链
```

**120 个候选的成本**：全部是数组索引（`mask.bits[(iz − oz)/2 * w + (ix − ox)/2]`），
每候选 O(足迹格数) = 对 4m 造物是 3×3=9 格、对 20m 造物是 11×11=121 格。
最坏 120 × 121 = 14,520 次数组访问 ≈ **0.1ms 量级**（未实测，但与 §4.2 的 800ms/射线相比差 4 个数量级）。
**这就是「预计算换实时」的全部收益。**

### 4.6 三条硬性否定的判据化

| 否定 | 判据（可机检） | 误判风险 |
|---|---|---|
| 不得压既有建筑 | 足迹 + 2m 退让内的所有格 `bits & B_BUILDING === 0` | **低**：`B_BUILDING` 来自图元 AABB，是保守上界（圆柱按外接方盒算），只会更严不会更松 |
| 不得悬空 | `|objectAABB.min.y − floor| ≤ 0.05`，或 `behavior==='fly'` 且 `altitude` 与 `floor` 差 ≥ 2m | **中**：`floorY` 是 2m 格的平均，格内若有 0.5m 台阶会差半格。补偿：落地时再做一次 4 点的**高度场**采样（不是射线），不一致就以高度场为准 |
| 不得落水面中央 | `bits & B_RIVER === 0`，且 `floorY ≥ 1.5`（水面 1.0 + 0.5 安全） | **低**：`B_RIVER` 用 `inRiverFootprint(x,z,6)` 算，含 6m 驳岸带；加上 `floorY` 双保险 |

**「水面中央」为什么要加第二道**：河宽 62m，`inRiverFootprint` 的 pad=6 已经把两岸 6m 包进去，
但如果某处驳岸标高低于 1.5m（浅滩），第一道会放过、第二道会拦住。
**两道判据不是冗余，是针对「岸边」这个灰度带的**——「中央」容易判，「岸边」才是事故现场。

### 4.7 降级链与失败

```
全拒
 ├─① 扩环到 40–150m（仍是 24 向，加 3 个半径）→ 重跑 R1–R7
 ├─② 允许 B_STEEP（自动补台基，≤3 格 = 1.5m）→ 重跑
 ├─③ 允许 B_ROAD（占半幅街，造物必须 ≤ 2m 宽）→ 重跑
 └─④ 返回 E_NO_SPACE，UI 提示「附近没有空地，请走到开阔处」
```

**为什么把「占街」放在最后而不是禁止**：100m 内如果全是街与房（城中心就是），
玩家的许愿会永远失败。允许「2m 宽的小物件占半幅街」是一个**体验兜底**，
但它必须满足两个条件：造物宽度 ≤ 2m、且不落在 `LANDMARK_KEEPOUT` 里。
**这条兜底不能用于 `persist: true` 的造物**（会永久堵街），只用于 `ttl` 存在的临时物。

**失败率预估（本卷的诚实边界）**：我没有实测「玩家在城中心的 120 个候选里有多少能过」。
按精细城区的建筑密度（`belt.coverage 54%`、`belt.coverageCourt 68.5%`，见 `artifacts/audit-baseline.json`），
城中心的空地率约 **30–45%**，120 候选里应当有 35–50 个通过——**但这是推算，不是实测**。
若实际通过率低于 10%，说明 `B_BUILDING` 的 AABB 过于保守（圆柱/屋顶的方盒外扩），
需要改成「按图元类型收紧」：圆柱用内接八边形、屋顶用真实三角投影。

**A2 为什么把「不相等」写成断言**：这是本卷最容易「修对又改错」的一处。
如果哪天有人为了「统一」把锚点改成 `heavenPoint(0, 233, 209)`，代码会照常跑、测试会照常过，
但凌霄殿会从 z=209 漂到 z=459.8——**画面上一眼能看出来，代码里一行都看不出来**。
把「必须不等」写成断言，等于把这个知识点钉在 CI 上。

**A7 的容差 0.5m 从哪来**：`heavenY` 是一次函数，计算无误差；但「场景内对应实体的实际表面」
包含台面铺装厚度（`platform()` 的 `+0.06` 与 `+0.12`，`src/sky/realm.ts:39`）与包围球近似，
0.5m 是「铺装厚度 + 0.3m 采样误差」的和。**再紧就会变成「测铺装厚度」而不是「测坐标口径」**，
失去断言的意图。

**A11 的判定方式要写清**，否则会退化成「看起来对」：

```
取 1,000 个随机格 (ix, iz)：
  expect = 任一合并前 Mesh 的世界 AABB 与该格（2m×2m×全高带）相交
  actual = (mask.bits[i] & B_BUILDING) !== 0
  断言 expect === actual
```

这条需要**在合并前**把 273 个 Mesh 的 AABB 存一份快照（`window.__preCompactAabb`），
否则合并后拿不到原对象。这份快照的代价是 273 × 6 个 float ≈ 6.5KB，可忽略。

**A14 的意义**：地府现在有 5 个文件各写一遍 `-260`（§2.3）。字面量不收敛，
下一次「地府整体下移 20m」就会漏改其中两处，表现为「一半建筑浮起来」。
这条断言不改行为，只防漂移。

## 7. 自认最弱的三段

1. **§3.3 的 S4（天宫）不是「找到的空地」，是「认定必须新建底座」。**
   我只证明了「既有星宿岛容不下 32m 足迹」（两次四角射线，一次穿透、一次命中构筑物），
   以及「(−150, 0) 这一柱在 y ∈ [1, 2100] 没有天宫几何」（单点射线命中 `bian_river`）。
   **我没有对 S4 的四角做过射线**——严格说，我只知道中心点是空的，四角是否也空未验证。
   如果四角有一个点落在某个云台边缘，新底盘的形状就要改。
   这是本节唯一一处「证据链只到中心点」的地方，必须在 D3 开工前补跑一次 `probe-sandbox-sites`。

2. **§4 的整条链路一次都没跑过。**
   `insertionMask` 的填充成本、120 候选的 0.1ms、降级链的实际触发率，全部是推算。
   尤其 `floorY` 的填充成本完全取决于 `terrainHeight()` 的单次耗时，而我**没有测**这个函数——
   这是本卷最大的未知数，也是 D2-2 被列为硬阻塞的原因。
   如果实测发现 `terrainHeight()` 是 3µs/次，整章要推倒重写（改成 4m 懒填 + 粗查）。

3. **§3 的「间距」有几个是算出来的，不是量出来的。**
   「距河 119/109/179m」是我用 `riverCenterZ` 与 `riverHalfWidth` 的公式算的（可复算，可信）；
   但「距最近道路 201/96/142m」是我用 `layout.ts` 的街道端点算的，**没有考虑实际铺装的形状**
   （铺装可能比街道数据宽，也可能在某处断开）。也就是说：**这几个数只能当量级，不能当精确断言**。
   A10 因此只断言「≥40m」这个宽松下界，不断言具体值。

**收口判据**：本卷的可交付性由 §5 的 14 条断言决定。其中 A1/A2/A3/A10/A14 是纯 Node 的，
可以立刻写、立刻跑；A4–A9 需要一台能起打包态的机器与约 3 分钟的单次加载；
A11–A13 依赖 D2-2 与 D2-3 两个阻塞项。
**在两个阻塞项解除之前，本卷的 §4 只能算「设计完成」，不能算「实现完成」**；
§3 的五块坐标可以先给 D3 用，但 S4 的四角必须补测后才算锁定。
