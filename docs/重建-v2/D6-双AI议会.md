# D6 · 双 AI 议会

> **卷首复述 D0 的 ADR（不得改口）**
> - **ADR-1** 天宫坐标只有一个真相源（`heavenY()`）；阶位与空间是两套坐标，不许混。
> - **ADR-2** 运行时新增几何只能「追加」：世界坐标、自带包围球、注册 LOD、`rt_` 前缀。
> - **ADR-3** 确定性：`seed + promptHash + modelVersion` 三件齐备才可重放。
> - **ADR-4** 打包态只有资产热替换；禁止在渲染进程内执行未签名模块。
> - **ADR-5（2026-11-03 修订）** Agent **可以写代码**，但代码**必须在游戏进程外执行**，跨界只传 `CreationBundle`。
> - **ADR-6** 双 AI 议会是**设计期**机制；运行期只保留轻量评审，必须设时延与成本上限。
> - **ADR-7** 性能预算前置：先算 `ΔT_static / Δ常驻MB / ΔengineMs`。
> - **ADR-8** 构建 API 白名单、四道预算门、交互四声明、`CreationBundle` schema、hash 与回滚。
>
> **结论先行**：议会不是「两个模型聊天」，是**一个提出者、一个只许攻击的反对者、一个不会让步的机械裁判**。设计期它已经跑过多轮，累计 **15 条打回 + 1 条编造**（拆账见 §0.2）；运行期它被压成「**3 轮、12,000 token、5 分钟**」的玩法——**产物从「一份部件清单」改成了「`build.ts` + `CreationSpec`」**，这是本卷与上一版最大的差别，也是 ADR-5 修订后唯一自洽的写法。
>
> **诚实边界**：本仓库**没有任何模型接入代码**（`grep -rn "openai\|anthropic\|llm" src electron` 为空），所以运行期议会的「云端档」是设计而非实测，所有模型侧时延标 **待验证**；规则与校验部分可在本仓库内实现并实测。文中不出现任何模型名、价格或未实测的时延基准——**只写预算，不写行情**。

## 0. 两种议会，别混为一谈

同一个词被用在两个地方，是本项目最容易出的错。上一版就混过一次：把「设计期抓出 15 条打回」当成了运行期的能力证明。两者共享的只有一件事——**攻击者只许攻击，不许改稿**；除此之外，产物、成本、裁判、失败代价全不一样。

### 0.1 一张表切开

| 维度 | 设计期议会 | 运行期议会 |
|---|---|---|
| 何时跑 | 写文档、定架构时，离线 | 玩家许愿时，在线 |
| 谁读结果 | 作者、评审、后续卷册 | 玩家 |
| **产物** | ADR、卷册、勘误清单 | **`build.ts` + `CreationSpec`**（不是部件列表） |
| 失败代价 | 返工一天 | 玩家等几分钟，看到一句「做不到」 |
| 轮数 | 不设硬上限，以收敛为准 | **≤3 轮，硬上限** |
| 成本约束 | 人力时间 | **≤12,000 token / 次，≤5min** |
| 裁判 | 人（lead 复核）+ 机检 | **校验器 + 沙箱**（不是第三个模型） |
| 能否执行产物 | 不需要 | **必须**——不跑一遍不知道面数 |

最后一行是本版新增的，也是范式变更的直接后果：旧版的产物是纯数据，校验器看一眼就能判；新版的产物是代码，**代码的面数只有跑出来才知道**。所以运行期议会多了一个设计期没有的角色：**沙箱作为裁判的一部分**。

### 0.2 设计期议会：已经跑过，有效

角色三个，权限写死：

- **提议者**：写出一版完整产物（一卷、一条 ADR、一张表）。必须给全，不许留「此处待补」——留白会让攻击者无从下手。
- **攻击者**：只读，只输出「打回理由」。每条必须带**卷号 + 段落 + 错误类型 + 可复核证据**（命令、行号、算术）。不许说「感觉不对」「建议优化」。
- **收敛者**：不是第三个模型，是**人 + 机检**。人仲裁「证据是否成立」，机检判「数字是否对得上」。

它的产物不是「更好的文字」，是**一份能照着改的勘误清单**。这一点很重要：议会的价值不在「讨论过」，在「留下了可执行的差异」。

#### 0.2.1 15 条打回是怎么来的

用户记的是「15 条打回、1 条编造」。这个数字**对，但必须拆开**，否则会误记成「某一轮抓了 15 条」：

| 轮次 | 范围 | 结果 | 出处 |
|---|---|---|---|
| 第一轮 | 旧版 16 卷（V1–V16） | **1 放行 / 15 打回** | `00-重建纲领.md:4` |
| 其中 V1–V8 | 8 卷 | 放行 1（V8）/ 打回 7 | `勘误-互审打回-全16卷.md`「V1–V8」段 |
| 其中 V9–V16 | 8 卷 | 放行 0 / 打回 8 | 同上「V9–V16」段 |
| 第二轮 | 本版 ADR 与卷册 | **8 条打回 + 1 条编造** | `00-重建纲领.md:57` |

`7 + 8 = 15`，与第一轮吻合；第二轮的 8 条是**另计**，不是把 15 又数一遍。写卷时把两者混成「15 条都是本轮抓的」，本身就是议会该抓的那种错——**数字对得上，口径对不上**。

再看几条具体的，才知道「打回」长什么样：

| 卷 | 打回内容 | 可复核性 |
|---|---|---|
| V10 | 「127 处 `Math.random`」复现不出（`grep` 87 行 / 探针 189 调用） | 两个命令即可证伪 |
| V11 | 「33 次 flush」实为 36 次（`world.ts:284` 的 35 项 + `build()` 内 1 次） | 数 `tasks` 数组长度 |
| V12 | `SPEC-总账.md` 行数写 1,335，实测 1,421 | `wc -l` |
| V13 | 行号系统性漂移 12 处 | 逐条定位 |
| V14 | 灵狐面数 810 vs 实算 750，而 B4 要求容差 0 | 部件面数相加 |
| V15 | 「约 60 位神佛」实测 35 条 | `DEITIES.length` |
| V16 | 「288,000 次/帧」量纲错 60 倍，应为 4,800 | 一次除法 |

七条里没有一条是「文笔不好」。这就是设计期议会的判据：**只打可证伪的**。

至于「1 条编造」：`00-重建纲领.md:57` 只记了数量，没有具名。按勘误里最接近的是 V15 的「约 60 位神佛」——但**「数字错」与「编造」不是一回事**：前者是无知，后者是无源。本卷不替它定性，只记一条纪律：**凡是「约」「大约」「数十」开头的数量词，一律视为未验证。**

#### 0.2.2 为什么议会抓得到，单人抓不到

不是「两个脑子比一个脑子好」——两个模型可能一起错。真正起作用的是三个**结构性**机制：

1. **强制证据**。每条意见必须带命令、行号或算术。这条规则把「我觉得」挡在门外，也把提议者从「解释思路」拉回「面对事实」。
2. **角色分离**。提议者不能宣布自己合格，攻击者不能改稿，裁判不能说人话。三方各自只有一个出口，任何一个出口被堵，流程就停——**停下来比错下去便宜**。
3. **机检兜底**。数字对不对不靠吵，靠 `wc -l`、`grep`、一次除法。七条打回里每一条都能用一个命令证伪，这不是巧合，是筛出来的。

反过来，单人写作最常犯的三类错——行号漂移、跨卷口径不一致、量纲错——**恰好都是「自己看不见」的错**：写的时候脑子里有上下文，读的时候会自动补全。换一双只读的眼睛，这些错立刻显形。

这也是为什么运行期议会要保留「角色分离」而不保留「两个模型」：**结构比模型重要**。用两个同样的模型，只要角色不混，也能抓错；用一个模型既写又审，再强也会放过自己。

### 0.3 运行期议会：玩法，不是审批

玩家许愿时，他不想被审。所以运行期议会的第一原则是**快**，第二原则是**能解释**。

流程四步：

1. **A 起草**：把 `IntentFrame` 变成 **`CreationSpec` + `build.ts`** 两件东西。
2. **B 攻击**：只读这两件，只输出**封闭枚举内**的反对意见：`O_UNSUPPORTED` / `O_BUDGET` / `O_LORE` / `O_PHYS` / `O_RANK`。
3. **裁判 C**：跑 C1–C6（§3.2）。全绿即收敛；有红则回 A 改。
4. **出门**：交给 D5 的 P4 四门与 P5 热替换。

第 3 步最关键：**裁判不是模型**。两个语言模型对喷时，最可能的结局不是「越吵越对」，而是**互相让步**——B 说「有点问题」，A 说「你说得对，我改」，然后一起错。校验器不会让步，它只会返回 `E_GATE_TRIS`。

### 0.4 三等分会：不是每次许愿都开议会

旧版把「议会」当成每次许愿的必经环节，于是 3 秒的预算被议会吃掉一半。新版按 D5 的三档分层，议会只在最贵的一档开：

| 档 | 需不需要议会 | 谁在判 | 时延 |
|---|---|---|---|
| L1 复用 | **不开** | 缓存 hash 比对 | ≤300ms |
| L2 参数化 | **不开** | 模板 + 四门 | ≤3s |
| L3 代码生成 | **开，≤3 轮** | A/B/C 三方 | 30s～3min，最坏 5min |

这条改动看起来是「削弱议会」，实际是「把议会放回它该在的位置」：**只有需要写新代码的愿望才值得开会**。「再来一条龙」开会，是把 200ms 的事拖成 3 分钟。

## 1. 运行期议会的产物：`build.ts` + `CreationSpec`

### 1.1 为什么不是部件列表——这是与旧版最大的差别

旧版 ADR-5 说「输出是数据」，于是议会的产物是一份 `CreationSpec` 差分：

```json
{ "op": "revise", "base": "crt_3f21a0c8",
  "diffs": [ { "slot": "head", "from": "H07", "to": "H06" },
             { "slot": "wing", "from": "W12", "to": "W10" } ] }
```

这份差分的表达力上限，就是 96 件预烘焙件的组合空间。它能表达「换一个头」，表达不了「把脖子弯成 S 形、在第七节加一圈逆鳞、再让尾巴缠住柱子」——因为后者不是「换件」，是**新的构造过程**。

ADR-5 修订之后，议会的产物变成两件，缺一不可：

| 产物 | 回答什么 | 形态 | 谁校验 |
|---|---|---|---|
| `CreationSpec` | **要什么**（意图、阶位、落点、预算声明） | `creation.spec.v1`，D4 §3.1 逐字不改 | `validate(spec)` + 三张表 |
| `build.ts` | **怎么造**（调用序列、参数、循环） | 只调白名单 API 的模块 | 静态五查 + 沙箱 + 四门 |

**为什么两件都要**：只有 `spec`，表达力被锁回部件库；只有 `build.ts`，**没有可索引、可存档、可比较的意图**——两个几何一样但写法不同的模块，会被当成两个不同的东西，缓存永远不命中，玩家也没法说「上次那条，头再小一点」。

`spec` 是**索引**，`build.ts` 是**构造**。索引稳定，构造可变：同一份 `spec` 可以配模板实现，也可以配模型实现，产出同一个 `bundle` schema。这就是为什么 D5 的 L2 与 L3 能共用一条下游管线。

### 1.2 A 的产出格式：整份重写，不做 patch

A 每次修订都**重交整份 `build.ts`**，不交 diff。三个理由：

1. **可审计**：`moduleHash` 每次变化都能对上「哪一轮的哪一版」，patch 叠加会让「这段代码是谁写的」变成考古。
2. **可回滚**：整份的上一版就是上一轮的文件，不需要反向应用 patch。
3. **可静态检查**：五条静态检查（§D5 1.3）作用在完整模块上；patch 形态下，检查器要先重建全文，多一步就多一个出错点。

代价是 token：整份重写比 patch 贵。但实测一份 200 行的 `build.ts` 约 2,800 token（按代码 4 字符/token 估），三轮也就 8,400——在 12,000 的预算内。**用 token 换可审计，这笔交易划算**。

### 1.3 一个完整回合：「我要一条盘在柱子上的龙」

**R1（A）**：给出 spec 与 build.ts 的核心段。

```jsonc
// spec：意图与索引
{ "schema": "creation.spec.v1", "bodyPlan": "long",
  "parts": { "torso": [], "head": [], "fore": [], "hind": [],
             "tail": [], "wing": [], "horn": [], "orn": [] },
  "girth": 1.0, "legLen": 1.0, "palette": { "hex": "#2f6a62", "accent": "#8ee8c8" },
  "realm": "heaven", "provenance": { "source": "council", "seed": 20261103,
    "promptHash": "a41f…", "modelVersion": "…" }, "hash": "…" }
```

```ts
// build.ts：只调白名单
export function build(api, spec, rng) {
  for (let s = 0; s < 8; s++) api.tube(arc(s), 0.62 - s * 0.055, 14);  // seg 取了 14
  for (let i = 0; i < 96; i++) api.at(...).extrude(SCALE, 0.06, 'metal');
  api.lathe(HEAD, 16); api.sphere(0.09, 10, ...); api.sphere(0.09, 10, ...);
  return api.emit();
}
```

**R2（B）**：两条阻断、一条警告，全部带证据。

- `O_BUDGET @ seg=14`：8 段管 `2×14×8×8 = 1,792`，鳞 1,152，头 `2×16×7 = 224`，眼 `2×100 = 200`，四肢爪鬃颌角合计 780 ⇒ **合计 4,148**，没超 20,000——**这条不报**，B 只报超的。
- `O_LORE @ metal`：96 片鳞全用 `metal`，等于整条龙金属化；`metal` 的合批组是给甲胄与器物的，肉身应 `ceramic` 打底、`metal` 只做脊线。**证据**：14 组材质的分工（`src/city/bake.ts:4` 的 `BGroup`）。
- `O_PHYS @ 落点`：`placement` 未给 `walkSurface` 采样，柱顶高度未验；若柱不在可行走面上，龙会悬空。**证据**：缺 `walkSurfaceY` 调用 → 缺陷是「没验」，不是「验了不过」。

**R2（A 修订）**：鳞片改 `ceramic`，脊线每 8 片插 1 片 `metal`（12 片）；`seg` 从 14 降到 10（8 段共省 **512** 面，把余量留给云）；补落点采样。重交整份。

**R3（B）**：一条 `warn`：「`seg=10` 时管身接缝在 3.2 圈下有 2 处法线折角，建议段间重叠 2 点」。不阻断。

**C**：C1 过（schema 与导出形状）、C2 过（零 import、零禁用符号、API 全在白名单）、C3 过（沙箱实测 3,636 面 / 约 393KB / 包围盒 9.4m / 双跑一致）、C4 过（无 `block`）、C5 过（两次 sha256 相同）、C6 过（落点三规则全过）⇒ `pass`。

三件事值得记下来：**① 答案不是 B 给的，是 A 在被否之后自己找的；② B 的三条意见都带证据，且「没超预算」这条它没报；③ C 从头到尾没说过一句人话。**

### 1.4 B 只否不改，在代码形态下更难守

旧版 B 不能改 spec，约束很自然；新版 B 看着代码，**一句「把 seg 改成 10 就好了」几乎脱口而出**。所以约束要更硬：

- B 的输出字段只有 `{ code, at, severity, evidence }`。`at` 是**代码位置**（`L12`）或**字段路径**（`placement.y`），不是建议。
- B 可以引用公式（「seg=14 时 1,792 面」），**不可以写替换值**。
- 违反一次即整轮作废——不是惩罚 B，是**保护 A 的修改责任**：一旦 B 给了方案，下一轮 A 就会偷懒「你行你上」。

这条约束看起来低效（B 明明知道答案），但它保证了一件更值钱的事：**改稿的人始终对结果负责**。

### 1.5 属性派生：机器算，人不算

`profileOfBuild(spec)` 是 D4 的纯函数，输入 `CreationSpec`，输出 `STR / AGI / SPI / PRE / LOAD` 与三个派生值。议会里的分工：

- **A 不手算**。A 只选参数，属性由函数给。A 若在文本里写「这只兽力量约 40」，那句话**不算数**。
- **B 不手算**。B 质疑时引用函数输出，不引用自己的估算。
- **C 只比对**。函数结果与 A 声明的结果不一致即 `E_DERIVE`。

这条分工来自设计期的教训：V14 的 20 行面数「多数不可由零件相加复现」，就是因为有人手算了一遍还写进了表。**机器算的归机器，人只负责选。**

注意一个边界：**代码生成的几何，`profileOfBuild` 算不出来**。它读的是 `parts` 与 `girth/legLen`，而 `build.ts` 可以完全不用 `parts`。所以本卷规定：**`tier='code'` 的产物，属性必须显式声明在 spec 的 `profile` 扩展字段里，并由 C 用包围盒与体积做一次粗校验**；算不出来的，就用 `realm` 的默认档，不许编。这是 ADR-8 之外的一个补丁，标记为「待 D4 追认」。

## 2. 攻击者的检查清单

### 2.1 五类一览

B 的每一条意见都必须落进下面五类之一，且带 `severity`（`block` / `warn`）与 `evidence`。**落不进五类的意见一律丢弃**——这是防止「我觉得违和」拖住流程的唯一办法。

| 码 | 问的问题 | 判据来源 | 需要沙箱吗 | 典型证据 |
|---|---|---|---|---|
| `O_UNSUPPORTED` | 这件事这个引擎做得到吗 | 白名单 + 禁用符号 + 能力边界 | 否 | `L7: import * as THREE` |
| `O_BUDGET` | 它会不会超预算 | 面数公式 + 三道上限 | 多数否，`isosurface` 要 | `seg=14 → 1,792 面` |
| `O_LORE` | 它像不像这个世界的东西 | 材质矩阵 + 比例区间 + 形制 | 否 | `metal × 96 片 = 全身金属化` |
| `O_PHYS` | 它站得住吗、穿不穿模 | `walkSurfaceY` + AABB + 载重 | 建筑要（落点查询） | `柱脚 4 点全无面` |
| `O_RANK` | 这道允许造它吗 | V13 六道表 + 35 尊 + 九型 | 否 | `天道不可造新兽` |

**五类里只有两类需要跑代码**：`O_BUDGET` 的 `isosurface` 分支，与 `O_PHYS` 的建筑落点。其余三类都是静态可判——这是议会能在 3 轮内收敛的前提：**贵的检查只做一次，便宜的检查做三轮**。

### 2.2 `O_UNSUPPORTED`：不可实现

四种子情形，按拦截成本从低到高：

1. **越白名单**：`api.<name>` 不在 10 个方法内。证据是方法名与行号。
2. **碰禁用符号**：`import` / `require` / `fetch` / `process` / `globalThis` / `eval` / `new Function` / `constructor` / `Date.now` / `Math.random` / `document` / `window`。证据是符号与行号。
3. **需要引擎没有的能力**：要新材质组（14 组固定）、要新行为（`behavior` 只有五值）、要联网、要读写存档。这一类**不是代码写错，是需求越界**，所以 B 要报在 `spec` 上而不是代码上。
4. **结构上不可能**：例如「让龙自己写诗」——那不是几何，是文本生成；「让房子悬空且可站立」——没有支撑面就没有 `walkSurface`。

第四种最容易吵。判据只有一条：**能不能用一句话指出「引擎里缺哪个东西」**。能指出（缺 `walkSurface`、缺材质组、缺行为枚举），就是 `O_UNSUPPORTED`；指不出，就不是。

### 2.3 `O_BUDGET`：超预算

B 在这里只做**算术**，不做测量。三个子门：

| 子门 | 算法 | 证据格式 |
|---|---|---|
| 面数 | 逐调用套 D5 §3.2 的公式求和 | `8×(2×14×8) + 96×(4×4−4) + … = 4,148` |
| 包围盒 | 由 `at()` 的平移与图元尺寸推 AABB，取最大边 | `max(x,y,z) = 12.4m ≤ 200m` |
| 内存 | 面数 × 108 B/面（由实测 102,816 B ÷ 952 面得出） | `4,148 × 108 ≈ 448KB ≤ 8MB` |

**108 B/面**这个系数来自 D5 附录 A 的实测（一具龙 102,816 B / 952 面 = 108.0），是非索引、三属性、float32 的口径。它是估算，不是承诺——真实字节以沙箱实测为准，B 只用它判断「数量级是否已经越界」。

两条纪律：

- **`isosurface` 不许估**。它的面数由标量场决定，同样的 `res` 能差一个量级。B 遇到它只能标 `needs-run`，把判断权交给 C。**装懂比不懂更糟**：估一个 1,500 面，跑出 12,000 面，玩家等到的是失败而不是提醒。
- **B 不许说「可能超」**。要么算出超了（给算式），要么标 `needs-run`。中间态没有信息量。

### 2.4 `O_LORE`：违和

这是五类里唯一有审美成分的，所以必须把它**压成可指认的规则**，否则它会变成「我不喜欢」。三条子规则，每条都能用表查：

**① 材质—题材矩阵。** 14 组材质各有分工：`wood`/`wall`/`roof`/`ash` 是建筑，`leaf`/`trunk` 是植被，`metal`/`ceramic`/`lacquer` 是器物与甲胄，`fabric` 是织物，`glow` 是光源，`water` 是水面，`earth`/`ground` 是地皮。**兽的肉身只能用 `ceramic`/`fabric`/`glow` 打底**，用 `metal` 打底等于把它做成铜像——可以，但必须在 `lore.nature` 里写明「铜身」，否则就是违和。

**② 比例区间。** 龙身长径比（脊线长 ÷ 最大截面直径）应在 **12–30**；小于 12 像蜥蜴，大于 30 像蛇。檐口出挑 ≤2.4m（D3 的 `E_OVERHANG`）；斗栱层高 ≤0.35H；开间模数 3.2m（D3 §2.4）。这些不是美学，是**已有构件制里写死的数**——B 引用它们，不发明它们。

**③ 形制。** 建筑走 D3 的 15 种 `PartId`：`column` `beam` `purlin` `bracket` `wallPanel` `door` `window` `railing` `eave` `ridge` `tile` `plinth` `stair` `lintel` `signboard`。用 `box` 拼一个「看起来像斗栱」的东西，B 要报：`bracket` 是 5 个 box 组成的一攒（60 面），手拼的 3 个 box 做不出华拱的悬挑，而且**不可拆**。

**最重要的一条纪律**：说不清落在①②③哪一条的，**降级为 `warn` 且不计入阻断**。违和可以是意见，不能是否决权。否则 B 只要说「我觉得别扭」，A 就永远过不了。

### 2.5 `O_PHYS`：违反物理

四条，全部可算：

| # | 检查 | 判据 | 不过的后果 |
|---|---|---|---|
| 1 | **支撑** | 建筑底面与 `walkSurface` 的接触面积 ÷ 底面面积 ≥0.6 | 半悬空、地基缺失 |
| 2 | **落地** | 生物的 collider 底部与 `walkSurfaceY` 差 ≤0.95（`WS_STEP_UP`）；`behavior.kind='fly'` 例外，但必须有 `altitude` | 龙浮在半空 |
| 3 | **穿模** | 新对象 AABB 与既有 building/POI 的 AABB 不相交 | 柱子插进墙里 |
| 4 | **载重** | `profileOfBuild().LOAD ≥ 骑手质量`（若声明 `interact.verb='骑'`） | 骑上去穿模或掉下来 |

第 2 条的例外要写清楚：`fly` 类不要求落地，但 `altitude` 必须有值，且 C6 要验「altitude 处没有建筑」。否则「会飞」就成了绕过所有落地检查的万能借口。

第 4 条是本项目的老坑：玩家以为「看起来很大」就能驮，实际 `LOAD = round(载 × K × 8)`（V14 的算例）。B 用一次乘法就能否掉「这龟很大所以能骑」——**能算的不许辩**。

### 2.6 `O_RANK`：违反阶位约束

三张表，缺一不可：

**① 九型骨架**（`src/sky/creatures.ts:507` 的 `BEAST_FORM`）。`bodyPlan` 只能取 `long / qilin / feng / kun / yaksha / luocha / baize / crane / tiger`，第十型不存在。

注意：**代码生成不取消九型**。`build.ts` 可以造出「六条腿的龙」，但 `spec.bodyPlan` 仍必须是 `long`——九型是**分类**，不是**拓扑许可**。这条区分很多人会搞混：ADR-5 放开的是构造方式，不是分类法。六条腿的龙仍然是龙，归 `long`，`profileOfBuild` 按 `long` 的基值算，多出来的两条腿只影响几何，不影响属性。

**② 35 尊神佛**（`src/data/deities.ts`，实测 35 条，合计 43,676 面，单尊 852–1,394）。神佛是**固定形象**，不是可造物：玩家可以「请一尊」，不能「造一尊新的」。`bodyPlan` 写成 `deity:如来` 直接 `O_RANK`。理由不是技术，是世界观：**神佛的名册是封闭的**，开放了就不再是神佛，是皮肤。

**③ 六道阶位**（`docs/MC融合方案/V13-六道阶位体系.md:253`）。表是这样的：

| 阶 | 造 | 骑 | 召（上限） | 拆 |
|---|---|---|---|---|
| 地狱 | 否 | 否 | 否 | 否 |
| 饿鬼 | 否 | 否 | 是（1） | 否 |
| 畜生 | 否 | 自身即造物 | 否 | 否 |
| 人 | **是（唯一全功能）** | 是 | 是（4） | 是 |
| 修罗 | 否 | 是 | 是（守卫 8） | 是（夺来的） |
| 天 | 否 | 是（飞） | 是（神将 3） | 否 |

议会要查两件事：**形体是否合法**（地狱道是亡魂，畜生道才用兽形），**当前道的已召唤数是否已到上限**。

这里有一个必须点明的命名区分，上一版踩过：**`realm` 是阶位，`placement.plane` 是空间**。一份 `realm: 'heaven'` 的天龙完全可能 `plane: 'renjian'`——它归天道管，但站在人间。`O_RANK` 查 `realm`，`O_PHYS` 的落点查 `plane`，**两个字段不许互相顶替**；把三界值写进 `realm`，会让 D4 的 `validate()` 判成非法阶位，反之亦然。

这里必须如实标注本卷最弱的一处（§6 详述）：
- **「有上限」是事实**，V13:253 有表；
- **「上限按 `interact` 遍历成本定的」是推断**，V13 只给数字没给理由；
- **「运行时已生效」是假的**——`grep -rn "召唤\|summon" src` 只命中 `src/sky/underworld.ts:2028` 一个着色用的数组，代码里没有实现。

所以 C5 的阶位检查是**按表兜底**，不是读运行时状态。这一条写进依赖项，不许假装已经生效。

### 2.7 检查顺序：先静态，再查表，最后跑

```
第 0 层（0.5ms）  静态五查：可解析 / 零 import / 禁用符号 / API 白名单 / 导出形状
第 1 层（0.1ms）  公式预算：面数、包围盒、字节数
第 2 层（0.1ms）  三张表：九型 / 35 尊 / 六道
第 3 层（64ms+）  沙箱：实测面数、确定性、落点
```

前三层加起来不到 1ms，能挡掉设计期统计里最常见的错：**越白名单**（模型爱 `import THREE`）、**超面数**（爱把 `seg` 开大）、**越阶位**（爱在错误的道上造东西）。第四层最贵，所以只在「前三层全绿」之后跑一次。

这个顺序还有一层含义：**B 的意见按层分组呈现给 A**。第 0 层的错先改，因为它会让第 3 层白跑——先改落点、再发现 `import` 还在，那 64ms 就白花了。**报错顺序就是修复顺序**，与 D4 `validate()` 的顺序纪律同源。

## 3. 轮数、收敛、僵局、成本

### 3.1 三轮，硬上限

| 轮 | 内容 | 输出上限 | 是否跑沙箱 |
|---|---|---|---|
| R1 | A 起草 `spec` + `build.ts` | ≤3,000 token | 否 |
| R2 | B 攻击 → A 修订（整份重交） | B ≤400 / A ≤2,800 | **是，一次**（在修订后） |
| R3 | B 再攻击 → A 终修 | B ≤300 / A ≤2,500 | **是，一次**（终验） |
| 结束 | C 判定 | 0 | — |

R3 之后**无论是否收敛都停**。这条必须写死，因为「再来一轮就好了」是无限对喷的入口，而它的成本是线性的、收益是递减的。

三轮够不够？设计期的经验是：**第一轮抓结构（合规、能不能造），第二轮抓数字（面数、比例），第三轮只剩措辞**。运行期的产物比一卷文档小两个数量级，三轮绰绰有余。

**为什么沙箱只跑两次而不是每轮一次**：单次 64ms 启动加构建，看着便宜，但代码生成档的沙箱预算给到 60s——三次就是 180s，直接把 5 分钟吃掉一大半。而 R1 的产物本来就要被 B 挑错，跑它等于给一个注定被改的版本付费。**只在「B 挑完、A 改完」之后跑**，这是最省的一次。

### 3.2 收敛判据：六条，全可机检

| # | 判据 | 检查方式 | 失败码 |
|---|---|---|---|
| C1 | schema 与导出形状合法 | JSON schema + 恰好一个 `export function build` | `E_SCHEMA` |
| C2 | 静态白名单 | 零 `import`/`require`、零禁用符号、`api.*` 全在白名单 | `E_FORBIDDEN` / `E_API` |
| C3 | 四道预算门 | 沙箱实测：面数 ≤20,000 / 包围盒 ≤200m / ≤8MB / 双跑一致 | `E_GATE_*` |
| C4 | 攻击者无阻断意见 | `objections.filter(o => o.severity==='block' && o.evidence).length === 0` | `E_OBJECTION` |
| C5 | 阶位与落点 | 三张表 + 100m 三规则（D5 §5.3） | `E_RANK` / `E_SITE` |
| C6 | 确定性 | 同 seed 两次 `bundleHash` 相同 | `E_NONDET` |

六条里，C1–C3、C5–C6 是**机械的**，C4 是**语义的但可枚举**。C4 之所以能机检，是因为 B 的输出被限制在五个码里，且每条必须带 `evidence`；**没有 evidence 的意见直接丢弃**，不进分母。

注意 C4 的写法有个细节：它过滤的是 `severity==='block'` **且带证据**的意见。一条 `block` 没证据，等于没提——这是防止 B 用「我觉得不行」把流程卡死。反过来，`warn` 从来不阻断，它只进 `council_log`，给下一版预算表当输入。

### 3.3 僵局：三级

**一级：B 说不可实现，C 说通过。**
裁决：**C 优先**，但 B 必须给出可复核证据（文件:行号 / 算术 / 探针名）。给不出，该意见降为 `warn` 并记日志；给得出，则 C 的判据有 bug，本轮作废，转人工。本质是「**谁主张谁举证**」，不是「谁声音大谁赢」。

**二级：B 与 A 都能自洽，结论相反。**
典型：A 说「八段管能盘住柱子」，B 说「第七段与柱身相交，穿模」。两边都能画出示意图。裁决：**跑机器**——`walkSurfaceY` 采样、AABB 相交、`profileOfBuild` 的载重。属性与几何是算出来的，不是辩出来的。算不出来的争，一律不叫争。

**三级：三轮未收敛。**
裁决：**降级到模板版 + 明确告知**。不说「失败了」，说「这次没谈拢，先给你标准版：<模板名>，要保留哪些改动？」同时把整段对话写进 `council_log`，供人工复审——**僵局不是垃圾，是下一版预算表的输入**。

### 3.4 成本上限：12,000 token，5 分钟

**token 账**（估算，按代码 4 字符/token）：

| 项 | 上限 | 依据 |
|---|---|---|
| 注入：白名单文档 + 一个示例模块 + 材质表 + 预算表 + 词表摘要 | 3,000 | 文档约 1,200，示例 800，其余 1,000 |
| R1 输出：spec 120 + build.ts 2,800 | 3,000 | 200 行模块的量级 |
| R2：B 400 + A 修订 2,800 | 3,200 | |
| R3：B 300 + A 终修 2,500 | 2,800 | |
| **合计** | **12,000** | 恰好用满，无余量 |
| 每会话（8 次深度许愿） | **96,000** | 12,000 × 8 |

**为什么从上一版的 6,000 涨到 12,000**：上一版的产物是一份 `CreationSpec`（354 B），这一版的产物多了一份 200 行的模块。**预算必须跟着产物走**，不然就是「要求写代码却只给写 JSON 的额度」——那会逼着模型把代码压成一行，可读性归零，审计也归零。

**墙上时钟账**：

| 项 | 预算 | 说明 |
|---|---|---|
| 3 轮生成 | 3 × 60s = **180s** | 单轮 60s，不是 D5 的 120s——因为议会档有三轮 |
| 2 次沙箱 | 2 × 60s = **120s** | 只跑 R2 末与终验 |
| **合计** | **300s = 5min** | 与 D5 的最坏情况同一个数 |

这个 300s 与 D5 的 `120 + 180 = 300` **是同一笔 5 分钟，两种拆法**：单发许愿（不经议会）是「一次生成 120s + 一次沙箱硬超时 180s」；议会档是「三次生成 180s + 两次沙箱 120s」。**两者不能叠加**——叠加就是 10 分钟，那是玩家不能接受的。

还要把两个「180s」分清楚：ADR-8 的 **180s 是单次硬超时**（到点 `kill`，防失控），D6 的 **60s 是单次预算**（超了算失败，防体验崩坏）。前者是安全阀，后者是产品参数。混用会出现两种错：拿硬超时当预算 → 每次都可能等 3 分钟；拿预算当硬超时 → 一个死循环把进程挂住。

### 3.5 议会不能打断玩家

三条硬要求，全部来自「玩家不想被审」：

1. **默认静默**：一轮就过的许愿，玩家只看到结果，看不到 A/B 的对话。把内部争论展示给玩家，是把工程成本转嫁成阅读负担。
2. **可中断**：必须有「算了」按钮，按下即中止；已花的 token 记入会话预算，但**不重试**。
3. **可后悔**：产物落地后 10 秒内可以「撤」，撤的是**整次事务**（含碰撞重建），不是只删模型。理由很简单：玩家说「不对」时，往往不是模型不对，是位置不对——只删模型会让他重说一遍。

第 3 条最容易被漏。撤销栈是既有设施（`V5:94` 的「替换必须整条命令回滚」），本卷的许愿事务直接复用它，不另起一套。

### 3.6 禁止事项

- 禁止 B 修改产物（一改就不再是攻击者，而且下一轮 A 会偷懒）。
- 禁止 A 自评「我觉得可以了」——收敛由 C 宣布。
- 禁止 C 输出自然语言理由（理由会变成第二个提议者）。
- 禁止在 R3 之后追加轮次。
- 禁止 A 与 B 共享同一份上下文快照：B 只看到产物与表，看不到 A 的「思考过程」。看到了就会开始理解并原谅。
- 禁止把沙箱实测结果当作「B 的意见」——测量归 C，判断归 B。两者混在一起，就分不清「这是规矩不允许」还是「这次碰巧超了」。

## 4. 议会也救不了的愿望

五类。每一类都给「为什么」与「怎么说」。话术不是文案，是**产品的一部分**：说得不对，玩家会以为系统坏了。

### 4.1 五类硬边界

| # | 类型 | 例子 | 为什么救不了 | 最近的可实现替代 |
|---|---|---|---|---|
| 1 | **跨维度** | 「一条能下地府的天龙」 | 三界是三个 y 带（天宫 >2150、人间 0 附近、地府 <−200），且天龙属天道；坐标系与阶位同时违反 | 「地府夜叉（536 面）」或「引魂灯」 |
| 2 | **超体量** | 「一条一万米长的龙」 | 包围盒上限 200m；再大则包围球、LOD 阈值、物理全失效 | 「最大号青龙，约 200m」 |
| 3 | **无支撑** | 「一座浮在空中的房子」 | 可行走面由 `walkSurfaceY` 给（`behaviors.ts:160`），空中没有面；NPC 会掉、玩家会穿模 | 「云台浮岛（有岛裙与落点）」或「吊脚楼」 |
| 4 | **越时代器物** | 「一把机关枪」 | 材质库与构件库是宋式；连发是**机制**，不是模型 | 「连弩」或「突火枪（单发）」 |
| 5 | **需要新机制/外部服务** | 「一条会自己写诗并发表的龙」 | `behavior` 只有五值；沙箱无网；无文本生成系统 | 「它会抬头看你——现有行为里最接近的一种」 |

与上一版相比，这份表**少了一类**：「生成新拓扑」不再是不可能——六条腿的龙、双头鸟都能造。**但剩下的每一条都更硬**：旧版还能说「部件库没有，等等看」，新版没有借口了——做不到，就说得出是哪条预算或哪个机制。

### 4.2 话术的三条纪律

**纪律一：先承认，不铺垫。**
「这个做不到」要放在第一句。放在第三句，前两句就成了借口。

**纪律二：一句边界，不辩解。**
只说**为什么**，不说「因为技术限制」「因为目前版本」。前者是事实，后者是托词。一句够，两句就开始像求原谅。

**纪律三：给一个能点的替代，带代价。**
「给你一只地府夜叉，536 面，2 秒」比「你可以试试别的」有用一百倍。替代必须**在词表内**、**能立刻执行**、**代价可见**。

### 4.3 三种最糟的回答

- **「正在努力为你生成……」然后转圈三分钟**：这是欺骗。做不到就说做不到。
- **「已为你生成一条天龙（简化版）」而不说简化了什么**：这是静默降级，本项目明令禁止。降级必须可见——哪一档降了、降在哪、少了多少面，都要写。
- **「抱歉，我不明白你的意思」**：这是把解析失败说成用户的问题。正确说法是「你是要天龙、龙舟，还是龙灯？」——给选项，不让用户重写。

### 4.4 一个正面例子

> 玩家：「我要一条能下地府的天龙。」
> 系统：「天兽过不了界——天龙属天道，地府只认亡魂与鬼差。给你一只**地府夜叉**（536 面，2 秒），或者一盏**引魂灯**带路，要哪个？」

三句话：承认（过不了界）、边界（天道 vs 地府）、替代（两个具体选项 + 面数 + 时延）。没有一句「抱歉」，没有一句「正在努力」。

### 4.5 拒绝之后：把「不行」变成一条路

拒绝不是终点，是**分叉点**。系统必须在拒绝的同时给出三条路，且三条都要能点：

| 路 | 做法 | 例子 |
|---|---|---|
| **换对象** | 换一个能表达同一意图的东西 | 天龙 → 夜叉 / 引魂灯 |
| **换位置** | 对象不变，换个能成立的界域或地点 | 天龙下地府 → 天宫召天龙 |
| **换说法** | 用词表内的词重新表达 | 「会写诗的龙」→「会点头的龙」 |

三条路的共同要求：**一步可达**。不能是「你可以到编辑器里自己调」——那是把工作推回给玩家。

还有两个细节：

**记住这次的意图。** 玩家被拒后往往立刻换个说法再试（「那给我一条会飞的」），如果系统把上下文丢了，就要重新解析一遍，体验断成两截。正确做法是把上一次的 `IntentFrame` 留在会话里，作为下一次的 `focusKind`——「会话偏好只补空、不覆盖」的另一个用途。

**拒绝不消耗额度。** 玩家被拒已经很沮丧，再扣一次额度，就是把「系统做不到」变成「你浪费了」。额度只对**成功的云端调用**计数，对本地拒绝不计——这条看起来是小事，它决定了玩家敢不敢试。

## 5. 验收断言

每条都能落到一个探针；未建的标 **[待建]**，由 D8 排期。**八条里有四条靠负样本驱动**——议会的失效方式不是「判错一次」，是「看起来在跑，其实什么都没拦」。

| # | 断言 | 探针 | 判据 |
|---|---|---|---|
| 1 | 设计期 15 条打回**每条**有卷号、段落、错误类型、可复核证据 | `probe-council-evidence.mjs` **[待建]** | 解析勘误表，四字段缺一即 BLOCK；「无出处」计数必须为 0 |

| 3 | 六条判据各有一个负样本，且各自触发自己的失败码 | `probe-council-converge.mjs` **[待建]** | 六个负样本分别打 C1–C6；正样本一次全绿；**失败码不许串台** |
| 4 | 产物必须两件齐全：`spec` 过 `validate()`、`build.ts` 过静态五查 | `probe-council-products.mjs` **[待建]** | 缺任一件即 BLOCK；`spec.hash` 复算一致 |

第 3 条要特别说明「**失败码不许串台**」：一个负样本如果同时触发 C1 和 C3，说明判据之间有耦合，收敛判定就不可信。比如「缺 `export`」应该只触发 C1，不该顺带报 `E_GATE_TRIS`——如果它报了，说明 C3 在 C1 失败后仍在跑，那是实现错误。

第 6 条的「沙箱 ≤2 次」是成本红线里最容易被悄悄突破的一条：加一次「预跑」很自然，再加一次「复验」也很自然，三次下来就是 180s。**这个计数必须被断言，不能靠自觉。**

## 6. 三处弱点与依赖

### 6.1 三处弱点（与 D5 同源，此处只写议会视角的后果）

**弱点一：`walkSurface` 没有局部重建入口。** 对议会的影响在 C5：建筑的落点检查要读 `walkSurfaceY`，而换装要写。读没问题，写只能全表重建。所以**建筑类许愿在 C5 只能验「新落点站得住」，验不了「换掉之后周边还站得住」**——后者要等局部重建入口。这一条在 D5 已写成依赖项，**本卷不重复估算耗时**（上一版那个「~80ms」没有实测来源，已删）。

**弱点二：`LodManager` 只能加不能减。** 对议会的影响在回滚：C3/C6 通过、P5 的 `registerLod` 成功之后若 `updateCollider` 失败，`groups` 里会留一个孤儿组。议会的处置是标 `orphan` 并在下次 `reset` 清掉，**不假装能撤销**。这不是议会能修的，是引擎缺一个 API。

**弱点三：六道可召上限是推断——要拆三层，别混。**
- **「有上限」是事实**：`V13:253` 的表写着 1/4/8/3/0/0。
- **「上限按 `interact` 遍历成本定」是推断**：V13 没写理由，本卷的归因是推断，不是原文。
- **「运行时已生效」是假的**：`grep -rn "召唤\|summon" src` 只命中一个着色数组，没有实现。

所以 C5 的阶位检查是「按表兜底」。这条最弱，因为它在「文档有」与「代码有」之间划了一道很多人会忽略的缝——**引用一张没被实现的表，和编造一个数字，性质不同但后果一样**。

### 6.2 本卷新增的一处诚实边界

**运行期议会的云端档整条链路都未实测。** 仓库没有模型接入代码，`build.ts` 也没有沙箱实现（D5 §9）。所以 §3.4 的 token 与时间账是**预算**不是**实测**；能实测的只有 64ms 启动、0.040ms 哈希、0.47ms 转译这些环节件。**预算与实测必须分开写**，否则下一轮评审会把预算当基准，再下一轮就拿它做产品承诺。

### 6.3 依赖项

| 依赖 | 需要谁 | 阻塞什么 | 没有它时 |
|---|---|---|---|
| 模型接入 | 未排期 | 运行期议会的云端档整条 | 只有模板档，`tier='code'` 直接拒 |
