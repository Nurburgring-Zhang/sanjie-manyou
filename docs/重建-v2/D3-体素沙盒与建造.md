### 0.2 必须上报的一处算术错误：1.6m 不是 0.32 与 0.5 的公倍数

裁定的**意图**（体素管非建筑、构件管建筑、交界要有统一单元）完全成立，本卷照办。但「1.6m 是 0.32 与 0.5 的最小公倍数」这句在算术上不成立：

- `1.6 / 0.32 = 5` —— 构件侧整除，成立；
- `1.6 / 0.5 = 3.2` —— 体素侧**不整除**，1.6m 边界落在第 3.2 个体素上，永远对不齐。

真正的最小公倍数是 **8.0m**：`8.0 / 0.32 = 25` 尺，`8.0 / 0.5 = 16` 体素，两侧同时整除。这是初等数论结论（0.32 = 8/25 m、0.5 = 1/2 m，最小公共周期 = LCM(8,1)/GCD(25,2) = 8 m），不是本项目特有的约定。

**本卷的处理**（保留裁定意图、只修算术）：

1. **1.6m 继续作为「营造单元」**，它是构件的模数（5 尺），也是开间 3.2m 的一半，建筑侧的一切排布以它为单位；
2. **新增 8.0m「超单元」** 作为体素与构件唯一能精确对齐的周期（16 体素 = 25 尺 = 5 营造单元）；
3. 超单元内部的差额用**砌筑灰缝**吸收：把每个 1.6m 单元的边界量化到最近的体素边界，五段的体素数是 **[3, 3, 4, 3, 3]**（累加 16 体素 = 8.0m），每段的实际宽度在 1.5–2.0m 之间摆动，与名义 1.6m 的最大偏差 **0.2m**，这条缝记为灰缝、由 `ash` 组的薄条渲染。

这条不是推翻裁定，而是把「1.6m 交界」从一句无法实现的口号，变成 §3 里可写进断言的三级格网（0.32 / 0.5 / 8.0）。**若 lead 认为应改回字面的 1.6m 对齐，则体素侧必须放弃 0.5m 改用 0.4m**（`1.6/0.4=4`，`0.32×5=1.6`，LCM=1.6），这会连带改掉全部方块尺寸与既有 `buildings.ts` 的 3.2m 模数——本卷不建议。此分歧列为 §6 未决项 U1。

## 1. 体素的数据与渲染

### 1.1 可编辑域的边界（先划死，再谈实现）

体素**不是**世界的底座，它是一层**可编辑补丁**，只允许出现在四类语义里：

| 允许 | 具体内容 | 与既有几何的关系 |
|---|---|---|
| 地形开挖 | 地表以下 0–12m 的可挖层 | 既有 `terrainHeight()` 仍是真的高度场；体素只覆盖「已开挖」的局部 |
| 矿脉 | 脉状体素簇，按品位分 3 档 | 不改 `terrain.ts` 的山体，只在山体内登记可采簇 |
| 洞穴 | 隧道/溶洞的内表面 | 洞内不生成既有 `city_*` 几何；洞口做 0.5m 台阶过渡 |
| 工事 | 挡马墙、拒马基座、壕沟、望楼基座 | 望楼的**楼身**是构件（§2），只有基座是体素 |

建筑（房屋、斗栱、栏杆、屋顶）**一律不得**用体素表达。判定不是靠文档，而是靠 §2.5 的「构件覆盖率」断言：任何被标记为 `building` 的包围盒，其体素占比必须为 0。

### 1.2 区块尺寸：32×32×16

一个区块 = 16m × 16m × 8m（32×32×16 格 × 0.5m），16,384 个格。选这个尺寸的三条理由都可算：

1. **调色板索引恰好 8 位**。方块类型 62 种（§1.5），6 位够用，留 2 位给「方向/湿度/损坏度」这类每格状态；一个 `Uint8` 存索引，原始 16,384B/区块。
2. **meshing 时间可算**。本机实测（探针见 §4.4）：包含 greedy 的全流程吞吐 **2.36M 格/秒**（1,265,992 格耗时 535ms）。16,384 格 ⇒ **6.9ms/区块**。这是单线程、未优化的下限；Worker 里跑，主线程只付 `postMessage` 与上传。
3. **与沙盒整除**。沙盒 64×64×48 格 = 2×2×3 = **12 区块**，12 × 16,384 = 196,608 格，无余数。

沙盒（可编辑地块）= 32m × 32m × 24m。5 块沙盒合计 983,040 格，这是本卷全部可编辑体素的上限。

### 1.3 存储：调色板 + RLE，带回退

每区块三段：

```
header: { paletteLen: u16, palette: u16[paletteLen], mode: u8 }   // ≤ 2 + 512 + 1 B
body  : mode=0 → raw: u8[16384]                                    // 16,384 B
        mode=1 → rle: (runLen: u16, idx: u8)[]                     // 每条 3B
```

- **调色板去重**：一个区块实际出现的方块类型通常 < 16；调色板按首次出现顺序编号，索引 0 固定为空气。
- **RLE 上限保护**：若 `runs × 3 + header ≥ 16,384 + header`，强制回退 `mode=0`。因此**单区块存储上界 = 16,899B**，不会被病态数据撑爆。
- **设计阈值**：地表区块 RLE 后 ≤ 原始 1/3（≤ 5,600B）。这是目标值，验收用 A2 的「≤ 12,288B」放宽线，避免把未测值写成事实。

5 块沙盒 × 12 区块 × 16,899B = **1.01MB**（最坏）；按 1/3 压缩的常态约 **0.34MB**。相对 2,615MB 峰值可忽略。

**为什么不用 3D 数组分块 + 稀疏哈希**：本项目的沙盒是**固定 5 块、固定尺寸**，不是无限世界；稀疏哈希省下的那点内存（< 1MB）换不来「遍历 196,608 格要跳表」的 meshing 开销。ADR-7 要求先算 Δ 再谈，这里 Δ 是负的（更慢），直接否掉。

### 1.4 渲染：逐材质 greedy meshing

算法用标准的三轴 × 双面掩码合并（每层构建 `Int16` 掩码，按材质 id 取正，沿 u 再沿 w 扩张矩形）。**必须逐材质**，因为不同材质组是不同的 draw；跨材质合并会把 13 个组合成 1 个，等于放弃材质区分。

顶点格式直接复用 `bake.ts` 的量化布局（`QBuf`，`:447-500`）：

| 属性 | 类型 | 字节 | 说明 |
|---|---|---|---|
| position | Float32 ×3 | 12 | 体素用**区块局部坐标**（0–16m），不写世界坐标，避免 Float32 在 ±16km 处丢精度 |
| normal | Int16 ×3 normalized | 6 | 轴对齐，只有 6 个值 |
| color | Uint16 ×3 normalized | 6 | 方块底色 × 面朝向明暗（顶 1.0 / 侧 0.82 / 底 0.62） |
| uv | Float32 ×2 | 8 | 只对 10 个 UV 组写；`glow/leaf/trunk/water` 四组不写 |
| **合计** | | **32B（UV 组）/ 24B（非 UV 组）** | 索引另计 |

索引用 **Uint32**（6 个/quad，24B）。一个 quad 的总成本 = `4×32 + 24 = 152B`（UV 组），非 UV 组 `4×24+24 = 120B`。全卷按 **152B/quad** 记预算，是保守侧。

不共享顶点。原因：相邻 quad 的法线/颜色不同，共享会让每个顶点携带两套属性，反而更贵；而且 greedy 之后的 quad 是矩形，四角本来就无邻接。

**UV 密度按组分开**，这是体素贴图看起来「不像一格一格刷漆」的关键：

- `ground` / `wall` / `earth` / `ash` / `plinth` 这类**块状材质**按 **1/0.5m** 平铺——一个方块正好一张贴图，缝隙落在格线上；
- `roof` 按 **1/0.32m** 平铺——瓦垄要按宋尺对缝，一个 0.5m 方块上重复 `0.5/0.32 = 1.5625` 次，读成「瓦压瓦」而不是「贴图被拉伸」；
- `wood` 按 **1/0.4m**（柱径 0.32–0.4m 的常见档），让木纹沿柱身方向连续。

UV 在 quad 的四角直接写世界尺度除以密度，不做 `texture.repeat`（`repeat` 是整张贴图的全局缩放，会让不同组的缝对不上）。代价是 UV 值域会超过 1（最长边 16m / 0.32 = 50），这也是 §0.3 里「UV 最大到 300+ 张平铺」那条既有注释的来源，Float32 足够。

**为什么不用纹理图集（atlas）做近景**：图集要求所有材质共享一张贴图与一个材质，`roof` 的 `aoMap`、`metal` 的 `metalness` 会一起失效；而这三者的视觉差异是街景能否成立的关键（§1.5 的远景降档已给出图集只在 >120m 启用）。

| `wall` | 7 | 夯土、砖、粉墙、石砌、土坯、瓦砾墙、女墙 | 是 |
| `ash` | 4 | 灰、炭渣、炉膛、烬 | 是 |
| `earth` | 6 | 素土、黏土、砂、砾、田垄、粪土 | 是 |
| `roof` | 3 | 筒瓦、板瓦、茅草 | 是 |
| `ground` | 6 | 石板、条石、夯土路、砖墁、卵石、泥 | 是 |
| `ceramic` | 5 | 缸、瓮、管道、瓦当、琉璃 | 是 |

draw 账：单沙盒最多 `13 + 1(glow) = 14`；5 块 = **70**。裁定的 `5×13 = 65` 是「只算方块材质」的口径，本卷多记 5 个 `glow`，因为灯笼与窗纸是必现的发光件，漏记会让预算假达标。§4 按 70 记。

### 1.6 异步构建：Worker + 三态

项目当前**没有任何 Worker**（`grep -rn "new Worker" src` 命中 0）。这是本卷要新增的依赖，不是既成事实：

```
src/voxel/chunk.worker.ts   新文件  收 { cx,cy,cz, voxels:ArrayBuffer } → 回 { quad, pos, nrm, col, uv, idx }
src/voxel/chunkStore.ts     新文件  三态机：cold → building → ready；LRU 上限 60 区块
src/voxel/sandbox.ts        新文件  5 块沙盒的注册、配额、事务写入口
```

三态与主线程预算：

| 态 | 触发 | 代价 | 主线程 |
|---|---|---|---|
| `cold` | 未进入沙盒 | 只存体素（≤16,899B/区块） | 0 |
| `building` | 进入沙盒 / 编辑后 300ms 去抖 | Worker 6.9ms/区块 | 上传 `BufferGeometry` ≈ 0.4ms/区块 |
| `ready` | 上传完成 | 常驻 152B/quad | 0 |

**载入期只建高度场，不建网格**。这是对上一版「首次进沙盒才初始化导致掉落」的正面修正：高度场（`Uint8Array`）在 `world.ts` 的既有 task 链里建，5 × 196,608B = 983KB、约 5ms，塞得进 74ms 余量；网格则留到进入时再建。角色脚下的碰撞查询走高度场 + 体素查询，**不依赖网格**，所以「传送→落地→高度场没建好→掉回人间」的路径被切断。

进沙盒的视觉代价：12 区块 × 6.9ms ÷ 4 Worker ≈ **21ms**，加 300ms 去抖，实际是「一帧黑幕 + 21ms 后出图」。这段用 0.25s 的遮罩淡入盖住，不写进 `engineMs`（它在交互期，不在载入期）。

### 1.7 一次编辑的完整时序

玩家左键敲掉一格，到画面上出现缺口，中间有六步。每一步的代价都可算，这决定了「能不能在一帧内完成」：

| 步 | 动作 | 代价 | 说明 |
|---|---|---|---|
| ① | 体素射线（DDA，Amanatides–Woo） | 命中距离 ≤ 6m 时 ≤ 12 次格步进 | 每步 3 次比较，无分配 |
| ② | `occupancy` 查表 | O(1) | `Map<cellKey, owner>`，key 是三元整数打包 |
| ③ | `editTx` 事务写 | O(1) | 写 `Uint8Array` 一格 + 标脏 |
| ④ | 标脏区块 | 1–4 个区块 | 单格有 6 个邻面；跨区块边界时脏 2 个，落在角上脏 4 个（三个轴各一面 + 对角），保守取 4 |
| ⑤ | 去抖 300ms → Worker 重建 | 4 × 6.9ms = 27.6ms（Worker 内） | 300ms 取自「按住左键连续挖」的节奏：一格 0.25s |
| ⑥ | 上传 `BufferGeometry` | 4 × 0.4ms = 1.6ms（主线程） | 只在换 `array` 时需要；复用缓冲可降到 0.1ms |

主线程总代价 = ① + ② + ③ + ④ + ⑥ ≈ **1.8ms**，落在 16.7ms 帧预算内；Worker 的 27.6ms 与主线程并行，玩家感知到的是 300ms 后的缺口——这个延迟属于「挖掘手感」，不是卡顿，因为 300ms 内方块已经逻辑消失（碰撞立即更新），只是画面还没重画。

若不做去抖，连续挖 10 格会产生 10 次重建 = 69ms/10 格 ≈ 每格 6.9ms，Worker 队列会积压；去抖后 10 格合并成 1 次，只重建最终状态。这是「编辑期」与「载入期」两套预算必须分开的原因：载入期不能有 300ms 的等待，编辑期必须有。

**脏区块的邻接规则**（容易漏）：删掉区块 A 边界上的一格，会让**邻块 B 的相邻面**从「被遮住」变成「暴露」，所以 B 也必须重建。规则写成：`dirty(c) = {c} ∪ {c ± e_i | 被删格在该轴上位于边界}`，最多 4 个（三个轴的正负各一，但删一格最多落在 3 个面上，加自身 = 4）。

**LRU 与容量**：5 块沙盒 × 12 区块 = 60，恰好等于 LRU 上限 60，所以**满编时不会发生驱逐**。上界写成 60 而不是 64，是为了让「60 = 5×12」这条恒等式可被断言；若将来加第 6 块沙盒，LRU 必须同步改成 72，否则会出现「走进第 6 块就把第 1 块的网格踢掉、回头再建」的抖动。

### 1.8 与 ADR-2 的「运行时只能追加」如何共存

ADR-2 的三条硬规则，逐条落：

| ADR-2 要求 | 体素侧做法 | 机检 |
|---|---|---|
| 运行时几何必须用**世界坐标**构建，不走载入期变换链 | 区块网格用**局部坐标**建，`mesh.position` 设为沙盒原点（世界坐标），`matrixAutoUpdate = false`。局部坐标 + 父变换 = 世界坐标，且不经过 `scaleHeavenGeometry`/`enlargeLingxiao` | `probe-runtime-assets` 断言 `rt_vox_*` 的世界 AABB 与设计值逐值一致（±0.001m） |
| 必须自带包围球并显式注册 LOD | 每区块 `geometry.boundingSphere` 手填（中心 = 8,4,8；半径 = `√(16²+16²+8²)/2 = 12m`），`LodManager.register({ id:'rt_vox_<s>_<c>', tiers:{near:[mesh],mid:[mesh],far:[],impostor:null} })` | `probe-runtime-assets` 断言每个 `rt_vox_` 网格都在 `LodManager` 的 `groups` 里 |
| 禁止落在 `city_*` 命名空间 | 全部前缀 `rt_vox_`；`compactStatic()` 只挑 `city_`（`world.ts:716`），天然跳过 | `probe-runtime-assets` 断言 `world` 场景里不存在 `city_vox*` |

**LOD 陷阱**（`engine.ts:316` 的 `isReady` 要求 `mid.size > 0`）：体素区块只注册 `near` 一档，`mid`/`far` 是**空数组**，`isReady(g,1)` 会返回 false，`firstReady` 会往回退到 `near`，这是正确行为；但如果把 `far` 也留空且 `ready.far=true`，就会出现「整组永不隐藏」。本卷的做法：`tiers.far` 传空数组且**不设 `card`**，`register()` 里 `all.size === 0` 的分支会直接 return（`engine.ts:194`），等于不注册成 LOD 组——但 ADR-2 要求注册。折中：体素区块**只在 `near` 档注册，显式 `setReady(id, 2, false)`**，让 `firstReady` 永远落回 near。这条要写进 A10 断言，否则会重演「空的 mid 让整组永不隐藏」。

## 2. 建造：构件制

### 2.1 为什么必须是 0.32m

`buildings.ts` 的开间模数是 **3.2m**：`baysOf(f)` 里 `Math.round((w - 1.4) / 3.2)`（`:1016`），屋顶檩条 `Math.round(w / 3.2)`（`:295`），城墙加固肋 `Math.floor(len / 3.2)`（`:1474`）。3.2m 若按宋尺 0.32m 算，正好 **10 尺**——这不是巧合，是既有代码已经隐含采用的营造尺。

构件制全部落在这套既有资产上，不新造一套：

- 斗栱：`dougongBand()`（`buildings.ts:814`），一攒 5 件，沿面阔均布；
- 举折：`roofProfile(t) = (1-t)^1.35`（`bake.ts:266`），`buildings.ts:198` 的 `yAt(t) = H*(roofProfile(t) + KICK*t³ + CORNER*t²)`；
- 栏杆：平座勾阑（`:932`）与塔身栏杆（`:1943`）；
- 墙厚：0.18m（`:1031` 的 `t = 0.18`），是内衬墙外退量的对接值。

### 2.2 网格与开间

- 基本格：**0.32m**（1 宋尺）。所有构件原点的 x/z/y 必须是 0.32 的整数倍；
- 开间：3.2m = 10 尺，进深同理；面阔 `w` 与开间数 `n` 的关系沿用 `baysOf` 的 `n = clamp(round((w-1.4)/3.2), 1, 3)`；
- 举折：屋面上任意点到脊的水平距离比 `t ∈ [0,1]`，高度 `H·roofProfile(t)`，再叠 `KICK·t³ + CORNER·t²` 的翘角项。**不允许**在构件侧重写一条曲线——一旦重写，屋面与垂脊就会像上一版那样「脊不贴自家曲面」。

### 2.3 结构完整性：三条几何判据，不做刚体

本项目**没有刚体求解器**（`physics.ts` 只有 `ImpactSystem` 的击飞弹道，不是结构力学）。所以结构完整性只能做成**图判据**，不能做成「塌方模拟」。三条判据全部是几何量，可手算、可机检：

| 判据 | 形式 | 阈值 | 依据 |
|---|---|---|---|
| 支撑链 | 构件节点到「地基节点」的最短路径存在 | 必须存在 | 图连通性，无阈值 |
| 悬挑 | 任一节点沿水平方向到最近支撑的水平距离 | **≤ 2.4m** | 0.75 × 开间 3.2m；宋式斗栱出跳多在一至两跳（约 0.9–1.5m），2.4m 已留 1.6× 余量 |
| 倾覆 | 重心水平投影到基底多边形的最短距离 / 基底半宽 | **≥ 0.15**（即重心离边≥15%半宽）；高宽比 ≤ 3:1 | 静力等效判据的几何化；不引入材料常数，避免「假精确」 |

违规不是「塌」，而是**拒绝 + 告警**：

- 放置期：`place()` 返回 `E_UNSUPPORTED` / `E_OVERHANG` / `E_OVERTURN`，UI 出红框，不落盘；
- 既有结构被改（拆了下层柱）：整棵子树进入 `warn` 态（材质染红、每 2s 闪一次），**不自动拆除**。理由：自动拆除会让玩家的建筑在他离线时消失，属于不可逆破坏；而「红着但还在」给了玩家撤销窗口（D9 的可撤销契约）。

**算例（三开间殿，同一座 §2.6 的框架）**：

- 支撑链：`台基 → 12 柱 → 6 额 → 8 斗栱 → 6 檩 → 屋面`。每一层都能追到台基，深度 6 层，无断链；
- 悬挑：斗栱出挑 0.72m（`buildings.ts:821` 的 `0.72` 进深），远小于 2.4m 上限；屋面出檐 0.6m（`:1026` 注释里的「墙外 0.6m」）也在限内；
- 倾覆：对称结构，重心投影在基底中心，距边 4.8m，`4.8 / 4.8 = 1.0 ≥ 0.15`；高宽比 `5.5 / 9.6 = 0.57 ≤ 3`；
- 反例：一根独立柱高 6.4m、截面 0.32m，高宽比 `6.4 / 0.32 = 20 > 3` ⇒ `E_OVERTURN`。除非它被额/枋连成整体，整体宽度变成 3.2m，比值降到 2.0，才通过。

**增量重算**：每次 `place` / `remove` 只重算受影响子树的三个量（支撑深度、最大悬挑、重心），复杂度 O(子树)，不重算全图。三开间殿 40 个节点，单次编辑 ≤ 40 次浮点运算，可忽略。

**不做红石**：Minecraft 的红石是「离散信号 + 每 tick 传播」的完整电路系统，需要一张独立的信号图、每 tick 的拓扑更新、以及 0/1 到 0–15 的强度衰减。本项目已有 `interact.ts` 的交互点与 `POINTS` 表，任何「机关」都能用「交互点 + 状态位」表达，红石带来的额外表达力（时序电路、时钟、存储器）与宋式市井的题材不匹配。列为 §6.1 的不做项。

### 2.4 构件数据

```ts
type PartId = 'column'|'beam'|'purlin'|'bracket'|'wallPanel'|'door'|'window'|
              'railing'|'eave'|'ridge'|'tile'|'plinth'|'stair'|'lintel'|'signboard';

interface ComponentNode {
  id: number;
  part: PartId;
  pos: [number, number, number];   // 世界坐标，必须是 0.32 的整数倍
  rot: number;                     // 绕 y，弧度，必须是 π/8 的整数倍
  span: [number, number, number];  // 长宽高，米；长/宽 ≤ 3.2×3
  support: number[];               // 父节点 id 列表（0..2 个）
  bgroup: BGroup;                  // 落在 13 组之一
}
```

15 种 `PartId` 与既有 `buildings.ts` 的构件一一对应，**不新增几何内核**：每个 `PartId` 的生成函数都走 `b.bog/cyl/...`，最终由 `Baker` 合批。构件的 draw 不额外增加——它们落进既有 `city_*` 合并体（ADR-2 允许，因为构件是「载入期烘焙」的一部分，不是运行时追加）。**只有玩家在运行时新建的构件**才走 `rt_build_*` 前缀，并且逐条满足 ADR-2 的三条。

### 2.5 构件与体素的分工断言

`building` 包围盒内体素占比必须为 0：

```

```

这条断言的作用不是洁癖，而是防止实现者图省事「用体素糊一面墙」——一旦允许，`roofProfile` 与 `dougongBand` 立即作废，D3 就退化成「MC 套皮」。

### 3.1 三级格网

| 级 | 尺寸 | 谁用 | 整除关系 |
|---|---|---|---|
| 构件格 | 0.32m | 构件、开间、斗栱 | 1.6/0.32 = 5 |
| 体素格 | 0.50m | 地形、矿脉、洞穴、工事 | 8.0/0.5 = 16 |
| **超单元** | **8.00m** | 交界仲裁 | 25 尺 = 16 体素 = 5 营造单元 |
| 营造单元 | 1.60m | 建筑排布、开间的一半 | 5 尺；量化到体素是 3 或 4 格（见 §3.3） |

### 3.2 吸附算法

输入：世界坐标命中点 `p`、当前模式 `mode ∈ {voxel, component}`、目标构件 `part`。输出：`SeamPlan`。

```
1. 超单元定位
   sc  = floor(p / 8.0)                     // 三个轴各自取整
   local = p - sc*8.0                       // 0..8
2. 营造单元定位（构件侧，严格 1.6m）
   ci = clamp(floor(local / 1.6), 0, 4)     // 0..4，共 5 个单元
3. 构件格对齐（严格 0.32m）
   q  = round((sc*8.0 + ci*1.6) / 0.32) * 0.32
4. 体素回填（仅当需要台基/墙脚）
   VB  = [0, 3, 6, 10, 13, 16]              // 五个单元的体素边界（超单元内）
   vx0 = VB[ci]; run = VB[ci+1] - VB[ci]    // → [3, 3, 4, 3, 3]
5. 返回 { sc, ci, q, run, vx0, seam: |VB[ci] - ci*3.2| * 0.5 }
```

关键性质（每条都能写成断言）：

- `q mod 0.32 == 0` —— 构件原点永远在宋尺格上，**不受体素影响**；
- `Σrun = 3+3+4+3+3 = 16` 体素 = 8.0m，与超单元严格闭合；
- 名义边界 `ci × 1.6` 换算成体素是 `3.2 / 6.4 / 9.6 / 12.8`，量化到整数格是 `3 / 6 / 10 / 13`，四段的偏差分别是 **−0.1 / −0.2 / +0.2 / +0.1 m**；
- 因此**单段最大偏差 0.2m**，且**不累积**（第 5 段回到 16 格 = 8.0m 整）。这是 0.5 与 1.6 不可通约的固有代价，不是实现缺陷。

### 3.3 灰缝是量化残差，不是砌筑缝

本卷初稿曾把一个 1.6m 单元写成「3 体素 + 0.1m 灰缝」，五个单元会得到 8.4m——这条式子本身不闭合，已在本轮自查中改掉。现改为**边界量化**：`[3,3,4,3,3]` 直接分完整 16 格，残差落在段与段之间，宽度 0–0.2m。

必须说清它的性质：宋式砖砌灰缝是 0.5–1.5cm 量级，而这里的缝最大 0.2m，**它不可能被当作砌筑缝**，它是格网换算的舍入误差。所以本卷加一条使用限制：

> 构件与体素的交界**只允许出现在台基、墙脚、壕沟沿**这类本来就有压边、有收分、有阴影的位置；**不允许**出现在屋面、栏杆、斗栱、门窗框上。

理由：0.2m 的偏差在 2m 以内近看是可见的；压边与阴影能吸收它，而屋面与栏杆是「一条线读到底」的构件，0.2m 的错位会被一眼看成「歪了」。这条限制同时也是 §3.5 情形 A 只允许 3 格基础墩的原因——基础墩越深，错位越容易被看见。

### 3.4 三开间殿落在体素台基上（完整算例）

把上面的规则跑一遍，所有数字可复算：

- 殿身：面阔 **9.6m** = 6 个营造单元；进深 **6.4m** = 4 个营造单元；
- 台基体素：按 `ceil(尺寸 / 0.5)` 取整——宽 `ceil(9.6/0.5) = 20` 格（10.0m），深 `ceil(6.4/0.5) = 13` 格（6.5m）；
- 六个单元的体素区间：跨越 1 个完整超单元（16 格）加下一超单元的第 1 段（3 格）⇒ `[0,3) [3,6) [6,10) [10,13) [13,16) [16,19)`，合计 19 格 = 9.5m；
- 第 20 格是**余量**：殿身 9.6m 比 19 格（9.5m）长 0.1m，这 0.1m 由台基左右各 0.2m 的出边走掉，不落在单元边界上；
- 进深侧：4 个单元 = `VB[4] = 13` 格 = 6.5m，比殿身 6.4m 多 0.1m，台基前后各出 0.05m——这个 0.05m 小于 0.1m 的可见阈值，读成「齐边」，可接受。

**四道校验**（都能写成单测）：

1. `19 + 1 = 20` 格，`20 × 0.5 = 10.0m ≥ 9.6m` ✅
2. 单元区间互不重叠且并集连续：`0..19` 无空洞 ✅
3. 殿身原点若在 `x = 0.32k`，台基原点必须在 `x = 0.5m` 的格上——两者只在 `k` 使 `0.32k` 为 0.5 的整数倍时重合，即 `k` 是 25 的倍数（`0.32×25 = 8.0`）。所以**台基原点固定取超单元原点**，殿身在其内偏移，不做两次取整 ✅
4. 若玩家把殿身改成 11.2m（7 个单元），台基宽变成 `ceil(11.2/0.5) = 23` 格（11.5m），单元区间延伸到第二超单元的第 2 段（`[16,19)` 后再 `[19,22)`），仍闭合 ✅

这个算例暴露了一件事：**台基尺寸由殿身尺寸决定，不由单元数决定**。若反过来「先铺 19 格台基再放殿」，殿身会短 0.1m 悬空——这正是上一版「先建沙盒再放建筑」会踩的坑。

### 3.5 三种冲突情形

**情形 A：构件悬在体素崖边（支撑不足）**

- 检测：构件的 `support` 链末端节点的下方 0.5m 内没有体素或地形；
- 处理：自动生成「基础墩」——从构件底面往下填体素，最多 3 格（1.5m）；超过 3 格返回 `E_NEED_FOUNDATION`，要求玩家先挖到实土；
- 不允许：悬空构件（`E_FLOATING`）。

**情形 B：体素开挖切到构件基础**

- 检测：体素删除操作的目标格，落在任一 `ComponentNode.support` 的下方 1 格内；
- 处理：**冻结**——删除被拒绝（`E_LOAD_BEARING`），并给出「先拆 XX 构件」的提示；玩家可以先拆构件再挖；
- 不允许：先挖后塌。理由同 §2.3：不可逆破坏不给撤销窗口。

**情形 C：同一格被两侧同时写**

- 检测：`editTx` 事务内，同一世界格被 `voxel.put` 与 `component.place` 各写一次；
- 处理：**以 8.0m 超单元为仲裁单位**，事务内后写者必须先 `undo` 前写者，否则整笔事务回滚（`E_CONFLICT`）。单写入口 `editTx` 是唯一合法写路径，禁止直接改 `Uint8Array`；
- 不允许：两套数据结构各自持有一份「这一格是谁的」的副本——只保留一份 `occupancy: Map<cellKey, 'voxel'|'component'>`，`cellKey = (sc, ci, sub)`。

三条冲突的代价：`editTx` + `occupancy` + 吸附约 **420 行**（裁定估 400–600 行，落在区间内）。

## 4. 面数与内存预算

### 4.1 口径：按暴露面，不按方块数

一个方块的 6 个面里，只有朝向空气的那几个要发。**埋在地下的方块不产生面**。所以预算必须分型，不能用一个「面/块」常数。本机实测三个 archetype（确定性样本，见 §4.4）：

| archetype | 样本 | 方块 | 暴露面 | 面/块 | greedy 后 quad | 压缩比 | quad/块 |
|---|---|---|---|---|---|---|---|
| 地表薄壳 | 48×24×48 | 16,457 | 7,376 | 0.448 | 2,245 | 3.29× | 0.136 |
| 地表薄壳 | 128×40×128 | 196,035 | 57,418 | 0.293 | 27,645 | 2.08× | 0.141 |
| 地表薄壳 | 256×64×256 | 1,265,992 | 279,312 | 0.221 | 160,603 | 1.74× | 0.127 |
| 洞穴 | 96×48×96 | 236,087 | 30,730 | 0.130 | 9,315 | 3.30× | 0.039 |
| 薄壳建筑 | 64×24×40 | 18,864 | 37,412 | **1.983** | 933 | **40.10×** | 0.049 |
| 纯平板 | 64×64×1 | 4,096 | 8,448 | 2.062 | 3 | 2,816× | 0.001 |

三条读数：

1. **地表的面/块最低（0.22–0.45）**，因为绝大多数方块被埋住；上一版写「1.3 面/块」对地表是**高估 3–6 倍**，对薄壳是**低估 35%**。
2. **薄壳建筑实测 1.983 面/块**，接近理论值 2（一堵 1 格厚的墙，两侧各 1 面）；上一版按 3 面/块算是保守上界，可用，但不能当实测。
3. **greedy 的压缩比跨度极大**（1.74× 到 2,816×），取决于面是否共面同材质。用单一压缩比做预算必然错，必须分型给区间。

### 4.2 容量契约：9,000 quad + greedy ≥ 6.7×

上一版的 `44,000 quad/沙盒` 是**未合并**口径，而 20,000 块 × 3 面 = 60,000 面，装不下。本卷把它换成等价契约：

```
单沙盒「玩家可建」quad 配额 = 9,000
薄壳场景：20,000 块 × 3 面 ÷ 6.7× = 8,955 quad ≤ 9,000     ✔
```

**这个 9,000 是「玩家编辑产生的面」，不是「沙盒总面数」**。这条区分必须写死，否则会和 §4.3 的 1M 方块档打架：一个沙盒装 196,608 格，若全是地形，按 0.0996 quad/块 算就是 19,582 quad，早就超过 9,000。地形与洞穴是**生成物**，它们的面数由 archetype 决定，不占玩家配额；配额只拦「玩家手搓出来的病态几何」。两笔账分列在 §4.3 末尾。

6.7× 是**要求的下限**，不是乐观值：实测薄壳 40.10×，余量 6 倍。若某次编辑让压缩比掉到 6.7× 以下（例如整片棋盘格），`sandbox.ts` 在配额用尽时拒绝放置（`E_QUOTA`），并提示「当前结构无法合批」。

退化上限（供对照，不采用）：若完全放弃 greedy，按 3 面/块 算，9,000 quad 只够 **3,000 块**；上一版勘误里的 14,600 块，是「44,000 quad ÷ 3 面」的结果，对应 2.2× 的隐含压缩假设。两个数都不如「9,000 quad + 6.7× 下限」严谨，故本卷采用后者，并把 14,600 与 3,000 作为**上下参照**记在此处。

### 4.3 三档预算表

混合比假设：60% 地表 + 30% 薄壳 + 10% 洞穴（按方块数）。逐项算：

```
面/块   = 0.6 × 0.321 + 0.3 × 1.983 + 0.1 × 0.130 = 0.1926 + 0.5949 + 0.0130 = 0.800
quad/块 = 0.6 × 0.135 + 0.3 × 0.049 + 0.1 × 0.039 = 0.0810 + 0.0147 + 0.0039 = 0.0996
```

（0.321 与 0.135 是三个地表样本 0.448/0.293/0.221 与 0.136/0.141/0.127 的均值。）内存按 152B/quad，顶点 = 4 × quad。

| 档 | 方块数 | 占沙盒 | 暴露面（未合并） | greedy quad | 顶点 | 几何内存 | draw（近景） |
|---|---|---|---|---|---|---|---|
| 1 万 | 10,000 | 0.05 块 | 8,000 | **996** | 3,984 | **151KB** | ≤ 14 |
| 10 万 | 100,000 | 0.51 块 | 80,000 | **9,960** | 39,840 | **1.51MB** | ≤ 28 |
| 100 万 | 1,000,000 | 5.09 块 | 800,000 | **99,600** | 398,400 | **15.1MB** | ≤ 70 |

逐行可复算：`10,000 × 0.0996 = 996`；`996 × 152 = 151,392B = 147.8KiB`（表里写 151KB，按 1,000 进制，保守）；`996 × 4 = 3,984` 顶点；顶点属性 `3,984 × 32 = 127,488B`，索引 `996 × 6 × 4 = 23,904B`，合计 151,392B ✅。三档是同一条式子乘 10 与乘 100，没有第二个假设。

区间（按 archetype 全押一侧）：

| 档 | 全薄壳（最省） | 全地表（最费） | 全洞穴 |
|---|---|---|---|
| 1 万 | 490 quad / 74KB | 1,410 quad / 214KB | 390 quad / 59KB |
| 10 万 | 4,900 / 745KB | 14,100 / 2.14MB | 3,900 / 593KB |
| 100 万 | 49,000 / 7.45MB | 141,000 / 21.4MB | 39,000 / 5.93MB |

**满编总量要分两笔账**（这是上一版 42.2MB 对不上 57.6MB 的同类错误，必须写清）：

| 项 | 计算 | 常态 | 最坏（全地表） |
|---|---|---|---|
| ① 地形/洞穴生成面（不占配额） | `983,040 × 0.0996` / `× 0.141` | 97,910 quad = **14.9MB** | 138,610 quad = **21.1MB** |
| ② 玩家可建（5 × 9,000 配额） | `45,000 × 152B` | 45,000 quad = **6.84MB** | 45,000 quad = **6.84MB** |
| ③ 体素数据（Uint8 + 调色板） | `5 × 196,608 + 5 × 512` | **1.01MB** | 1.01MB |
| **合计** | ① + ② + ③ | **≈ 22.8MB** | **≈ 28.9MB** |
| 占 2,615MB 峰值 | 合计 ÷ 2,615 | **0.87%** | **1.11%** |

`152B/quad` 已含索引，不另加。**结论：满编 5 块沙盒的体素系统是 23–29MB，不是一个「零头」但也远不到 42MB**——上一版的 42.2MB 只算了玩家可建面，漏了地形自身；本卷把两笔账并排列出，避免同一个坑。

**最坏情形（必须防）**：棋盘格 6 面/块、greedy 无效 ⇒ 1M 方块 = 6,000,000 quad = **912MB**，是全城常驻几何（1,734.6MB）的 53%。所以配额是硬门禁，不是建议值。

实测探针（本机，`node`，确定性样本，无随机）：

```
地表 48×24×48      blocks=16,457   exposed=7,376   greedy=2,245   3.29x   14ms
地表 128×40×128    blocks=196,035  exposed=57,418  greedy=27,645  2.08x   96ms
地表 256×64×256    blocks=1,265,992 exposed=279,312 greedy=160,603 1.74x 539ms
洞穴 96×48×96      blocks=236,087  exposed=30,730  greedy=9,315   3.30x   54ms
薄壳 64×24×40      blocks=18,864   exposed=37,412  greedy=933     40.10x  —
平板 64×64×1       blocks=4,096    exposed=8,448   greedy=3       2816x   —
```

吞吐 = 1,265,992 ÷ 0.539s = **2.36M 格/秒**（含 greedy 与掩码分配，单线程）。

ADR-7 要求的 Δ 账：

| 项 | Δ | 依据 |
|---|---|---|
| Δ`T_static` | **+0 面**（体素与构件都不进 `city_*` 合并体） | 体素是 `rt_vox_*`，构件是 `city_*` 但只在载入期烘焙；玩家新建构件走 `rt_build_*` |
| Δ常驻几何 | **+22.8MB**（常态满编）/ **+28.9MB**（全地表最坏） | §4.3 的 ①+②+③ |
| Δ`engineMs` | **+5ms**（只建高度场，不建网格） | 983KB `Uint8Array` 填充，5 个 196,608 元素循环 |

**为什么 5 块不同时可见**：沙盒分布在人间 3 块、天宫 1 块、地府 1 块，任一时刻玩家只可能在一个界；视锥剔除后通常 0–1 块。70 calls 是「全可见」的理论上界，不是常态。

## 5. 可执行验收断言

全部落到 `scripts/probe-voxel-*.mjs`（待建）或 `tests/` 单测。判定只有 `PASS` / `BLOCK` + 退出码。

**两类断言，两种跑法**，不能混：

- **纯单测（A1–A3、A6–A9）**：`vitest run`，无浏览器、无 GPU、无打包态。这类断言的输入是确定性样本（固定种子），输出是布尔与计数，可在 CI 里跑；
- **打包态探针（A4、A5、A10–A12）**：必须对着 `release-v96` 的 `file://` 页面跑，因为要读 `renderer.info`、`LodManager.groups`、真实 draw call。这类断言在 `vite dev` 下不成立（HMR 会重置场景）。

四类探针的最小契约（与既有 `probe-*.mjs` 同款）：

```
node scripts/probe-voxel-quota.mjs --url file:///.../dist/index.html --sandbox 3
→ 输出 JSON { pass: boolean, quads: number, limit: 9000, sample: 'shell20k' }
→ 退出码 0=PASS / 1=BLOCK
```

**A4 的分档设计**：断言不是「不许超过」，而是「超了要按契约拒绝」。所以 A4 同时验两件事：① 合规样本（20,000 薄壳块）不触发 `E_QUOTA` 且 quad ≤ 9,000；② 病态样本（棋盘格）必须在第 1,501 块被拒。只验①会让「配额形同虚设」蒙混过关。

**A12 的重放口径**：同一编辑序列（10 次挖、10 次放）跑两遍，比对**区块字节**而不是比对网格——网格对浮点顺序敏感，字节对顺序也敏感，但区块是 `Uint8Array`，比对是精确的、无容差的。网格只在 A3 里做集合等价。

| # | 断言 | 判据 | 落点 |
|---|---|---|---|
| A1 | RLE 往返无损 | 10,000 个确定性种子区块，`decode(encode(v)) == v` 逐字节；且 `encode` 后 ≤ 16,899B | 单测 |
| A2 | 区块存储阈值 | 地表样本 RLE ≤ 12,288B；超限自动 `mode=0` | 单测 |
| A3 | greedy 面覆盖等价 | 合并前后逐面比对（法线、材质、中心点），集合完全相等；quad 数 ≤ 未合并面数 | 单测 |
| A4 | 单沙盒配额 | 满编压力样本（20,000 薄壳块）quad ≤ 9,000；棋盘格样本在第 1,501 块触发 `E_QUOTA` | `probe-voxel-quota` |
| A5 | draw 上界 | 5 沙盒全可见 + 近景 ⇒ draw ≤ 70；远景图集档 ⇒ ≤ 5 | `probe-voxel-draw` |
| A6 | 顶点字节 | UV 组 32B/顶点、非 UV 组 24B/顶点；quad = 152B | 单测（读 `BufferGeometry` 的 `array.byteLength`） |
| A7 | 构件格对齐 | 任意构件原点 `pos % 0.32 == 0`（三轴）；旋转是 `π/8` 整数倍 | 单测 |
| A8 | 超单元闭合 | `[3,3,4,3,3]` 累加 = 16 体素 = 8.0m；四段量化偏差 = −0.1/−0.2/+0.2/+0.1m，最大 0.2m | 单测 |
| A9 | 举折单调 | `roofProfile(0)==1`、`roofProfile(1)==0`、`t∈(0,1)` 严格递减；与 `bake.ts:266` 同式 | 单测 |
| A10 | 运行时追加合规 | 每个 `rt_vox_*` 有包围球、已注册 LOD、世界 AABB 与设计值差 ≤ 0.001m；场景内无 `city_vox*` | `probe-runtime-assets` |
| A11 | 结构判据边界 | 悬挑 2.39m ⇒ PASS，2.41m ⇒ BLOCK；重心偏移 14% ⇒ PASS，16% ⇒ BLOCK | `probe-build-struct` |
| A12 | 确定性 | 组装路径零 `Math.random` / `performance.now`；同一编辑序列两次重放，区块字节完全相同 | `probe-determinism` 扩展 |

**A10 的补充**：必须同时断言 `LodManager.isReady(group, 1) === false`（因为 `mid` 为空），否则「空 mid 让整组永不隐藏」的旧陷阱会回归（`engine.ts:316`）。

## 7. 自认最弱的三段

1. **§4.1 的实测样本是合成的，不是真实玩家的建造分布**。六个 archetype 的压缩比（1.74×–2,816×）都是我自己构造的确定性体，真实沙盒里「一半墙一半地形」的混合比例没有实测。§4.3 的加权数（0.0996 quad/块）是假设，不是观测；上线前必须用真实存档跑一遍 `probe-voxel-quota`。同理，**23MB 的满编结论依赖「60/30/10 混合比」**，若玩家把 5 块沙盒全建成薄壳（受 5×9,000 配额封顶），总量是 6.84 + 1.01 = **7.85MB**；全挖成洞穴则是 38,338 quad = 5.83MB + 1.01 = **6.84MB**。23MB 是混合常态，不是上界；最坏仍是全地表的 **28.9MB**。
2. **§3.3 的边界量化残差最大 0.2m，是这套方案的固有代价**。它由 0.5 与 1.6 不可通约决定，不是实现能消掉的；本卷用「只允许出现在压边位置」来限制它，但这条限制能覆盖多少真实建造场景，没有实测。若美术在近景看出错位，唯一根治方案是改体素尺寸（U1 的 B 案）。
3. **§1.6 的 21ms 进沙盒延迟是推算，不是实测**。它由「6.9ms/区块 × 12 ÷ 4 Worker」得出，但 Worker 启动、`postMessage` 拷贝、GPU 上传都没测；真实值可能是 40–80ms。若超过 100ms，需要预取相邻沙盒或用 `SharedArrayBuffer`（U3）。缓解手段是先加载玩家最近进入的那一块（1 块 = 12 区块），把 4 块的预取推到进入后空闲帧——但这条「先近后远」的调度本身也没实测，只是把风险从「首帧」挪到「后续帧」。

**收口判据**：本卷的可交付性不取决于文字，取决于 §5 的 12 条断言。其中 A1–A9 可在无 GPU 环境下跑完，A10–A12 必须对 `release-v96` 的打包态跑。**在这 12 条全绿之前，本卷只能算「设计完成」，不能算「实现完成」**；§4.3 的三档数字也只是预算，不是实测吞吐。
