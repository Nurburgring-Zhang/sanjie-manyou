# D7 性能与预算

> **本卷服从 D0《重建纲领》的 ADR-2、ADR-3、ADR-4、ADR-5、ADR-7。**
>
> - **ADR-7（性能预算前置）**：任何新增系统先算 `ΔT_static / Δ常驻MB / ΔengineMs`；合计超 `engineMs 11,451` 或 `T_static 18.96M` 的方案**先砍再谈**；当前余量 **74ms**。本卷是这条裁定的执行细则，也是它唯一的账本。
> - **ADR-2（烘焙是基底，运行时只能追加）**：决定造物、体素、玩家建筑各进哪本账——它们**不进** `T_static`，只进 `T_frame` 与常驻。
> - **ADR-3（确定性）**：决定成本模型必须按固定 `seed` 与固定样本给，不允许「跑一次看看」的浮动数字。
> - **ADR-4（打包态只有资产热替换）**：决定 `CreationBundle` 只能走 fetch + 校验 + 挂载，没有 HMR、没有代码热更，因此它的耗时全部是**同步可测**的。
> - **ADR-5（代码在进程外执行，跨界只传数据）**：决定「构建 180s」不计入 `engineMs`，但**必须**计入用户等待；本卷给这条等待定价，D9 给它画 UI。
>
> 行号基线：工作树 `806fa79`（v93）+ v96 未提交改动，**未锁 commit**。锁 commit 之前，行号只作定位线索，不作判据。

## 0. 先把口径钉死：四个数字、两个机位、一条抖动

这一节不是前言，是**判据的前置条件**。本项目已经因为口径混用返工过两轮（「四个静态面数字」与「draw 从 186 到 608」），本卷不允许第三次。

### 0.1 载入的四个数字，只有三个是加法项

| 项 | v95 | v96 | Δ | 来源 |
|---|---:|---:|---:|---|
| `navToEngineMs` | 420 | **297** | −123 | `verify-packaged.mjs` 读 `window.__loadStartAt` |
| `engineMs` | 11,451 | **11,629** | **+178** | 同上，读 `__loadEndAt − __loadStartAt` |
| 其中 `flushMs` | 856 | **918** | +62 | `world.ts:788` 逐次累计（**⊂ engineMs，不可另加**） |
| **合计** | 11,871 | **11,926** | +55 | `navToEngineMs + engineMs` |
| 距 12,000 红线 | 129 | **74** | −55 | 减法 |

四条复算，逐条可核：

```
297 + 11,629 = 11,926          ✓ 合计
12,000 − 11,926 = 74           ✓ 余量
918 / 11,629 = 7.89%           ✓ flush 占 engineMs（不是额外项）
918 / 33 步  = 27.8ms/步        ✓ 每步末尾一次 flush
```

**第一条纪律**：`flushMs` 是 `engineMs` 的**子集**。把它加到 11,926 上，会得到 12,844 的假超线结论——这是上一版勘误里出现过的错。

**第二条纪律**：`navToEngineMs` 的 −123 掩盖了总量只 +55 的事实。导航变快不是本事，**构建变慢才是风险**：`engineMs +178` 恰好是「2.1 去格网」与「B8 常量单源化」的代价。总账的处置建议（先把 `engineMs` 压回 11,451）本卷照办，并把它写成本卷的第一目标：

```
目标不是「保住 74ms」，而是「先补回 178ms，再谈新增」。
需要回收 = 178（回归）+ 74（余量）= 252ms。
```

### 0.2 面数只有三个口径，且不能互相换算

| 口径 | 值 | 定义 | 谁在量 |
|---|---:|---|---|
| `T_static` | **18,959,342** | `world.assetAudit` 逐组 triangles 求和，**不含**实例展开、**不含**多 pass | `probe-face-accounting.mjs` |
| `T_scene` | **19,873,969** | 场景内所有 Mesh 的 `geometry` 三角面求和，`InstancedMesh` 只算**单份** | 同上 |
| `T_frame` | **45,911,485** | `renderer.info.render.triangles`，**含**实例展开、**含**多 pass | 同上 |

三条反推，用来验证口径本身没被写错：

```
T_frame / T_static = 45,911,485 / 18,959,342 = 2.422×      ← 实例展开 + 阴影 pass
T_scene − T_static = 19,873,969 − 18,959,342 = 914,627     ← 非烘焙几何（地形、天空、实例池）
T_frame / calls    = 45,911,485 / 378        = 121,459 面/call
```

**顶点数的交叉核验**（这条是本节最有用的自检）：

```
常驻几何 attr            = 1,734.6MB
T_static × 3             = 56,878,026 顶点（VGeo/Baker 都是三角汤，顶点 = 面 × 3）
平均字节/顶点            = 1,734.6e6 / 56,878,026 = 30.50B
QBuf 布局                = 24B（无 UV 组）+ 8B（有 UV 组）
解出带 UV 的顶点占比 f    = (30.50 − 24) / 8 = 0.8125
```

`f = 81.25%` 与「14 组里 10 组带 UV、且按面数加权后 UV 组占约八成」完全吻合。**两个独立来源（字节账与源码布局）对上了**，说明 `1,734.6MB` 与 `T_static 18.96M` 不是互相矛盾的两个数，而是同一份几何的两种记法。

**第三条纪律**：谈面数必须写「哪个口径 + 哪个机位」。`34.81M` 与 `45.91M` 都是 `T_frame`，只是相机不同；`18.96M` 是烘焙总量。三者不能相减，也不能互相作阈值。

### 0.3 draw 有两个机位，中间隔着一条 222 的抖动带

`src/core/engine.ts:787-788`：

```ts
this.renderer.shadowMap.autoUpdate = false;
if ((Engine.shadowTick++ & 1) === 0) this.renderer.shadowMap.needsUpdate = true;
```

阴影贴图**隔帧更新**。于是同一个场景、同一台相机，draw call 会在两个值之间跳：

| 读数 | 值 | 机位/条件 | 来源 |
|---|---:|---|---|
| 面数探针机位 | **378** | `probe-face-accounting` 的采样帧 | D0 §0 |
| HUD 出生点机位 | **372** | `verify-packaged` 的 v96 读数 | `SPEC-总账` v96 段 |
| 阴影帧峰值 | **594** | 阴影 pass 打开的那一帧 | `SPEC-总账` §0「474–594」 |

378 与 372 差 6（1.6%），是两台相机视锥不同；372 与 594 差 222，是**奇偶帧**。这意味着：

> **任何小于 222 的 Δdraw 断言，在不锁 parity 的采样下都不可判。**

所以本卷定义 **预算机位 P0**：

- 位置：`verify-packaged` 的出生点（与 v96 HUD 同一机位、同一朝向、同一画质档 `high`）；
- 时间：加载完成后 3s，相机静止；
- 奇偶：只采**阴影帧**（`shadowTick & 1 === 0`），采样 3 次取中位数；
- 基线：**calls 372 / tris 45,923,185**。

**P0 与 D0 的 378 不冲突**，它们是两台相机。本卷的所有增量断言对 P0 记；所有面数比例对 `T_static` 记。两个基准各自只在一种用途上生效，不互相换算。

顺带记一条**探针自身的缺陷**：`engine.ts:755-756` 把 `this.frameMs.shift()` 写了两遍，窗口实际是 599 帧而不是注释暗示的 600。对 p95 的影响约 0.17%，不影响结论，但会让「同一份数据两次算 p95 差一帧」。修它是 D1 的事，本卷只登记。

### 0.4 内存有三档，混用会得出相反的结论

| 档 | 值 | 定义 | 来源 |
|---|---:|---|---|
| 峰值堆 | **2,615MB** | 40ms 采样全程序列最大值 | `probe-mem.mjs` |
| 稳态堆 | **1,950MB** | 加载结束、场景静止后的堆 | `probe-mem` 的 `heapEnd` |
| 常驻几何 | **1,742.7MB** | attr 1,734.6 + idx 8.1 | `probe-mem` |
| 运行时开销 | **207.3MB** | 稳态 − 常驻 | 1,950 − 1,742.7 |
| 生成期瞬态 | **665MB** | 峰值 − 稳态 | 2,615 − 1,950 |
| 目标 | **1,536MB** | D0 §0 | — |

三档各自的含义不同：**峰值是「会不会被系统杀掉」，稳态是「能不能和别的程序共存」，常驻是「几何本身有多重」**。D0 只给了一个目标值 1,536，没有说它管哪一档——这是 D0 需要补的一句话，本卷在 §1.3 给出证据说明它**在常驻这一档就已经不可能**。

### 0.5 判定语言

本卷只用三种判定，不用「基本达标」「接近目标」这类模糊词：

- **PASS**：实测值 ≤ 阈值，且差值 ≤ 测量噪声（本卷取 1%）；
- **BLOCK**：实测值 > 阈值；
- **UNMEASURED**：探针未建或未跑。**UNMEASURED 不等于 PASS**，也不等于 BLOCK——它是「未验证」，在 D8 的矩阵里必须显式标出。

## 1. 基线逐值复述

### 1.1 载入：11,629 里有多少是「构建」

`engineMs 11,629` 是一个黑箱。它由三部分构成，但只有一部分被单独记过账：

| 组成 | 值 | 状态 | 依据 |
|---|---:|---|---|
| 33 个加载步的步体 | 未单独求和 | **未测** | `__loadTimings` 有每步 `dt`，但没有对 v96 求和发布 |
| 33 次 `baker.flush` | **918ms** | 已测 | `__flushMs` |
| `compactStatic` 合批 | 未单独记 | **未测** | 只有 `__heapPre/__heapPost`，没有 `__compactMs` |
| `settle` 等待 | **≥400ms** | 代码可读 | `world.ts:811` |
| 33 次 `await raf()` | **≤551ms** | 可算上界 | 33 × 16.7ms |
| 残差 | 未知 | — | 上四项之外 |

于是有一条**必须成立的恒等式**，它是本卷所有优化项的前提：

```
engineMs = Σ 步体 + flush(918) + compact + settle(≥400) + Σ raf(≤551) + 残差
11,629  =   ?    +  918   +    ?     +   ≥400        +   ≤551     +   ?
```

把已知项扣掉：`11,629 − 918 − 400 = 10,311ms` 仍然没有归属。这不是「有 10 秒浪费」，而是**账没记全**——`compactStatic`、步体、raf 究竟各占多少，只能靠 `probe-load-attrib` 拆。在拆之前，任何「某项能省 X ms」的说法都只是上界，不是收益。

**这就是本卷对 M0 的第一条要求**：先建 `probe-load-attrib`，把这条恒等式闭合到 ±50ms。没有它，74ms 的修补只能靠猜。

### 1.2 两条已经能读出来的浪费

不需要新探针，光读代码就有两处**确定**的开销：

**(a) `settle` 的 400ms 硬等待**（`world.ts:807-812`）：

```ts
phase('settle');
await Promise.all([idle(800), new Promise<void>((resolve) => setTimeout(resolve, 400))]);
```

注释写得很清楚：它是为了让 `__heapPre` 稳定，给 idle GC 一个结算点。问题是——

- 它在 `__loadStartAt` 与 `__loadEndAt` 之间，**被完整计入 `engineMs`**；
- `Promise.all` 等的是两者中**慢的那个**，而 `setTimeout(400)` 是硬下界，所以这段**至少 400ms**，最坏 800ms（`idle(800)` 的超时）；
- 它的产出是一对**只给探针看**的数字（`__heapPre` / `__heapPost`）。

也就是说：**一段纯测量用途的等待，占了生产路径的 3.4%–6.9% 载入时间**。这不是优化，是**把仪器装进了发动机**。

**(b) 33 次逐步 `await raf()`**（`world.ts:805`）：

每个加载步结束时无条件让一帧。`raf` 的语义是「等下一次垂直同步」，在可见窗口下最多 16.7ms。33 步 ⇒ **上界 551ms（4.74%）**。其中真正需要让帧的，是那些「步体本身超过 ~16ms」的步骤；一个 2ms 的步骤让一帧，等于用 16.7ms 买 14.7ms 的空等。

同一份代码在 `bake.ts:1303` 已经承认过这个教训：

> 「旧实现每装一组就让一帧，实测 **271 次让帧共等掉 4.6s**，而真正装配只有 0.63s —— 每组 2.3ms 的活却要等 16.7ms 的帧，**让帧反而成了 flush 的主成本**。」

`flush` 内部已经改成「累计装配 ≥8ms 才让一帧」。但**外层 33 步的 raf 与 `compactStatic` 的逐批 raf 没有改**。这是同一类浪费在两个层级的残留。

### 1.3 内存：1,536MB 目标已经结构性不可达

先把账摆平：

| 项 | 计算 | 值 |
|---|---|---:|
| 常驻几何 | 1,734.6 + 8.1 | **1,742.7MB** |
| 运行时开销 | 1,950 − 1,742.7 | **207.3MB** |
| 稳态堆 | 实测 | **1,950MB** |
| 峰值堆 | 实测 | **2,615MB** |
| 目标 | D0 | **1,536MB** |
| 常驻超目标 | 1,742.7 − 1,536 | **+206.7（+13.5%）** |
| 稳态超目标 | 1,950 − 1,536 | **+414（+27.0%）** |
| 峰值超目标 | 2,615 − 1,536 | **+1,079（+70.2%）** |

**不可达的证明只有两步：**

1. 目标 1,536 减去运行时开销 207.3，留给几何的预算是 **1,328.7MB**；实测常驻 1,742.7，超出 **414MB（−23.8% 才达标）**。
2. 想靠「削峰值」补，最多能削 665MB 的瞬态，削完稳态仍是 **1,950MB**，离 1,536 还差 414MB。**所以削峰值这条路在数学上无效**——它连方向都不对。

结论：**1,536MB 只能在「常驻几何减 414MB」或「改目标」之间二选一。** 中间没有第三条路。

四条可选路径，逐条给代价（顶点数按 56.88M 计，运行时开销按 207.3MB 不变，全部为线性外推、**未实测**）：

| 方案 | 字节/顶点 | 常驻 MB | 稳态 MB | 达标 | draw 代价 | 视觉风险 |
|---|---:|---:|---:|:--:|---|---|
| 现状 | 30.5 | 1,742.7 | 1,950.0 | ✗ +414 | 0 | — |
| A：normal `Int16→Int8` | 27.5 | 1,572.4 | 1,779.7 | ✗ +244 | 0 | 大面积平滑面可能出现 1/255 法线台阶 |
| B：A + color `Uint16→Uint8` | 24.5 | 1,401.7 | 1,609.0 | ✗ +73 | 0 | 渐变面色带（夜空、水面、釉面最明显） |
| C：B + pos `Float32→Int16` 局部量化 | 18.5 | 1,060.4 | 1,267.7 | ✓ −268 | **+200～600** | 1cm 量化；跨块接缝 |
| D：C 只对 >500m 的合并体切块 | ~21.0 | 1,202.6 | 1,409.9 | ✓ −126 | +80～200 | 同上，弱一档 |

**为什么 C/D 会推高 draw**：`pos` 改成 `Int16` 必须配一个**每网格的局部原点**，否则 ±327.67m 的量程装不下 10km 的城。而现在一个 `city_roof_9`（167MB / 1,824k 面）可能横跨数公里——要给它局部原点，就得按空间切块，切一块多一个 mesh、多一次 draw。**内存与 draw 在这里是直接对立的**，不是可以同时优化的两个指标。

**本卷的建议（交 lead 裁决，不擅自定）**：

- **推荐 P-1**：把目标改成「稳态 ≤ 1,950MB、峰值 ≤ 2,700MB」，并把**「不增长」作为棘轮**（每次交付必须 ≤ 上一次 + 1%）。理由：零成本、零视觉风险、立刻停止「假达标」；代价是承认现状。
- **备选 P-2**：只做方案 A（normal 压 8 位，省 170.6MB、零 draw 代价），把稳态压到 1,779.7MB，**仍不达标但缩小差距**。它可以在 P-1 之下作为独立收益项。
- **不建议现在做 C/D**：它换来的 268MB 要以 200–600 个 draw 为代价，而 draw 预算在 §4.4 已经只剩 162–190 的余量（见下）。**用一个已经紧张的预算去换另一个已经超标的预算，是把问题搬家，不是解决。**

### 1.4 draw：372 是基线，600 是天花板，中间只剩 228

| 项 | 值 | 说明 |
|---|---:|---|
| P0 基线 | 372 | v96 HUD，阴影帧 |
| 预算上限 | **600** | `SPEC-总账` §0（不是 ADR，是可调的产品预算） |
| 可用增量 | **228** | 600 − 372 |
| 阴影帧与非阴影帧差 | 222 | 同一场景的奇偶帧差 |
| 每 call 平均面数 | 121,459 | 45.9M / 378 |

**「可用增量 228」这句话必须配上 §4.4 的联合上界才完整**：228 不是「随便加 228 个 draw」，它要被造物、玩家建筑、体素沙盒三家分。三家各自的上限相加会**超**，这是本卷发现的第一个跨卷冲突。

### 1.5 v96 的 +178 没有被归因，只能算「疑似」

总账写「很可能来自 2.1 去格网与 B8 常量单源化」。本卷不接受「很可能」，也不假装知道。可核的事实只有三条：

1. `infill` 的实例数：`infill_wall 122,459`、`infill_glow 20,140`、`infill_fabric 2,921`（`SPEC-总账` §3.4）；
2. `infill` 的逐实例写色用的是**复用的** `Color`（`infill.ts:2917` 的 `const c = new THREE.Color()`），所以「每实例装箱」这条常见怀疑**不成立**——本卷核过，不写进账；
3. `engineMs +178` 与 `flushMs +62` 同时发生，而 `flushMs` 只占 `engineMs` 的 7.9%，说明增量主要发生在**步体**，不在上传。

归因结论：**UNMEASURED**。要归因，必须先有 `probe-load-attrib`（按步求和）与一次 v95/v96 的同机位对照。在拿到之前，本卷不给「去格网害的」这种结论。

## 2. 运行时造物的成本模型

### 2.1 `CreationBundle` 到底有多重

ADR-8.4 给的上限是 **8MB（顶点+索引）**，单件面上限 **20,000 三角面**。这两个数不是同一个量级，必须先把它们对齐，否则预算会按 8MB 记，实际只有 2.9MB，白留 5MB 的幻觉余量。

按「4 档 LOD + 1 份碰撞网格」的完整包算（`W12_MAT` 用顶点色，不需要 UV，故 24B/顶点）：

| 组成 | 面数 | 顶点（面×3） | 字节 |
|---|---:|---:|---:|
| L0 | 20,000 | 60,000 | 1.44MB |
| L1（55%） | 11,000 | 33,000 | 0.79MB |
| L2（25%） | 5,000 | 15,000 | 0.36MB |
| L3（8%） | 1,600 | 4,800 | 0.12MB |
| 碰撞网格（≤10%） | 2,000 | 6,000 | 0.14MB |
| 缩略图 128² PNG | — | — | 0.02–0.04MB |
| 行为/交互/材质 JSON | — | — | ≈0.002MB |
| **合计** | **39,600** | **118,800** | **2.87–2.89MB** |

若改用带 UV 的 32B 布局（`CreationBundle` 允许声明 `uv`），上限是 **3.80MB**。所以：

> **8MB 是门的宽度，不是车的宽度。** 预算按 **2.9MB（无 UV）/ 3.8MB（有 UV）** 记；8MB 只用于拒收异常包，不用于容量规划。

这条区分有直接后果：D4 §4.2 写「几何缓存 LRU 16 = 1.64MB」，那是按 952 面的兽体算的。**换成 20,000 面的 Agent 造物，同样的 16 条要 45.6MB（27.8 倍）**。缓存预算必须从「按条数」改成「按字节」，见 §2.5。

### 2.2 加载 8MB 的 I/O 与解压：分五段，差三倍

同一个 8MB 包，走「二进制帧」还是走「JSON + base64」，耗时差 3–6 倍。这不是实现细节，是**协议选择**：

| 段 | 二进制路径 | base64 + JSON 路径 | 依据 |
|---|---:|---:|---|
| 磁盘读 | 4–8ms | 4–8ms | SSD 顺序 1–2GB/s；慢盘 100MB/s 时 **80ms** |
| gzip 解压 | 20–40ms | 20–40ms | zlib 200–400MB/s（8MB 输出） |
| base64 解码 | **0** | **60–120ms** | `atob` 50–100MB/s，且产生一份中间字符串（+33% 峰值） |
| sha256 校验 | 10–27ms | 60–80ms | WebCrypto 300–800MB/s；纯 JS 实现约 100MB/s |
| `BufferGeometry` 装配 | 4–8ms | 4–8ms | 1–2GB/s memcpy |
| GPU 上传 | 4–8ms | 4–8ms | 同上 |
| **合计** | **42–91ms** | **152–264ms** | 逐项相加 |

三条读数：

1. **base64 是最大的单点风险**。它和解压、校验叠加后，把一个 60ms 的加载变成 260ms，而且中间那份字符串会把峰值堆再抬 2.7MB。**ADR-8.4 的 schema 写的是 `"<base64|bin>"`，本卷要求实现只走 `bin`**：`MessagePort` / `structuredClone` 传 `ArrayBuffer`，JSON 只承载元数据。
2. **sha256 不要用纯 JS**。8MB 上差 50ms，而它每次都跑。用 `crypto.subtle.digest('SHA-256', buf)`，Electron 渲染进程可用。
3. **慢盘是尾部风险**。4–8ms 的前提是 SSD；机械盘或杀软实时扫描下可能 80ms。**加载不是每帧发生，80ms 可以接受；但它必须异步**，不能卡在提交帧里。

### 2.3 对 `T_frame` / calls / 内存的影响：四条公式

```
ΔT_frame(单 pass) = tris / 45,923,185        // 分母 = P0 机位的 T_frame
ΔT_frame(阴影帧)  = 2 × tris / 45,923,185    // 阴影 pass 再来一遍
Δcalls            = 1（每份唯一几何 1 个 InstancedMesh）+ 1（阴影帧）
ΔGPU              = bundle 字节（4 档 LOD 全上传）
```

**分母为什么用 45,923,185 而不是 D0 的 45,911,485**：增量必须在**同一台相机**的基线上算（§0.3）。两者差 11,700 面（0.025%），不改变任何结论，但写成两个数就会有人把它们相加。

算例（逐项可复算）：

| 情形 | tris | ΔT_frame（单 pass） | ΔT_frame（阴影帧） | Δcalls | ΔGPU |
|---|---:|---:|---:|---:|---:|
| 现有兽体 1 只 | 952 | +0.0021% | +0.0041% | +1 / +2 | 0.08MB |
| Agent 造物 1 只（上限） | 20,000 | +0.0436% | +0.0871% | +1 / +2 | 2.87MB |
| 24 只全上限 | 480,000 | **+1.045%** | **+2.091%** | +24 / +48 | 68.9MB |
| 24 只现有兽体 | 22,848 | +0.0498% | +0.0995% | +24 / +48 | 1.9MB |

**为什么 24 只全上限也只有 1.045%**：因为 `T_frame` 的分母是 45.9M，而造物是「一次性 20k、不与烘焙几何合并」的小对象。**造物的面数从来不是问题，draw 与内存才是**——这与 D4 §4.2 的结论一致，本卷用同一口径复算后确认。

**但有一个反直觉的结论**：24 只全上限的 `ΔT_frame` 只有 1.045%，可它的 `ΔGPU` 是 **68.9MB = 常驻几何的 3.95%**——**是帧时间增幅的 3.8 倍**。如果继续加造物，先撞到的会是内存，不是帧时间。这决定了配额该按「bytes」管，不该按「只数」管。

### 2.4 为什么它绝不能进 `engineMs`

单次加载 42–264ms，而余量是 **74ms**。也就是说：

```
一次 Agent 造物的加载 = 余量的 0.57× ～ 3.6×
```

**一次就吃穿，而且是在最不该出问题的地方**（载入是玩家对品质的第一印象）。所以三条硬规则：

1. `CreationBundle` 的加载**只允许发生在载入完成之后**（`__loadEndAt` 之后），任何把它塞进加载步的实现都直接 BLOCK；
2. 加载必须**异步且可分帧**：`fetch → arrayBuffer → 校验 → 装配` 四段各让一次，单段同步 ≤16.7ms；
3. 装配完成到挂载必须**在同一帧内提交**（≤16.7ms），不允许「半挂载」状态被渲染——否则玩家会看到一帧残缺几何。

三个时间尺度必须分开记，混在一起就说不清「慢在哪」：

| 尺度 | 值 | 在哪 | 谁负责 |
|---|---|---|---|
| 构建（沙箱子进程，ADR-5） | ≤180,000ms | 游戏进程外 | D5 / M2 |
| 加载（bundle → 几何） | 42–264ms | 交互期，异步 | 本卷 §2.2 |
| 挂载（挂场景 + LOD + 碰撞） | ≤16.7ms | 单帧内 | D5 §4.3 |

### 2.5 连续生成 10 次：缓存账与 token 账

「连续生成 10 次」不是拍的数字，它**正好是会话预算的上限**：

```
单次深度许愿 ≤ 6,000 token（D6 §2.5）
会话上限     ≤ 60,000 token（D5 §6.2）
60,000 / 6,000 = 10 次 ⇒ 第 11 次必须被拒，且要给出额度提示
```

内存与 draw 的账：

| 项 | 值 | 说明 |
|---|---:|---|
| 10 份 bundle（无 UV） | 28.7MB | 10 × 2.87 |
| 10 份 bundle（有 UV） | 38.0MB | 10 × 3.80 |
| 同时挂载 | 1 份 | 每次替换上一个（设计约束） |
| Δcalls | **0** | 挂载数不变，只换几何 |
| Δgeometries | **+1 / 次**，旧的必须 `dispose()` | 断言 A10 |
| 峰值堆增量 | +28.7MB（JS）+ 2.9MB（GPU）+ 2.9MB（换装瞬态） | ≈ +34.5MB |
| 存档增量 | **0**（默认 `persist:false`） | D0 ADR-8.3 |
| 若 10 次全 `persist:true` | **+28.7MB 存档** | 必须显式提示 |

**缓存必须按字节，不按条数**：

```
挂载中（不可驱逐）= 24 × 3.8MB = 91.2MB   ← 上限，不是常态
未挂载缓存（可驱逐）= 64MB                 ← 约 22 条 @2.9MB
合计上界 = 155.2MB = 常驻几何的 8.9%
```

D4 的「LRU 16」在 952 面的兽体上等价于 1.64MB，在 20,000 面的 Agent 造物上等价于 45.6MB。**同一个「16」，两种含义，差 27.8 倍**——所以本卷把 D4 的条数上限改写成字节上限，并把这条列为对 D4 的**对齐项**（不是推翻，D4 的 16 条在它的量级上仍然成立）。

### 2.6 为什么造物不该触发 shader 编译（一条容易被漏掉的卡顿源）

D4 §4.3 已经论证过：`W12_MAT` 是 `MeshStandardMaterial({ vertexColors: true })`，神像、八兽、造物三者共用同一个材质实例，three 会复用同一个 program，只多 `InstancedMesh` 实例。这是既有代码验证过的路径。

但它有一个**前提**，本卷必须写死：**program 的复用是按 define 集合做的，不是按材质实例做的**。只要 `CreationBundle` 声明了任何 define 级特性——`map`、`normalMap`、`roughnessMap`、`skinning`、`morphTargets`——three 就会为该组合**新编译一个 program**。实测代价：首帧一次 10–50ms 的编译停顿（具体值取决于显卡驱动缓存，未测）。

所以 ADR-8.2 的「不许新建材质组」需要补一句执行细则：

> `CreationBundle` 的 `materials` 只允许引用现有 14 组的 **id**，不允许携带贴图或任何 define 级开关。颜色差异一律走顶点色（`color` 属性），不走材质参数。

这条不是洁癖：它的收益是**把「生成一次造物」的首次渲染从「可能卡 10–50ms」变成「确定 ≤16.7ms」**。而卡顿比面数更伤体验——多 20,000 面的代价是 0.04% 的帧时间，多一个 program 的代价是一次可见的停顿。

## 3. 74ms 怎么补：五项压缩，一条也不能动内容

### 3.1 先把「不动内容」写成可判定的约束

用户 2026-11-01 的裁定是「六项保真度一项都不许减」。这句在工程上必须翻译成六条可机检的等式，否则「优化」会悄悄变成「删东西」：

| 约束 | 判据 | 探针 |
|---|---|---|
| 面数不变 | `T_static` 逐组 triangles 与 v96 相等，**容差 0** | `probe-face-accounting` |
| 实例不变 | `live 4,495 / heroes 165 / 1,011,881 instances` 三项相等 | `probe-mem` + `probe-world` |
| 构件不变 | `assetAudit` 的组数 14、组名集合不变 | `probe-face-accounting` |
| LOD 不变 | `LOD_ENTER` 一族常量不变 | `probe-lod` |
| 阴影不变 | 阴影视锥 ±120m / far 760 不变 | `probe-shadow` |
| 像素不变 | 同一机位截图逐像素相等（加载屏除外） | `probe-shot-diff` **[待建]** |

**允许改的只有六类**：执行顺序、让帧策略、缓存、编码、资源打包格式、测量开关。**这六类之外的一切改动，都不属于「性能优化」，属于「内容变更」，必须另开裁定。**

### 3.2 五项压缩（S1–S5）

#### S1 · 把 `settle` 的 400ms 从生产路径摘出去

- **位置**：`src/world.ts:807-812`
- **机制**：`await Promise.all([idle(800), sleep(400)])` 的产出是 `__heapPre` / `__heapPost` 两个**只给探针用**的数字。生产路径改为 `sleep(120)`；探针路径用 `?settle=400` 保留原行为。
- **收益**：**280–680ms**（保留 120ms 稳定窗 → 280；全删 → 400；若 `idle(800)` 也走满 → 800 − 120 = 680）
- **依据**：`setTimeout(400)` 是代码里的硬下界，不依赖任何测量
- **风险**：`__heapPre` 抖动增大 → 峰值读数与历史不可比。**处置：把「生产载入时间」与「探针峰值堆」拆成两次测量、两个数字，各自登记口径**，不再用一次运行同时出两个结论
- **视觉影响**：**零**（不碰渲染）
- **验证**：`probe-load-attrib` 在同一机位跑 `?settle=400` 与默认两遍，差值必须落在 280–680 内

这一项单独就够覆盖 74ms，而且**顺带补回 v96 的 178ms 回归**：280 − 178 = 102ms 的净改善。它不需要改一行几何、不需要一次像素对比——**这是全卷性价比最高的一条，也是唯一一条「收益有硬下界」的**。

#### S2 · 逐步 `await raf()` 改成时间预算

- **位置**：`src/world.ts:805`（33 次，每步一次）
- **机制**：与 `bake.ts:1303` 已采用的策略同构——累计步体耗时 ≥12ms 才让一帧，而不是每步必让。`bake.ts` 的预算是 8ms，这里取 12ms，因为步间还要留出 `flush` 的时间
- **收益**：**150–500ms**（上界 33 × 16.7 = 551ms）
- **依据**：上界可算；实际收益取决于「步体 < 5ms 的步有多少个」，需 `__loadTimings` 求和
- **风险**：① 进度条从「每步一跳」变成「几跳」，观感变粗；② 单次长任务上限从 16.7ms 抬到 12ms + 最重一步，`probe-blocking` 的 p95 会变差
- **缓解**：进度条本来就不该按步跳（D9 要求按阶段），跳变粗反而更接近设计意图；`probe-blocking` 的门槛是 p95 ≤400ms，12ms 的预算离它很远
- **验证**：`probe-load-attrib` + `probe-blocking` 双门同时过

#### S3 · `compactStatic` 的逐批让帧与包围球

- **位置**：`src/world.ts:763`（每合并批一次 `await raf()`）、`src/world.ts:748`（每个合并体一次 `computeBoundingSphere()`）
- **机制**：① 让帧改时间预算（同 S2）；② `computeBoundingSphere()` 是 O(顶点) 全量扫描，改为「源包围球的并集」再取外接球——保守但便宜
- **收益**：**60–300ms**（让帧部分 ≤16.7 × 批数；包围球部分 20–60ms）
- **依据**：批数 = `ceil(总字节 / 48MB)`，需先加 `__compactBatches` 计数；包围球扫描 56.88M 顶点的成本可算
- **风险**：① 少让帧 → GC 窗口减少 → **峰值堆可能上升 5–10%**，与内存目标相反；② 并集球比精确球松 → 少量 LOD 误判（远景本该切档的没切）
- **验证**：`probe-mem` 峰值涨幅 ≤2%；`probe-lod` 的档位分布不变

#### S4 · 把 6 张画布贴图移到构建期

- **位置**：`src/city/bake.ts:1339` 起（`materialSet()`），已有 `__texMs` 单独计时
- **机制**：6 张 256² 画布、上万次描边，是首帧 `flush` 里唯一的大段同步开销（代码注释自己这么写）。改为构建期生成 PNG 打包，运行时 `TextureLoader` 读文件
- **收益**：**`__texMs` 全额**（未测；按「上万次 canvas 描边」估 80–300ms）
- **依据**：项目自己的注释认定它是整段同步开销，且已单独计时——只差把数字读出来
- **风险**：纹理版本漂移 → 视觉回归。**必须先跑像素 diff，差一个像素就不合入**
- **验证**：`probe-shot-diff`（同机位、同时间、同画质）逐像素相等；`__texMs` 归零

#### S5 · 合并相邻小步的 flush

- **位置**：`src/world.ts:783`（每步一次 `baker.flush`）
- **机制**：改为「累计几何 >60MB 或步体 >400ms 才 flush」，而不是每步必 flush
- **收益**：**60–150ms**（33 次 × 27.8ms 的一部分）
- **依据**：`flushMs 918 / 33 = 27.8ms/次`；合并 N 次省的是固定开销，不是几何装配本身
- **风险**：**这是一条会推高峰值堆的优化**。逐步 flush 的存在理由就是「峰值 = 单步几何量」；合并两步就可能让峰值翻倍。必须先证明 ≤ +2%
- **验证**：`probe-mem` 峰值 ≤ 2,667MB（+2%）；不达标就整条撤掉

### 3.3 收益不能相加：同一段等待只能省一次

S1、S2、S3 都作用在「等待」上，而等待是**互斥的**：你把 400ms 的 settle 删了，就不能再把那 400ms 算进 raf 的收益里。所以：

```
等待类总上界 = settle(400) + 逐步 raf(551) + compact raf(≤300) = ≤1,251ms
```

这是**上界**，不是可承诺的收益。三项共享 1,251ms 的池子，实际能拿多少取决于每一项的真实占比——而这正是 `probe-load-attrib` 要回答的。

保守承诺表（只用「有硬依据的下限」）：

| 组合 | 回收 | engineMs | 合计 | 余量 | 依据 |
|---|---:|---:|---:|---:|---|
| 现状 | 0 | 11,629 | 11,926 | **74** | v96 实测 |
| +S1 | 280 | 11,349 | 11,646 | **354** | `sleep(400)` 改 120 |
| +S2 | +150 | 11,199 | 11,496 | **504** | 33 次 raf 里至少 9 次可省 |
| +S3 | +80 | 11,119 | 11,416 | **584** | 让帧预算 + 包围球并集 |
| +S4 | +80 | 11,039 | 11,336 | **664** | `__texMs` 下限 |
| +S5 | +60 | 10,979 | 11,276 | **724** | 合并 ≥3 次 flush |

到「+S5」，余量从 74 变成 724，等于**多出 9.8 倍的安全垫**，且 `T_static` 一个面都没动。理论峰值（S1 400 + raf 551 + compact 300 + tex 300 + flush 150 = 1,701）是 1,775ms 余量，但本卷**不承诺这个数**——它需要五项全部跑满上限，概率极低。

### 3.4 执行顺序与「先量后改」

顺序不是按收益排，是按**确定性**排：

1. **S1 先做**：唯一有代码硬下界的一项，且零视觉风险。做完立刻重跑 `verify-packaged`，把 `engineMs` 从 11,629 拉到 ≤11,349；
2. **S0（探针）与 S1 同批**：`probe-load-attrib` 必须先建，否则 S2–S5 的收益无法归因，只能又变成「感觉快了」；
3. 再 S2 → S3（同类，共享等待池，一起量）；
4. S4 单独做，因为它需要像素 diff；
5. S5 最后，因为它是唯一会推高内存的一项，放在内存基线稳定之后。

**一条硬纪律**：每一项改动提交时，必须同时提交「改前/改后」两次 `probe-load-attrib` 输出（同机位、同 release、同画质档）。没有对照的提交，一律视为 UNMEASURED，不计入余量。

### 3.5 被否掉的四条，以及为什么

| 方案 | 看起来能省 | 为什么否 |
|---|---|---|
| 减面 5%（约 95 万面） | 载入与帧时间都降 | **违反用户 2026-11-01 的「六项保真度全保留」裁定**。这不是性能问题，是内容问题，本卷无权处置 |
| `COMPACT_BATCH_MB` 48 → 96 | 合并批数减半，draw 与让帧都降 | 峰值堆「源 + 目标」两份同时驻留，批预算翻倍 ⇒ 峰值从 2,615 推到 3,400+，直接顶穿内存目标。**用内存换时间的反向操作** |
| 关阴影 / 降 `shadowSize` | `T_frame` 与帧时间显著降 | ① 省的不是 `engineMs`，对 74ms 无用；② 改变画质，属内容变更；③ `shadowTick` 隔帧已经是既有优化，再降是重复砍 |
| 把 `flush` 推迟到首帧之后 | `engineMs` 数字变好看 | **把等待从载入搬到第一帧**，用户感知从「加载条」变成「进游戏卡一下」，更差；且 `probe` 会把它算进 `frameP95`，问题只是换了个账本 |

这四条的共同点：**它们都能让某一个数字变好，但都让另一个数字变坏**。性能预算的意义不是优化单个指标，是在四个指标（时间/面数/draw/内存）之间守住一组同时成立的约束。

逐项复算：

```
造物    952 × 2 = 1,904
建筑  1,608 × 2 = 3,216
体素 22,582 quad × 2 = 45,164，阴影帧 ×2 = 90,328
体素内存 22,582 × 152B = 3.43MB
造物 bundle 952 × 3 顶点 × 24B × 1.88（4 档 LOD 系数）= 0.13MB
合计 tris 1,904+3,216+90,328 = 95,448 → /45,923,185 = 0.208%
draw   372 + 1 + 1 + 14 = 388
```

**一行只记一次账**：「造物 1 只」与它的 bundle 是同一个对象，合并成一行；峰值列写 0.26MB 是换装瞬态（新旧同时驻留一帧），稳态列写 0.13MB。**不许把同一个 bundle 在「几何」和「缓存」两行各记一次**——初稿犯过这个错，合计虚高 1.6MB。

**注意体素那行是常态而非满配**：22,582 quad = 地形 19,582 + 玩家已建 3,000，不是 D3 的 9,000 配额上限。满配见最坏表。

| 162 座玩家建筑 × 1,608 | +520,992 | +162 | +23.8 | 0 | 0 |

### 4.3 表 C · 连续生成 10 次

| 项 | 值 | 依据 |
|---|---:|---|
| 单次 token | ≤6,000 | D6 §2.5 |
| 10 次累计 | **60,000** | = D5 §6.2 会话上限 |
| 第 11 次 | **必须拒**，并显示剩余额度 | 额度是纪律的可见化（D5 §6.4） |
| 单份 bundle | 2.87MB | §2.1 |
| 10 份累计（JS） | **28.7MB** | 10 × 2.87 |
| 同时挂载 | **1** | 每次替换上一个（设计约束） |
| Δcalls | **0** | 挂载数不变 |
| Δgeometries | **+1/次**，旧的必须 `dispose()` | 断言 A10 |
| 峰值增量 | **+34.5MB** | 28.7 JS + 2.9 GPU + 2.9 换装瞬态 |

**这张表的关键不是内存，是「10」这个数**：它不是产品经理拍的，是 `60,000 ÷ 6,000` 算出来的。这意味着「连续生成 10 次」这条需求**恰好等于把整个会话预算用尽**——第 11 次不是「慢」，是「不允许」。UI 必须能表达这件事（D9 §2.4），否则玩家会以为系统坏了。

### 4.4 联合上界：draw 600 只够 162 座

把三家的 draw 增量写成一条不等式：

```
372（基线） + 24（造物） + N（玩家建筑） + 14 × S（可见沙盒数） ≤ 600
⇒ N ≤ 204 − 14S
```

| 可见沙盒 S | 建筑上限 N | 与 D3 的 200 座比 |
|---:|---:|---|
| 0（沙盒都在别的界） | 204 | 超 4 |
| 1（常态） | **190** | 超 10 |
| 3（人间三块全在视锥内） | **162** | 超 38 |

**D3 §2.6 写的 200 座，在三种情形下全部越界。**这不是 D3 算错——它算的是「100 座时 14.7MB 常驻可接受」，那是**内存**口径；它没有把 draw 的联合预算算进去。两卷各自都对，相加就错，这正是 D0 开头说的「16 卷互审 15 打回」的同类问题。

三条处置，按代价排序：

| 处置 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A（推荐）** | D3 的 `E_BUILD_LIMIT` 从 200 降到 **160** | 玩家少建 40 座 | 零成本，立刻可断言；160 与「三沙盒全可见」的 162 只差 2，留了余量 |
| B | draw 预算 600 → 650 | 帧时间与 `frameP95` 一起涨 | 不可取：v96 的 `frameP95` 已经是 50ms，没有余量 |
| C | 沙盒远景图集档默认开（14 → 1 draw） | 远景材质降档 | 需先验证 D3 的 U2（2048² 图集够不够） |

**推荐 A + C 双保险**：A 立刻生效（不依赖任何未验证项），C 在 U2 通过后追加，届时上限可回到 200（`204 − 3 = 201`）。

### 4.5 内存三档：谁管哪一档

运行时新增**不影响载入峰值**——峰值 2,615MB 发生在世界生成期，那时还没有任何玩家造物。所以三个数字各管各的，不能混：

| 档 | 谁在管 | 阈值 | 运行时新增的影响 |
|---|---|---|---|
| 峰值堆 | 载入 | ≤2,700MB（建议值，见 §1.3） | **无**（不同时发生） |
| 稳态堆 | 长期游玩 | ≤1,950 + Δ | 直接相加 |
| 常驻几何 | 几何预算 | ≤1,742.7 + Δ | 直接相加 |

按表 B 的最坏：稳态 1,950 + 105.7 = **2,055.7MB**，常驻 1,742.7 + 105.7 = **1,848.4MB**。两者都在「建议目标」之内（若采纳 P-1），但都超出 D0 原定的 1,536MB——**再一次说明 1,536 必须改**。

## 5. 可执行验收断言

分两类跑，不能混（同 D3/D4 的体例）：

- **单测**：`vitest run`，无 GPU、无打包态，输入是确定性样本；
- **打包态**：必须对 `release-*` 的 `file://` 页面跑，因为要读 `renderer.info`、`performance.memory`、真实 draw。`vite dev` 下不成立——HMR 会重建场景。

探针未建的标 **[待建]**，由 D8 排期。

| # | 断言 | 判据 | 落点 | 类型 |
|---|---|---|---|---|
| A1 | 载入恒等式闭合 | `Σ步体 + flush + compact + settle + Σraf` 与 `engineMs` 之差 **≤50ms**；四项各自 ≥0 | `probe-load-attrib.mjs` **[待建]** | 打包态 |
| A2 | `settle` 摘除生效且不动内容 | 同机位两次：`engineMs` 降幅 ∈[280, 680]；`T_static` 逐组相等 | `probe-load-attrib` + `probe-face-accounting` | 打包态 |
| A3 | 面数零变化 | `T_static` 逐组 triangles 与 v96 基线相等，**容差 0** | `probe-face-accounting.mjs` | 打包态 |
| A4 | P0 机位可复现 | 同 parity 采 3 次，`calls` 极差 **≤2**、`tris` 极差 ≤0.1% | `probe-p0-baseline.mjs` **[待建]** | 打包态 |
| A5 | `Δdraw` 可加性 | 注入 N 个 `rt_` 对象，`calls` 增量 = N（±1）；移除后回到基线 ±1 | `probe-runtime-assets.mjs` **[待建]** | 打包态 |
| A6 | 常驻字节不超表 | 表 A ≤1,747.6MB；表 B ≤1,848.4MB（1,742.7 + Δ） | `probe-mem.mjs` | 打包态 |
| A7 | 稳态棘轮 | 稳态 ≤1,950 × 1.01，且比上一次交付 **不增长**（保存基线文件） | `probe-mem` + `artifacts/perf-baseline.json` **[待建]** | 打包态 |
| A8 | bundle 加载 p95 | 二进制路径 **≤120ms**（8MB，100 次采样取 p95）；base64 路径只作反例记录，**不得**用于生产 | `probe-bundle-load.mjs` **[待建]** | 打包态 |
| A9 | 单次生成 ΔT_frame | 20,000 面造物挂载后，`T_frame` 增量 **≤0.05%**；24 只 ≤1.05% | `probe-creation-draw.mjs` **[待建]** | 打包态 |
| A10 | 连续 10 次的稳定性 | `calls` 增量为 **0**；`memory.geometries` 增量 **0**（旧的已 `dispose`）；常驻 ≤+40MB | `probe-creation-repeat.mjs` **[待建]** | 打包态 |
| A11 | `flushMs` 不增长 | ≤918 × 1.01 = **927ms** | `probe-mem.mjs`（读 `__flushMs`） | 打包态 |
| A12 | 像素零变化 | 改前/改后同机位、同时间、同画质截图**逐像素相等**（加载屏除外） | `probe-shot-diff.mjs` **[待建]** | 打包态 |

**A1 为什么是「恒等式」而不是「阈值」**：如果四项之和对不上 `engineMs`，说明还有一段没被记账的黑箱。先闭合，再优化——否则任何收益都可能只是把耗时挪到了没记账的那一格。

**A4 的 ±2 是硬门槛**：§4 表 A 的最小增量是 16 个 call，±2 的噪声占 12.5%，可以判；若实测极差 >2，说明 parity 没锁住或画质档漂了，**必须先修探针，不能带着噪声判 Δ**。

**A9 与 A10 的分工**：A9 管「一次生成贵不贵」，A10 管「生成十次会不会累积」。后者更容易被忽略——单次 2.9MB 看起来无害，十次不 dispose 就是 29MB 的泄漏，而 `InstancedMesh` 的 `geometry` 不会随 `remove()` 自动释放。

**A12 是本卷唯一一条「非性能」的断言，但它必须存在**：S1–S5 全部声称「不动画面」，那就得有能力证明。没有它，「优化」与「偷偷降质」无法区分。

## 6. 不做、未决、依赖

### 6.1 明确不做

| 不做 | 理由 |
|---|---|
| 把 1,536MB 目标「做出来」 | §1.3 已证不可达：削峰值最多 665MB 瞬态，削完稳态仍 1,950。除非采纳 P-2 的顶点压缩，而它的 draw 代价与 §4.4 的联合上界正面冲突 |
| 顶点位置量化（方案 C） | 需要空间切块，draw +200～600，而 draw 只剩 162–190。**用一个紧张预算换另一个超标预算，是搬家** |
| GPU 侧 profiling（capture、shader 计时） | 本卷只到 CPU 侧与字节/draw 账；GPU 计时在 Electron 里不稳定，且需要额外工具链。列为 D1 的可选扩展 |
| 改自适应画质的阈值 | `probe-quality` 已验「19ms 不误降、47.2ms 三档递降」，改它等于重做一套验证 |
| 跨平台（macOS/Linux）性能基线 | 本项目只发 Windows portable；跨平台基线没有设备可测，写了就是编 |
| 自动性能回归 bisect | 需要每次提交都跑打包态（约 30s 一次 + 手工机位），CI 无 GPU。列为不做 |

### 6.2 未决

- **U1（必须 lead 裁决）**：1,536MB 目标。本卷推荐 **P-1**（改目标为稳态 1,950 / 峰值 2,700，加「不增长」棘轮），备选 **P-2**（先做 normal 8 位，省 170.6MB，仍不达标）。**在这条裁决之前，所有内存断言只能对「现状 + Δ」判，不能对 1,536 判。**
- **U2**：`settle` 的双路径（生产 120ms / 探针 400ms）会让「载入时间」与「峰值堆」两个数字来自不同配置。本卷的处置是「两个数字各自登记口径」，但这需要 lead 认可——否则会有人拿生产载入时间配探针峰值堆，得出「又快又省」的假结论。
- **U3**：`__texMs` 的真实值未读。S4 的收益（80–300ms）是估值，不是实测。
- **U4**：D3 的 `E_BUILD_LIMIT` 200 → 160 是否接受。若拒绝，则 §4.2 的最坏表要改成 200 座 + draw 638（超预算 6.3%），并显式标 BLOCK。

| 依赖 | 需要什么 | 阻塞说明 |
|---|---|---|

## 7. 自认最弱的三段

1. **§3.3 的收益表只有 S1 有硬依据，S2–S5 全是上界推算。**`__loadTimings` 记的是每步 `dt`，但「步与步之间的 raf 等待」「`compactStatic` 的让帧」「`settle` 的 400ms」三者没有独立计时，所以我只能给「≤551ms」「≤300ms」这种上界，给不出「预计省 320ms」。表里 S2 写 150、S3 写 80、S4 写 80、S5 写 60，都是**下限估计**，不是实测中位数。真跑出来可能是两倍，也可能为零——尤其是 S5，如果 `flush` 的 27.8ms/次里大部分是几何装配而非固定开销，合并 flush 几乎不省时间。

2. **§1.3 的四个压缩方案（A/B/C/D）是线性外推，没有一份实测。**它们假设「顶点字节 × 顶点数 = 常驻」，但真实 GPU 驱动会对齐到 4/8/16 字节边界，`Int16×3` 的 6B 属性很可能被填到 8B，那样方案 C 省的是 4B/顶点而不是 6B，结论从「达标」变「不达标」。**这条必须先做一次 100 万顶点的实测，再谈 268MB 的收益。**另外 `Int8` 法线在平滑大曲面上的视觉退化没有做主观评测，我只写了「可能出现台阶」，没写「多严重」。

3. **P0 机位的可复现性完全没有验证。**372 这个数只出现过一次（v96 的 `verify-packaged` 头行），我没有跑过第二次，更没跑过「同一 parity 三次取中位数」。如果同机位重复采样的极差本来就 >16，那么 §4 表 A 的 `+16` 增量根本判不出来，A5 的「±1」也无从谈起。这一条不是文字风险，是**整个 draw 预算体系的地基**——地基没夯过，上面的 600、228、162 都只是算术。

再多说一条**不算在三条内、但必须写在交付前**的：§2.2 的 42–91ms 是按「8MB 输出、SSD、WebCrypto」三段拼出来的，**没有真跑过一次 8MB 的 `CreationBundle` 加载**。仓库里目前没有任何 bundle 文件，也没有 loader。这个数字的用途是「证明它不能进 `engineMs`」——这个结论在 3 倍误差内都成立（42×3 = 126ms 仍 >74ms），所以不影响决策；但它**不能**当作 A8 的阈值依据，A8 的 120ms 必须等第一次真跑后重定。
