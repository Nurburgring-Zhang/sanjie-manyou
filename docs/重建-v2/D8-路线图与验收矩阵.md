# D8 路线图与验收矩阵

> **本卷服从 D0《重建纲领》的全部七条 ADR，其中四条是直接约束：**
>
> - **ADR-7（性能预算前置）**：每个里程碑的退出判据里必须有 `ΔT_static / Δ常驻MB / ΔengineMs` 三项，缺一项不算退出。当前余量 **74ms**，D7 给出五项压缩后下限 724ms。
> - **ADR-4（打包态只有资产热替换）**：M3 的退出判据只能对 `release-*` 的 `file://` 页面判，`vite dev` 下不成立。
> - **ADR-5（代码在进程外执行，跨界只传数据）**：M2 的全部判据围绕「越权必 BLOCK」与「产物必须是数据」两件事。
> - **ADR-6（议会是设计期机制，运行期只保留轻量评审）**：M4 的时延上限是 3s / 30s，不是「尽量快」。
> - **ADR-1（坐标唯一真相源）/ ADR-2（烘焙是基底、运行时只能追加）/ ADR-3（确定性）**：分别约束 M5 的沙盒落位、M1 的 `rt_` 注册表、以及全部「重放 / hash 一致」类断言；本卷不复述它们的细则，只在退出判据里引用。
>
> 另受 **D0 §3 写作纪律第 3、4、5 条**约束：每条断言必须落到 `probe-*.mjs`；需要别人改的文件只写「依赖 + 阻塞」，不写「我会改」；完稿必须过 `probe-audit-coverage`。
>
> 行号基线：工作树 `806fa79`（v93）+ v96 未提交改动，**未锁 commit**。本卷 M0 的第一项任务就是消除这个前提。

## 0. 本卷要解决的不是「排期」，是「判据」

一份路线图如果只写「第几周做什么」，它唯一的用途是被延期。本卷要回答的是三个更硬的问题：

1. **每一步什么时候算做完**——判据必须是命令、文件或断言，不能是「功能正常」；
2. **哪些断言已经在跑、哪些只是写在纸上**——这是 §2 矩阵存在的理由；
3. **做完的东西怎么进总账**——`artifacts/SPEC-总账.md` 是唯一真相源，进不去就等于没做（§3）。

先给一条**贯穿全卷的计数原则**：本卷只承认三种状态，`绿 / 待建 / 待卷`，外加一个必须显式标注的 `实测（未自动化）`。**不允许出现「基本完成」「大体可用」**——那些词在验收时等于零。

## 1. 路线图 M0–M6

### 1.1 依赖图（先看形状，再看细节）

```
M0 基线锁定（3）
 └─ M1 运行时追加（8）
     ├─ M2 沙箱构建（12）
     │   ├─ M3 热替换（10）
     │   │   └─ M4 议会（9）
     │   ├─ M5 体素沙盒（20）      ← 与 M2/M3/M4 并行
     │   └─ M6 造物进化（18）      ← 与 M2/M3/M4 并行
```

两条关键路径：

- **安全路径** M0 → M1 → M2 → M3 → M4 = **42 人日**（这条决定「Agent 能不能安全造东西」）；
- **内容路径** M0 → M1 → M5 / M6 = 3+8+max(20,18) = **31 人日**（这条决定「玩家有没有东西可玩」）。

两条路径在 M1 之后分叉，所以**至少 2 人**才能让日历接近 `max(42, 31) ≈ 42 人日`；单人串行是 80 人日。这个数字不是排期承诺，是「需要几个人」的下界。

**目标**：把「可复现」这件事本身做出来。没有它，后面所有数字都是浮点。

**退出判据（全部可机检）**：

```
① node scripts/probe-load-attrib.mjs --url file:///.../index.html   → exit 0
   且 |Σ五项 − engineMs| ≤ 50ms
② node scripts/probe-face-accounting.mjs                            → exit 0（三条自洽）

⑤ git status --porcelain 为空
```

**依赖**：无。但需要先把并行 agent 的未提交改动合并或 stash——**这是 M0 唯一的真实阻塞**。

**风险**：① 锁 commit 会打断并行工作流，须一次性协调；② 摘 `settle` 会改变 `__heapPre` 的读数口径，总账里引用峰值堆的那几行必须同步改口径，否则会出现「同一版本两个峰值堆」。

### 1.4 M2 · 沙箱构建（12 人日）

**目标**：ADR-5 的第 2 段落地——**任意 JS 只在没有 fs/net/dom、有超时和内存上限的进程里跑，产物是纯数据**。

| 交付 | 内容 |
|---|---|
| 构建 API 注入 | ADR-8.1 的白名单 12 个函数，注入到沙箱全局；`emit()` 是唯一出口 |
| 进程隔离 | Node 子进程 + 权限模型；`--max-old-space-size=512`；180s 硬超时 → `terminate()` |
| `CreationBundle` v1 | 二进制帧（非 base64），`sha256` 校验，schema 版本 |
| 四道预算门 | 面 ≤20,000 / 包围盒 ≤200m 且无 NaN / 顶点+索引 ≤8MB / 同 seed 逐字节一致 |
| 三个探针 | `probe-sandbox-escape` / `probe-bundle-budget` / `probe-bundle-determinism` |

**退出判据**：

```
① probe-sandbox-escape：fs 读、net、child_process 三个负样本全 BLOCK；正常构建 PASS
② probe-bundle-budget：20,001 面 / 201m / 8.1MB / 两次不一致，四个负样本各拒一次
③ probe-bundle-determinism：同 seed 两次 sha256 相等（逐字节，不是「几何等价」）
④ probe-bundle-load：8MB 二进制路径 p95 ≤ 120ms（100 次）
⑤ 子进程超时样本：180s 后 500ms 内被 kill，无残留进程（`tasklist` 断言）
```

**依赖**：M1。

**风险（本卷最高）**：① `--experimental-permission` 在 Electron 33 内置的 Node 版本上是否可用，**未验证**——M2 的第一个动作应是 30 分钟的 spike，不通就换「独立 Node 可执行 + 最小环境变量」方案；② Windows 上权限模型的实际拦截面与 Linux 不同，负样本必须在 Windows 上跑，不能引用 Linux 文档；③ 沙箱里禁止 `import` 意味着构建模块必须**自包含**，任何工具函数都要由注入层提供，API 面会膨胀。

### 1.10 里程碑与断言的归属（B5 的依据）

归属原则：**每条断言只归一个「主里程碑」**，不重复计数；「贯穿」表示没有单一里程碑能关掉它。

| 里程碑 | 主责断言 | 条数 |
|---|---|---:|
| M0 | D1·01；D7·A1/A2/A3/A4/A11；D8·B1–B6 | 12 |
| M1 | D1·02/03/04；D5·6；D7·A5 | 5 |
| M2 | D5·1/2/3/8；D7·A8 | 5 |
| M3 | D5·4/5/7/9；D7·A10 | 5 |
| M4 | D6·1–7 | 7 |
| M5 | D2·01–04；D3·A1–A12 | 16 |
| M6 | D4·A1–A12 | 12 |
| 贯穿 | D7·A6/A7/A9/A12；D9·C1–C9 | 13 |
| **合计** | — | **75** |

逐行相加与 §2.2 的 75 行相等，这是 B1 的第一道自检。

**「贯穿」这一行不是垃圾桶，是「没有单一里程碑能关掉它」的意思**：像素零变化（D7·A12）要在每次合入时跑，不能等某个里程碑结束；`T_static` 零变化（D7·A3）同理。这类断言必须挂在**每次提交**上——B5 的双向映射要允许「贯穿」这个值存在，否则它们会被硬塞进某个里程碑，然后在那个里程碑结束后失去看守。

**这张表本身就是一次纠错记录**：初稿把 D3·A10 同时算进 M1 与 M5、D4·A11 算进 M3 与 M6、D6·C3 算进 M2 与 M4，总数变成 76 > 75。B5 要求双向映射，正是为了逼出这种「看起来都有主」的重叠。

## 2. 验收矩阵：D1–D9 全部断言

### 2.1 状态定义（先定义，再填表）

| 状态 | 含义 | 判定方式 |
|---|---|---|
| **绿** | 探针存在，最近一次运行 PASS，且记录在案 | 有 `artifacts/probe-runs/*.json` 且 ≤7 天 |
| **实测** | 数字真跑过，但没有固化成自动化断言 | 有人工运行记录（本卷引用其读数） |
| **未跑** | 探针文件存在，本卷未对其运行 | 文件存在 + `node --check` 通过 |
| **待建** | 探针或测试文件不存在 | 文件不存在 |
| **待卷** | 所属卷未出，断言为 ADR 派生占位 | 即使探针已存在也不计入 |

**`待卷` 这一档必须存在**：D1/D2 尚未写，把它们写成「待建」会让人误以为「只是没写测试」，而实际是「连断言都还没定」。

**「绿 = 0」是本卷最重要的一个数字。** 它不是说项目没做过验证——`probe-boss`、`probe-goalchain`、`probe-threat2` 等既有探针都是绿的，只是它们不在 D1–D9 的范围内。它说的是：**本轮重建提出的 75 条断言，没有一条已经跑在自动化里。**

这带来两个直接后果：

1. **路线图的真实起点不是「实现功能」，是「把纸面断言变成可运行的门」**。M0 之所以排在最前、且占 3 人日，就是因为它要先把「判据本身」建起来；
2. **任何「已完成」的声明在此之前都不可信**。包括本卷自己——D7 的 12 条断言里，只有 3 条能立刻跑（且本卷没跑），其余 9 条连文件都没有。

### 2.4 三条读表规则（否则这张表会被读错）

**规则一：阈值不能跨卷搬。** D3·A5 写「近景 draw ≤70」，D7 写「P0 基线 372」。两个数都是 draw，但不是同一本账：前者数的是**一块沙盒内部**的材质组数，后者数的是**整帧**的 call。把 70 当成「还能再加 70」会得到完全错误的预算。同理，D4 的「+24 draw」与 D7 表 B 的「+24」是同一件事，但 D4 的基线是 378、D7 的是 372——**两个基线差 6，所以两条断言不能互相印证**。

**规则二：状态只能由运行记录改，不能由作者改。** 一条断言从「待建」变「绿」，唯一合法的路径是：探针文件出现 → `node --check` 过 → 跑一次 → `pass:true` 的 JSON 落盘。作者在文档里写「已实现」不算。这条规则的成本很低（一次运行），但它挡住了整类「文档先行」的虚假进度。

**规则三：每行必须能回答「失败了会怎样」。** 一条断言如果失败之后没有任何处置（不 BLOCK、不降级、不告警），它就只是观察，不是验收。矩阵里 75 行都写了阈值，但**只有 12 行（D7 的）明确写了失败处置**（BLOCK 还是 UNMEASURED）。这不是别的卷的错——它们的断言写在各自的验收章节里，处置在正文；但矩阵作为汇总表，应该在将来的版本里补一列「失败处置」。

## 3. 与 `artifacts/SPEC-总账.md` 的衔接

这一节回答三个操作问题：新增项怎么登记、怎么保证「每条都有 probe 证据」、怎么过 `probe-audit-coverage` 那道白名单 + 零容忍的门。

### 3.1 证据链有四环，断一环就是纸

```
断言（D8 §2 的一行）
  → 探针文件（scripts/probe-*.mjs，必须 node --check 通过）
    → 运行记录（artifacts/probe-runs/<name>-<date>.json，含 exit code 与关键读数）
      → 总账行（引用运行记录的 id，不引用「我记得跑过」）
```

四环里最容易缺的是**第三环**。这个项目已经吃过两次亏，是同一条教训的三代：

| 代 | 门的判据 | 翻车方式 |
|---|---|---|
| 第一代 | 探针文件**存在** | `probe-mem.mjs` 里 `CHROME` 被 import 两次，语法错，**从来没跑通过**，总账三行却一直把它当证据 |
| 第二代 | 存在 + `node --check` 通过 | 语法对了，但可能是「能编译、跑起来全 BLOCK」——门仍然绿 |
| 第三代（本卷要求） | 存在 + 可编译 + **≤7 天内的 PASS 记录** | 尚未实现，即 D8·B3 |

**所以「每条都有 probe 证据」的准确含义是**：不是「有个文件名写在旁边」，而是「有一个 JSON，里面 `pass: true`、`exitCode: 0`、日期在 7 天内、读数与阈值对得上」。

### 3.2 登记格式：六字段，缺一不登记

新增项进总账时，必须写成六字段的一行：

| 字段 | 内容 | 反例 |
|---|---|---|
| `id` | `D<卷>·<编号>`，如 `D7·A1` | `A1`（与审计编号撞车，见 §3.3） |
| `口径` | 该数字属于哪个口径：`T_static` / `P0 calls` / 稳态堆 / 二进制 p95 | 只写「面数」 |
| `证据` | `probe-xxx.mjs` + 运行记录文件名 | 只写「已测」 |
| `状态` | `绿 / 实测 / 未跑 / 待建` | `基本完成` |
| `责任卷` | `D3` / `D5` / `D7`… | 「后端」 |
| `到期` | 必须清掉的里程碑（`M0`…`M6`） | 空 |

**`口径` 这一列不是形式主义**。D0 §0 已经因为「四个静态面数字」返工过一次；D7 §0.3 又发现 draw 有 372/378/594 三个读数。同一个数字在不同口径下差 60%，不写口径的登记等于没登记。

**`到期` 这一列是防腐剂**。一个 `待建` 如果没有到期里程碑，它会永远停在那里，而且看起来「已经在计划里了」——这比没有登记更糟，因为它制造了「有人在管」的错觉。

### 3.3 现有 `probe-audit-coverage` 的三个盲区（已用同一正则实测）

我读了 `scripts/probe-audit-coverage.mjs` 的全部 110 行，并用它自己的两条正则跑了四个样本。结论不乐观：**这道门与「重建卷」在结构上不兼容**。

**盲区一：ID 正则没有卷命名空间。**

```js
const ID_RE = /\b(A[1-5]|B[1-8]|C1|N[1-3])\b/g;
```

用同一正则跑 `| D3·A1 | RLE 往返无损 |`，`matchAll` 返回 `["A1"]`；`D8·B1` 返回 `["B1"]`；`D9·C1` 返回 `["C1"]`。也就是说：**重建卷的编号会被审计门当成审计编号**。后果是双向的——

- 审计 A1 的 `hits` 被 D3 的行灌水，`NAKED` 的统计失真；
- 更糟的是 D7·A1 那行写了 `probe-load-attrib`（待建），门会把它记到审计 A1 头上，判定 `BROKEN=probe-load-attrib`，**让一个与审计无关的 ID 变红**。

**盲区二：`[待建]` 引用一律判 BROKEN。**

门的规则是「引用了就必须存在且可编译」。而重建卷的断言**天然包含大量待建探针**（D8 §2 里 61/75 行）。把 D 系列表塞进 `SPEC-全面审计-20261103.md`，结果不是「登记成功」，是**整道门变红，且红的原因与被审对象无关**。

**盲区三：白名单只有 `why`，没有到期。**

```js
const ALLOW_NO_PROBE = [
  { id: 'A4', why: '复核后现象不成立：虹桥 crown 9.1m、34 段随拱起伏，不是平板路' },
  { id: 'B4', why: '用户 2026-11-03 裁定：天宫不跟随昼夜，属设计决定' },
];
```

两条理由都成立，但**没有失效条件**。「现象不成立」可能因为一次重构又成立；「用户裁定」可能被下一次裁定推翻。没有 `expires` 的白名单，就是一张永久的免死金牌。

### 3.4 处置：不塞进审计文件，另开一区 + 另建一门

**第一步：物理隔离。** D1–D9 的断言**不进** `SPEC-全面审计-20261103.md`（那是缺陷审计的登记区，ID 空间是 A/B/C/N）。重建项登记在 `SPEC-总账.md` 新开的 **§12「重建 v2 验收矩阵」**，ID 用 `D<卷>·<编号>` 全名，不与审计编号混排。

**第二步：新门 `probe-rebuild-matrix.mjs`（B1–B6 的载体）。** 六条判据：

```
B1 行数：D1–D9 每卷行数 ≥ 该卷声明的断言数（缺行即 BLOCK）
B2 可编译：每个被引用的 probe 文件 node --check 通过（0 语法错）
B3 有记录：状态为「绿」的，必须有 ≤7 天的 PASS JSON
B4 白名单：每条有 {id, why, expires, evidence}，缺字段即 BLOCK
B5 可映射：每个里程碑的退出判据至少映射到 1 行矩阵（反向：每行至少属于 1 个里程碑）
B6 有口径：每行的「口径」字段非空，且取值在枚举内
```

**B1 与 B5 是这条门真正的价值**：它们把「路线图」与「验收」焊在一起。一条断言如果既不属于任何里程碑、也没有人负责，它就会永远停在 `待建`——B5 让它无处可藏。

**第三步：零容忍的重定义。** 审计门的零容忍是「NAKED = 0」。重建门不能用同一条，因为 `待建` 是**合法状态**（M0 还没做完，探针当然不存在）。所以重建门的零容忍是两条：

```
零容忍 A：未标 [待建] 的裸引用 = 0   （写了 probe-xxx 但文件不存在，且没标待建 ⇒ BLOCK）
零容忍 B：已过到期里程碑仍在 [待建] = 0  （M2 结束了，M2 名下的探针还缺 ⇒ BLOCK）
```

这两条合起来，等价于「**允许现在没有，不允许一直都没有**」。而审计门那条「NAKED = 0」保留原样，两边井水不犯河水。

### 3.5 白名单纪律：棘轮，不是橡皮图章

`ALLOW_NO_PROBE` 的语义必须从「豁免」改成「**带到期日的临时豁免**」：

| 字段 | 作用 |
|---|---|
| `id` | 被豁免的编号 |
| `why` | 为什么可以没有探针——**只准两类理由**：① 现象复核后不成立；② 用户明确裁定关闭 |
| `evidence` | 支撑 `why` 的证据（截图、裁定原文、复核记录） |
| `expires` | 到期里程碑或日期；到期未续即失效，门自动变红 |

**不准因为「不好测」进白名单。** 现有两条是正面范例：A4 是「复核后现象不成立」（有具体读数：crown 9.1m、34 段），B4 是「用户裁定」（有日期与决定）。两条都指向**外部事实**，不是「我们决定不测」。

### 3.6 状态映射：五档对四档，`待卷` 不进总账

总账用四档：`✅已验证 / 🟡已实现未验收 / 🔴未实现 / ⚠️做偏了`。D8 用五档。映射必须固定，否则同一条在两个文件里会有两种颜色：

| D8 状态 | 总账状态 | 理由 |
|---|---|---|
| 绿 | ✅ 已验证 | 有 PASS 记录 |
| 实测 | 🟡 已实现未验收 | 数字真跑过，但没有自动门 |
| 未跑 | 🟡 已实现未验收 | 探针在，没跑 |
| 待建 | 🔴 未实现 | 连探针都没有 |
| **待卷** | **不登记** | 卷未出，断言是占位，不是承诺 |

最后一行是本节最容易被忽略、也最重要的一条：**D1/D2 的 8 行不写进总账**。理由不是「还没做」，而是**它们的断言是我从 ADR 反推的占位，不是那两卷作者的裁定**。把占位写进唯一真相源，等于用我的推测污染别人的卷——这正是上一版 16 卷互审时「跨卷前提不一致」的同类错误。

### 3.7 一次真实的登记演练（拿 D7·A1 走一遍）

空谈格式没用，走一遍。D7·A1 是「载入恒等式闭合」，它的六字段应该是：

```
id      D7·A1
口径    engineMs（打包态，P0 机位，release-v96）
证据    probe-load-attrib.mjs + probe-runs/load-attrib-20261105.json
状态    待建
责任卷  D7
到期    M0
```

现在它能走到哪一步？只能走到「登记」。因为：

- `probe-load-attrib.mjs` 不存在（`scripts/` 下 88 个 probe 里没有它），所以 B2 的「可编译」无从判；
- 没有运行记录，所以 B3 的「≤7 天 PASS」不成立；
- 状态只能是 `待建`，且 `到期=M0` —— **M0 结束时它还缺，零容忍 B 就会触发**。

这条演练暴露了一件事：**登记本身不产生任何进展**。它唯一的价值是把「还缺什么」变成一行可被机器读到的文字。矩阵里 61 行 `待建` 就是 61 份这样的欠条；它们不会自己还，但至少不会消失。

## 4. 不做清单与理由

一份路线图的可信度，一半来自它承诺了什么，另一半来自它**明确不做什么**。以下九条不是「暂时没排」，是「本轮不做，且写明为什么、什么条件下可以重新考虑」。

| # | 不做 | 理由 | 重新考虑的条件 |
|---|---|---|---|
| N1 | 跨平台验收（macOS / Linux） | 本项目只发 Windows portable（`package.json` 的 `dist:win` → `electron-builder --win portable`）。没有设备就没有基线，「支持」只剩「能编译」——那不是验收，是声明 | 有真机与对应 GPU 驱动，且愿意维护第二份基线 |
| N2 | 在 CI 里跑打包态探针 | CI 无 GPU，只能用 SwiftShader 软件光栅；同一场景在软件光栅下的 `calls/tris` 与真 GPU 不同（`probe-blocking` 已经记录过「软件光栅 p95 200ms / 硬件 p50 17ms」的差异）。跑出来的绿是**假绿** | 有 self-hosted runner + 真 GPU + Windows |
| N3 | 自动性能 bisect | 单次打包态约 30s 起（启动 + 加载 12s + 采样 3s），bisect 需要 O(log n) 次；一次回归的定位成本低于搭这套设施 | 提交频率上升到每周 >20 次，且回归频繁 |
| N4 | 覆盖率百分比门槛 | 覆盖率与「断言有没有验到行为」无关。本项目已经有过「探针文件存在、总账判 OK、实际从没跑通」的案例——百分比只会把这个问题埋得更深 | 永不。改用「每条断言必须有 PASS 记录」（B3） |
| N5 | 每卷独立发版 | 10 卷共享同一份 ADR 与同一批基线数字。D0 §0 的数字已经在 v95→v96 之间漂过一次（余量 129→74）；独立发版会让漂移变成常态 | 每卷有独立的基线文件与独立探针集 |
| N6 | 把内容生产排进工程人日 | 96 件部件里缺 56 件，这是内容流水线（D4 §1.6 的「脚本即交付物」），与工程不是同一种工时。混算会让 M6 的 18 人日变成 40 人日的假账 | 内容与工程分开排期、分开验收 |
| N7 | 代写 D1 / D2 | 两卷未出。我在 §2 写的 8 行是从 ADR-1/ADR-2 反推的**占位**，不是那两卷作者的裁定。代写会制造两份 ADR 解释，正是上一版 16 卷互审失败的原因 | D1/D2 落盘后，由其作者替换占位 |
| N8 | 规划 M6 之后 | M6 的产出会反过来改架构：若 `beastGeo(opt.suppress)` 不可行，整个「替换 vs 加挂」的装配模型要重做；若 D3 的 U1 改判为 0.4m 体素，M5 的全部数字要重算。现在排 M7 是画饼 | M6 的退出判据全绿 |
| N9 | 把「云端议会」写进 M4 的验收 | 仓库无任何模型接入代码（D5 §6.1 已标「待验证」）。写进验收只会得到一个 mock 的绿，而 mock 的绿比红更危险 | 有真实模型接入与 token 计量 |

**这九条里，N2 与 N4 最容易被违反**：它们都披着「更严格」的外衣——「CI 也跑一遍不是更好吗」「加个覆盖率门槛不是更规范吗」。但在这个项目里，两者都会**降低**信号质量：前者制造假绿，后者把「有没有证据」偷换成「覆盖了多少行」。

## 5. 可执行断言（本卷）

本卷的断言不是验「路线图写得好不好」，是验「这张矩阵有没有在骗人」。

| # | 断言 | 判据 | 落点 |
|---|---|---|---|
| B1 | 矩阵完整性 | D1–D9 每卷行数 ≥ 该卷声明数（D3=12、D4=12、D5=9、D6=7、D7=12、D9=9、D8=6、D1/D2 各 4）；缺一行即 BLOCK，并打印缺的编号 | `probe-rebuild-matrix.mjs` **[待建]** |
| B2 | 探针可编译 | 矩阵里每个被引用的 probe 文件 `node --check` 通过；`[待建]` 标记的跳过存在性检查，但记入待建清单 | 同上 |
| B3 | 有 PASS 记录 | 状态为「绿」的行，必须有 ≤7 天的 `artifacts/probe-runs/<name>.json` 且 `pass:true`、`exitCode:0` | 同上 |
| B4 | 白名单有到期 | `ALLOW_NO_PROBE` 每条含 `{id, why, evidence, expires}`；缺字段或已过期即 BLOCK | 同上 + 改 `probe-audit-coverage.mjs` |
| B5 | 里程碑可映射 | 每个里程碑的退出判据至少映射 1 行矩阵；反过来每行至少属于 1 个里程碑（双向） | 同上 |
| B6 | 口径非空 | 每行「口径」字段在枚举内（`T_static` / `P0 calls` / 稳态堆 / 二进制 p95 / 结构性），空值或越界即 BLOCK | 同上 |

**B1 的阈值为什么按卷写死**：如果只断言「总行数 ≥75」，删掉 D3 的 12 行再加 12 行 D9 也能过。按卷写死，才挡得住「用容易写的卷替换难写的卷」这种退化。

**B5 是唯一一条「反向也查」的**：只查「里程碑有没有断言」会漏掉「断言有没有人管」。一条不属于任何里程碑的断言，永远不会被清掉——它是矩阵里的僵尸。

**B6 的必要性来自 D7 的教训**：同一个 `2,615MB`，在「峰值堆」与「稳态堆」两个口径下分别是 +70% 与 +27% 超标。不写口径的行，读者只能猜，而猜错一次就会得出相反结论。

### 6.3 回填节奏：让矩阵活着

一张矩阵最容易的死法不是写错，是**写完就没人再打开**。所以要有三个固定动作：

| 时点 | 动作 | 产物 |
|---|---|---|
| 每次合入 | 跑「贯穿」类断言（D7·A3/A12、D8·B1/B2/B6） | 运行记录 JSON |
| 每个里程碑结束 | 回填：实际人日、实际读数、状态变化、新增的 `待建` | 矩阵 diff + `perf-baseline.json` 更新 |
| 每两周 | 复核白名单：到期的删、理由失效的删、新增的必须带 `evidence` | `ALLOW_NO_PROBE` diff |

**回填必须写「实际人日」而不是「是否按期」**。按期与否是项目管理词汇，实际人日是下一次估算的唯一输入——本卷 §1.9 的系数之所以只能靠猜，就是因为前面几轮没有留下这个数。

## 7. 自认最弱的三段

1. **§2 的 75 行里，61 行是「待建」，我没有能力证明它们实现后真的能跑通。**更具体地说：D3 与 D4 的 24 条断言是别的卷写的，我只做了「搬运 + 阈值转录」，**没有逐条核过它们与 D7 的预算是否自洽**。已经发现一处硬冲突（D3 的 200 座 vs D7 的 162 座联合上界），那么很可能还有第二处、第三处没被发现——例如 D3·A5 的「近景 draw ≤70」与 D7「P0 基线 372 + 增量」是两套账，前者按沙盒内部计，后者按整帧计，**两个 70 不是同一个 70**。这类口径错位我只能靠抽检，抽不到就是漏。

2. **§1.9 的人日估算没有历史数据支撑。**「120–150 行/人日」是我按行业经验给的系数，本仓没有任何一次「多少人几天写了多少行」的记录（`git log` 只有提交，没有工时）。所以 80 人日不是估算，是**量级猜测**；真实值落在 50–130 之间都合理。更严重的是 M2/M3 这两个高风险项——它们的成本主要由「权限模型能不能用」「事务回滚要几轮才稳」决定，与行数几乎无关，用行数估它们本身就是错的方法。

3. **§3.3 的三个盲区我只做了正则层面的实测，没有跑过整道门。** 我用 `probe-audit-coverage.mjs` 里的同一条 `ID_RE` 与 `probe-` 正则验证了 `D3·A1`→`A1`、`D8·B1`→`B1` 的碰撞，也读了它的切片逻辑（从「缺陷 → 探针 对照表」之后开始扫），但**我没有真的把一张 D 系列表插进那个文件再跑一次门**。所以「塞进去会整道门变红」是**推断**，不是观测。它很可能对，但按本项目的纪律，推断必须标成推断。

最后补一条**不在三条内、但必须说**的：本卷最重要的产物是 §2 的那张表，而那张表里**绿 = 0**。我写它的时候反复想把它写得好看一点——比如把「实测」算成「部分绿」，或者把 D1/D2 的占位也算成「已规划」。最后没有这么做，因为一旦开始修饰这张表，它就不再是验收矩阵，而是一份自我评价。**一张 0 绿的矩阵比一张 20 绿的矩阵有用**：前者告诉你起点在哪，后者只告诉你作者会写字。
