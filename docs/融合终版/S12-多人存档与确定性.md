## ③ H4 spike 定案（GO，五修订强制并入）

`artifacts/spike-H4-idb-save.md` 收口 **GO——28.7MB 存档可在 IndexedDB 原子写，P0-4 不降级**。实测：A 原始 JSON 写入合计 p95 260ms、落盘 17.2MB；B deflate-raw 691.7ms、落盘反 38.22MB——**Chrome 存储层已自动 Snappy，手工压缩是双重浪费，方案 A 定案、禁止手工 deflate-raw**。原子性：双 store（slots+index）单 readwrite 事务，注入错误自动 abort 回滚、lastGood 机制成立；**实锤坑：put 同步抛 TypeError 事务照常 complete（半写提交）⇒ 所有 value 先 stringify 成功再进事务、put 包 try/catch 且 catch 里显式 tx.abort()**。配额 10GB/用量 0 无压力；**persist()=false ⇒ 进 Electron 主流程启动时必须申请持久化授权，denied 时 UI 提示**。恢复演练：v3 截断 512KB → parse 失败 → 自动回退 v2 → hash 通过（版本化槽位 + lastGood + 截断回退成立），`probe-save-atomic` 必须含「写坏→回退→校验」三步断言。载入 29MB ≈220ms 可接受（用户触发，非关键路径）。诚实备注：payload 为确定性合成（同量纲非逐字节真实），**P0-4 探针须在真实存档序列化上复测一次**；多人部分仍 P2 远期，本 spike 只裁单人存档形态。

**V10 细节补充**：破口三/四/五——可变步长（`engine.ts:844`）、`performance.now()` 进玩法（历史点位 `player.ts:216`/`physics.ts:80`，现均已可注入）、浮点超越函数与跨引擎差异（定点化「什么时候必须做」有专门判据，不做预防性定点）。联机四件套：固定步 + 命令缓冲、**RNG 流分区**（每系统独立流，禁共享序列——单机侧纪律已生效）、状态哈希（对账用，量化后哈希、原值存档）、联机前必须清掉的禁止项清单 + 分阶段落地。存档侧：备份环 slot.0/1/2（本层裁为 IndexedDB 双 store 槽位）、**三次破坏性迁移的纪律**（每次 schema 大版本跃迁都要走的三步）、版本协商与前向兼容（`schema`/`minReader` 双字段）、容量与性能预算。Electron 侧：preload/IPC 设计（白名单通道）、单机存档目录（`%APPDATA%/CyberQingming/saves/`，本层降为导出/云同步形态）、云同步与冲突解决（远期）。回放：ReplayV1 格式、哈希规范化、`probe-replay.mjs` 流程、L0/L1/L2 分级、「回放能证明什么、不能证明什么」的边界声明。

## ④ 冲突裁决

1. **V10 备份环（slot.0/1/2 文件）vs H4 IndexedDB 双 store 版本化槽位。** 判给 **H4**（更新、有实测）：载体改 IndexedDB（slots store 存 v1/v2/v3 + index store 存 lastGood 指针），V10 的「备份环 + 原子写」语义原样映射到双 store；文件路径形态保留给 Electron 导出/云同步场景（远期）。
2. **V10 SaveV4 checksum fnv1a32 vs H4 SHA-256 校验。** 判给**并存分工**：schema 内完整性用 fnv1a32（快，防手改损坏，V10 原判）；存储层回退校验用 SHA-256（H4 实测口径，防截断/位翻转）。两者目的不同，字段都进 schema，探针分别断言。
3. **V10 「127 处 Math.random」vs 今日探针 103 处。** 判给**实测 103**（卷写作后已清 24 处）；A 类 7 文件零命中的棘轮现状直接采纳为 P0-0 的「已完成」证据，P0-0 剩余工作收敛为：SIM 时钟全接注入接口复核 + `TimeOfDay` 解停摆走固定步（S06 裁决 2）。
4. **V10 存档与 `.acs/task-state.json` 边界。** 三方一致（V10 §3.1 原判）：游戏存档（玩家数据，IndexedDB）与 ACS 任务状态（agent 工作流）零耦合，运行时互不读。无裁决项。
5. **V10 多人 lockstep/RNG 流分区/定点化 vs 清单 v3 无对应条目。** 判给**不做（P2 远期）**：多人整体不在 P0–P4；但「RNG 流分区」的前半（新系统自建独立种子、禁扰 `world.ts:296` 主序列）是 P0 纪律立即生效。
6. **V10 inventory 上限 300 vs S03–S05 物品/建造/蓝图扩展。** 判给 **V10 300 起步、P1-2 复核**：矿块/工料/构件蓝图入包后若超 300，按 count 合并同类优先；改上限须同步 schema minReader 升版，不许静默放宽。

**V10 §1.2 补充（最严重破口）**：`crowd.spawnActor` 的初始状态曾直接消费 `Math.random`（出生外观/速度/相位/朝向），读档后 NPC「换一批」的根因即在此——当前树已改注入流（`crowd.ts:27-30` 注释明确「只接受一个注入的 `rng()`，谁构造 Crowd 谁给源」），且 `spawnActor` 的 id 发号（`crowd.ts:1286`）保证同 spawn 顺序下稳定。这条给 P0-1 实体表的启示：**实体身份的确定性 = 发号顺序确定性 + 随机源确定性**，两者缺一，H1 的 16/16 断言就会退化。spawn 顺序的稳定性由载入期 tasks 数组的确定性顺序保证（`world.ts:303`，35 步序即发号序）——任何往 tasks 中段插新步的改动都必须同步评估 crowd 发号序列漂移，这是 S01 与 S12 的交叉检查点。
