# V14 造物编辑器

> **本卷回答**：Spore 的造物编辑器（部件拼装 + 属性派生）如何在一个「烘焙静态 Mesh、无骨骼蒙皮」的项目里落地。
>
> **结论**：**砍掉自由拖拽，保留选择与派生**。8 个槽位、96 件预烘焙部件、9 种体型原型、20 条可复核的属性样例；所有组合在烘焙期合并成一具几何，运行期实例化。
>
> **与 Spore 的差异**：Spore 让你捏形状，我们让你选部件；Spore 的乐趣在「捏」，我们的乐趣在「算得清、带得走、用得上」。这不是能力不足的托词——本卷 §4 会给出面数、内存、draw call 的硬账，证明自由拖拽在这个项目里不是「贵一点」，是「贵一个数量级」。
>
> **诚实边界**：Spore 编辑器的具体部件数、点数曲线、蒙皮算法**未联网核实**（本轮检索配额不可用），涉及处标「待检索核实」。本项目侧所有面数与内存均为 `beastGeo` / `pools.ts` 实测或按属性字节数计算，公式与样例逐项对得上。

### 1.2 挂点而不是拖拽：三个硬理由

1. **没有蒙皮**。现有生物是 `beastGeo(form)` 一次成形的 `VGeo` 静态顶点（`src/sky/creatures.ts:660`），没有骨骼、没有权重。自由拖拽要么每帧重算顶点（CPU 蒙皮），要么引入 `SkinnedMesh` + 骨骼 + 权重绘制；两条都远超一个玩法卷的预算。
2. **面数不可预算**。自由变形会产生不可预测的三角形密度；固定部件才能给出「单体 ≤1,393 面」这个上界（§4.3）。
3. **确定性**。同一份 `Build` 必须产出同一 `hash`、同一几何、同一属性；自由拖拽的浮点坐标会让存档、回放、多人 lockstep 全部漂移（V10 的确定性要求）。

Spore 的自由度是它的护城河，也是它难以上移动端的根因之一（具体平台限制待检索核实）。我们不追这个自由度，追的是「每个部件都能被预算、被实例化、被复验」。

`bodyPlan` 只能取 `BEAST_FORM` 的九型（`src/sky/creatures.ts:491`）。每个原型给出一套脊柱截面、腿位、颈位、头位、尾位、翼位；玩家选原型 = 选骨架，不是选皮肤。

### 1.5 解锁：见过才会造

96 件里 24 件初始解锁（每槽 3 件），其余 72 件按 `seen` 图鉴解锁：见过该类生物、该类器物或该类神像，才出现对应部件。**部件不收铜钱、不收阴德、不收业力**——工匠铺只收铜钱做「改色」，不卖部件。理由与 V16 §4.3 同源：五币 DAG 里不能再开一条「钱 → 部件 → 战力」的路径，否则造物编辑器会变成付费变强。

这条规则有一个副作用是好的：玩家想造龙，先得在野外见过龙。它把「造物」和「探索」绑在一起，而不是和「刷钱」绑在一起。

## 二、拼装规则

### 2.1 三类规则：互斥、依赖、缩放

规则不是「建议」，是 `validate(bp)` 的硬判定。每条规则都有一个错误码，UI 直接显示错误码对应的中文，不写第二套文案。

**互斥（8 条）**

| # | 规则 | 理由 | 错误码 |
|---|---|---|---|
| 1 | `W12` 无翼与 `W01–W11` 互斥 | 空槽占位符不能与实体同选 | `E_EXCLUSIVE` |
| 2 | `R11` 无角与 `R01–R10`、`R12` 互斥 | 同上 | `E_EXCLUSIVE` |
| 3 | `O11` 无饰与 `O01–O10`、`O12` 互斥 | 同上 | `E_EXCLUSIVE` |
| 4 | 龟躯 `T10` 禁翼 | K=1.25、载 6，翼面积不足以离地 | `E_EXCLUSIVE` |
| 5 | 象躯 `T12` 禁翼（`W06` 鲲鳍除外） | K=1.70，只有鳍类可解释 | `E_EXCLUSIVE` |
| 6 | 蛇躯 `T11` 禁后肢 `B03/B07/B08/B09/B12` | 无胯，接不上蹄/腿 | `E_EXCLUSIVE` |
| 7 | 人躯 `T03` 禁蹄类后肢 `B06/B07/B08/B12` | 人躯可接人腿/猿腿/狼腿/虎腿/龟腿/蛇尾肢 | `E_EXCLUSIVE` |
| 8 | 蝎尾 `A11` 与任意双翼互斥 | 尾刺上翘与飞行姿态冲突 | `E_EXCLUSIVE` |

**依赖（6 条）**

| # | 规则 | 理由 | 错误码 |
|---|---|---|---|
| 1 | 鞍鞯 `O08` 需 `K ≥ 1.15` | 体量太小驮不动人 | `E_REQUIRES` |
| 2 | 甲片 `O09` 需 `K ≥ 1.00` | 小体量披甲会穿模 | `E_REQUIRES` |
| 3 | 锁链 `O12` 需 `Σ威 ≥ 20` | 威压不够镇不住 | `E_REQUIRES` |
| 4 | 羽尾 `A08` 需至少 1 只翼 | 有翼才有羽 | `E_REQUIRES` |
| 5 | 鹿角 `R01` 仅限 `H06/H03/H04` | 鹿首/人首/猿首才接得住分叉角 | `E_REQUIRES` |
| 6 | 莲座 `O10` 需后肢为空 | 盘坐姿态 | `E_REQUIRES` |

**缩放（4 条）**

- `girth` 0.85–1.15：整体粗细，影响碰撞半径的视觉但不改物理半径（物理半径由体量档给，见 §5）。
- `legLen` 0.85–1.15：腿长，改髋高与离地间隙；`legLen` 改变后必须重算 `groundClearance`，否则脚会陷进地面。
- 部件随 K 缩放：头/尾/饰 `s = K^0.5`，四肢 `s = K`，翼 `s = K^0.8`，角 `s = K^0.6`。幂次不是随手写的：头尾要「相对变大」才可爱，翼要「相对变小」才不违和，角要「几乎不变」才锋利。
- **禁止单轴缩放、禁止旋转挂点**。单轴缩放会把圆柱压成椭圆，旋转挂点会让两只前肢不对称——这两条是穿模的主要来源。

### 2.2 校验器

```ts
// src/sky/parts.ts
export type BuildError = 'E_NO_TORSO' | 'E_NO_HEAD' | 'E_SLOT_MULTI' | 'E_UNKNOWN_PART'
  | 'E_EXCLUSIVE' | 'E_REQUIRES' | 'E_SCALE_RANGE' | 'E_BUDGET';
export function validate(bp: Build): { ok: boolean; code?: BuildError; detail?: string };
```

校验顺序固定：① 槽位完整性（躯干、头各恰好 1）→ ② 部件 id 存在且属于该槽 → ③ 互斥 → ④ 依赖 → ⑤ 缩放范围 → ⑥ 面数预算。**顺序不能乱**：先报「缺躯干」比先报「翼超预算」有用。

负样本必须逐条测，不能只测正样本：

| 负样本 | 期望错误码 |
|---|---|
| 空 `torso` | `E_NO_TORSO` |
| 两个 `head` | `E_SLOT_MULTI` |
| `T10 + W02` | `E_EXCLUSIVE` |
| `T03 + B07` | `E_EXCLUSIVE` |
| `O08` 配 `T01`（K=0.70） | `E_REQUIRES` |
| `A08` 无翼 | `E_REQUIRES` |
| `girth = 1.40` | `E_SCALE_RANGE` |
| 全件拉满（`T12+H12+F12×2+B12×2+A08+W05×2+R10+O09`） | 通过（1,393 面 ≤ 1,400） |

最后一行是「最坏组合」的边界测试：它必须**通过**，否则预算写错了。任何合法组合都不该被预算误杀。

### 2.3 蓝图与哈希

```ts
export interface Build {
  id: string;                 // 'b_<hash8>'
  bodyPlan: BeastForm;        // 九型之一
  parts: Record<SlotId, string[]>;  // 槽位 → 部件 id
  girth: number;              // 0.85–1.15
  legLen: number;             // 0.85–1.15
  hash: string;               // 稳定摘要
}
```

`hash` 的计算：把所有部件 id 按槽位排序拼接，`girth` / `legLen` 四舍五入到两位小数，再取 SHA-1 前 8 位。**必须量化到两位**——浮点尾差会让同一份蓝图在两次保存后得到两个 hash，几何缓存直接击穿，玩家会看到「同一只坐骑每次载入都重建」。这条与 V10 的确定性纪律同源。

`hash` 相同 → 几何缓存命中；`hash` 不同 → 新建一具。缓存上限 16 具，LRU 淘汰；场上同时存在的原型数上限 12（§4.4）。

### 2.4 编辑器 UI：三栏，不引入新框架

复用 `InteractSystem.makePanel()` 的面板样式（`src/game/interact.ts:69`），不引入 React/Vue，也不新写一套 CSS：

- **左栏**：8 个槽位标签页（躯干/头/前肢/后肢/尾/翼/角/饰），点开显示该槽的 12 件部件网格，未解锁的置灰并显示「未见过」。
- **中栏**：3D 预览。**不另开渲染器、不另建场景**——把造物的 `Group` 放在玩家面前 3 m、镜头对准，打开编辑器时暂停玩家输入。代价是编辑器打开期间多 10 个 draw call（主角 Group），关闭即释放。
- **右栏**：五行属性 + 三个派生值（速度/载重/威压）实时刷新，调 `derive(bp)`，不写第二套公式；底部显示面数 `tris / 1400`，超预算时数字变红并禁用「完成」。
- **底栏**：「试骑」「保存」「放弃」。保存前跑 `validate()`，失败时直接显示错误码（如 `E_REQUIRES`），不弹第二套文案。

不引入新框架的理由很实际：现有 UI 全部是原生 DOM + `panel` 样式，再加一个框架会带来一份运行时与一套构建配置；编辑器只在人道打开，使用频率远低于移动与交互，不值得为它加一整个依赖。

## 三、属性派生

### 3.1 五个属性，各自对应一个已有系统

造物不是「一张卡面写五个数字」，每个属性都必须落到一个**已经在跑的系统**上，否则它就是装饰。

| 属性 | 对应系统 | 具体落点 |
|---|---|---|
| 力量 `STR` | 战斗 | `physics.ts` 的 `PhysProfile.power`，进 `tierOf()` 五档判定 |
| 敏捷 `AGI` | 移动 | `player.ts` 的 `effectiveSpeed()` 与坐骑速度 |
| 灵性 `SPI` | 交互 | 解锁「通语」（与兽对话）/「显圣」（NPC 跪拜）两个交互开关 |
| 威压 `PRE` | NPC 反应 | `behaviors.ts` 的避让半径与 `ui:toast` 台词档位 |
| 承载 `LOAD` | 坐骑/载货 | `Rideable.riderAnchor` 与可驮重量（kg） |

**为什么不做单一「战力」**：V15 的业缘图需要「同一只兽对不同人有不同态度」——威压高的兽让人躲，灵性高的兽让人信，力量高的兽让人怕。压成一个战力，这三种反应就分不开了。这也是 V13 拒绝给六道加「战力」列的同一个理由。

### 3.2 公式

```ts
// K = 躯干体量系数（T01–T12 的 K 列）
STR = round(Σstr_i × K)
AGI = round(Σagi_i × (1.40 − 0.40 × K))
SPI = round(Σspi_i × (1 + 0.12 × (角件数 + 饰件数)))
PRE = round(Σpre_i × K)
LOAD = round(Σload_i × K × 8)          // kg

速度   = clamp(3.6 × (AGI / 20) ^ 0.7, 2.5, 14)   // m/s
威压半径 = clamp(PRE / 8, 0, 8)                     // m
战力   = round(STR × (1 + SPI / 50))
```

五个公式各有一句解释：

- **力量乘 K、敏捷除 K**：体量越大越有力、越不灵活。`1.40 − 0.40K` 在 K=1 时恰好是 1.0（人道基准），K=0.70 时是 1.12（小鼠更灵），K=1.70 时是 0.72（巨象更笨）。选这个线性式而不是 `1/K`，是因为 `1/K` 在 K→0 时会爆炸，而线性式在 0.70–1.70 区间内平滑、可手算。
- **灵性乘「角 + 饰」**：角与饰是「非功能件」，它们不参与力量/敏捷，只抬灵性。每多一件角或饰 +12%，上限由槽位自然封顶（1 角 + 1 饰 = +24%）。
- **承载乘 8**：把抽象的「载」换算成 kg，玩家能直接对照「这只能不能驮我」。人道成年人体重按 65 kg 估，`LOAD ≥ 65` 才驮得动人。
- **速度用 0.7 次幂**：敏捷从 10 涨到 40，速度不会涨 4 倍，只涨约 2.4 倍；幂函数让高敏的收益递减，避免「全点敏捷」成为唯一解。
- **战力是派生值，不参与门禁**：它只用于 UI 排序与 NPC 台词，不参与任何阈值判定。门禁只看 `merit/demerit`（V13）与 `LOAD`（坐骑）。

### 3.4 三个算例，验公式

以「墨鼠」为例：躯干 T01（K=0.70），头 H01，前肢 F01×2，后肢 B01×2，尾 A01，无翼，无角，无饰。

- 原始和：力 `4+1+1+1+1+1+0+0+0 = 9`；敏 `6+4+4+5+5+2 = 30`；灵 `1+1+0+0+0+0 = 2`；威 `0`；载 `2+0+1+1+1+1 = 6`。
- `STR = round(9 × 0.70) = 6`；`AGI = round(30 × 1.12) = 34`；`SPI = round(2 × 1.0) = 2`；`PRE = 0`；`LOAD = round(6 × 0.70 × 8) = 34`。
- 速度 `3.6 × (34/20)^0.7 = 5.27 → 5.2`；威压 `0/8 = 0`；战力 `6 × (1 + 2/50) = 6.24 → 6`。

以「青牛」为例：T08（K=1.40）+ H08 + F08×2 + B08×2 + A04 + R02 + O08。原始和力 44、敏 12、灵 2、威 20、载 17。`STR = 62`、`AGI = round(12 × 0.84) = 10`、`SPI = round(2 × 1.12) = 2`、`PRE = 28`、`LOAD = round(17 × 1.40 × 8) = 190`。速度触底 2.5，威压 3.5 m，战力 64。**它能驮起 190 kg，但跑不过一个步行的人**——这就是「牛」。

以「应龙」为例：T11（K=1.10）+ H11 + F09×2 + B09×2 + A06 + W05×2 + R04 + O05。原始和力 34、敏 37、灵 21、威 29、载 5。`STR = 37`、`AGI = round(37 × 0.96) = 36`、`SPI = round(21 × 1.24) = 26`、`PRE = 32`、`LOAD = 44`。速度 5.4，威压 4.0 m，战力 56。它是表里唯一「力/敏/灵/威都在 26 以上」的造物，代价是载重只有 44 kg（驮不动人）。

三条算例都能手算复现。**如果实现后 `derive()` 的输出与这三条差 1，就是公式写错了，不是舍入问题**——因为表里所有输入都是整数，唯一引入浮点的是 K 与幂运算，而这两处都在脚本里固定了 `Math.round`。

### 3.5 属性不写进存档

`Build` 只存部件与缩放，**不存属性**。属性每次 `derive(bp)` 现算。理由：一旦把属性写进存档，改平衡时旧档不会更新，玩家会拿着一只「上个版本的老虎」在新版本里打；现算则天然跟随版本。代价是每次生成要跑一次五行公式（<0.01 ms），可以忽略。

## 四、技术方案：程序化软体蒙皮 → 预烘焙拼装

### 4.1 Spore 的做法，与本项目的三条硬约束

Spore 的编辑器让玩家把部件拖到任意位置、拉长缩短，生物的身体是一张**程序化软体网格**：部件提供骨架与权重，网格按骨架实时变形（具体蒙皮算法与权重规则待检索核实）。这条路线在本项目里走不通，不是审美选择，是三条硬约束：

1. **几何是静态的**。`beastGeo()` 产出的是 `VGeo` 顶点数组，`geo()` 把它写成非索引 `BufferGeometry`（`creatures.ts:450`），没有骨骼、没有权重、没有 `SkinnedMesh`。
2. **预算是封死的**。静态面 13.35–15.09 M、载入 8.3–9.7 s、红线 12 s（共享约束 §一）；自由变形会让每个生物的三角形密度不可预测，预算表直接失效。
3. **确定性是底线**。V10 要求同种子同结果；自由拖拽的浮点坐标会让同一份蓝图在两次载入后产生不同几何与不同 hash。

所以本卷的方案是：**部件预烘焙 + 挂点拼装 + 整具实例化**。玩家选的是「哪件」，不是「在哪」。

### 4.2 三条路线，逐项算账

| 路线 | 做法 | draw calls | 关节动画 | 面数 | 内存 | 开发量 | 用在哪 |
|---|---|---|---|---|---|---|---|
| A 整具合并 | 部件在烘焙期 `merge` 成一具几何 | **1 / 原型** | 无（整具摆动） | ≤1,393 | 147 KB/原型 | 2–3 天 | 背景生物、守卫、机关 |
| B 分件刚体骨架 | 10 个 `Mesh` 组成 `Group`，按挂点摆 | **10 / 只** | 有（刚体摆动，无蒙皮） | 同上 | 147 KB + 10 个对象 | 5–7 天 | 主角坐骑/宠物（≤2 只） |
| C 软体蒙皮 | `SkinnedMesh` + 骨骼 + 权重 | 1 / 只 | 有（平滑） | +30–50% 顶点 | +8–16 B/顶点 + 骨骼矩阵 | 3–4 周 | **不选** |

选 **A + B 混合**：背景生物走 A，主角造物走 B。理由不是「B 更好看」，是**只有 1–2 只造物值得为关节动画付 10 个 draw call**。场上 24 只全走 B 就是 240 draws，在现有 186 draws 的基础上翻一倍还多；而 24 只全走 A 只有 ≤12 draws（按原型去重），代价是腿不会摆——在 4 m 以外，玩家看不出腿有没有摆。

C 被排除的另一个原因是**它和 A/B 不兼容**：一旦引入蒙皮，所有生物都得走同一套骨架与权重，现有 42 类 `SPECIES` 与 35 尊 `DEITIES` 都要重做。这不是一个玩法卷能承担的改动。

### 4.4 缓存、池与场上限

- **原型去重**：场上 24 只，最多 12 个不同 `hash`。同一 `hash` 共用一具几何、一个 `InstancedMesh`（`max = 24`），因此 draw calls = 不同原型数（≤12），不是只数。
- **LRU 16**：缓存上限 16 具（12 在场 + 4 预取），超出淘汰最久未用的；淘汰前必须确认场上无实例，否则几何会被提前释放。
- **池容量**：每个原型一个 `BeastPool`（`creatures.ts:108`），`max = 24`；现有 `beast_*` 池的 `max = 6` 是给 42 类生物用的，编辑器池另开，不复用那 6 个槽。
- **换装**：玩家在编辑器里改一个部件 → `hash` 变 → 旧实例释放、新几何创建。单次重建 1,393 面约 1–3 ms（VGeo push 循环），在 UI 里可接受；不允许每帧改部件。

对外只暴露四个函数（V13 §4.1 已约定，签名在此定稿）：

```ts
export interface CreatureHandle {
  bp: Build; profile: PhysProfile;
  group?: THREE.Group;      // 主角造物（B 路线）
  pool?: BeastPool;         // 背景造物（A 路线）
  slot?: number;
}
export function buildCreature(bp: Build): CreatureHandle | null;  // validate 失败返回 null
export function disposeCreature(h: CreatureHandle): void;
export function mountOf(h: CreatureHandle): Rideable;             // kind: 'custom'
export function profileOfBuild(bp: Build): PhysProfile;           // 供 physics.tierOf() 直接消费
```

`buildCreature` 返回 `null` 而不是抛异常，是因为它会在 UI 的实时预览里被频繁调用；抛异常会把一次「部件不合法」变成一次面板崩溃。错误码由 `validate()` 单独给出，预览层只负责显示。

### 4.5 内存估算

非索引几何每三角形 3 顶点，每顶点三属性：

| 属性 | float32 | 量化后（同 Baker 口径） |
|---|---|---|
| position | 12 B | 12 B |
| normal | 12 B | 6 B（Int16 normalized） |
| color | 12 B | 6 B（Uint16 normalized） |
| **每顶点** | **36 B** | **24 B** |
| **每三角形** | **108 B** | **72 B** |

| 对象 | 面数 | 顶点 | float32 | 量化 |
|---|---|---|---|---|
| 单原型（最坏） | 1,393 | 4,179 | **147 KB** | **98 KB** |
| 12 原型 | 16,716 | 50,148 | **1.72 MB** | **1.15 MB** |
| 24 实例矩阵 | — | — | 24 × 64 B = 1.5 KB | 同 |
| VGeo 构建瞬时 | 1,393 | 4,179 | ≈301 KB/只（9 个 number 数组） | 同 |
| 12 只顺序构建峰值 | — | — | +0.3–3.6 MB（取决于 GC） | 同 |

对照现有：`beastGeo('long')` 952 面 / 2,856 顶点 / 100 KB（float32，实测）。**一具造物比一条天龙重 47%**，因为它多了可换部件与更细的头/翼；这是可接受的增量。

显存之外还有 CPU 侧：`Build` 对象 < 1 KB、`hash` 字符串 8 B、`Group` 的 10 个 `Mesh` 对象约 10 KB（仅主角）。总计 < 50 KB，可忽略。

### 4.6 载入时间

- 96 件部件是**数据**，不是几何；只有被选中的 10 件才 `partGeo()`。
- 12 个原型 × 1,393 面 = 16,716 面，VGeo 逐顶点 push 约 15 万次，估 30–60 ms（按现有 `beastGeo` 构建 9 型、每型 <1 ms 的量级外推）。
- 不生成贴图（复用 `W12_MAT`）、不编译新 shader（同材质同 define）、不写 GPU 之外的缓存。
- 预算是 **120 ms**；超出即 BLOCK。若改为「首次打开编辑器才构建」，主载入路径增加 **0 ms**，代价是第一次打开编辑器多 0.1 s 的 loading 指示。

### 4.7 骨架与步态：复用 `BEAST_FORM`，不造第二套

- **挂点**：`spine` 截面表给 `spineY(z)` / `spineHalfW(z)`（`creatures.ts:626/636`），四肢挂点 = `(±spineHalfW(legs.z) + 0.02, spineY(legs.z), ±legs.z)`；颈/头挂点直接用 `neck.at` / `neck.tip` / `head.at`。这两个函数目前是模块私有，**必须导出**（`export function spineY` / `spineHalfW`，两行改动，零运行时成本）。
- **步态**：不做 IK。每条腿是一段刚体，绕髋关节按 `sin(phase + offset)` 摆动，摆幅 `0.35 rad × min(1, speed/4)`；前肢与后肢相位差 π。这与现有 `beastGeo` 的直腿造型一致，不会出现「看起来像软体、动起来像木棍」的割裂。
- **主角 Group**：10 个 `Mesh` 共用 `W12_MAT`，每帧写 10 个矩阵；`bl()`（`creatures.ts:985`）已经是现成的「父矩阵 × 局部变换」工具，直接复用。
- **不做的事**：不做脚部贴地（foot planting）、不做脊柱弯曲、不做尾巴物理。这三样都是蒙皮路线的附属品，刚体骨架做不好，硬做只会穿模。

### 4.8 与 `Baker` 材质组的复用边界

| 用途 | 材质 | 合批方式 | 额外 draw |
|---|---|---|---|
| 背景造物（坐骑/守卫/宠物） | `W12_MAT`（顶点色，`creatures.ts:11`） | 每原型 1 个 `InstancedMesh` | +1/原型 |
| 主角造物（≤2） | `W12_MAT` | 10 个 `Mesh` 的 `Group` | +10/只 |
| 载入期已知的静态机关/巢 | Baker 的 `earth`/`wood`/`ash` 组 | 随城市一起合批进 `city_*` | **0** |
| 运行期新建的机关 | `W12_MAT` 单独 `Mesh` | 不合批 | +1/件 |

**为什么生物不走 Baker 的材质组**：Baker 的 14 个组按世界 UV 以 0.24/m 展开（`bake.ts:773` 的 `scaleGeoUV(geo, 0.24, uvDims)`），而造物是局部坐标、会随实例移动/旋转；把生物塞进 Baker 组，贴图会在生物身上滑动。顶点色没有 UV 依赖，实例怎么转都不会花。

**代价**：造物没有木纹/布纹/瓦纹，只有顶点色的明暗。对一个 1–4 m 高、主要在 4 m 外被看到的生物，这个代价可以接受；如果以后要给近景主角加纹理，正确做法是给 `W12_MAT` 加一张 object-space 三平面贴图，而不是把它塞进 Baker。

**不新增材质**：`W12_MAT` 已在用（42 类生物与 35 尊神像共享），复用它是零 shader 编译、零纹理绑定。新增一个 `MeshStandardMaterial` 的成本不是「多一个对象」，是首次使用时的 shader 编译（约 5–20 ms，待实测）与一组贴图绑定；在一个 12 s 红线的项目里，这类零碎编译应该被当成预算项，而不是随手加。

## 五、造物拿来干什么：坐骑、宠物、机关、守卫

造物不是图鉴里的收藏品。它必须能上场，否则玩家捏完就忘。四种用途对应四套 AI 与四笔性能账，逐项写清。

### 5.1 坐骑

**接入点**：`Rideable.kind` 目前是 `'horse' | 'crane' | 'dragon' | 'qilin'`（`src/game/player.ts:15`），加一个 `'custom'` 是一行 union 扩展。`player.ts:249-299` 的 mount 分支只看 `flying`、`riderAnchor`、`pos/yaw/phase`，**不看 kind**——所以自定义坐骑不需要新物理，也不需要改 `groundHeight()`。

**能不能驮人看体量 K，能驮多少看 LOAD**：

- `K ≥ 1.10` 才能驮一个成年人（人道玩家按 65 kg 估）。K=1.10 的应龙、K=1.20 的鹤仙、K=1.30 的骏马、K=1.40 的青牛、K=1.70 的鲲鹏都合格；K=0.70 的墨鼠、K=0.85 的灵狐不行。
- `LOAD` 只决定「还能多带多少货」，不决定「能不能骑」。这样表里应龙 44 kg 的载重不会让它变成「不能骑的龙」——龙是驮人的，货少而已。
- `riderAnchor = spineY(0) + h × 0.5`，从体型原型的脊柱表取，不手填。

**飞行坐骑**：`flying = true` 需要 `wingCount ≥ 1` 且 `SPI ≥ 15`（灵力托举）。应龙 SPI 26、鲲鹏 21、鹤仙 19 合格；蝠妖 9 不合格，只能地面滑行。这条规则把「有翅膀」与「飞得起来」分开，避免玩家给墨鼠装一对蝶翼就飞天。

**代价**：地面坐骑走 A 路线（1 draw/原型），飞行坐骑若给主角骑则走 B 路线（10 draws）。`player.ts` 的飞行分支已经有 `m.pos.y` 夹取与 `groundHeight` 防穿（`player.ts:264-273`），自定义坐骑直接复用。

### 5.2 宠物

**AI 三态**：`follow`（距玩家 > 6 m 时靠近）、`idle`（3–6 m 内原地摆尾）、`alert`（16 m 内有敌对目标时朝目标转头，不主动攻击）。没有寻路：朝玩家位置做 `lerp`，每帧 `p += (target - p) × min(1, dt × 2.5)`；脚下高度直接调 `player.groundHeight(x, z, y)`，与玩家共用同一套地面查询。

**代价**：每只宠物每帧 1 次距离平方 + 1 次 lerp + 1 次矩阵写；4 只上限，合计 < 0.02 ms（按 60 fps 估算）。不新增 draw（与坐骑共用原型池）。

### 5.3 机关

**接入点**：`InteractSystem.add(pos, r, label, exec)`（`src/game/interact.ts:40`）。造物机关就是一个带半径的交互点：玩家进入 `r` 内按 E，触发 `exec`（喷火/落石/开门/召守卫），然后进入冷却。

- **载入期已知的机关**（预设 blueprint）：走 Baker 的 `earth`/`wood`/`ash` 组，随城市合批，**0 额外 draw**。
- **运行期新建的机关**：单独 `Mesh` + `W12_MAT`，**+1 draw/件**，上限 8 件。
- **每帧成本**：`InteractSystem.update()` 本来就每帧遍历全部交互点（`interact.ts:252-258`），加 8 个点只是多 8 次距离平方，可忽略。

机关是最便宜的用途，也是最容易被滥用的：如果允许玩家在城里随便摆 200 个喷火机关，`interact` 的 O(n) 遍历会从 61 项涨到 261 项。上限 8 不是性能问题，是设计问题——机关应该是「布置」，不是「铺满」。

### 5.4 守卫

**AI**：巡逻走 `CreatureSystem.runners` 的同款路径点循环（`creatures.ts:1015` 的 `pts` 数组 + 线性插值），不引入寻路网格。仇恨半径 = `PRE`（威压米数），攻击调 `ImpactSystem.resolve(profileOfBuild(bp), speed, target, dir)`，冷却 1.2 s。

**代价**：每 3 帧做一次距离检查（与 `world.ts:1305` 的 `npcSweep` 同款节流），8 名守卫 = 每帧约 2.7 次距离平方；攻击时才有 `resolve()` 调用。合计 < 0.1 ms。

### 5.5 四类用途的成本总表

| 用途 | AI | 每帧成本 | 上限（V13 §4.1） | 额外 draw | 额外内存 |
|---|---|---|---|---|---|
| 坐骑 | 玩家驱动，无 AI | 1 次矩阵写 | 2 | +1/原型（A）或 +10/只（B） | 147 KB/原型 |
| 宠物 | 三态跟随 | 1 距离 + 1 lerp | 4 | 共用原型池 | 0（同原型） |
| 机关 | 触发式，无 AI | 空闲 0，触发 1 次 | 8 | 载入期 0 / 运行期 +1 | < 1 KB/件 |
| 守卫 | 路径点 + 仇恨 | 每 3 帧 1 距离 | 8 | 共用原型池 | 0（同原型） |
| **合计** | — | **< 0.2 ms/帧** | 22 | **≤12（原型去重）** | **≤1.9 MB** |

这张表解释了为什么 V13 要给每个阶位设「召」的上限：不是怕玩家强，是怕玩家把 24 只造物全放出来当守卫，`interact` 与 `impacts` 的遍历成本会翻倍。上限是预算的前置，不是事后补丁。

### 5.6 一个完整样例：从捏到骑

玩家在人道，已在郊野见过马、鹿、虎，图鉴解锁 `T07/H07/F07/B07/A03/O08`。他捏了一只「青骢」：躯干 T07、头 H07、前肢 F07×2、后肢 B07×2、尾 A03、饰 O08，无翼无角。

- 面数：`320 + 170 + 75×2 + 85×2 + 60 + 45 = 915`，低于 1,400。
- 属性原始和：力 `11+3+3+3+4+4+1+0 = 29`、敏 `6+4+4+4+5+5+2+0 = 30`、灵 `3`、威 `11`、载 `14`；K=1.30 → `STR 38 / AGI 26 / SPI 3 / PRE 14 / LOAD 146`；速度 4.3 m/s、威压 1.8 m、战力 40（与 §3.3 的「骏马」同一行，因为部件完全相同）。
- `hash` 取部件排序 + `girth/legLen` 两位量化；`buildCreature(bp)` 返回句柄；`mountOf(h)` 得到一个 `kind: 'custom'` 的 `Rideable`，`riderAnchor = spineY(0) + h × 0.5 ≈ 1.5 m`。
- 玩家上马，`state === 'mount'`，速度 4.3 m/s；因为 `wingCount = 0`，`flying === false`，按 Space 只抬头不升空。
- 他想飞，加一对鹰翼 W02：面数 `915 + 260 = 1,175`，仍合法；但 `SPI` 只从 3 涨到 6（原始灵性 5 × 1.12 的饰件系数），**低于飞行门槛 15**，所以 `flying` 仍是 false。想飞，得换鹿首 H06（灵性 4，比马首多 3）再配鹿角 R01（灵性 +2、角件 +1），`SPI = round((3+3+2) × 1.24) ≈ 10`，仍不够；还得加云翼 W10 或玉冠角 R08。**这就是「属性派生」的意义：飞行不是勾一个复选框，是部件组合算出来的结果。**

这条链路里没有任何一步需要新代码路径：编辑器产出 `Build` → `buildCreature` 产出几何与 `PhysProfile` → `mountOf` 产出 `Rideable` → `player.ts` 现有的 mount 分支消费它。**造物系统是插在现有管线上的，不是另起一条。**

## 六、与 `creatures.ts` / `deities.ts` 共存：不造第二个轮子

### 6.1 三套东西，各管一段

| 系统 | 管什么 | 数量 | 数据源 | 谁在改 |
|---|---|---|---|---|
| `CreatureSystem` | 世界自带的动物与鬼怪 | 42 类（37 原 + 5 增） | `SPECIES`（`creatures.ts:56`） | 美术/关卡，不由玩家改 |
| `deities.ts` | 神佛雕像与法座 | 35 尊 | `DEITIES`（`src/data/deities.ts`） | 美术/剧情，静态 |
| `EditorCreatureSystem`（本卷） | 玩家造的坐骑/宠物/机关/守卫 | 24 只 / 12 原型 | `Build`（玩家存档） | 玩家 |

三者**不共享生命周期**：`CreatureSystem` 在 `world.init` 里一次性建池；`deities` 在场景构建期落位；`EditorCreatureSystem` 在玩家第一次打开编辑器时才建第一个池。这样即使玩家从不造物，前两者的载入成本一分不增。

### 6.2 复用什么，不复用什么

| 符号 | 位置 | 复用方式 |
|---|---|---|
| `VGeo` | `creatures.ts:185` | 部件几何的唯一内核，不新写 |
| `sh2` / `P3` | `creatures.ts:179/173` | 顶点色明暗与三元组类型 |
| `beastGeo` | `creatures.ts:660` | 九型原型的整具几何；编辑器不重写 |
| `BEAST_FORM` | `creatures.ts:491` | 体型原型表；需 `export`（当前是模块私有） |
| `spineY` / `spineHalfW` | `creatures.ts:626/636` | 挂点高度/半宽；需 `export` |
| `BeastPool` | `creatures.ts:108` | 实例池；每个原型一个，`max=24` |
| `W12_MAT` | `creatures.ts:11` | 唯一材质；不新增 |
| `FORM_EYES` | `creatures.ts:965` | 眼位参考；编辑器自己算眼位，不读它 |
| `bl()` | `creatures.ts:985` | 主角 Group 的局部矩阵合成 |

**明确不做的四件事**：

1. **不往 `SPECIES` 里加条目**。玩家的造物不是世界物种，不能进 42 类的名录；进了会污染 `CreatureSystem` 的刷新逻辑与生物统计。
2. **不新写几何内核**。`VGeo` 的 `box/frus/cyl/cone/tube/fan` 已够拼 96 件部件；再写一套 `PartGeo` 只会让两套顶点色/法线约定分叉。
3. **不新增材质**。`W12_MAT` 被 42 类生物 + 35 尊神像共用，再加一个 `MeshStandardMaterial` 就是多一次 shader 编译与一组贴图绑定。
4. **不新开眼睛池**。现有 `eye` 池 `max=160`（`creatures.ts:167`），42 类生物已用掉一部分；编辑器 24 只 × 2 眼 = 48，会把余量压得很紧。最小改法是把 `max` 从 160 提到 240（一个数字，+0 draw，实例矩阵 +80 × 64 B = 5 KB），而不是新建 `editorEye` 池。

### 6.3 与神像的边界

`deities.ts` 用 `VGeo` 拼的是**静态神像**（冠/持物/法座/背光），没有移动、没有 AI、没有实例池的逐帧矩阵。编辑器造物是**动态生物**（有步态、有仇恨、有坐骑逻辑）。两者共享 `VGeo`，但不共享装配代码：神像的 `statueGeo` 不会因为编辑器加了一件「莲座」而改变，反之亦然。

唯一需要对齐的是**配色**：神像用 `sh2()` 做明暗，编辑器部件也用 `sh2()`；如果一边改成线性空间、一边保持 sRGB，同屏会出现「神像偏亮、造物偏暗」。这条写进 `parts.ts` 的文件头注释，避免下一任维护者各写一套。

### 6.4 同屏共存测试：24 + 42 + 35

最后一笔账要把三套东西放在同一帧里算，否则「不重复造轮子」只是口号。

测试场景：12 个原型 × 2 只 = 24 只编辑器造物，站在虹桥两岸；现有 42 类生物照常刷新（`CreatureSystem` 的 `SPECIES` 不动）；35 尊神像照常在天宫落位。

| 项 | 现值（无编辑器） | 加 24 只造物 | 增量 |
|---|---|---|---|
| draw calls | 186（交付报告实测） | 198 | **+12** |
| 静态/动态总面 | 13.35–15.09 M | +33,432 | **+0.25%** |
| GPU 几何 | — | +1.72 MB | **+1.72 MB** |
| shader program | N | N | **0** |
| 材质实例 | N | N | **0** |

`probe-coexist.mjs` 的做法：先跑一次基线记 `calls/geometries/programs/triangles`，再生成 24 只造物重测，逐项断言差值不超过上表。**最容易被忽略的是 `programs`**——如果实现时给造物加了新材质，`calls` 可能只 +12，但 `programs` 会 +1，首次渲染多一次编译，表现为「打开编辑器第一次卡一下」。这一项必须单独断言。

## 七、可执行验收断言

每条都能写成 `scripts/probe-parts-*.mjs` / `probe-editor-*.mjs`，输出 `PASS` / `BLOCK` + 退出码。断言不测「看起来像」，只测数字、哈希、draw call 与错误码。

**B1 部件库完整性**：`PART_SLOTS` 恰好 8 个槽位；每个槽位 `PARTS[slot].length >= 12`；96 个 id 全局唯一；每件 `partGeo(id).tris <= cap(slot)`（躯干 340、头 180、前肢 95、后肢 100、尾 75、翼 150、角 60、饰 50）。任一超标即 BLOCK，并打印超标件的 id 与实测面数。

**B2 校验器负样本**：§2.2 的 8 条负样本逐条跑 `validate()`，返回的 `code` 必须与表内期望**完全相等**（不是「包含」）；最坏组合 `T12+H12+F12×2+B12×2+A08+W05×2+R10+O09` 必须 `ok === true`。这条同时防「校验太松」与「预算误杀」。

**B3 面数上界**：20 条预设 `Build` 全部 `tris <= 1400`（不含眼）；最坏组合 `tris === 1393`（允许 ±0，因为表内值是整数相加）；LOD1 全部 `<= 850`；含眼 `<= 1600`。若实现后某件实测超标，先改部件，不改断言。

**B4 属性金标准**：§3.3 的 20 行逐行跑 `derive(bp)`，五个属性与表内值**逐项相等，容差 0**；`速度/威压/战力` 三个派生值容差 0.1（幂运算的浮点尾差）。再跑 §3.4 的三条手算样例（墨鼠/青牛/应龙），任意一项差 1 即 BLOCK——这说明公式实现与文档不一致，不是舍入问题。

**B5 哈希稳定**：同一 `Build` 连续保存两次，`hash` 相同；把 `parts` 的插入顺序打乱，`hash` 相同；`girth` 从 `1.0` 改成 `1.0000001`，`hash` 相同（两位量化）；`girth` 从 `1.00` 改成 `1.01`，`hash` 必须不同。第四条防「量化过头、改色不生效」。

**B6 渲染预算**：场上 24 只、12 个不同原型，`renderer.info.render.calls` 增量 `<= 12`（每个原型 1 个 `InstancedMesh`）；若 2 只主角走 B 路线，再 `+20`（10/只），总增量 `<= 32`；`renderer.info.programs.length` 与改动前相等（不新增 shader）；`renderer.info.memory.geometries` 增量 `<= 12`。

**B7 内存与载入**：单原型几何 `<= 147 KB`（float32）/ `<= 98 KB`（量化）；12 原型 `<= 1.72 MB` / `<= 1.15 MB`；`window.__s14BuildMs <= 120`；主载入总时长仍 `<= 12 s`（沿用现有 `probe-mem.mjs` 的 `loadMs` 口径）。四项任一超限即 BLOCK。

**B8 共存契约**：`DEITIES.length === 35`、`SPECIES` 42 条、`beast_*` 池的数量与 `max` 不变、`eye` 池 `max === 240`（从 160 提升后的值）、`SPECIES` 里没有新增编辑器条目。这条防「为了造物，把世界物种表改了」。

**B9 坐骑闭环**：造一只 `K >= 1.10` 的地面坐骑，`mountOf()` 后 `player.state === 'mount'`，移动速度与 `AGI` 派生值误差 `<= 0.2 m/s`；下马后 `state === 'foot'`、`actor.pos` 回到坐骑右侧 2 m（`player.ts:395` 的现有语义）；给 `K=0.70` 的墨鼠装鞍鞯必须被 `validate()` 拒绝（`E_REQUIRES`）。

**B10 用途上限**：放 8 个机关 + 8 名守卫 + 4 只宠物 + 2 只坐骑，`interact.list.length === 61 + 8`（机关进交互表，其它不进）；`renderer.info.render.calls` 增量 `<= 12 + 8`（原型 + 运行期机关）；连续跑 600 帧，`__s14AiMs` 平均 `< 0.2 ms/帧`。

**B11 确定性**：同一 `Build` 在两次独立载入（清缓存、重进）后，`partGeo` 合并结果的顶点数组 SHA-256 相同；`derive()` 输出相同；`hash` 相同。这条是 V10 lockstep 的前置——造物如果不能逐字节复现，多人模式里两只坐骑会长得不一样。

## 八、风险与未决

1. **96 件部件的面数是按图元累加的估算，不是实测**。表内数字与 `beastGeo` 同口径，但部件实现后可能有 ±10% 偏差；B1/B3 会把偏差抓出来，代价是可能要重做 3–5 件超标的部件。
2. **属性表没有经过平衡测试**。20 条样例只能证明「公式自洽」，不能证明「青牛与白象之间有得选」。首版建议把 `PART_FORM` 的数值做成可热改的 JSON，先跑 10 名测试者的选择分布，再定稿。
3. **主角 Group 的 10 draws 是硬成本**。如果两只主角 + 12 个原型同屏，draw calls 会从 186 涨到 218（+17%）。在 4K/集成显卡上这可能就是 60 fps 掉到 52 fps 的那一下；备选是主角也只走 A 路线，牺牲腿部摆动。未决。
4. **没有 IK，高速时脚会滑**。刚体腿在 6 m/s 以上会出现「腿在原地摆、身体在飞」的观感；现有 `beastGeo` 的生物也有同样问题，只是它们速度低（1–5.5 m/s）。造物如果跑得比 5.5 m/s 快，滑步会被看见。
5. **载入 30–60 ms 是估算**。按 `beastGeo` 九型的构建耗时外推，没有在目标机上实测；B7 的 120 ms 是上限，不是预期值。
6. **预览位可能与场景冲突**。编辑器把造物放在玩家面前 3 m 预览，若玩家站在墙边或河岸，预览体会插进墙里/浮在水上。最小修法是用 `walkSurfaceY(x, z, y)` 选一个可行走的预览锚点（与 NPC 出生同款，`crowd.ts:1258`），找不到就退到玩家身后；不修的话，玩家会以为「造物穿模」，其实是预览位穿模。

> **本卷最弱的三段（自认）**：
> ① §3.3 的 96 件部件数值——为满足「每槽至少 12 件」而填，部分部件区分度不足（例如 A01 鼠尾与 A10 龟尾只差 1 点敏捷），没有经过选择率测试，很可能有一半部件永远没人选。
> ② §4.7 的步态——只写了「刚体摆腿 + 相位差 π」，没有写清不同体型原型（两足/四足/无足/飞行）各自的相位与摆幅，实际实现时每个原型都要单独调，工作量被低估。
> ③ §5.4 的守卫 AI——「路径点 + 仇恨半径 + 1.2 s 冷却」是最小可跑版本，没有处理「守卫卡在建筑角」「多守卫互相阻挡」「玩家绕柱」三种常见情况，上线后大概率要补碰撞规避。
