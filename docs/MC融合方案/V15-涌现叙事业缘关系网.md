## 0. 先给结论

1. **业缘不是善恶积分，是一张「谁看见了什么、谁告诉了谁」的可追溯图。** 积分只能回答「你是好人吗」，图能回答「虹桥卖茶的那家为什么给你赊账、漕帮为什么在码头堵你、阎罗殿为什么多扣你一魂」。前者是数值，后者才是叙事。
2. **没有观察者，就没有边。** 这是本卷的第一原则，也是与「给每个行为加好感度」这种做法最根本的分歧：一次无人目击的杀人在关系网里不存在，只在玩家自己的行状里留一条「无人知晓」。它可以日后被物证翻出来，但不能当场生效。
3. **本作能承载的具名节点约 300 个，不是 4,500 个。** 现有世界有 165 位好汉、约 60 位神佛、61 个交互点掌柜、18 个 `POIS` 键、12 个势力；4,500 名活体路人来自对象池（`src/actors/pools.ts`，`MAX_HUMANS = 4800`），**没有稳定身份**。因此「每个路人记得你」在本架构里是做不到的，也不该承诺。路人的态度只能聚合成「坊/行会/场所」的态度，再由具名节点代言。
4. **它是 16 卷里性价比最高的系统**：新增静态面 **0**，新增堆 **硬上限 8MB、实际约 3.6MB**（占当前峰值堆 1.83–1.86GB 的 **0.2%**），载入增量 **≤ 0.01s**，开发量约 **24 人日（估）**。对比之下，任意一条「全局体素化」都要 +8M 面、+5s 载入（见 V16 §5）。
5. **它的风险不在性能，在身份与存档**：现有存档只有 `cq_coins / cq_yinde / cq_peach` 三个 `localStorage` 标量（`src/game/interact.ts:31-33`），业缘要自带版本化存档、稳定 id 与确定性随机流，否则读档即漂移。

## 1. 业缘图（Karma Graph）的数据结构

### 1.1 节点：四类，全部有稳定引用

```ts
type NodeKind = 'person' | 'faction' | 'place' | 'event';

interface KNode {
  id: number;        // 0..N-1，分配后永不复用；存档只存 id
  kind: NodeKind;
  ref: string;       // 'hero:luzhishen' | 'poi:hongqiao' | 'faction:caobang' | 'evt:000417'
  name: string;      // 显示名，进图鉴/行状
  x: number; z: number;  // 场所与势力的锚点；人物取当前岗哨，用于半径查询
  born: number;      // 游戏日（浮点，1 日 = 420s，见 1.3）
  dead?: number;
}
```

四类节点的现实来源必须写死，否则会退化成一张空表：

| 类型 | 数量（本项目实测） | 来源 | 备注 |
|---|---|---|---|
| `person` | 约 300 | 165 好汉（`heroes 165`）+ 约 60 神佛（`src/sky/deities.ts`）+ 61 交互点掌柜（`src/data/interactPoints.ts`）+ 少数具名衙役/摊主 | 只有这些有稳定身份 |
| `faction` | 12 | 官府、禁军、漕帮、脚行、商户行会、寺观、瓦舍勾栏、水军、鬼市、天宫、地府判司、梁山 | 路人只挂势力，不挂个人 |
| `place` | 约 100 | 18 个 `POIS` 键 + 61 个交互点 + 坊/桥/城门 | 场所是流言的容器 |
| `event` | ≤ 5,000（环形缓冲） | 每次 `emitKarma()` 生成一条 | 超限时最旧事件压缩成「日汇总」节点 |

**事件节点必须独立存在，不能只留一条边。** 原因是它要同时被三样东西引用：编年史（按时间线渲染）、物证（日后被翻出）、流言（从事件向人传播）。若把事件摊平进边里，就无法回答「这条仇是怎么结下的」。

### 1.2 边：10 类，覆盖善恶、恩仇、债务

要求至少 6 类，这里给 10 类，因为「恩/仇/债」各自的衰减与传播规律不同，混成一类会让数值失真。

| 边 | 语义 | 权重域 | 半衰期（游戏日） | 方向 | 生成条件 |
|---|---|---|---|---|---|
| `grace` 恩义 | 你帮过他 | 0..100 | 6 | A→B | 受惠者目击或受益 |
| `grudge` 仇怨 | 他恨你 | 0..100 | 12 | A→B | 受害者/亲属目击 |
| `debt` 债务 | 欠钱/欠人情 | 0..∞ | 不衰减，清算即止 | A→B | 交易/赖账/借粮 |
| `kin` 亲缘 | 血缘/师承 | 固定 | 不衰减 | A↔B | 静态表，运行时不改 |
| `patron` 香火 | 人供奉庙/神 | 0..100 | 30 | 人→庙/神 | 功德箱、香火钱 |
| `witness` 目击 | 他看见了你 | 0..100（可信度） | 3 | 事件→人 | 观测管线命中 |
| `rumor` 流言 | 他听说了你 | −100..100 | 1 | 人→人 | 口传 tick |
| `office` 职属 | 他属于某势力 | 固定 | 不衰减 | 人→势力 | 静态表 |
| `feud` 势力敌对 | 两势力有仇 | −100..0 | 30 | 势力↔势力 | 剧情/玩家行为 |
| `karma` 业 | 这件事记在他账上 | −100..100 | 见 1.3 | 事件→人 | 每个观察者一条 |

**`witness` 与 `karma` 必须分开。** 前者是「记忆」，会淡忘（半衰期 3 日）；后者是「账」，按善恶各自的半衰期走。一个人可以记得看过你（`witness` 尚在），但已经不再计较（`karma` 已衰减到 0）。这两条如果合并，就会出现「三年前的旧账和昨天的事一样重」的失真。

边的六条不变量，落地时必须写进 `graph.ts` 的 `assertInvariants()`，并由单测覆盖：

1. **不自指**：`a !== b`，任何边都不允许指向自己。
2. **同源唯一**：`(a, b, kind, src)` 四元组唯一；同一事件重复结算只累加 `w`，不新建边。否则一次误触会生成两条仇，数值翻倍。
3. **业必有源**：`kind === 'karma'` 的边必须带有效 `src`（事件 id），不允许「凭空记一笔」。
4. **目击需可信**：`kind === 'witness'` 的边 `acc > 0`；`acc = 0` 视为没看见，直接不建。
5. **清算不删除**：`debt` 还清后写 `t1`（失效日），边保留。删边会让「他以前欠过你」这段历史消失，而行状要能回溯。
6. **层级不越权**：个人边（`grace/grudge`）不自动升级为势力边（`feud`）；势力态度只能由「该势力下 ≥ 3 个具名节点同向」聚合而来。这条防止「得罪一个摊贩 = 与整个商户行会为敌」的粗暴放大。

### 1.3 衰减：按游戏日算，不按秒算

项目里一整个昼夜是 **7 分钟**（`src/core/palette.ts:35`：`speed = 1 / 420`，即 420 秒/日），且 `paused = true` 是默认值——玩家不打开昼夜循环，时间就不走。这带来一个必须显式处理的问题：**如果业缘严格跟 `TimeOfDay.phase` 走，暂停时永远不衰减，测试也无法复现。**

处理办法：业缘自带 `KarmaClock`，按下面的规则推进，并向探针暴露 `world.karma.advance(days)`：

```
days += dtReal / 420            // 昼夜循环开启时
days += dtReal / 420 / 8        // 暂停时按 1/8 兜底推进（1 小时真实时间 ≈ 1.07 游戏日）
```

衰减公式用整数定点，避免浮点累积漂移：

```
w(t) = round_half_away_from_zero( w0 * 2^(-(t - t0) / H) )
```

- `H` 取 1.2 表中的半衰期；`debt / kin / office` 不衰减。
- 衰减按 **0.25 游戏日** 为一档批量结算，而不是每帧结算。这样存档前后、不同帧率下结果逐值一致，也把开销从「每帧 5 万条边」降到「每 105 秒 5 万条边」。
- 权重用 `int16` 存，单位 **0.1 业力点**（下称「毫业」）。+10 业力 = +100 毫业。整数存储是确定性的一部分：浮点在两端的舍入不同会让读档后的哈希对不上。

**为什么半衰期取这些值**：一局 1–2 小时的会话约等于 8–17 个游戏日（按 7 分钟/日）。仇怨半衰期 12 日 ≈ 84 分钟真实时间，正好是「一次会话内会淡化、但不会当场忘」；流言 1 日 ≈ 7 分钟，符合「街谈巷议三天就换话题」的市井节奏；恩义 6 日比仇怨短，是因为人情比仇更容易被时间抹平——这也是本项目要的调子：**仇记得久，恩忘得快**。

### 1.4 存储布局：SoA + CSR，不用对象图

5,000 事件 + 50,000 条边如果用 `Map<id, {…}>`，光对象头就要几十 MB。改用结构数组：

```ts
// 节点：6 条平行数组
nodes = { id: Int32Array, kind: Uint8Array, refId: Uint16Array,
          x: Float32Array, z: Float32Array, born: Float32Array };
// 边：7 条平行数组，按 (a, kind) 排序后建 CSR
edges = { a: Int32Array, b: Int32Array, kind: Uint8Array,
          w: Int16Array, acc: Uint8Array, t0: Float32Array, src: Int32Array };
// CSR：偏移 + 邻接
csr = { off: Int32Array /* N+1 */, adj: Int32Array /* E */ };
```

CSR 只在「边集合变更超过 256 条」或「读档后」重建，重建 5 万条约 2ms。查询 `attitude(a,b)` 走 `off[a]..off[a+1]` 的线性扫描，出度硬上限 32，因此最坏 32 次比较。`topK(a,3)` 用固定 3 槽的有界堆，O(32 log 3)。物价修正 `priceMod(place)` 不进 CSR，走「场所聚合缓存」，边一变就打脏，O(1) 读取。

## 2. 行为 → 业缘映射表（36 条）

### 2.1 业力量纲

先定义刻度，否则「+5」和「+10」没有区别：

- **1 点** = 一桩小事（施一碗粥、让一次路）。
- **10 点** = 一桩人命（救一人、杀一人）。
- **50 点** = 一坊之劫（清空一个坊的活口、决堤淹一条街）。
- **100 点** = 一城之劫（只做上限，不轻易给）。

存储用「毫业」（0.1 点），表里写的是业力点，落到代码乘 10。

### 2.4 双账：同一件事，两本账

第 26 条是整张表的样板。玩家在将台打死巨灵神：

- **人间账**：`W` 看见除害，`G` 漕帮松一口气，`U` 记「阳寿未尽而杀神」——净 **+8**。
- **天庭账**：`T` 神像/耳目记「戕害天将」，凌霄殿的蟠桃宴请帖永久关闭——净 **−5**。

两条 `karma` 边同时存在，方向相反，互不抵消。这就是「业缘图」相对「善恶分」的核心差异：**它允许你同时是英雄和罪人，并且两个身份各有各的后果。** 如果只做一个全局 `karma: number`，这个设计瞬间塌回一条数轴。

### 2.5 屠村这条为什么现在做不了

第 27 条的 −50 是所有条目里最重的，但本项目**没有村庄实体**：城市之外是地形与零散聚落（`src/city/infill.ts` 的 `infill_block_*` 在 4.1–6.9km 只是体块），没有可交互的村民群体。要落地这条，必须先有 `crowd.despawnInRadius(pos, r)` 与「坊级人口账」，而这两样都不存在。**所以这条在表里是设计上限，不是可玩内容。** 同理，第 28 条决堤需要可破坏河堤，属于 V2/V5 的体素范畴，本卷不承诺。

### 2.6 六条重点行为的完整判定

任务书点名的六条（救人、诬告、毁庙、放生、屠村、施粥）不能只给一行数字，必须给到「按什么键、满足什么条件、谁看见、后果是什么」。以下六段就是这六条的落地契约。

**救人一命（+10）**：触发不是「靠近」，是「拖上岸」——玩家必须在水里按 E，持续 3 秒，期间移动速度 ×0.5。成功要同时满足：落水者 `hp > 0`、玩家 `state === 'swim'`、两者距离 < 2.5m。观察者按 §3.2 取半径 30m 内、面朝水面的人；被救者本人必为 `B`，其家属若在 15m 内额外记 `B`。若岸上无人，`visibility = 'none'`，只有被救者知道——但这条边会在 1 游戏日后由被救者口传给 1–2 个邻居，因为**当事人本身就是一个观察者**。这是规则二（玩家不是观察者）的唯一例外：受害者/受惠者永远是观察者，否则「救人」这件事在系统里彻底不存在。

**诬告（−6）**：在府衙递状，选「告某人通敌」。判定需要三样：状纸（书坊 5 文）、被诬者姓名（必须已进图鉴，即玩家见过）、至少 1 名 `O` 在场。后果分两步：立时 `O` 记 −6，被诬者若在 40m 内则记一条 `grudge` −30（这是仇怨边，不是业力边）；1 游戏日后开审，若玩家拿不出物证，`O` 追加「诬告反坐」−4，并 `wanted = true` 持续 3 日。**这是全表唯一「先赢后输」的行为**：短期得利、长期反噬，正好对上「恶」的叙事节奏。

**毁庙（−15）**：需要「砸」的动作命中神像碰撞体。神像本身是 `T` 节点，必为观察者；同时 `U` 记「毁神像」，因为生死簿记的是「业」不是「人」。后果：该庙 `patron` 边清零、香火归零、庙祝永久拒绝交易；若庙属天宫（如凌霄殿配殿），天庭账再 −15，蟠桃宴请帖永久关闭。**毁庙不能靠「没人看见」逃掉**——神像就是观察者。这是本卷有意为之的「不可欺」设计：有些事天生有见证。

**放生（+1）**：在汴河/瑶池边把鱼、龟放回水里。判定：背包有活物（渔户处 2 文）、在水边 3m 内按 E。观察者 `W/T`；若放的是瑶池锦鲤，`T` 额外 +2（天宫喜欢这个）。上限每游戏日 +5。**放生是最廉价的善业来源，所以必须设日上限**，否则它会变成「善业印钞机」——和 V16 里扛包变成铜钱印钞机是同一类错误。

**屠村（−50）**：本作无村庄（§2.5 已说明），这里的「村」指一个坊。落地需要 `crowd.despawnInRadius` 与坊级人口账，两者都不存在，因此**这条只作为设计上限存在，不实现**。若未来实现，判定必须是「连续 60 秒内该坊活体减少 ≥ 80%」，而不是「杀了一个人」——数值要对上「一坊之劫」的量纲。

**施粥（+1）**：在 E18 素斋付 10 文舍粥，持续 30 秒，每 5 秒给 1 名饥民盛一碗。判定：至少 6 个路人进入 8m 内并停留 ≥ 2 秒。观察者 `W/B/T`；若当天粮价 > 1.5× 基准（V16 的粮价状态），额外 +2。上限每游戏日 +3。**施粥的关键不是钱，是「有人排队」**——没有饥民，施粥不成立，这防止玩家在空街上刷善业。

## 3. 可观察性：没有观察者，就不进关系网

### 3.1 五条通道

| 通道 | 产生方式 | 延迟 | 失真 | 例 |
|---|---|---|---|---|
| 目击 | 半径内 `actor` + 视线 + 注意力朝向 | 即时 | 无 | 街口斗殴被 7 人看见 |
| 物证 | 事件在 `place` 上留 `trace` 节点 | 即时 | 无 | 血迹、焦痕、被砸的匾 |
| 口传 | `rumor` 边按社交图逐跳扩散 | 5–30 游戏分钟/跳 | 每跳 ×0.7，可能反号 | 「听说虹桥那家被砸了」 |
| 阴司 | 死亡/立誓/生死簿相关事件强制入账 | 1 游戏日 | 无 | 阎罗殿的案卷 |
| 天宫耳目 | 神像/神佛在场，或事件发生在天宫境内 | 即时 | 无 | 毁庙当场被记 |

### 3.2 观测管线

```
emitKarma(evt):
  cand = crowd.within(evt.pos, evt.radius)          // 空间哈希，4m 格
  cand = cand.filter(a => los(evt.pos, a.pos) && facing(a, evt.pos))
  if cand.length > 16: cand = 取最近 16 个（按距离升序，同距按 id）
  tags = []
  if anyDeityWithin(evt.radius) or evt.inHeaven: tags.push('T')
  if evt.inUnderworld or evt.kind in DEATH_KINDS:  tags.push('U')
  if anyOfficialWithin(evt.radius):               tags.push('O')
  if evt.factionHit:                              tags.push('G')
  if cand.length == 0 and tags.length == 0:
      evt.visibility = 'none'                      // 关键分支
      chronicle.push(evt, '无人知晓')
      return                                       // 不建任何边
  for a in cand: addEdge(evt, a, 'witness', acc=reliability(a))
  for a in cand: addEdge(evt, a, 'karma',   w=evt.delta * trust(a))
  for t in tags: addEdge(evt, tagNode(t), 'karma', w=evt.delta)
  scheduleRumor(evt, cand, t+5..30min)
```

三个实现细节决定它能不能跑：

1. **视线判定不能对 4,500 人做。** 先用 4m 空间哈希取半径内候选（典型 ≤ 20 人），再对最近的 8 人做一次射线；其余按距离做概率采样（`p = 1 - d/r`，用 `karmaRng`）。这是「近似」而不是「精确」，必须在文档里承认：**远处的目击是概率性的，不是确定性的。**
2. **注意力朝向**：`Actor` 有 `yaw`（`crowd.ts` 的实例矩阵里就是它）。只把「面朝事件 ±100°」的人算目击者，背对的人不算。这一条能把「全街同时转头」的假感压下去。
3. **观察者上限 16**：超过 16 人时只取最近 16 个。不是为了性能，是为了叙事——「全城 4,500 人同时恨你」没有意义，「街口 16 个人看见了」才有。

### 3.3 三条硬规则

**规则一：没有观察者，就没有边。** 事件节点仍然存在，`visibility='none'`，只进玩家自己的行状。它不产生 `karma`、不产生 `witness`、不产生 `rumor`。

**规则二：玩家自己不是观察者。** 玩家知道自己干了什么，但「知道」不等于「关系网知道」。如果玩家自己算观察者，那所有暗处行为都会立刻产生自我边， secrecy 机制直接失效。

**规则三：物证可以把「无」变成「有」，但不能把「有」变成「无」。** 一具埋掉的尸体在 3 游戏日后被野狗刨出，`trace` 节点生成，此时才补 `O/U/W` 的边。反过来，烧掉的账本不能撤销已经发生的目击——**记忆不能被销毁，只能被稀释**。

### 3.4 流言：传播、失真、反号

- 每个携带 `rumor` 边的人，每游戏小时向 1–3 个「同坊/同行业/同势力」的邻居传一次。
- `acc' = floor(acc * 0.7)`；当 `acc' < 40` 时，每次传播有 **15%** 概率**反号**（善行传成「伪善」、恶行传成「被冤枉」）。
- `acc' < 5` 或跳数 > 5 时消亡。
- 反号不是 bug，是本卷要的涌现：**你救了人，但传到你仇家耳朵里，可能变成「他作秀」**。这让「名声」第一次变成一个玩家无法完全控制的东西。

传播预算：1 Hz，每次抽 32 条 `rumor` 边；5 万条边里 `rumor` 占比按上限 30% 估（1.5 万条），全量轮一遍约 8 分钟——比流言半衰期（7 分钟）略长，因此实际会有少量边没轮到就衰减，这是可接受的（也符合「有些闲话你没听到就过去了」）。

### 3.5 反侦察：能骗人，骗不了簿子

| 手段 | 效果 | 代价 |
|---|---|---|
| 面衣/夜行 | 目击半径 ×0.4 | 白天穿会被 `O` 标记「形迹可疑」 |
| 灭口 | 移除该目击者的 `witness`/`karma` 边 | 若 `U` 已记录（死亡类事件），新增「杀害证人」−12，且不可撤销 |
| 毁物证 | 删除 `trace` 节点 | 需要火/水；失败则留新 `trace` |
| 贿赂 | `O` 的边权重 ×0.5 | 有 20% 概率反噬（`O` 记「行贿」−3） |

这张表是本卷的策略深度所在：**它让「善」和「恶」都不是一键选择，而是有成本、有反噬、有信息差的操作。**

### 3.6 一次完整取证：从落水到全城皆知

以「虹桥救人」为例，走一遍五个通道，看清涌现是怎么发生的：

- `t=0`：玩家在虹桥北侧跳河，拖起一名落水童子。半径 30m 内有 9 人面朝水面，取最近 8 人建 `witness` 边（可信度 90/85/80…），`B` 为童子；`U` 因「阳寿将尽而被救」记一条中性记录（不加减业力，只记「改命」）。
- `t=0`：`O` 不在场（虹桥无衙役），`T` 不在场（无神像）；`G` 漕帮有 2 人在码头，距 26m、面朝河，命中。
- `t=+10 分钟`：8 名目击者各向 1–3 个同坊邻居传；`acc` 从 90 降到 63，话从「有人落水」变成「有个外乡人跳河救了个娃」。
- `t=+1 日`：`acc` 降到 44；其中一条在传播时掷出反号，变成「那人是先把娃推下去的」，挂到玩家的 `rumor` 边上，权重为负。
- `t=+1 日`：`U` 的「改命」记录被阎罗殿读取，判官在 `yanluo` 节点多一句判词「你改过一次命，寿数记着」。这不是加减业力，是内容解锁。
- `t=+3 日`：`witness` 边按 3 日半衰期降到 50%，而恩义边（6 日半衰期）还有 70%。于是出现「记得的人少了，但记得的人更认你」——这正是两条边分开存的意义。

全程没有新增一个模型、一张贴图、一个 draw call；改变的是 8 个人、2 个势力、1 座庙、1 个判官节点上的 11 条边。**涌现叙事的成本结构就是这样：几何不变，关系变。**

### 4.1 三个案例的完整链路

**案例 4（宫门盘查）**：玩家恶业 −22，走到紫宸殿丹陛。判定不是「全局 karma < −20」，而是「`O`（禁军）对玩家的 `karma` 边 ≤ −20」——如果玩家只得罪了漕帮、没得罪官府，宫门不该拦。拦下后推回 12m，`zichen` 的 `threatSpec` 复用 `push` 类型；连续 3 次强闯，`O` 追加 −5，并解锁「海捕文书」支线。这条链路的重点是：**门禁读的是势力边，不是全局分。**

**案例 7（三生石结局）**：玩家在三生石前读前世。系统取 `topK(player, 3)` 的 `karma` 边，按「符号 × 边类型」映射到 6 个结局：善+恩→「还恩」；善+仇→「以德报怨」；恶+仇→「索命」；恶+恩→「负义」；无记+债→「欠债未还」；无记+亲→「骨肉重逢」。每个结局给一段 120 字判词 + 1 个图鉴条目。**结局不是「好人/坏人」二选一，而是「你最重的那三笔是什么」。**

**案例 10（城门通缉）**：`karma ≤ −60` 时 `wanted = true`。城门 `teleport` 返回 `false`，HUD 提示「城门有画影图形」。捕快不是新模型，复用现有 `crowd` 的守卒职业（`jobs.ts` 的 `soldier`），在城门 POI 生成 2 名，行为走现有 `BEHAVIOR_LIB.patrol`（`behaviors.ts:309`）。**不新增 draw call，因为它们是池里的实例。** 通缉持续 3 游戏日，或玩家在鬼市花 50 阴德买「销案」。

## 5. 自动编年史：本人行状

### 5.1 数据结构

```ts
interface KarmaEntry {
  seq: number;        // 单调递增，存档保留
  day: number;        // 游戏日
  hour: number;       // 0..23，由 phase 换算
  placeKey: string;   // POI/坊
  eventId: number;
  delta: number;      // 毫业
  tags: string[];     // W/V/B/O/G/T/U/X
  visibility: 'public' | 'rumor' | 'secret' | 'none';
  text: string;       // 模板渲染结果，存档存文本，不存模板参数
}
```

**存文本而不是存模板参数**，是一个刻意的选择：模板会随版本改，旧存档重放时如果模板变了，行状会跟着变；存文本则「历史不会被 later 的代码改写」。

### 5.2 文本生成：确定性模板，不调用模型

每类事件 3 个句式变体，按 `hash(eventId) % 3` 选，不用随机数——读档后同一事件必须是同一句话。

```
"{日}·{时}，{地}。{事}，{果}。"
例：初三·午时，州桥。见一童子落水，赴水救之，围观者七人。善业 +10。
例：初七·夜半，丰都鬼市。砸王记纸马招牌，为巡夜鬼差所录。恶业 −8，阴司已知。
```

「围观者七人」不是装饰：它把 `witness` 边数直接写进文本，玩家能从行状里读出「这件事有多少人看见」，从而推断流言会传多快。**行状不是日志，是可操作的情报。**

一段真实的行状长这样（同一局，五个游戏日）：

```
初九·辰时，州桥。见一童子落水，赴水救之，围观者八人。善业 +10，漕帮闻之。
初九·午时，虹桥。赏琵琶一曲，钱五文。善业 +0.5，歌者记之。
初十·夜半，丰都鬼市。与摊主争纸扎之价，推搡。恶业 −2，巡夜鬼差见之。
十一·申时，紫宸殿。禁军盘查，三闯。恶业 −5，海捕文书出。
十二·卯时，三生石。读前世，得「还恩」一判。
```

同一份行状有三种读法，缺一不可：

- **玩家读**：知道自己在哪一步把路走窄了（「三闯」之后才出通缉），而不是被系统突然惩罚。
- **验证者读**：每条都能对回 `eventId` 与 `witness` 边，能复算权重，不是文学创作。
- **设计者读**：能看出哪类事件在真实游玩里高频（如果十条里有六条是赌输赖账，说明赌坊的负业给重了）。

这也是为什么行状必须**同时存文本与结构化字段**：文本给人读，字段给机器核。

### 5.3 HUD 与图鉴的接线

- `world.objectiveProgress()` 返回值加 `karma: { deeds, merit, demerit }`；`#goalMain` 后缀渲染 `· 行状 23`。这是 DOM 文本，**不新增 draw call**（现有 HUD 已是 DOM overlay）。
- 图鉴面板（`src/ui/ui.ts` 的 `#codex`）新增第 4 个 tab「行状」，复用现有 `.panel`/`.tabs` 样式，不新建面板、不新建 canvas。
- 目标链每完成一个节点（`objective:done`），写一条 `place` 边 + 一条行状，文案取 `levelPlan.ts` 的 `objective` 原句。这样「目标链」和「行状」是同一件事的两种读法：前者是「还要去哪」，后者是「已经做过什么」。

### 5.4 与 `artifacts/` 记录体系的衔接

运行时的 Electron 打包版**不保证可写文件系统**，所以不能声称「游戏会把行状写进 artifacts」。正确做法分两层：

1. **运行时**：行状只在内存与 `localStorage`，面板可读。
2. **开发期**：`scripts/probe-karma.mjs --dump` 把 `window.__karma` 导出成 `artifacts/karma-run.json` 与 `artifacts/karma-run.md`，格式对齐仓库现有探针产物（`PASS/BLOCK` + 退出码 + 机位/种子）。这两份文件是**验收证据**，不是玩家存档。

导出的 Markdown 用仓库既有的「状态四档 + 证据」写法，便于和 `SPEC-总账.md` 并排阅读。

## 6. 性能与存档

### 6.1 规模上限（硬编码，不可配）

| 项 | 上限 | 依据 |
|---|---|---|
| 事件节点 | 5,000 | 环形缓冲；超出压缩为日汇总 |
| 总节点 | 5,412 | 300 人 + 12 势力 + 100 场所 + 5,000 事件（预算按 5,400 取整） |
| 边 | 50,000 | 人均出度 ≤ 32；事件目击 ≤ 16 |
| 单事件目击者 | 16 | §3.2 |
| 行状条目 | 1,000 | 超出折叠为「某月摘要」 |

### 6.2 查询复杂度

| 查询 | 复杂度 | 频率 |
|---|---|---|
| `attitude(a,b)` | O(32) | 每次交互 |
| `topK(a,3)` | O(32 log 3) | 每次判案/结局 |
| `priceMod(place)` | O(1)（缓存） | 每次开shop |
| `within(pos,r)` | O(候选)（4m 哈希） | 每次事件 |
| 衰减 tick | O(E)/0.25 日 | 105 秒一次 |
| 流言 tick | O(32)/秒 | 每秒 |

### 6.3 内存与载入

按 §1.4 的布局逐项算：

- 节点：5,400 × 48B ≈ **259KB**
- 边：50,000 × 24B ≈ **1.2MB**
- CSR：`off` 5,400×4B ≈ 21.6KB + `adj` 50,000×4B ≈ **200KB**
- 字符串驻留：5,400 × 约 24B ≈ **130KB**
- Map/索引开销按 ×2 计

合计约 **3.6MB**，硬上限写 **8MB**。对比：当前静态面 13.35M × 132B/面 ≈ **1.76GB** 几何缓冲（`SPEC-载入与渲染分级.md` §2.1 的 `FBuf` 口径），业缘图占 **0.2%**。这是「少而深」最直接的证据：**它买到的东西最多，占的地方最少。**

载入增量：读档 `JSON.parse` 400KB 约 3–6ms，重建 CSR 约 2ms，合计 **≤ 10ms**，即 **0.01s**，相对 12s 红线可忽略。

### 6.4 存档体积

只存「显著边」（|w| ≥ 5 毫业，即 0.5 业力点）：

- 显著边约 8,000 条 × 40B（JSON，短键）= **320KB**
- 行状 500 条 × 160B = **80KB**
- 节点表 + 聚合 = **约 40KB**

典型 **400KB**，最坏 **900KB**。`localStorage` 上限通常 5MB，占 8%–18%，安全。写入时机：`objective:done`、`coins:change`（去抖 5s）、`visibilitychange`。不每帧写——现有 `cq_coins` 是每次交易同步写，业缘不能沿用这个坏习惯。

格式带版本：`{v:1, seed, day, nodes:[…], edges:[[a,b,k,w,acc,t0,src],…], chron:[…]}`。`seed` 用于恢复 `karmaRng` 的流位置；读档后先重放 `day` 对应的衰减档数，再接受新事件。

### 6.5 读档与版本迁移

存档带 `v`。v1 只有 `{seed, day, edges, chron}`；未来加「坊级人口账」时升 v2。迁移规则：v1 的 `place` 边按 POI 前缀映射到坊，映射不到的进 `orphan` 桶，**不丢弃**。迁移必须幂等：同一份 v1 连续迁移两次，结果哈希相同，探针 `--case=migrate` 断言这一点。旧存档没有 `karma` 字段时视为空图，不阻断启动——现有 `localStorage` 三键的读取已经是「缺省即默认值」的写法（`interact.ts:31-33`），业缘沿用同一风格。**不写迁移脚本的存档系统，第二个版本就会坏**，这是本项目已经踩过的坑（原 `SPEC-总账.md` 被写成 21,501 字节全零、无备份）。

## 8. 风险与明确的「不做」

| 风险 | 概率 | 影响 | 处理 |
|---|---|---|---|
| 路人无身份导致「记得我」的承诺落空 | 高 | 高 | 宣传口径改为「势力/场所记得你」，不写「每个人记得你」 |
| 流言反号让玩家觉得「系统乱判」 | 中 | 中 | 行状里显示「传闻失真」，把机制暴露给玩家，而不是藏起来 |
| 存档膨胀到 900KB 后写卡顿 | 低 | 中 | 去抖 + 只在关键节点写；必要时降为二进制 |
| 与 V16 的五币耦合后出现刷业力套利 | 中 | 高 | 业力**不可兑换**（V16 §4.3 明文禁止），且每日净增上限 ±20 |
| 探针依赖随机流，复现不稳 | 中 | 高 | 独立 `karmaRng` + 固定 seed + 0.25 日批量衰减 |

把风险量化，避免「中/高」变成拍脑袋：

- **身份覆盖率**：300 / 4,500 = **6.7%**。这是本卷能承诺的上限，也是宣传口径必须写清的数字。
- **存档写入耗时**：900KB `JSON.stringify` + `localStorage.setItem` 在中端机上约 15–30ms，仍在 50ms 主线程预算内；若实测超 50ms，降级为「只写显著边 + 行状增量」。
- **流言 tick**：1 Hz × 32 条边 × 每条约 3 次邻居查询 ≈ 100 次操作/秒，可忽略；真正的成本在**首次建图**（读档重建 5 万条边的 CSR，约 2ms）。
- **最坏情况**：玩家在 1 小时内触发 5,000 条事件（几乎不可能，按现有 61 个交互点与 17 个目标节点，正常游玩约 200–600 条），此时环形缓冲开始压缩，行状折叠为日摘要。**压缩不是丢失，是降采样。**

**本卷明确不做**：

1. **不做「每个路人独立记忆」**——身份系统不存在，做了就是假实现。
2. **不做实时 LLM 生成行状**——打包版无网络、无模型，且不可复现；只做模板。
3. **不做全城 4,500 人的实时态度重算**——只算具名节点与场所聚合。
4. **不做跨存档的「世界记忆」**——存档是单机的，没有服务器。
