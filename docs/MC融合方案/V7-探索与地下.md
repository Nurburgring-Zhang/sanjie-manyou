## 0. 起手：五条不可绕过的事实

写方案之前先把地基钉死，否则后面每一条都会漂。

| # | 事实 | 来源（实读） | 对「洞穴/地下」的直接约束 |
|---|---|---|---|
| F1 | 地形是**高度场**，`TERRAIN_SIZE=62000`、`TERRAIN_SEG=300`，格距 `206.67m` | `src/world/terrain.ts:329` | 62km 见方只有 301×301 个顶点。一个 12m 宽的洞口只占 0.058 个网格单元——**地形网格物理上表达不了洞口** |
| F2 | 地形网格一次性烘焙成 Mesh，与建筑同批进 `Baker` 的 14 个材质组 | `src/city/bake.ts:4`（`BGroup` 联合类型） | 运行时不能在已合并的 BufferGeometry 上"挖洞"，只能整块重建 |
| F3 | 三界是**垂直分层**：人间 `y≈0`、天宫 `y≈2150`、地府 `y=-260` | `src/sky/heavenFrame.ts:11-19`、`src/sky/underworld.ts:10` | "无限世界"只可能横向；纵向是有限的、被三界钉死的 |
| F4 | 天宫换算唯一入口 `heavenPoint/heavenY`；`POIS` 的天宫点已全部改走它 | `src/sky/heavenFrame.ts:22-29`、`src/city/layout.ts:169-176` | 任何新天宫点位**必须**走 `heavenPoint`，否则重演"传送到殿前 130m 空中"的旧账 |
| F5 | 静态面 `13.35–15.09M`（已超标）、载入 `8.3–9.7s`（红线 12s） | `00-共享约束.md` §一 | 洞穴与遗迹的**总面数预算必须 ≤ 0.3M**，否则 12s 红线当场破 |

由 F1+F2 得出一条硬结论，它决定整卷的形状：

**洞穴不是"挖"出来的，是"另做一具几何、再用结构物把接缝盖住"。**

这不是偷懒，是唯一可行的做法。要把地形网格加密到能表达 12m 洞口（格距 ≤ 6m），顶点数会从 301×301=90,601 涨到 (62000/6)²≈1.07 亿——比现在整个项目的静态面数还大三个数量级。

## 1. 洞穴系统

### 1.1 噪声算法选型：两种形状，两套代价

洞穴的"形状语言"由噪声的**等值面拓扑**决定，不是由参数调出来的。本项目只能承担两族。

#### 方案 A：3D 值噪声 + Marching Cubes（"奶酪洞"）

数学形式：

```
f(p) = Σ_{i=0..2} 0.5^i · vnoise3(p · s · 2.1^i)
固体 ⟺ f(p) > t        t ∈ [0.52, 0.62]
```

`vnoise3` 可以直接扩用 `terrain.ts:11` 的 `hash2`——把它从二维 `hash2(ix,iz)` 扩成 `hash3(ix,iy,iz)`，三轴各乘一组互质常数再做 `Math.imul` 折叠，就能得到确定性、无外部依赖、可在 Node 里跑的三维值噪声。这一点很关键：项目已经有 `src/core/rng.ts` 的确定性 RNG 和 `hash2`，**不需要引入 simplex/perlin 第三方库**。

形状特征（这是选它的唯一理由）：**大空腔 + 短支洞**。等值面在阈值附近生成球状空腔，空腔之间靠细颈相连，连通性差、断面圆钝、没有长距离走廊。适合做"洞厅"，不适合做"迷宫"。

代价（可复算）：

| 项 | 算式 | 结果 |
|---|---|---|
| 体素采样数 | 512m×96m×512m 区域 @ 4m 体素 = 128×24×128 | 393,216 个 |
| 噪声开销 | 每样本 3 阶 × 8 次 hash3 ≈ 24 次整数运算 | ≈ 9.4M 次运算，JS 约 10–25ms/洞 |
| 表面体素数 | 经验占比 10–14% | ≈ 4.7 万 |
| 三角形数 | MC 每表面体素平均 2.2 个三角形 | ≈ 10.3 万 tris |
| 显存 | `VGeo` 通道 108 B/tri（pos+normal+color 各 3×f32，非索引） | ≈ **11.1 MB/洞** |

另外还要付 300–400 行 Marching Cubes 实现（256 项边表不可手写，必须生成）。

**结论：方案 A 只用于洞厅，且全项目只用 4 次（4 个洞厅），不用于主隧道。** 4×11.1MB=44MB 显存，仍然偏重，因此进一步降到 6m 体素（85×16×85=11.6 万体素，表面≈1.4 万，≈3.1 万 tris，3.3MB/洞厅），**4 个洞厅合计 13.2MB**。

#### 方案 B：脊线抽取 + 管体放样（"意面洞"）

不体素化。直接在噪声场里**追踪脊线**：

```
g(p) = |F2(p) - F1(p)|          // Worley 细胞噪声的前两近距离差
脊线 ⟺ g(p) < 0.08 且 ∇g·d < 0   // 沿细胞边界走
```

实现上取 24m 细胞、6m 步长做一次粗网格（512/6≈85³≈61 万采样，只算 2 次最近邻，≈8ms），把 `g < 0.08` 的格子串成折线，再用现成的 `VGeo.tube(spine, rw, rh, seg, hex)`（`src/sky/creatures.ts:327`）放样。**这是本项目的既有能力，龙的躯干、麒麟的颈、仙鹤的腿全走这一个函数**，不需要新写几何内核。

形状特征：**细长隧道网、分叉多、断面近圆、有长距离主巷**。这正好是洞穴该有的样子——玩家要的是"走着走着分岔了"，不是"走进一个球"。

代价（可复算）：

| 项 | 算式 | 结果 |
|---|---|---|
| 单条隧道 | 120m / 3m 一段 = 40 个脊点 × 8 边 = 320 quad | 640 tris + 16 端帽 |
| 每洞穴隧道数 | 40 条（含 8 条死巷、4 条环路） | 26,240 tris |
| 洞厅（A 方案 1 个，接在 B 的主巷末端） | 6m 体素 MC | ≈31,000 tris |
| 井口/井筒/收口 | `b.cyl` + `VGeo.tube` | ≈1,200 tris |
| **单洞穴系统合计** | | ≈58,400 tris，**6.3 MB** |

B 的另一个优势：**脊线是数据不是几何**。同一份脊线表可以同时喂给①几何放样②`caveGroundY(x,z)` 的可站面查询③小地图的洞穴平面图④生物生成点。A 方案做不到这一点——MC 出来的只有三角形，没有语义。

#### 选型结论

- **主隧道网：方案 B**（4 个洞穴系统 × 40 条隧道）
- **洞厅：方案 A，限 4 个**（每洞穴系统 1 个），6m 体素
- **不采用**：2D 域扭曲 + 垂直剖面（第三种常见做法）。理由是它只能生成"竖井 + 一层平巷"，与本项目已有的地府垂直分层在视觉上撞车——玩家分不清自己在洞穴还是在地府边缘。

总预算（这是 V7 最硬的一个数）：

```
4 洞穴 × 58,400 tris = 233,600 tris ≈ 0.23M
显存 = 233,600 × 108 B = 25.2 MB
占现有静态面 13.35M 的 1.75%
```

0.23M 是**可接受的**（1.75%），但必须锁死：一旦洞穴系统加到 6 个就破 0.35M，与 V11 的 chunk 预算抢额度。

### 1.2 与静态地形的接缝：三层遮蔽

问题本体：地形高度场网格没洞，井筒要穿过去，交线必然出现三角形穿插。

解法是**不试图消除穿插，而是用三层结构把它盖住**：

**第一层：井台裙边（collar）**
一圈 12 边石砌环，外径 14m、内径 11m、高 1.2m，走 `b.cyl('wall', 14, 14, 1.2, 12, x, y, z, 0x6f6656)` + 一圈压顶石。它压在地形上，地形网格自身的起伏（`terrainSurfaceY` 与 `terrainHeight` 的双线性差）由 1.2m 的竖直面吸收。

关键判据：**洞口点必须满足 `|terrainSurfaceY(x,z) − terrainHeight(x,z)| < 0.5`**。这个差是双线性插值 vs 解析函数的固有误差，206.67m 格距下坡度 0.35 时约 0.36m（`0.5 × 206.67 × 0.35 / 2`）。超过 0.5 说明选在了陡坡上，裙边会露缝——选址算法必须**先算这个差再决定要不要放洞**，不是放完再修。

**第二层：竖井（shaft）**
`VGeo.tube` 从 `terrainSurfaceY` 向下 40m，8 边，半径 11m→10.5m 微收。井壁单独一具几何、单独一个 Mesh，`side: THREE.BackSide`——玩家从井口往下看时看到的是井壁内表面，从洞内往上看也是。

**第三层：洞顶收口（dome）**
倒锥，把井筒底（半径 10.5m）与洞厅顶（半径 18m）之间的环形夹角封住。用 `VGeo` 的 `fan(apex, rim)`（`creatures.ts:426`）一次成形。

三层的顺序不能换：先裙边（压地形）→ 再井筒（垂直过渡）→ 后收口（水平过渡）。反过来做，收口会与地形三角形打架。

**为什么不改地形网格**：可以把洞口所在的那个 206.67m × 206.67m 网格单元挖空（把该格的 2 个三角形删掉）。技术上可行——`Baker` 的 `positionsOf()` 能拿到顶点数组——但删掉一个 206m 的格子意味着地面出现一个 206m 的大坑，必须用裙边补一整块地面几何（≈200 tris），而且这块的边界要与周围 4 个格子严丝合缝。**收益是"井筒不再与地形穿插"，代价是"每洞多一块 206m 的补地 + 边界对齐逻辑"**。本卷判断：不值。三层遮蔽的穿插藏在裙边内部，玩家看不见。

### 1.3 地面查询：新增 `caveGroundY`

现有地面查询链（`src/game/player.ts:300-345`）：

```
realmY（天宫/地府实化平面） > groundHeight() > terrainHeight()（城外）
```

洞穴必须插进这条链，且**不能污染 `walkSurfaceY`**。`walkSurfaceY`（`src/actors/behaviors.ts:137`）是 4m 空间哈希，专为城内建筑地坪设计，`WS_STEP_UP=0.95`、`WS_STEP_DOWN=1.05` 的语义是"台阶"；把 40m 深的竖井塞进去，`WS_STEP_DOWN` 会直接把玩家判定成"不可站立"。

正确做法是仿 `bridgeDeckYAt`（`layout.ts:133`）——**解析函数，不进哈希**：

```ts
// src/world/caves.ts（新增）
export function caveGroundY(x: number, z: number): number | null {
  // 1) 先判是否在某洞穴的竖向包围盒内（AABB，O(洞穴数)=4）
  // 2) 若在，沿该洞穴的脊线表做最近段投影，取管的半径 → y = 脊线.y − r·cos(θ)
  // 3) 洞厅：查预烘的 8m 高度图（64×64 f32 = 16KB/厅）
  // 4) 都不在 → null
}
```

调用点只有一处要改：`player.ts` 的 `groundHeight()` 里，在 `walkSurfaceY` 之前插一层 `caveGroundY`。**其余 4999 个角色一行不改**——因为 NPC 不下洞（见 §1.6 的生物/NPC 范围界定）。

### 1.4 光照与雾

**雾**：`scene.fog` 全局只有一份，切它是最便宜的方案。

| 状态 | `fog.color` | `fog.near` | `fog.far` |
|---|---|---|---|
| 人间白昼（现状） | 由 `world.ts` 氛围阈值写 | — | ≈3200（估算，待实测当前值） |
| 洞穴内 | `0x0a0c10` | 4 | 90 |

切换点不是"进洞/出洞"这一个布尔，而是**按 `caveGroundY` 是否命中做 0.4s 插值**——硬切会让玩家看到一帧全黑。代价：每帧改 3 个 uniform，`MeshStandardMaterial` 的 `fogNear/fogFar` 是 uniform 不是宏，**不触发 shader 重编译**。

**光照**：这是最容易踩坑的地方。

Three.js 的 `PointLight` 数量是 shader 宏（`NUM_POINT_LIGHTS`）。项目现在若有 N 盏点光，再加第 N+1 盏会让**所有** `MeshStandardMaterial` 重编译一遍——几千个材质实例、一次几秒的卡顿。所以铁律：

> **洞穴系统全局只允许 1 盏 PointLight（玩家手持灯），且它从世界初始化时就在场景里，只是 `intensity=0`。**

灯参数：`color 0xffc98a`、`distance 24`、`decay 1.6`、`intensity` 随"是否有火把"在 0 / 2.4 之间插值。灯挂在 `player.actor.pos` 上偏移 `(0, 1.6, 0)`。

**发光体一律走实例池，不走灯**：
- 矿脉微光 → `GLOW_MAT`（`pools.ts:120`，`toneMapped:false`）
- 鬼火/萤苔 → `GLOW_SOFT_MAT`（加法混合、`depthWrite:false`）
- 钟乳石滴水高光 → 顶点色里预乘一个亮值（`sh2(hex, 1.4)`）

**阴影**：洞内 `castShadow` 全部关闭。点光阴影是 6 面 cube map，成本是平行光的 6 倍；洞内本来就没有方向感，用顶点色烘焙的假 AO（`bake.ts` 的 `shade()` 语义：+y 提亮 1.1 / −y 压暗 0.78）就够。

### 1.5 载入：洞穴单元（CaveUnit），不是 chunk

本项目没有 chunk 流式（那是 V11 的事），洞穴也不需要——总量只有 4 个。

```ts
interface CaveUnit {
  id: string;
  mouth: THREE.Vector3;        // 井口世界坐标
  box: THREE.Box3;             // 竖向包围盒
  spine: P3[][];               // 40 条脊线（数据，非几何）
  hall: { cx: number; cz: number; h: Float32Array }; // 64×64 高度图
  built: boolean;
  group: THREE.Group | null;
}
```

触发：玩家 `x/z` 距 `mouth` < 60m 且 `!built` → 入队。队列**每帧最多建 1 个**——单个 58,400 tris 的构建约 25–60ms（估算，实测待验证），两三个同帧触发就会掉到 20fps 以下。

卸载：距 `mouth` > 220m → `group.visible = false`。**不 dispose**：重建一次 60ms，来回走一趟就卡两次；显存 6.3MB/洞 × 4 = 25.2MB 常驻是可接受的。

### 1.6 谁下洞：先把范围钉死

`crowd.ts` 的 `walkSurfaceY` 只覆盖城内建筑，NPC 不下洞。洞穴里的活物全部走 `CreatureSystem` 的 `BeastPool`（`creatures.ts:108`），不占 `MAX_HUMANS`。这条界线在 V8 会再强调一次——它是整个生物系统的成本前提。

### 1.7 洞内水体：阴河不是装饰

洞穴第三层（−140 ~ −180）必须有一条连续水面，理由有三，缺一不可：

1. **空间合理性**：一个 160m 深的洞穴系统没有地下水，玩家会立刻读出"这是搭出来的棚"。
2. **玩法**：水面是洞穴里唯一的**水平参照**。没有水面，玩家在洞里失去上下方向感（洞内已无天光、无远景、雾 90m）。
3. **叙事接口**：地府的"黄泉"在 −260，洞穴的阴河在 −170，两者相距 90m 岩层。设定上"阴河渗下去就是黄泉"，为 `abyssGate` 的存在提供地理依据。

实现上**不能复用** `waterAt()`（`terrain.ts:346`）——那是给河流湖泊用的解析函数，遍历 `RIVERS` 与 `LAKES` 的折线，每帧对每个角色调用成本不可接受。正确做法：

```ts
// src/world/caves.ts
export const CAVE_WATER_Y = -172;                  // 全局唯一水位
export function caveWaterAt(x: number, z: number): boolean {
  // 只查当前激活洞穴的 AABB + 该洞穴的水面多边形（8–12 顶点）
}
```

材质复用 `city/water.ts` 的既有水体材质，但**关闭反射**——`Reflector`（交付报告轮 9 加的水面倒影）是 512×512 的 render target，洞内再开一个等于多一整趟场景渲染。洞内的水只需要"暗 + 有反光条"，用 `MeshStandardMaterial` 的 `roughness 0.15` + 顶点色即可。

宽度上，阴河贯穿第三层的 3 条主巷，河宽 6–9m，水深视觉 1.2m。玩家可以涉水（`player.ts` 已有 `swim` 状态，`p.y = surface − 0.75`），但洞内水位固定在 −172，`swim` 的 `surface` 取 `CAVE_WATER_Y` 而不是 `-1.05`——**这是一处必须改的分支**，否则玩家在洞里游泳会瞬间被拉到 y≈−1.8，直接穿回地面。

## 2. 矿脉与遗迹：14 类可探索点

### 2.1 统一数据契约

```ts
// src/data/ruins.ts（新增）
export interface RuinPart { kit: string; n: number; at: [number, number, number] }  // kit 对应 worldAtomCatalog 的件号
export interface RuinDrop { item: string; price: number; cur: 'copper' | 'yinde' | 'peach' | 'none'; unique?: boolean }

export interface RuinSpec {
  id: string; name: string;
  host: 'city' | 'country' | 'under' | 'sky';
  ring: [number, number];       // 距城心水平环带（m）
  elev: [number, number];       // terrainHeight 窗口（m）
  slopeMax: number;             // 坡度上限（tan）
  maxCount: number;             // 全局数量上限
  noiseCh: number;              // 选址噪声通道（与地形 fbm 不同种子）
  box: [number, number, number];// 包围盒 w×h×d
  tris: number;                 // 单座面数预算
  parts: RuinPart[];
  drops: RuinDrop[];
  danger: 0 | 1 | 2 | 3 | 4 | 5;
  threat?: ThreatSpec;          // 复用 data/levelPlan.ts 的 ThreatSpec
}
```

选址是纯函数，可机检、可复现：

```
candidate(x,z) = ring 命中 ∧ elev 命中 ∧ slope(x,z) ≤ slopeMax ∧ hash2(x>>4, z>>4, noiseCh) > 0.62
```

`hash2` 直接复用 `terrain.ts:11`——**不新增噪声库**，且同一 seed 在任何机器上产出同一组坐标（这是 V10 存档/多人的前提）。

### 2.2 矿脉：先定义"可采的东西"是什么

遗迹是"地点"，矿脉是"资源"。两者共用一套选址，但**数据结构必须分开**——因为矿脉要能采、要能采空、要能被存档记住。

**矿脉不是方块，是节点。** 本项目没有体素（V2 会详细论证），"挖掉一块矿石、露出一个新面"在几何层不成立：`Baker` 出来的是一具合并好的 `BufferGeometry`，删三角形等于重建整块。所以矿脉只能抽象成三件东西：

```ts
// src/data/oreNodes.ts（新增）
export type OreKind = 'coal' | 'iron' | 'copper' | 'lead' | 'tin' | 'cinnabar' | 'jade' | 'gold' | 'silver' | 'sulfur';

export interface OreNode {
  id: string;                    // `${caveId}:${index}`，存档主键
  kind: OreKind;
  at: [number, number, number];  // 世界坐标（贴洞壁）
  n: [number, number, number];   // 法线：矿脉长在哪个面上
  layer: 0 | 1 | 2;              // 层位
  reserve: number;               // 剩余可采次数
```

五条分布规则，全部可执行、可机检：

1. **层位绑定**：`layer 0`（y −20 ~ −60）只出石炭；`layer 1`（−70 ~ −120）出铁/铜/铅/石炭；`layer 2`（−140 ~ −180）出锡/朱砂/玉/金/银/硫。这条规则让"越深越贵"成立，不需要额外的价值曲线。
2. **聚类而非均匀**：在脊线参数 `t ∈ [0,1]` 上按 `hash2(⌊t×64⌋, caveSeed + layer) > 0.78` 布点。平均每 8–10 个采样点出一簇，玩家体感是"走一段遇一窝"。
3. **贴壁**：节点位置 = 脊线点 + 法线 × (管半径 − 0.3)。**不允许放在洞心悬空**——那会让"矿脉"读成一盏吊灯。
4. **每洞穴 30 个节点**，4 个洞穴共 120 个。上限不是拍脑袋：120 个节点 × 每簇 8 个压扁球 × 每球 8×6 段 ≈ 12 tris = **11,520 tris**。
5. **采空不刷新**：`reserve` 归零即永久归零，几何换成"采空面"（一个凹坑 `b.frustum` + 4 片碎屑 `b.box`，约 40 tris），只换顶点色与一小块几何，不重建洞穴 Mesh。**这是确定性存档的前提**（V10），也是反刷矿的唯一可靠机制。

**这笔面数必须单列**：§7 表里的 233,600 是洞穴本体，矿脉簇的 11,520 是额外的。两者相加 245,120，A7 断言的 0.25M 预算**只剩 4,880 余量**。这不是保守估计，是刚好卡线——任何"再给矿脉加个发光粒子"的想法都会当场突破预算。

与 V4 的接口：V4 定义"矿石 → 锭 → 器物"的配方链，本卷只负责"矿石从哪来、有多少、采完怎样"。**两边绝不能各写一份矿种表**——`OreKind` 是唯一真相源，V4 的配方必须 `import` 它。

### 2.5 数量与成本的现实核对

全表上限合计 63 座。若全部按"20 单位"内部密度（`crowd.density`）缩放，实际生成约 63 × 0.85 ≈ 54 座。

- **选址计算**：54 次候选扫描 × 每类约 200 个候选点 = 10,800 次 `terrainHeight` 调用 ≈ 8ms（`terrainHeight` 内含 4 次 fbm，实测单次约 0.7µs）。可接受，但应在**载入期一次算完并存表**，不每帧算。
- **几何**：54 座 × 平均 3,000 tris = 162,000 tris，但按 LOD 只建最近 8 座 → 24,000 + 46×18 ≈ 24,800 tris。
- **内存**：24,800 × 132 B（Baker 通道含 UV）= 3.3 MB。

## 3. 三界互通

### 3.1 现状：只有一组门，且方向不对称

实读 `src/game/player.ts:428-431`：

```ts
export const PORTALS: PortalDef[] = [
  { x: 470, y: 0, z: 24, to: [0, -260, -130], label: '你穿过了「阴阳界」……' },
  { x: 0, y: -260, z: -124, to: [472, 0, 28], label: '你回到了阳间……' },
];
```

三个必须点破的事实：

1. **天宫根本没有传送门。** 去天宫只有 `World.teleport(key)`（`world.ts:1500`），它是 UI/图鉴用的——会 `setCamMode('fly')`、改机位、改 yaw/pitch。也就是说"上天宫"目前是**开发者调试通道**，不是玩家可理解的玩法。
2. **回程落点 `(472,0,28)` 与去程入口 `(470,0,24)` 相距 4.47m**，刚好大于判定半径 2.6m。这是一个**靠 1.87m 余量维持的不循环不变量**——任何人把入口挪 2m 就会产生无限传送环。这条必须写进注释和探针。
3. 判定是每帧 `Math.hypot(p.x-pt.x, p.z-pt.z) < 2.6 && |p.y-pt.y| < 4`，**没有冷却、没有条件、没有代价**。

### 3.2 门的设计：两组合法门 + 一条单向秘境

| id | 起点 | 终点 | 条件 | 代价 | 冷却 | 双向 |
|---|---|---|---|---|---|---|
| `heavenGate` | 泰山顶（`MOUNTAINS[0]` 峰顶，y 由 `terrainHeight` 定） | `POIS.nantianmen.pos` | 完成人间 3 个 `LEVEL_ORDER` 节点 + 持「度牒」 | 度牒 ×1（府衙 60 文，一次性物品） | 60s | 是（回程落泰山南麓，不是峰顶） |
| `yinYangGate` | 人间 `(470, 2, 24)` | 地府 `(0, −260, −130)` | 无 | 0 | 30s | 是（现状保留，补冷却） |
| `abyssGate` | 天宫「无底洞」（`heavenPoint(0, 206.12, -18)`） | 地府枉死城 `(0, −260, −250)` | 完成 `star9` + `shibayu` | **蟠桃 1** | 180s | **否（单向）** |

为什么第三条要单向、且代价是蟠桃：

- **设定**：三界在《西游记》体系里确实可以直通（孙悟空闹地府），完全禁止反而不合母题。
- **技术**：若做成双向，三个门构成零成本环，玩家可在 60s 内三次穿越，把冷却设计彻底作废。单向 + 高代价 + 180s 冷却，是唯一能在"允许直通"与"不能刷"之间同时成立的解。
- **经济**：蟠桃点是天宫币，来源只有蟠桃宴（`PEACH_GRANT`，`interact.ts:96`）。用天宫币支付"从天宫下地府"是方向正确的——玩家必须先在人间赚铜钱、上天宫换蟠桃、才能开这条捷径。

### 3.3 与 `POIS` 体系的兼容（五条铁律）

新增门 = 新增 POI key，必须同时满足：

1. **注册**：进 `POIS`（`city/layout.ts:158` 或 `world.ts` 的运行时注册段）。`World.teleport` 与 `respawnPlayerAt` 都按 key 查表，缺 key 静默失败。
2. **天宫坐标走 `heavenPoint`**：`abyssGate` 的落点写 `heavenPoint(0, 206.12, -18)`，绝不允许写裸世界坐标。历史账（`layout.ts:145-157`）就是裸坐标 ×2.2 漏乘导致传送落在 130m 空中。
3. **`CAM_OFF` 有偏移**：`World.CAM_OFF`（`world.ts:1489`）每加一个 key 就要给机位，否则默认 `[12,7,16]` 会扎进墙里。
4. **若作为 `LEVEL_PLAN.recover`**：`world.respawnPlayerAt` 只校验 key 存在，不校验 key 可站。必须在 `probe-heaven-pois.mjs` 的 `EXPECT` 表里加一行，做向下射线落脚判据。
5. **探针侧独立抄一份**：`probe-heaven-pois.mjs` 的 `EXPECT` 是**故意手抄**的（文件头注释写明"防止改了 layout 又改探针自证"）。新增门也照这个规矩办。

`abyssGate` 的具体改动面（这是最小的）：
- `layout.ts`：`POIS` 加 1 条（天宫，走 `heavenPoint`）
- `world.ts`：`CAM_OFF` 加 1 条；`POIS` 加 1 条（地府）
- `player.ts`：`PORTALS` 加 1 条（单向）
- `levelPlan.ts`：`LEVEL_ORDER` 不动——门不是关卡节点，不占 17 个进度名额

### 3.4 冷却与状态的实现细节

```ts
// player.ts
private portalCd: Record<string, number> = {};   // id → 到期时间戳（performance.now）
private portalLockUntil = 0;                     // 传送后 1.5s 内不检测任何门
```

三条纪律：

- **用 `performance.now()`，不用 `dt` 累加**。`dt` 在暂停/切标签页时会被 clamp，累加式冷却会永远走不完。
- **落地后 1.5s 全局锁**。`usePortal` 已经是 460ms 淡出 + `busyUntil = now + 1000`（`player.ts:385`）。若目的地 2.6m 内恰好有另一扇门，玩家会被连续弹两次——`portalLockUntil` 就是防这个。
- **冷却的 UI 必须可见**。`bus.emit('ui:toast', ...)` 已有；冷却中撞门要给"还需 X 秒"，否则玩家以为门坏了。

### 3.5 保留 `teleport()` 的理由

`World.teleport(key)` 不能删。理由：它做的是"整体移动机位 + 化身 + 朝向重算"（`world.ts:1500-1535`，含 `setCamMode('fly')` 后 yaw/pitch 重算的修 bug 注释），而 `usePortal` 只动 `actor.pos` 与相机跟随。两者语义不同：

- **门** = 玩法内的空间移动，有代价、有冷却、玩家可理解
- **`teleport()`** = 图鉴"点击飞至"、恢复点复活、探针定位

把它们合并成一套，会让图鉴传送也走淡出动画与冷却，反而更差。**保持两套，但在 `teleport()` 上补一条注释说明它不是门。**

## 4. 维度边界：垂直分层 vs 水平无限

### 4.1 现状的精确数字

| 界 | y 范围 | 横向范围 | 来源 |
|---|---|---|---|
| 人间 | `0` – `3800`（昆仑峰） | `±20000`（`player.ts` clamp） | `terrain.ts:41`（昆仑 h=3800） |
| 天宫 | `heavenY(196)=2131` – `heavenY(230)≈2206` | 缩放后 `±800` 量级（arena r=44×2.2=96.8；palace 台基世界 z≈136） | `heavenFrame.ts:22` |
| 地府 | `−260` | 十八狱环 r=60+20=80，丰都 120 | `underworld.ts:10` |

> **与任务书的一处口径差**：任务书写「地府在 `y≈−240`」，代码里 `UNDER = { y: -260 }`。两个数都对得上各自的对象——`−260` 是地府地坪，`−240` 量级对应的是**望乡台台面**（`POIS.wangxiang` 注册为 `UNDER.y + 18 = −242`，`world.ts:306`）。本卷一律用 `UNDER.y = -260` 作地府基准，因为几何、人群、`hellPlan` 全按它排队；`−242` 只是单个抬高的台。这一条写在这里，是为了防止后续有人按任务书的 −240 去改 `UNDER.y`——那一改会把十八狱环、丰都鬼城、阎罗殿全部抬 20m，与 `terrainHeight` 的城下伏笔脱开。

### 4.2 一个真实的空间矛盾：天宫低于昆仑

`MOUNTAINS`（`terrain.ts:41`）里昆仑 `h=3800`、天山 `h=3300`；而天宫台面在 2131–2206。

**也就是说：从昆仑山顶往下 1600m 就是天宫。** 这在设定上说不通——"万山之祖"怎么能俯视天庭。

三个方案：

| 方案 | 做法 | 面数 | 载入 | 风险 |
|---|---|---|---|---|
| A 接受并解释 | 不改坐标，用"昆仑高过天"的设定：昆仑是西王母道场，本就在天庭之上 | 0 | 0 | 无 |
| B 抬高天宫 | `HEAVEN_LIFT` 1935 → 4000 左右，使台面 ≈4200 | 0 | +0 | **8 处 `PLATFORMS`、全部 `heavenY` 调用、天空盒、雾 far、相机 near/far 全要改**；玩家从地面飞 4200m 才到天宫，`camera.far` 得重设，浮点精度在 4km 高度开始出现 z-fighting |
| C 压低昆仑 | `h` 3800 → 1800 | 0 | 0 | 破坏"万山之祖"的地貌气势；且 `buildMountainLife` 的雪线、冰川、栈道全按 h 归一，改 h 会连带整条山体生成链 |

**选 A。** 但必须把话说透：这个"接受"不是因为设定合理，而是因为**它不可见**。

- 昆仑在 `x=−27000, z=4000`；天宫在 `x∈[−800,800], z∈[−300,300]`
- 水平距离 ≈ 27km
- 雾 far ≈3200m（估算，待实测）

所以在任何相机位置，两者都不会同屏。矛盾只存在于**数据表**里，不存在于**画面**里。这是一次"用不可见性偿还几何债"的交换——代价 0，但必须在文档里留痕，防止未来有人做全局地图时突然发现。

### 4.3 垂直 vs 水平的取舍

| 维度 | 优势 | 代价 | 本项目选择 |
|---|---|---|---|
| **垂直分层**（现状） | 零流式成本；三界各自有明确边界；传送是瞬时的 | 横向只有 40km×40km；天宫只有 1.6km 宽；"探索"受限于手工内容量 | ✅ 天宫/地府/人间都走这条 |
| **水平无限**（MC 式 chunk） | 真正的"走不到头"；程序化内容成本低 | 需要 chunk 流式（V11）、LOD 分级、异步构建、存档记录 modified chunks；现有 `Baker` 是一次性烘焙，改造量等于重写渲染层 | ❌ 本卷不做，留给 V11 |

**地下是唯一"可以便宜地做大"的方向。** 理由：

- 洞穴的几何是独立单元（§1.5），不参与 `Baker` 的一次性合并
- 洞穴的"无限"是**向下**的，而向下不需要新地形，只需要新单元
- 玩家的移动速度（`effectiveSpeed`，步行约 1.6m/s、跑约 4m/s）在 40m 高的竖井里已经足够产生"深"的感觉

### 4.4 地下的垂直预算

```
人间地表       y = 0
洞穴第一层     y = −20  ~ −60     （废石炭井、浅层隧道）
洞穴第二层     y = −70  ~ −120    （主隧道网、洞厅）
洞穴第三层     y = −140 ~ −180    （最深，塔基地宫 / 阴河）
岩底封板       y = −200           （不透光底板，物理封死）
地府           y = −260
```

三层合计 160m 垂直空间，与地府之间留 60m 岩层。**这 60m 是硬隔离**：

- 从洞穴最深处向下射线，不会命中地府几何（地府最高构件在 −260+18=−242，与 −180 相距 62m）
- 视觉上，第三层底部是封闭的岩底，玩家看不到"下面还有世界"
- 若未来要打通（"地府入口在矿井底部"），只需在岩底开一个洞 + 加一条 `PORTALS`，不需要改结构

**为什么不做第四层**：−180 到 −242 只有 62m，做第四层会让岩层只剩 20m，`Baker` 的三角形在 20m 间距下必然穿插。三层是"能塞下且不打架"的上限。

## 5. 探索激励

### 5.1 地图揭示：只加三个字段

现状：小地图（`ui.ts`）显示 `POIS` + 主角实时点；`codexLog`（`world.ts:211`）记录 `{code, name, note}`。

新增：

```ts
// world.ts
discovered = new Set<string>();      // POI key / ruin id
private saveDiscovered(): void { localStorage.setItem('cq_discovered', JSON.stringify([...this.discovered])); }
```

三处接线：

1. `objectiveReached(key)`（`world.ts:1580`）成功时 `discovered.add(key)`
2. 遗迹首次进入包围盒时 `discovered.add('ruin:' + id)`
3. 小地图渲染时按 `discovered.has(k)` 决定是否画点

代价：0 几何、0 面数、3 个字段。收益：把"传送列表"变成"探索成果"，这是 MC 式探索最便宜的一层反馈。

### 5.2 成就：复用 `codexLog`，不新建系统

`codexLog` 已经是唯一真相源，且 Boss 胜利（`world.ts:638`）与关卡达成（`world.ts:1580`）都往里写。探索成就只需加前缀：

| code 前缀 | 含义 | 示例 |
|---|---|---|
| `node:` | 关卡节点达成 | `node:lingxiao` |
| `ruin:` | 遗迹首次探索 | `ruin:kiln:3` |
| `cave:` | 洞穴系统首次贯通 | `cave:coal-1` |
| `boss:` | Boss 击败 | `juling` |

查重一律用 `codexLog.some(e => e.code === X)`——这是项目已有的写法（`world.ts:1579`），照抄。

**"唯一掉落"的判定必须挂在这上面**：`drops` 里 `unique:true` 的项，在生成掉落表时先查 `codexLog`，已存在则替换成普通掉落。这样"刷唯一物品"在数据层就不成立，不需要额外做反作弊。

### 5.3 稀有资源与三币的衔接

三币单向律（`interact.ts:93-99` 已实现）：

```
铜钱 ──烧纸(burnpaper)──▶ 阴德        （单向，不可兑回）
蟠桃 ──赏赐(peachgrant)──▶ 铜钱 100    （单向，不可兑回）
```

这条律是**不能破的**。所以遗迹掉落的设计必须遵守一条铁律：

> **遗迹不掉币，只掉物；物只能在对应界的 NPC 处换成该界的币。**

| 掉落归属 | 例子 | 收购点 | 换得 |
|---|---|---|---|
| 人间物 | 陶俑、瓷片、弩机、陨铁 | 人间各商铺（`POINTS` 的 B 类 16 处） | 铜钱 |
| 地府物 | 判官笔、纸钱、生死簿残页 | 丰都鬼市（`POIS.fengdu`） | 阴德 |
| 天宫物 | 舍利函、玉简 | 瑶池（`PEACH_GRANT` 旁边） | 蟠桃点 |

这样做的**经济后果是可算的**：玩家要拿阴德，必须下地府；要拿蟠桃，必须上天宫；要拿铜钱，必须在人间。三界的"币"与"界"严格绑定，探索动机自然分层。

**唯一例外**：`舍利函`。它不可售，但可以在瑶池换 1 点蟠桃。这需要一个新动作 `sacred`（不复用 `peachgrant`，因为方向相反：`peachgrant` 是"蟠桃→铜钱"，`sacred` 是"物品→蟠桃"）。加一个 `GoodRow.act` 分支即可，`interact.ts` 的 `openShop` 已经按 `g.act` 分发。

### 5.4 激励的量化：每类遗迹给什么

| 层级 | 内容 | 数量 | 玩家成本 |
|---|---|---|---|
| 即时 | 普通矿/瓷片（8–30 文/件） | 每座 3–6 件 | 走到就能拿 |
| 短期 | 稀有物（60–200 文） | 每座 1–2 件 | 需要下到危险度 3+ 的遗迹 |
| 长期 | 唯一物（`unique:true`） | 全表 8 件 | 需要探索全部 14 类 |
| 元层 | 成就条目（`codexLog`） | 14 条 + 4 条洞穴 | 图鉴集齐 |

8 件唯一物：`tomb` 墓志拓片、`kiln` 窑变盏、`taoistRuin` 玉简、`yinYamen` 生死簿残页、`beacon` 戍卒简、`mortuary` 路引、`pagodaCrypt` 舍利函、`hangingCoffin` 崖墓帛画。

**为什么是 8 而不是 14**：有 6 类（`wreck`/`coalMine`/`riverShrine`/`paperRuin`/`meteor`/`saltWell`）的定位是"资源点"不是"叙事点"。给它们也塞唯一物，会让"唯一"贬值。8/14 是一个刻意的稀缺比例。

## 9. 本卷自认最弱的三处

1. **§1.1 的面数推算全部是估算，没有一次真跑。** 58,400 tris/洞穴是从"40 条 × 640 tris + 31,000 洞厅 + 1,200 井筒"加出来的，但 `VGeo.tube` 的实际段数/边数取决于脊线采样密度，真实值可能差 ±30%。A7 只能证明"不超 0.25M"，证明不了"这一版就是最优"。

2. **§4.2 的"不可见"结论依赖一个我没实测的雾距。** 3200m 是从 `world.ts` 氛围阈值的量级推的，没有跑 probe 读 `scene.fog.far` 的真实值。若实际 far 是 8000m，昆仑与天宫在极端机位下可能同屏，"接受矛盾"的方案就要重审。

3. **§2 的 14 类遗迹掉落价格没有与现有 61 个交互点做交叉校验。** 陶俑 80 文、窑变盏 200 文这些数是我按"比现有 B 类商铺高半档"定的，但 `interact.ts` 的初始铜钱是 500（`interact.ts:31`），若某类遗迹一次能刷出 400 文以上，会破坏前 30 分钟的节奏。这一条必须等 V4（采矿·冶炼·合成）的完整价格表出来后再校一次。
