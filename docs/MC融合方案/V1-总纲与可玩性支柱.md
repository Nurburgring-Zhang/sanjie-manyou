> 卷次 V1 / 12 ｜ 上游：`docs/MC融合方案/00-共享约束.md` ｜ 下游：V2（体素 × 烘焙）、V3（方块与材质）、V12（路线图与验收）

> 本卷只回答三个问题：**为什么融、融到什么程度、融进来的东西落在现有三界的哪一格**。所有结论必须落到具体文件、函数或数据结构；估算值一律标注「估算」，无法确认的一律写「待验证」。

## 0. 判据口径

本卷引用的数字分三类，写作时逐条标注：

| 类别 | 含义 | 本卷来源 |
|---|---|---|
| **实测** | 仓库代码注释或文档里记录的运行观测值 | `src/city/bake.ts`、`src/city/infill.ts`、`src/world.ts` 的注释台账 |
| **代码事实** | 从源码直接读出、不依赖运行的结构与常量 | 逐条给出 `文件:行号` |
| **估算** | 由代码事实外推，未实跑 | 标「估算」，并写出外推公式 |

三条不可违反的项目硬约束（来自共享约束，本卷全部方案都必须满足）：

1. **一个实例都不许删**——不能用删建筑、减密度来换性能。
2. **不许整体等比放大蒙混**——构件尺寸守真实，靠数量与跨度造巨大感。
3. **载入红线 12s**——当前基线 8.3–9.7s，可用余量约 2.3–3.7s。

这三条直接决定了 V1 的推荐档位：任何「把全城重做成体素」的方案都会同时违反第 1 条与第 3 条，因此只能在**局部**做加法。

## 1. 为什么融：现有作品的四个「零」

「融 MC」最容易滑向「给画面加方块滤镜」。本卷拒绝这个方向，理由不是审美，而是**它不产生任何新的玩家动作**。真正值得融的是 MC 的四条底层能力，而这四条在本项目里目前都恰好是零。

### 1.1 世界状态差分 = 0

`src/city/bake.ts:677` 的 `Baker` 只做三件事：累积顶点（`push`）、按材质组装配（`flush`，`bake.ts:1297`）、交给 `world.ts:710` 的 `compactStatic()` 按材质合并成 ≤48MB 批次。整条链路是**单向追加**的：

```
builder → Baker.buf[14 组] → flush() → city_<组>_<batch> → compactStatic() → 合并体
```

没有任何一步提供「按空间范围删除或替换几何」的入口。`compactStatic()` 跑完（`world.ts:821`）之后，原先按坊、按建筑分块的 Mesh 已经并成少数几个大 Mesh，连「哪一栋楼在哪一段顶点里」都不再可查。

后果是可量化的：**玩家对世界做出的持久改变，字节数为 0**。当前所有交互（`src/data/interactPoints.ts` 的 `POINTS`，61 个点）读写的都是角色状态与钱包，没有一条写入场景几何。

### 1.2 因果规则系统 = 0

现有物品体系是「价目表」而不是「配方图」。`interactPoints.ts` 的 `GoodRow` 结构是 `{name, price, act, say}`——四字段里没有输入项，也没有产出项。玩家能买，不能造。

MC 的合成表之所以是玩法而不是 UI，是因为它满足 `输出 = f(输入集合, 工作站)` 且**可被玩家穷举与记忆**。本项目要获得同等级的玩法，需要一张真实的配方 DAG，而不是给 61 个点各加一个「制作」按钮。

### 1.3 空间化资源分布 = 0

`src/world/terrain.ts:281` 的 `terrainHeight(x,z)` 是纯解析函数：城内 `|x|,|z| < 5200` 恒返回 0，城外是 fbm 噪声 + 山体场 + 河道下切 + 湖盆。它描述**形状**，不描述**内容**。

也就是说：地下没有矿，山里没有洞，河床没有砂。玩家走到任何一处，脚下的东西与十公里外完全相同。这不是美术问题，是「探索」支柱缺了物质基础。

### 1.4 自建结构 = 0（且有一个隐蔽的硬障碍）

`src/actors/behaviors.ts:137` 的 `walkSurfaceY(x, z, fromY)` 是角色站立的唯一真相源。它查的是一张 4m 网格空间哈希（`WS_CELL = 4`，`behaviors.ts:45`），表在 `ensureWalkSurface()` 里**构建期一次性写死**，数据来自 `beltRoomSpecs()`、`riverRoomSpecs()`、`STREET_HOUSE_SLOTS` 三张静态表。

这条比前三条更关键：**即使 V2 让玩家成功放置了方块，只要 `walkSurfaceY` 不认识它，玩家就站不上去**——造出来的东西是贴图，不是建筑。所以「建造」支柱的验收线不是「方块出现了」，而是「`walkSurfaceY` 在自建结构上返回了正确的面高」。

### 1.5 结论：融的是「可变性」，不是「方块」

四条零指向同一件事：本项目缺的是**玩家可持久改变世界状态**的能力。MC 值得搬的是它的**状态模型**（区块化的可写体素 + 确定性规则 + 空间化资源），而不是它的**外观模型**（1m 立方体 + 16×16 贴图）。

这也直接决定了第 5 节「不该搬什么」的判据：凡是**只改外观、不增加玩家动作**的机制，一律不搬。

## 2. 融合档位：轻 / 中 / 深

三档共用同一套度量口径，避免「感觉更丰富」这类无法比对的说法：

- **代码量**：新增 + 改动的 TypeScript 行数。外推基准：`src/city/bake.ts` 1,621 行、`src/city/infill.ts` 4,046 行、`src/world/terrain.ts` 1,978 行，全仓 78 个 `.ts` 共 82,842 行。
- **面数**：静态三角面增量。基线 13.35–15.09M（共享约束口径），其中 `WardInfill` 单独统计 10,589,198 面（`infill.ts:62` 注释台账）。
- **载入时间**：`world.init()` 的 35 个 task + 36 次 `flush` + 一次 `compactStatic` 的总耗时（task 数按 `world.ts` 的 tasks 数组实测 35 项；文件内旧注释写的「33 步」是历史测量值，已过时）。基线 8.3–9.7s。
- **可玩性收益**：用两个可数指标——**新增动词数**（玩家能对世界做的、此前做不到的动作种类）与**持久度**（重启进程后仍然存在的玩家改动，落在哪些子系统）。

### 2.1 轻档：装饰性体素沙盒（Voxel Decor）

| 项 | 数值 |
|---|---|
| 范围 | 3 块 32×32×16 的「试造场」，合计 49,152 体素 |
| 数据结构 | `Map<number, Uint16Array>`，键 = 沙盒 id，不做区块切分 |
| 代码量 | 新增约 1,500–2,200 行；改动 2 个文件（`world.ts` 加 1 个 task，`behaviors.ts` 加 1 个查询分支）**（估算）** |
| 面数 | +0.03–0.08M（按 3 块满铺 6 面外露计，单块上限 2×(32×32 + 32×16 + 32×16) = 4,096 quad = 8,192 tri）**（估算）** |
| 载入 | +0.05–0.15s（不新增贴图，复用 `createCityTextures()` 已有 9 张）**（估算，待实测）** |
| 新增动词 | +2（放置、破坏） |
| 持久度 | 仅方块层；**不进 `walkSurfaceY`**，玩家仍站不上自建结构 |

轻档的定位是**管线验证**，不是产品形态。它能证明「破坏→重建 Mesh→立即可见」这条链路通，但因为不接入行走面、不接入配方、不接入资源分布，它一个支柱都不完整。

### 2.2 中档：局部体素沙盒 + 烘焙背景（推荐）

| 项 | 数值 |
|---|---|
| 范围 | 5 个 64×64×48 沙盒，合计 983,040 体素；三界各布点（人间 3 / 天宫 1 / 地府 1） |
| 数据结构 | 16³ 区块，`Uint16Array(4096)` 调色板索引 + 每区块调色板；空区块不分配 |
| 代码量 | 新增约 5,000–7,500 行；改动 6 个文件（详见 §4）**（估算）** |
| 面数 | 实战 +0.20–0.60M；上限 +1.02M。单沙盒实心壳 = 20,480 quad = 40,960 tri（公式见 §2.4）；玩家薄壳按 20,000 块 × 3 面外露 = 60,000 quad = 120,000 tri/沙盒，5 个共 0.60M；上限按单沙盒 204,800 tri（实心壳的 5 倍，对应大量内隔墙）× 5 = 1.02M |
| 载入 | +0.3–0.9s（5 个沙盒的空区块 + 首次网格构建）**（估算，待实测）** |
| 新增动词 | +9（放置、破坏、采集、合成、熔炼、脚手架、承重校验、蓝图拓印、审判改写，逐条对应 §3.1–§3.6） |
| 持久度 | 方块层 + 行走面 + 配方产物 + 资源分布，四个子系统 |

中档的关键在于**烘焙世界一格代码都不改**：`compactStatic()` 仍然跑，`city_*` 仍然合并，体素网格走独立的 `vox_*` 前缀与独立材质实例。代价是**两套几何共存**，收益是现有画面零回归风险。

### 2.3 深档：全量体素化（Voxel Everything）

先算代价，再谈可行性。

城区外郭墙在 ±5000（`infill.ts:3330` 注释），即 10km × 10km。以 1m 体素、只算**地表一层**：

```
10,000 × 10,000 = 1e8 个地表体素
每个至少 1 个朝上可见面 = 1e8 quad = 2e8 tri
```

对比当前静态面 13.35–15.09M，**仅地面一层就是现有全场景的 13 倍**。再叠加建筑立面（当前 10.59M 面的 infill 全部要重建成方块），面数至少再翻一倍。

| 项 | 数值 |
|---|---|
| 代码量 | 25,000–40,000 行（等于重写 `infill.ts` + `architecture.ts` + `bake.ts` 三层）**（估算）** |
| 面数 | ≥ 2×10⁸ tri，超出当前 13 倍以上 |
| 载入 | 不可估——需要把 35 步烘焙管线整体换成流式体素生成 |
| 结论 | **否决**。同时违反「一个实例都不许删」与「12s 红线」两条硬约束 |

深档唯一有价值的部分是「统一数据模型便于破坏」，但为这一个收益付出 13 倍面数与全量重写，性价比不成立。

### 2.4 三档的文件级改动清单

前面的行数是总量，评审时需要能逐文件对账。下表按「改哪个文件、加多少行」拆开，行数为**估算**，外推基准是现有同职责模块：`bake.ts` 1,621 行承载 14 个材质组与 5 种图元，`infill.ts` 4,046 行承载 240 个坊的院落填充。体素子系统的职责大致等于「bake 的装配层 + infill 的填充层」，取其和的二分之一到三分之二。

| 文件 | 轻档 | 中档 | 深档 |
|---|---|---|---|
| `src/city/bake.ts` | 0 | +40（导出材质克隆入口，避免共用 `onBeforeCompile` 补丁） | 重写 |
| `src/city/infill.ts` | 0 | 0（完全不动） | 重写 |
| `src/world.ts` | +30（新增 1 个 task） | +180（task、LOD 注册、`compactStatic` 后置断言） | 重写 |
| `src/actors/behaviors.ts` | +15（加一条查询分支） | +90（接高度图，改动 `walkSurfaceY` 的候选面集合） | +90 |
| `src/game/physics.ts` | 0 | +60（挖掘力度到 `ImpactTier` 的映射表） | +60 |
| `src/core/engine.ts` | 0 | +25（输入绑定加一个动作） | +25 |
| 新建 `src/voxel/*` | ~1,400 | ~5,200 | ~30,000 |
| `tests/*.test.ts` | +300 | +900 | +4,000 |
| **合计** | **≈1,750** | **≈6,500** | **≈34,000** |

这张表暴露了一个反直觉的事实：**中档的 6,500 行里有 5,200 行在新建目录，现有文件只碰 395 行**。这正是中档风险可控的原因——回归面被压缩到 6 个文件的局部改动，而不是全仓铺开。深档相反，它必须先重写 `bake.ts` 与 `infill.ts` 两个共 5,667 行的核心文件，任何一处行为漂移都会同时影响三界。

再看面数的外推公式，避免「拍脑袋」：

```
单沙盒满铺实心壳面数 = 2×(64×64) + 2×(64×48) + 2×(48×64)
                    = 8,192 + 6,144 + 6,144
                    = 20,480 quad = 40,960 tri
5 个沙盒全满        = 204,800 tri
玩家薄壳建筑（每块平均 3 面外露）= 20,000 块 × 3 quad × 2 tri = 120,000 tri/沙盒
5 个沙盒实战区间    = 0.20M ~ 0.60M tri
```

上界 1.02M 不是「5 个沙盒各填一个实心壳」——那是 204,800 tri。它按**单沙盒 204,800 tri** 计，相当于在实心外壳之外再挖出四倍于外壳面积的内隔墙，即「每个沙盒都被建成一座内部全是房间的楼」。取这个上界，是因为验收断言必须按最坏情况立，不能按平均值立。

### 2.5 推荐：中档

**理由一：只有中档能让「建造」支柱成立。** 轻档的方块不进 `walkSurfaceY`，玩家造了站不上去；深档进得去但跑不动。中档把体素区注册为**额外的行走面来源**（在 `walkSurfaceY` 的候选面集合里加一路查询），这才让「自建结构可通行」这条验收线可过。

**理由二：中档把风险关在 5 个盒子里。** 体素区是离散的、有界的、可枚举的。任何性能或视觉回归都能通过「关掉某个沙盒」定位，不需要二分整个场景。深档一旦出问题，整个画面同时坏。

**理由三：中档的面数与载入增量落在余量内。** 面数上限 1.02M ≈ 基线的 6.8%；载入上限 0.9s，把 9.7s 推到 10.6s，仍在 12s 红线内留 1.4s 给后续卷。

**否决轻档的理由**：它证明不了任何支柱。一个只能放方块、站不上去、造不出东西、挖不到矿的系统，在验收表上四行全空。

## 3. 可玩性支柱 × 三界映射

MC 的玩法拆成六根支柱。本节逐条给出：**MC 原机制 → 人间 / 天宫 / 地府三格 → 现有接口 → 缺口 → 验收判据**。

先定三界的物理事实（全部来自代码）：

| 界 | y 基准 | 现状 |
|---|---|---|
| 人间 | `y ≈ 0`，城内地形恒 0（`terrain.ts:281`） | 外郭 ±5000，精细城区 ±660，里坊 920–4880 |
| 天宫 | `y ≈ 2150`（`HEAVEN_LIFT=1935`、`HEAVEN_SCALE=2.2`、基准面 196） | 几何以缩放前坐标烘焙，加载后由 `scaleHeavenGeometry` 就地改顶点 |
| 地府 | `y ≈ −260`（`UNDER.y`，`sky/underworld.ts:10`） | 丰都鬼城 + 十八狱环 + 奈何桥 + 望乡台 |

### 3.1 创造（Crafting）

MC 原机制：工作台 + 配方图 + 输入输出可穷举。

| 界 | 形态 | 现有接口 | 缺口 | 判据 |
|---|---|---|---|---|
| 人间 | **营造**：木作 / 砖作 / 彩画三工种，输入是原料，输出是构件 | `src/city/itemKit.ts`、`props.ts` 已有大量家具器物几何，但没有配方结构 | 缺 `Recipe` 数据结构与 DAG 求解 | 存在 ≥30 条配方，且每条可在 UI 里展开成输入清单 |
| 天宫 | **仙造**：步数更少、单步代价更高（2 步而非 4 步），产物可悬浮 | 无 | 缺「灵力」资源与悬浮放置判定 | 天宫配方平均步数 ≤ 人间的一半 |
| 地府 | **改判**：产出不是几何而是**数据**——改写生死簿条目，改变 NPC 的命运状态 | `src/actors/crowd.ts` 的角色状态、`jobs.ts` 的行为表 | 缺「可被改写」的状态字段 | 改写后 NPC 的行为权重在下一 tick 变化，且可回读 |

三界的创造差异必须落在**规则**上而不是皮肤上：人间多步、天宫少步高价、地府不产几何产状态。否则三界只是三套贴图。

### 3.2 生存（Survival）

MC 原机制：生命 / 饥饿 / 状态效果 / 昼夜 / 天气。

| 界 | 形态 | 现有接口 | 缺口 | 判据 |
|---|---|---|---|---|
| 人间 | **市井生存**：钱、饭、夜禁。吃饭是消费不是续命 | 61 个交互点里 E 类 18 个吃喝点已有价目与文案 | 无饥饿值；无夜禁规则 | 夜间进入特定区域触发盘查事件；饱食提供可量化的移动/采集增益 |
| 天宫 | **仙体**：不吃不睡，消耗「香火」；香火来自人间供奉 | 无 | 缺跨界的资源流 | 人间供奉行为使天宫资源池数值上升，可读 |
| 地府 | **魂力**：死亡不是失败，是把「阳寿」换成「阴德」 | `game/physics.ts` 的 `ImpactTier` 已有 `shatter` 档 | 缺死亡后的状态迁移 | 一次死亡产生一条可查询的阴德增量记录 |

生存支柱在三界必须**互斥**：人间会饿、天宫不饿、地府不在乎饿。三套同一套数值就是没做。

### 3.3 探索（Exploration）

MC 原机制：地形生成 / 洞穴 / 遗迹 / 生物群系 / 维度。

| 界 | 形态 | 现有接口 | 缺口 | 判据 |
|---|---|---|---|---|
| 人间 | 街巷 + 河道 + **地下**。地下是全新空间 | `terrainHeight` 只给地表；`riverGeom` 给河道 | 无洞穴系统、无地下空间 | 存在 ≥3 条可进入的地下通道，每条长度 ≥200m |
| 天宫 | 云海 + 星宿九府 + 悬浮岛链 | `sky/realm.ts:2212` 的 `buildStarPalaces`、`sky/expansion.ts` 的远景宫阙 | 岛链之间无路径 | 存在 ≥2 条可步行到达的岛链连接 |
| 地府 | 十八狱环 + 忘川 + 望乡台 | `sky/hells.ts`、`underworld.ts` | 十八狱当前是环形占位（`docs/PHASE2-PLAN.md` M1） | 每狱有独立装置与可交互点 |

探索的判据必须是**可达性**而不是「有内容」：一条 200m 的通道要能走通，不是贴图上有条缝。

### 3.4 建造（Building）

MC 原机制：放置 / 破坏 / 结构完整性（无）+ 红石。

| 界 | 形态 | 现有接口 | 缺口 | 判据 |
|---|---|---|---|---|
| 人间 | **宋式木构**：柱、梁、枋、椽有真实受力关系；建三层楼要验柱网 | `src/city/architecture.ts` 的 `dougongBand` 等构件函数 | 无结构判定 | 悬挑超过 N 格时拒绝放置并给出原因 |
| 天宫 | **云气承载**：无重力但有「云气」预算，超出则整片下沉 | `sky/realm.ts:36` 的 `platform()` | 无预算模型 | 超预算时可见下沉，且可撤销 |
| 地府 | **反向建造**：越建越窄——每加一堵墙，可通行宽度减一 | 无 | 缺「负向」规则 | 通道宽度降到阈值以下时触发封闭事件 |

三界的建造规则必须彼此**不可移植**：人间验受力、天宫验预算、地府验宽度。这是三界差异最容易被做成真玩法的地方。

### 3.5 战斗（Combat）

MC 原机制：近战 / 远程 / 护甲 / 附魔 / Boss。

| 界 | 形态 | 现有接口 | 缺口 | 判据 |
|---|---|---|---|---|
| 人间 | 市井斗殴，五档冲击 | `game/physics.ts:35` 的 `tierOf(force, profile)` 已返回 `none/stagger/knockdown/launch/shatter` | 无武器/护甲数值层 | 同一招式对 `fragile` 与普通目标产生不同 `ImpactTier` |
| 天宫 | Boss 战（巨灵神） | `src/game/boss.ts`、`data/boss.ts` 的 `recoverPoi='jiangtai'` | 无装备成长 | Boss 三阶段可复现，阶段切换有可读的 HP 阈值 |
| 地府 | **规则战**：打不死，只能「判」。胜负由证据而非伤害决定 | 无 | 全新系统 | 存在一场不依赖 HP 归零的胜负判定 |

战斗是本项目**已有最多基建**的支柱（`ImpactSystem` + Boss 导演 + 108 将动作），因此融合时应**优先复用**，只补数值层与装备层。

### 3.6 社交（Social）

MC 原机制：村民交易 / 繁殖 / 多人。

| 界 | 形态 | 现有接口 | 缺口 | 判据 |
|---|---|---|---|---|
| 人间 | 交易、雇佣、结义 | 61 个交互点、`crowd.ts` 1400 槽位、`jobs.ts` 行为表 | 无关系状态（好感/契约） | NPC 记住玩家上一次行为并改变报价 |
| 天宫 | 香火 / 供奉 / 神谕 | `sky/deities.ts`、`data/deities.ts` | 无供奉反馈 | 供奉累积到阈值触发一次神谕事件 |
| 地府 | 审判 / 轮回 / 因果 | 无 | 全新 | 存在一条从「人间行为」到「地府判决」的可查询因果链 |

社交支柱的判据统一为**记忆**：NPC 或系统是否记住了玩家上一次的行为。没有记忆的社交只是对话树。

### 3.7 支柱覆盖率小结

口径先说明：**完整度 = 该支柱下「已有实现且能挂 probe 断言」的判据条数 / 该支柱判据总数**。§3.1–§3.6 每根支柱 3 条判据，合计 18 条。下表是**自评**，不是实测——V12 会用 probe 结果逐条替换；在此之前任何下游卷引用这些百分比都必须保留「自评」标注。

| 支柱 | 现有基建 | 中档融合后完整度（自评） | 主要缺口 |
|---|---|---|---|
| 创造 | 低（只有几何库） | 60% | 配方 DAG |
| 生存 | 中（吃喝价目） | 55% | 状态数值 |
| 探索 | 中（三界地标） | 50% | 地下空间 |
| 建造 | **零** | 70%（中档主要收益） | 结构判定 |
| 战斗 | **高** | 80% | 装备层 |
| 社交 | 中（人群行为） | 45% | 关系记忆 |

中档把「建造」从 0 拉到 70%，是六根支柱里唯一从零起步的一根——这也是推荐中档的第四条理由。

### 3.8 支柱之间的耦合，以及为什么顺序不能反

六根支柱不是并列的六个功能模块，它们共享状态，因此有严格的实现顺序。顺序错了会出现「功能都在、但互相不可见」的空壳。

| 依赖 | 上游 → 下游 | 耦合的具体状态 | 顺序错时的症状 |
|---|---|---|---|
| 建造 → 创造 | 配方消耗的原料来自已放置的方块 | `VoxelStore` 的方块计数 | 配方系统只能凭空产出，等于商店 |
| 创造 → 探索 | 探索需要工具（镐、灯、绳） | `RecipeGraph` 的产物 id | 地下挖不动，只能看 |
| 探索 → 生存 | 生存压力的空间分布（夜禁区、瘴气区） | 区域标签表 | 全图一个难度，生存变成数值条 |
| 战斗 → 建造 | 破坏地形的能力来自武器力度 | `tierOf` 的输出 | 打不烂墙，战斗与建造两张皮 |
| 社交 → 存档 | 社交需要「记忆」，记忆需要持久化 | `VoxSave` + 角色状态表 | 对话树，NPC 每次见面都失忆 |

据此给出的硬顺序是：**V2 体素层 → V5 建造 → V4 创造 → V7 探索 → V6 生存 → V9 战斗 → V8 社交 → V10 多人**。

有一个反模式必须写下来：**先做社交**。它看起来最便宜（不需要几何、不需要物理、只需要对话），但没有记忆层的社交在验收时只能测「对话选项是否出现」，测不出「NPC 是否记得你」。而「记得」这件事的前提是状态持久化，也就是 V10 的存档契约。所以社交排在倒数第二，不是因为它难，是因为它的判据依赖链最长。

### 3.9 三界规则不可移植，是硬约束不是风格

如果三界共用一套生存数值、一套建造规则、一套战斗公式，那么三界就退化成三张地图。为了避免这一点，本卷给每条规则加一条**不可移植断言**：

| 规则 | 人间取值 | 天宫取值 | 地府取值 | 不可移植断言 |
|---|---|---|---|---|
| 饥饿 | 有，随 time 下降 | 无 | 无 | 天宫/地府的 `hunger` 字段恒为 `null` |
| 坠落伤害 | 有，按 `ImpactTier` 五档 | 无（云气托举） | 有，但落点是轮回井不是死亡 | 三界的 `onFall` 走三个不同函数 |
| 建造约束 | 柱网受力 | 云气预算 | 通道宽度 | 同一个放置请求在三界返回三种拒绝原因 |
| 死亡 | 掉钱、回城 | 跌境、掉香火 | 转生、清空阳寿 | 三条互不调用的死亡流程 |

这四条断言会在 V6/V5/V9 分别落成单测。它们的作用不是增加工作量，而是**防止后续卷偷偷把三界合并成一套**。

### 4.3 必改（这三处不改，融合不成立）

**改动一：`src/actors/behaviors.ts:137` `walkSurfaceY()`**

现状：查 4m 空间哈希 + 桥面解析函数，两条来源。必须加第三条：体素区查询。实现上不能每帧遍历体素，应在 `SandboxManager` 里维护每个沙盒的**顶面高度图**（64×64 的 `Float32Array`），破坏/放置时增量更新对应格。查询变成一次数组索引。

风险：`walkSurfaceY` 是 5000 人群每帧调用的热点（`behaviors.ts` 注释：5000 人 × 60fps）。加一条分支的成本必须实测，不能假设可忽略。

**改动二：`src/world.ts:821` 之后的加载序列**

现状：`await compactStatic()` 之后场景里只剩合并体。体素沙盒若在此之前创建，会被 `compactStatic` 的 `m.name.startsWith('city_')` 过滤掉（安全）；但若误命名为 `city_vox_*`，会被合并进烘焙批次，从此无法单独重建。必须在 `compactStatic` 之后创建，或用 `vox_` 前缀并加一条断言。

**改动三：`src/city/bake.ts:1468` 材质实例表**

现状：`materialSet()` 缓存在 `this.mats`，14 个材质全局唯一。体素网格如果复用同一批材质实例，会与烘焙体共享 `onBeforeCompile` 补丁（`plasterHook`、`roofFluteHook`、`roofEmissiveTint`），这些补丁按世界 Y 做着色带，用在方块上会产生不可预期的色带。必须为体素区克隆一份材质，或确认补丁对方块中性。

### 4.4 一次「破坏」的完整调用链

这是整卷最需要写实的部分：从鼠标按下到画面更新，中间经过哪些函数、哪些数据结构、哪一步可能卡。中档方案要求这条链上每一步都有明确的落点，否则实现时会出现「都写完了但接不上」。

```
① 输入        Engine.bindInput() 的 pointerdown（engine.ts，现有）
              新增动作 id 'vox.break'，不改现有键位
② 拾取        SandboxManager.pick(rayOrigin, rayDir)
              —— 只与 5 个沙盒的 AABB 求交，不用 THREE.Raycaster
③ 体素遍历    Amanatides-Woo DDA，步长 = BLOCK_SIZE(0.5m)
              最多 128 步，超时即返回 null（防止射线打穿全图）
④ 判定        命中体素 id → BlockRegistry.get(id)
              hardness 与工具 power 比较 → 复用 physics.ts:35 的 tierOf()
              none/stagger → 拒绝；knockdown 以上 → 破坏成功
⑤ 写状态      VoxelStore.set(wx, wy, wz, AIR)
              同时写一条差分到 VoxSave 的待提交队列
⑥ 脏标记      chunkDirty[ci] = true
              若命中的是区块边界体素，额外标记 6 邻区块（面剔除会变）
⑦ 重建        SandboxManager.flushDirty(4ms)
              取出脏区块 → ChunkMesher.build(chunk) → 写入该 (沙盒, 材质组) 的预分配缓冲
              用 BufferAttribute.addUpdateRange() 只上传改动段（A3 策略，详见 V2 §1.3）
              不走「每次 new BufferGeometry」——那条路 10,000 次操作后会泄漏上万个 geometry
⑧ 高度图      更新沙盒的 64×64 顶面高度图 heightmap[i]
⑨ 行走面      下一次 walkSurfaceY(x,z,fromY) 查询自动看到新面（无需重建整表）
⑩ 持久化      VoxSave 在离开沙盒或每 N 秒落盘一次（V10 定契约）
```

三个容易踩的坑，必须写在实现前：

**坑一：不要用 `THREE.Raycaster`。** `compactStatic()` 之后，场景里是少数几个上千万三角形的合并体，没有 BVH 加速结构。一次 `raycaster.intersectObjects(scene.children)` 会把 13.35–15.09M 面全测一遍，单次 10ms 量级，鼠标按住不放就是每秒 60 次。必须走体素 DDA，把复杂度压到 O(128)。

**坑二：区块边界必须标 6 邻。** 面剔除依赖邻居的实心/空。破坏 (15,y,z) 会让 (0,y,z) 那个区块的 -X 面从「被遮挡」变成「暴露」。只标本区块会留下一个洞——洞在下一帧不会自动补，因为没有任何东西再触发重建。

**坑三：`walkSurfaceY` 不能重建整表。** 现有 `ensureWalkSurface()` 是幂等的一次性构建（`if (WS_GRID) return`），重建意味着 5000 人的查询基础全部失效。正确做法是体素区单独走一张高度图，在 `walkSurfaceY` 里作为**第三个候选面来源**叠加，不碰 `WS_GRID`。

### 4.5 新建模块的接口契约

为了让 12 卷之间能并行，本卷先把中档需要的 5 个核心签名定死。签名一旦定下，V3（方块）、V4（合成）、V5（建造）可以各自实现而不互相阻塞。

```ts
// src/voxel/blocks.ts
export interface BlockDef {
  id: number;                 // 1..65535，0 = 空气
  name: string;
  group: BGroup;              // 复用 bake.ts 的 14 材质组
  color: number;              // 顶点色，与烘焙构件同一套调色
  hardness: number;           // 与 tool.power 比较，走 physics.tierOf
  drops: { id: number; n: number }[];
  solid: boolean;             // 是否参与面剔除与行走面
  realm: 'human' | 'heaven' | 'hell' | 'any';
}

// src/voxel/store.ts
export interface VoxelStore {
  get(wx: number, wy: number, wz: number): number;
  set(wx: number, wy: number, wz: number, id: number): void;
  chunk(cx: number, cy: number, cz: number): Uint16Array | null;
}

// src/voxel/mesher.ts
export interface ChunkMesher {
  build(store: VoxelStore, cx: number, cy: number, cz: number): THREE.BufferGeometry | null;
}

// src/voxel/sandbox.ts
export interface Sandbox {
  id: string;
  realm: 'human' | 'heaven' | 'hell';
  origin: [number, number, number];   // 世界坐标
  size: [number, number, number];     // 体素数
  heightAt(lx: number, lz: number): number | null;  // 局部坐标 → 顶面世界 y
}

// src/voxel/save.ts
export interface VoxSave {
  append(op: { x: number; y: number; z: number; id: number }): void;
  flush(): Promise<void>;
}
```

两条契约要点：

1. **`BlockDef.group` 必须是 `BGroup` 的成员**，不能是自由字符串。这样 V3 新增方块时，编译器会强制它落到 14 个材质组之一，从源头杜绝「每个方块一套材质」导致 draw call 爆炸。
2. **`Sandbox.heightAt` 返回世界 y，不是局部 y。** 天宫沙盒的 `origin` 是 `heavenPoint()` 算出来的世界坐标，如果这里返回局部值，`walkSurfaceY` 会在 2150m 的高空返回 0，角色直接掉进人间。这条是 V2 种子/坐标契约的一部分。

## 5. 明确不该搬的 MC 机制

每条给出**理由**与**替代方案**。判据统一为：搬进来是否增加玩家动作；若只增加视觉相似度，则不搬。

### 5.1 无限世界

**不搬。** 三条硬冲突：

1. 本项目的核心构图是《清明上河图》的**有限长卷**：外郭 ±5000、精细城区 ±660、里坊 920–4880（`infill.ts:3330`）。无限世界会让「画卷」这个母题失效。
2. 技术上是负资产：`terrain.ts:329` 的地形是单张 62,000m 见方、300 段的 `PlaneGeometry`；相机 `far = 52000`（`engine.ts:488`）；雾是 `FogExp2(0x3a3050, 0.0018)`。无限地形需要重做这三样，收益为零。
3. 违反「一个实例都不许删」的对称约束——无限世界意味着要么程序化生成无限内容（成本无上限），要么重复利用有限素材（玩家一眼看穿）。

**替代**：有限三界 + 局部体素沙盒。玩家要的是「我能改变这里」，不是「这里没有尽头」。

### 5.2 纯方块美术

**不搬。** 现有美术资产的核心恰恰是方块做不出来的东西：

- `bake.ts:273` 的 `buildCurvedUnit()` 生成举折曲面屋面；`infill.ts:1120` 注释记录近档正房 86 面（4 列 × 3 环举折 + 方脊 + 封头 + 檐口板）。方块化后这 86 面会退化成 6 面盒子，屋顶的「反宇」曲线全部消失。
- 14 个材质组里 `roof` 用 `DoubleSide` + 法线贴图 + AO 贴图（`bake.ts:1474`），方块的单面贴图无法承载。
- 用户硬指令「构件尺寸守真实」与 1m 体素直接冲突：宋式斗拱的构件尺寸在 0.1–0.3m 量级。

**替代**：体素只用在**玩家新建**的部分，且方块边长取 0.5m（半米砖），既能对齐宋式砖材，又不至于让自建物看起来像另一个游戏。

### 5.3 红石电路

**不搬。** 两个理由：

1. **世界观冲突**：本项目是北宋汴京 + 赛博霓虹，没有电学基础。红石粉、中继器、活塞在宋代市井里无处安放。
2. **工程成本**：红石需要一套 20Hz 的确定性 tick 调度器，与现有 `Engine.step(dt)` 的变步长渲染循环（`engine.ts` 的 `dt = Math.min(0.1, ...)`）不兼容。新建一套定步长模拟层的成本，与 V2 的体素层相当，但收益只在少数玩家。

**替代**：V5 会给出「机关」等价物——水碓、齿轮、绳索、配重，用宋代的机械语汇实现同样的「输入→延时→输出」逻辑，且天然贴合世界观。

### 5.4 饥饿条

**不搬。** 理由：与现有经济系统重复且基调冲突。`interactPoints.ts` 已有 18 个吃喝点、完整价目（点茶 2 文、羊羔酒 15 文、席面 80 文）。再叠一条饥饿条，等于用两套系统管同一件事，且「饿死」与「画中漫游」的体验基调相反。

**替代**：饱食作为**增益**而非**惩罚**——吃过东西后一段时间内采集速度 +X%、NPC 态度 +Y。数值待 V6 定。

### 5.5 下界 / 末地维度

**不搬。** 本项目已有三界，且三界的垂直带已被占满：天宫 2150、人间 0、地府 −260。再加维度只会稀释现有的三界叙事，且每个维度都要一套独立的生成规则。

### 5.6 无限垂直高度

**不搬。** 建筑高度上限受 `camera.far`、阴影相机（`world.ts:858`，`near=10 / far=760`）、雾密度三重约束。现有天宫已在 y=2150，再往上没有内容承载。

### 5.7 村民交易 GUI

**不搬。** `interactPoints.ts` 的 61 个点已经覆盖吃喝/赌/戏/歌/买/骑/船七类，且带宋代物价考据。MC 的绿宝石经济是另一套货币体系，接进来会与现有三币（铜钱/阴德/蟠桃点）打架。

### 5.8 多人服务器

**暂不搬，移交 V10。** 理由不是不需要，而是**确定性前提未成立**：多人 lockstep 要求「同种子同世界」，而当前 `world.init()` 的 35 个 task 共享一个 `RNG(20260905)` 实例，消耗顺序与调用顺序强耦合（`world.ts:324` 注释明确「拆分只按调用点切，共享 rng 消耗顺序逐字不变」）。在 V2 把体素世界的种子契约独立出来之前，谈多人没有意义。

### 5.9 不搬清单总表

| # | MC 机制 | 判决 | 一句话理由 | 替代 |
|---|---|---|---|---|
| 1 | 无限世界 | 硬否决 | 与有限长卷母题冲突，且需重做地形/相机/雾三层 | 有限三界 + 局部沙盒 |
| 2 | 纯方块美术 | 硬否决 | 举折曲面屋面（86 面/栋）与 14 材质组无法承载 | 仅玩家新建部分用 0.5m 方块 |
| 3 | 红石电路 | 硬否决 | 无电学世界观 + 需新建 20Hz tick 层 | V5 的机关（水碓/齿轮/配重） |
| 4 | 饥饿条 | 硬否决 | 与 18 个吃喝点重复，且与漫游基调相反 | 饱食作为增益 |
| 5 | 下界/末地 | 不搬 | 三界已占满垂直带（2150 / 0 / −260） | 无 |
| 6 | 无限垂直高度 | 不搬 | 受 `camera.far=52000`、阴影 `far=760`、雾密度三重限制 | 无 |
| 7 | 村民交易 GUI | 不搬 | 61 个交互点 + 三币已覆盖，再叠一套会打架 | 复用 `openShop` |
| 8 | 多人服务器 | 延后至 V10 | 确定性前提未成立：全局 `RNG` 单序列强耦合调用顺序 | V2 先立种子契约 |

判据统一：**搬进来是否增加玩家动作**。第 1–4 条连「增加动作」都做不到却要付出架构级代价，所以是硬否决；第 5–7 条只是没必要；第 8 条是顺序问题，不是价值问题。

## 6. 本卷结论与移交

**结论一**：融合的目标是补「玩家可持久改变世界状态」这一条能力，不是换美术风格。判据是新增动词数与持久度，不是画面像不像 MC。

**结论二**：推荐**中档（局部体素沙盒 + 烘焙背景）**。5 个 64×64×48 沙盒、16³ 区块、`vox_` 命名空间、独立材质实例。估算增量：代码 5,000–7,500 行、面数 +0.2–1.0M、载入 +0.3–0.9s。

**结论三**：三处必改——`behaviors.ts` 的 `walkSurfaceY` 要加体素来源；`world.ts` 的加载顺序要保证体素在 `compactStatic` 之后；`bake.ts` 的材质实例要为体素区克隆。

**结论四**：八条 MC 机制不搬，其中「无限世界」「纯方块美术」「红石」「饥饿条」四条是硬否决，其余四条是延后或替换。

**移交给 V2 的三个待解问题**：

1. 体素与烘焙的**所有权边界**怎么划——一个 64×64×48 的沙盒落在已有建筑内部时，谁让位？
2. 破坏后的**增量重建粒度**——按 16³ 区块重建，还是按沙盒整体重建？draw call 怎么算？
3. **种子契约**——体素世界的确定性怎么与现有 `RNG(20260905)` 的单序列解耦，而又不破坏「逐值可复现」？

这三个问题在 V2 逐条给出方案与代价。

### 6.1 风险登记

| 风险 | 触发信号（可观测） | 影响 | 缓解 |
|---|---|---|---|
| 体素区与既有建筑穿模 | 沙盒 AABB 与 `walkSurfaceY` 矩形表重叠 | 玩家在墙里放方块 | 沙盒选址前跑一次 `w9OverlapProbe`（`infill.ts:729`）风格的 AABB 检查 |
| 材质补丁污染 | 方块颜色在世界 Y 方向出现非预期色带 | 观感断裂 | 体素专用材质克隆，禁用 `plasterHook` / `roofFluteHook` |
| `walkSurfaceY` 变慢 | 人群帧耗时上升 | 5000 人同时卡 | 体素查询走数组索引而非遍历；先用 `probe-walksurface.mjs` 立基线再改 |
| 载入超红线 | `__flushMs` + 各 task 自报之和 > 11s | 无法发布 | 沙盒区块空载时零分配，只在首次进入时生成 |
| 天宫坐标漂移 | 体素顶点被 `scaleHeavenGeometry` 二次缩放 | 仙宫方块变形 | 命名必须 `vox_` 前缀，并加一条「场景中不存在 `city_vox*`」的断言 |
| 存档膨胀 | 差分条目数随游玩线性增长 | 启动变慢 | 按区块压缩（RLE）+ 上限截断，V10 定 |

这六条里，**只有「材质补丁污染」和「天宫坐标漂移」是本卷新引入的风险**，其余四条在现有系统里已经存在，融合只是放大了它们。把它们列出来，是为了让 V12 的验收矩阵能逐条挂上 probe，而不是等到出问题再回头找。

### 6.2 本卷自检

| 检查项 | 结论 |
|---|---|
| 是否给出 ≥3 种融合档位 | 是，轻/中/深，各带代码量/面数/载入/收益四列 |
