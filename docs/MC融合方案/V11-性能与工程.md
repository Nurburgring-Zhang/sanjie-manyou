### 11.1.2 静态面：13.35M 与 15.09M 是两条记录，不是一个区间

- **13.35M**：`release-v83` 打包态 `probe-load` 实测 `tris=13,353k`，口径是 `world.assetAudit.groups` 逐组三角面之和（见 `scripts/probe-mem.mjs` 头注第 3 条：「静态面：`world.assetAudit` 逐组三角面 + detail 台账；`renderer.info` 只作旁证」）。分组为 roof 4,171k（31%）、wood 3,425k（26%）、ash 1,328k（10%）、leaf 1,248k（9%）、其余 ≈3,181k（24%）。
- **15.09M**：`SPEC-总账.md` 第 844 行，「人间七项」轮记录「三角面 14.32M → **15.09M（+771k，预算 +800k 内）**」。该行**没有绑定 release 号**，也没有说明是实测还是 `w9TriEstimate()` 估算。

### 11.1.6 `renderer.info` 口径 ≠ 静态几何合计：差的是实例与 pass

这是全卷最重要的一条口径纪律。

- `probe-mem.mjs` 的 `staticTris` = `assetAudit.groups[*].triangles` 之和 = **13,353k**。它数的是 **Baker 烘出来的唯一几何**。
- `verify-packaged.mjs` 的 `triangles` = `renderer.info.render.triangles`，是**某一帧实际提交的三角形**。它包含：① 视锥内可见的那部分烘焙几何；② `InstancedMesh` 的**实例展开**（infill 台账 10.59M 就在这里）；③ **阴影 pass 的重复提交**（`castShadow` 的 9 个材质组会再画一遍）。
- `SPEC-载入与渲染分级.md:55` 记录的「**4500–4700 万/帧**」就是后者。

用 13.35M + 10.59M = 23.94M 唯一几何，乘 2 个 pass ≈ **47.9M**，与 45–47M 同量级。这解释了口径差，但**具体分解（哪些组进阴影、可见比例多少）仍是估算，标「待验证」**。工程结论只有一句：**13.35M 不是「每帧画 13.35M」，不能用它反推 GPU 压力；也不能用 45M 去反推内容量。**

### 11.1.7 内存有三个口径，混用就会得出相反结论

| 口径 | 定义 | 记录值 | 对 ≤1.5GB 的判定 |
|---|---|---|---|
| `heapEnd` | 载入结束时的 `usedJSHeapSize` | **1,826 / 1,863 / 1,861MB**（v83 三次） | 🔴 超 22% |
| 常驻堆 | 合批结束、GC 后的稳定值 | **1,374–1,394MB**（v84） | ✅ 达标 |
| 真峰值 | 载入期 40ms 采样序列的最大值 | **2,304–2,622MB**（v84） | 🔴 超 54–75% |

`SPEC-总账.md:375` 已经认过一次错：前几轮拿 `heapEnd` 当「峰值」，那个数从来不是峰值。V11 统一用**真峰值**做预算，`heapEnd` 只用于「驻留是否回归」的对比。

真峰值的来源也能量化：`attr ≈1,211MB`，合批期「源几何 + 合并结果」两份同时驻留 ⇒ 峰值 ≈2× attr ≈2.4GB（`SPEC-总账.md:617`）。`release-v84` 改成增量合并 + `transfer(0)` 同步归还后，`pre 1,674MB → post 1,670MB`（改前是 `1,541 → 2,261MB`，单步 +720MB）。**这条因果链是闭合的，可以作为体素内存预算的模板。**

## 11.2 体素化后的预算重算

### 11.2.1 单位与顶点格式：先把「一个面多少钱」定死

一个体素方块 = **1m³**（与 MC 同尺度，也与本项目「构件尺寸守真实」的硬指令一致）。

一个暴露面 = 1 个四边形 = 2 个三角形。当前烘焙管线是**非索引**、每顶点 28B（pos f32×3 = 12B，normal i16×3 = 6B，color u16×3 = 6B），UV 组再加 8B：

- **P0 现有管线**：6 顶点/面 × 28B = **168B/面**（带 UV 的 10 个组 216B/面）。
- **P1 体素优化管线**：索引四边形，pos 12B + normal i8×3 = 3B + uv u16×2 = 4B + AO 1B → 20B/顶点；4 顶点 = 80B，6 个 u16 索引 = 12B ⇒ **92B/面**。
- **P2 greedy 合并**：单面字节同 P1，但**面数**下降。收益全部来自面数，不来自格式。

后文所有表按 **P1 = 92B/面** 计；与 P0 对比时另注。

把 92B 拆开看，每一档降精度都要有理由，不能「看起来更省」就降：

- **位置必须 float32**。世界坐标是 ±16km，1m 体素的角点在 16km 处若用 float16，分辨率约 16m，整块会抖成马赛克。这一项 12B 不能动。
- **法线可以 i8×3**。体素面只有 6 个朝向（±X/±Y/±Z），i8 的 256 档里只需要 6 个值，浪费但便宜；若做 6 向打包，1B 就够，第一版不优化。
- **UV 用 u16×2**。图集是 64×64 一格、每格 16 像素边距，u16 的 65536 档远超需要；4B 足够。
- **AO 1B**。体素环境光遮蔽只有 0–3 四档，1B 里只用了 2 bit，但拆位打包会让 mesher 复杂度翻倍，第一版不做。

对比 P0：同样 100 万面，P0 是 **168MB**，P1 是 **92MB**，省 **76MB（45%）**。这 76MB 是「改格式」白送的，不损失任何观感；而把体素数据从 1B/块压到 0.125B/块，100 万块只省 **0.9MB**。两者的性价比差 84 倍。**所以优化顺序必须是：先定格式，再谈压缩；先砍面数，再砍字节。**

### 11.2.2 每新增一种可破坏方块，增量落在哪

「新增一种方块」不等于「新增一个面」，它加的是五样东西：

| 增量项 | 走图集/纹理数组 | 走独立材质 | 说明 |
|---|---|---|---|
| 纹理 | 64×64 RGBA = **16KB**，含 mip ≈21KB | 同左，但每材质一份 | 32 种 ≈ **0.5–0.7MB** |
| 顶点属性 | 0（UV 选层）或 +1B/顶点（`blockId`） | 0 | 若用 `blockId` 分支着色，+6B/面 |
| draw call | **0**（同材质同图集） | **+1/可见 chunk/类型** | 32 种 × 64 chunk = **2048 calls**，灾难 |
| 着色器 | 1 个采样分支或纹理数组层索引 | 每类型一个 program | 独立材质还会打断合批 |
| 行为元数据 | ≈32B/类型（硬度、掉落、可燃） | 同左 | 可忽略 |

**结论：材质必须走单一图集或 `DataArrayTexture`。** 一旦允许「一种方块一个材质」，draw call 会从 +0 变成 +2048，这不是优化问题，是方案是否成立的问题。纹理成本（0.5–0.7MB / 32 种）在 1.2GB 的几何属性面前是噪声。

P1 格式下，每新增一种方块对**面数**的增量为 0——面数只由「这种方块被放置了多少、暴露了多少面」决定。

### 11.2.3 第一档：1 万个可破坏方块

假设沙盒是一组建筑薄壳（墙、楼板、屋面），不是 1 万个互相孤立的方块。

| 项 | 最坏（全孤立） | 典型（薄壳，2.2 面/块） | greedy 后（0.9 面/块） |
|---|---|---|---|
| 方块数 | 10,000 | 10,000 | 10,000 |
| 暴露面（quad） | 60,000 | 22,000 | 9,000 |
| 三角面 | 120,000 | 44,000 | 18,000 |
| 顶点数（4/面） | 240,000 | 88,000 | 36,000 |
| 网格字节 @92B/面 | **5.52MB** | **2.02MB** | **0.83MB** |
| 体素数据 8bit | 9.8KB | 9.8KB | 9.8KB |
| 体素数据 4bit | 4.9KB | 4.9KB | 4.9KB |
| 体素数据 RLE | ≈2–6KB | ≈2–6KB | ≈2–6KB |
| chunk 头（16³，约 8 个） | ≈2KB | ≈2KB | ≈2KB |
| **合计内存** | **≈5.6MB** | **≈2.1MB** | **≈0.9MB** |
| 占 13.35M 静态面 | +0.90% | +0.33% | +0.13% |
| draw call（64³ 渲染块） | +1 | +1 | +1 |

**1 万方块在任何一项预算里都不是问题**：面数增量 <1%，内存 <6MB，draw call +1，载入期 meshing 约 5–15ms（按 1–3M voxel/s 的保守吞吐）。它是「可以立刻做」的量级。

### 11.2.4 第二档：100 万个可破坏方块

关键不在「100 万」这个数，在**拓扑**：100 万个实心堆叠和 100 万个地表薄壳，面数差 20 倍。

| 项 | 实心 100³ | 地表薄壳（1km²、1 层） | 最坏（全孤立） |
|---|---|---|---|
| 方块数 | 1,000,000 | 1,000,000 | 1,000,000 |
| 暴露面（quad） | **60,000** | **1,300,000** | **6,000,000** |
| 三角面 | 120,000 | 2,600,000 | 12,000,000 |
| 网格字节 @92B/面 | **5.52MB** | **119.6MB** | **552MB** |
| 体素数据 8bit | 0.95MB | 0.95MB | 0.95MB |
| 体素数据 4bit | 0.48MB | 0.48MB | 0.48MB |
| 体素数据 RLE | ≈0.02MB（整块同质） | ≈0.24MB（0.25B/块） | ≈0.5MB |
| **合计内存** | **≈6.5MB** | **≈120.6MB** | **≈553MB** |
| 占 13.35M 静态面 | +0.90% | **+19.5%** | **+89.9%** |
| 16³ chunk 数 | 245 | 245 | 245 |
| draw call（每 chunk 1 次） | +245 | +245 | +245 |
| draw call（64³ 渲染块） | +4 | +4 | +4 |

读法：

1. **实心 100³ 只要 5.5MB 网格**——比很多人直觉小得多，因为内部面全被剔除。100 万方块本身不是问题。
2. **地表薄壳要 120MB、+2.6M 面**——这一档才会撞红线：静态面 13.35M → 15.95M（超 15.09M 上限），常驻堆 +120MB，合批期峰值 +240MB（按 11.1.7 的 2× 模板）⇒ 真峰值从 2.30–2.62GB 推到 **2.54–2.86GB**，离历史 GC 悬崖 3.3GB 只剩 0.44–0.76GB。
3. **最坏全孤立要 552MB**——直接不可行，不需要再算。

所以「100 万可破坏方块」这句话必须带拓扑限定。**说「100 万实心方块可行、100 万地表方块不可行」才是准确的。**

用本项目的真实尺度把这件事说透。一个 100m × 100m × 100m 的实心台基正好是 100 万块：玩家能站上去、能挖穿、能看见的只有外表面 **6 万面**，内部 99% 的方块永远不产生几何。反过来，1km × 1km 的地表薄壳也是 100 万块，但它的每一块都贴着空气，顶面 100 万 + 高差侧壁约 30 万 = **130 万面**，是前者的 21.7 倍。两者的方块数完全相同，代价却差一个数量级——**「可破坏方块数」不是预算单位，「暴露面数」才是。**

这也解释了为什么「100 万实心方块」在玩法上没有意义：玩家挖进去以后，每挖掉一块只会新暴露 1–3 个面（朝向洞内的那几面），而洞外的 6 万面早已存在。它便宜，是因为它几乎没有可交互的表面；它不好玩，也是同一个原因。真正需要预算的是「玩家能看见、能挖到、挖了会改变轮廓」的那一层，也就是地表薄壳。

### 11.2.5 面数与内存的增长律

设 `n` 为方块数、`s` 为暴露面/块：

```
网格字节 B(n, s) = n × s × 92
体素数据 D(n)   = n × b        （b = 1B 或 0.5B 或 RLE 的 0.05–0.4B）
```

`B` 与 `n` **线性**，但 `s` 由形状决定：实心体 `s ≈ 6/n^(1/3)`（趋近 0），薄壳 `s ≈ 1.3`，孤立 `s = 6`。**这就是为什么「加方块」有时几乎免费、有时立刻爆炸。**

每新增一种方块类型，若走图集：`ΔB = 0`、`ΔD = 0`、`Δdraw = 0`、`Δtex ≈ 21KB`。若走独立材质：`Δdraw = 可见 chunk 数`，这是唯一会让方案从可行变不可行的单点。

## 11.3 chunk 流式

### 11.3.1 分块尺寸：数据块 16³，渲染块 64³

| 块尺寸 | 体素数 | 数据 8bit | 数据 4bit | 1M 方块占块数 | 单块 meshing（1–3M voxel/s） | 单块重建对玩家的可感度 |
|---|---|---|---|---|---|---|
| 16³ | 4,096 | 4KB | 2KB | 245 | **1.4–4.1ms** | 无感 |
| 32³ | 32,768 | 32KB | 16KB | 31 | **11–33ms** | 轻微 |
| 64³ | 262,144 | 256KB | 128KB | 4 | **87–262ms** | 明显卡顿 |

选择：**16³ 做数据与编辑粒度，64³ 做渲染合批粒度**。理由：编辑必须细（一次破坏只脏 1 个 16³ 块），draw call 必须粗（64³ 一块一次调用，1M 方块只要 4 次）。代价是「一次编辑要刷新一个 64³ 的渲染块」，靠 11.4 的 BatchedMesh 化解。

### 11.3.2 可见性剔除：四层，按成本从低到高

1. **距离剔除**：`dist > renderDistance × chunkSize` 整块不提交。沙盒视距建议 128m（8 个 16³ 块）。
2. **视锥剔除**：chunk AABB 与相机 frustum 六平面测试。16³ 块的 AABB 测试是 6 次点积，成本可忽略。
3. **背面剔除**：体素面只生成「邻块为空气」的那一侧，天然没有内壁。这是体素相对烘焙几何最大的优势——烘焙盒体是 12 面全出，体素只出暴露面。
4. **遮挡剔除（可选）**：沙盒在地下时用「高度图 + 当前层」快速跳过被地表盖住的块。**第一版不做**，因为实现成本高于收益；用视距 128m 把可见块数压到 ≤256 即可。

按 128m 视距、16³ 块、地表单层估算：可见数据块 ≈ `17×17` 列 × 4 层 = **1156 块**；视锥剔除后 ≈ 300–450 块；合并到 64³ 渲染块后 ≈ **18–25 次 draw call**。这个量级可以接受。

### 11.3.3 异步构建：Worker 池 + Transferable

```
主线程                          Worker（2–4 个）
  │  edit(block)                  │
  ├─ 标记 chunk dirty ───────────►│
  │                              ├─ 读 chunk 体素（SharedArrayBuffer 或拷贝）
  │                              ├─ greedy meshing
  │                              ├─ 生成 Float32Array/Uint16Array
  │◄────── postMessage(transfer) ─┤  （零拷贝移交）
  ├─ 入上传队列                   │
  ├─ 每帧 ≤2ms 上传               │
```

约束：

- **Worker 数 = `min(4, hardwareConcurrency - 1)`**。低于 2 个会让首次进入沙盒的等待变长；高于 4 个在 8 核机上会与渲染线程抢核。
- **必须 transfer，不许 structured clone**。一个 16³ 块的网格约 46KB–1.5MB，clone 会把它复制一遍并产生 GC 垃圾；transfer 是零拷贝。
- **Worker 内不碰 three.js**。只输出纯 TypedArray（position/normal/uv/index），主线程负责 `BufferGeometry` 与 GPU 上传。这样 Worker 可以独立测试，也不会把 three 的模块图带进 worker bundle。
- **首次进入沙盒的预生成**：只生成玩家脚下 3×3 个 16³ 块（≈9 块 × 2ms = 18ms），其余在后台按距离由近到远排队。**不许在载入期生成整个沙盒**，那是把流式又变回同步。

### 11.3.4 GPU 上传预算：与现有 33 次 flush 的关系

现有账：33 次 flush 累计 **2,372ms（v82）→ 975ms（v83）→ 709ms（v86）**。按 40,058,574 顶点 × 28B ≈ 1.12GB 总属性字节算：

- v82：1.12GB / 2.372s ≈ **472MB/s**
- v83：1.12GB / 0.975s ≈ **1.15GB/s**
- v86：1.12GB / 0.709s ≈ **1.58GB/s**

这是「建 BufferGeometry + 上传」的混合吞吐，不是纯 PCIe 带宽。用它做体素上传的上界是合理的。

体素单块上传量：

| 场景 | 面数 | 字节 @92B | 上传耗时 @1.15GB/s |
|---|---|---|---|
| 16³ 空块 | 0 | 0 | 0 |
| 16³ 地表块 | ≈400 | 37KB | **0.03ms** |
| 16³ 建筑块 | ≈2,000 | 184KB | **0.16ms** |
| 64³ 渲染块（16 个 16³ 合并） | ≈6,400 | 589KB | **0.51ms** |

预算：**每帧上传 ≤2ms、≤4MB、≤4 个 16³ 块**。按 60fps 算，2ms 占帧预算 12%，与现有 `flush` 的 8ms 装配节流同量级，不会把主线程压穿。

**与 33 次 flush 的本质区别**：载入期 flush 是「33 次、每次几十 MB、集中在 8–10s 内」；体素流式是「每帧 1–4 次、每次几十到几百 KB、摊在几分钟里」。前者决定 12s 红线，后者只决定进入沙盒时的首帧卡顿。**两者不能互相抵消，也不能把体素生成塞进载入期来「顺便」省一次流式。**

### 11.3.5 为什么不复用 `compactStatic`

`compactStatic`（`src/world.ts:710`）按材质把 `city_*` 网格合并，批预算 `COMPACT_BATCH_MB = 48`，合并后 `matrixAutoUpdate = false`、几何不再变。它有三个前提与体素不兼容：

1. **一次性**：只在载入末尾跑一次，没有「增量合并」入口。
2. **整组合并**：一次编辑要让整块合并几何失效，重合并成本 = 整组字节数 / 1.15GB/s。一个 48MB 批要 42ms。
3. **名字契约**：只收 `city_` 前缀，体素网格若混进去会被误合并，且破坏后无法回溯到 chunk。

所以体素必须走**独立的渲染路径**：不叫 `city_*`、不进 `compactStatic`、不参与静态合批。这不是洁癖，是防止「一次破坏触发全城重合并」的唯一办法。

但「独立」不等于「另起一套世界」。沙盒仍然要挂在同一个 `scene` 下、用同一个 `renderer`、吃同一套雾与光照；它只是不参与静态合批。判断标准很简单：**把 `vox_*` 全部隐藏，画面应当剩下完整的烘焙三界；把 `city_*` 全部隐藏，画面应当只剩下沙盒本身。** 两组几何互不依赖，才能各自独立地重建、释放、降级。

chunk 的生命周期因此必须显式建模，不能靠「加载了就一直在」：

```
未载入 → 数据就绪 → 网格就绪 → 可见 → 休眠 → 释放
   ↑                                  │
   └────────── 玩家远离 ──────────────┘
```

- **未载入 → 数据就绪**：生成或读盘，16³ 块约 0.2ms。
- **数据就绪 → 网格就绪**：Worker meshing，1.4–4.1ms。
- **网格就绪 → 可见**：上传并挂进 BatchedMesh。
- **可见 → 休眠**：距离超过视距 1.5 倍，保留数据、释放网格（省显存），回来时只重建网格。
- **休眠 → 释放**：距离超过视距 2.5 倍或内存超预算，数据与网格全释放。

每个状态迁移都带一个 `generation` 计数器。玩家快速跑动时，一个块可能在「数据就绪」时已经被判定远离；Worker 回来时比对 `generation`，过期就丢弃结果，不传进主线程。**没有这个计数器，快速移动会积累大量「为已经不存在的视野建的网格」，表现为内存缓慢上涨、越跑越卡**——这是流式系统最常见的泄漏形态，比一次性大涨更难查。

## 11.4 LOD 与合并：破坏后如何不失去合批

### 11.4.1 问题

烘焙世界的合批是**静态**的：`compactStatic` 把 N 个网格合成 1 个，draw call 从 1045 降到 474（历史记录）。体素世界一旦允许破坏，任何一次编辑都会让「那一块」的几何变化。如果沿用「合并成一个大网格」，一次编辑就要重建整个大网格——**破坏的实时性和合批的静态性直接冲突**。

三个方案：

| 方案 | 做法 | 一次编辑成本 | draw call | 结论 |
|---|---|---|---|---|
| A 全局重建 | 编辑后重跑 `compactStatic` | 42ms–1.5s | 最低 | ❌ 不可行 |
| B 分块重建 | 每个 16³ 块一个 Mesh，编辑只重建该块 | 1.4–4.1ms meshing + 0.03–0.16ms 上传 | +245（1M 方块） | 🟡 可行但吃 draw call |
| C 分块 + BatchedMesh | 所有块塞进一个 `BatchedMesh`，编辑替换一个 geometry slot | 同上，但只上传该 slot | **+1–4** | ✅ 推荐 |

`THREE.BatchedMesh`（three 0.180 提供 `addGeometry` / `setGeometryAt` / `deleteGeometry`）把多块几何放进一次 draw call，同时保留逐块替换能力。**API 存在性已核对 `node_modules/three/src/objects/BatchedMesh.js`（三个方法都在，行号 627/714/826）；运行时行为尚未实跑，标「待验证」。** 若实跑发现 `setGeometryAt` 触发的重上传比预期贵，退回方案 B，并把 1M 方块的 draw call 预算改成「64³ 渲染块 + 每块一个 Mesh」。

### 11.4.2 脏块重建队列：优先级、合并、预算

一次 `destroy(x,y,z)` 的影响面：

- 该方块所在的 16³ 数据块（必脏）；
- 若方块在块边界（`x%16 ∈ {0,15}` 等），相邻最多 3 个块也脏（因为邻块要补出/newly exposed 面）；
- 对应 64³ 渲染块（1 个）。

队列算法：

```
type Dirty = { chunk: ChunkKey; reason: 'edit'|'neighbor'|'stream'; priority: number; t: number }

onEdit(block):
  for each chunk in affectedChunks(block):        // 1–4 个
     dirty.mark(chunk, 'edit')
  schedule()                                       // 下一帧处理

priority(chunk):
  d = distance(camera, chunk.center)
  cover = screenCoverage(chunk)                    // AABB 投影面积 / 屏幕面积
  age = now - chunk.lastEdit
  return (cover * 1000) / (d + 16) + (age < 120 ? 2 : 0)

每帧:
  budget = 4ms
  while (queue not empty && spent < budget):
     c = queue.popMax(priority)
     if (c.version changed since queued) continue   // 合并：只重建最新版本
     mesh = worker.build(c)                         // 同步等待已完成的 future
     batched.setGeometryAt(c.slot, mesh)
     spent += uploadMs(mesh)
```

四条纪律：

1. **合并窗口 120ms**：同一块在 120ms 内被编辑多次，只重建一次。连续挖掘（玩家按住鼠标）不会每块都触发重建。
2. **帧预算 4ms**：超过就停，下一帧继续。首帧允许一次「紧急重建」到 8ms（玩家正对着的块），但不得超过 8ms。
3. **版本号防抖**：入队时记 `version`，出队时比对；版本变了说明已有更新的重建在途，直接丢弃旧的。这是避免「队列里堆十个同块任务」的关键。
4. **降级路径**：若队列长度 > 64 或最老任务等待 > 500ms，切到「只删面、不补面」的快速模式（视觉上洞的边缘可能缺一圈面），等空闲时再做完整重建。**这是显式降级，必须在 HUD 或日志里标记 `[DEGRADED]`，不许静默。**

把一次普通挖掘按时间轴摊开，可以看到它为什么不卡：

| 时刻 | 主线程 | Worker | 备注 |
|---|---|---|---|
| t=0 | `destroy()` 改 1 个体素、标脏、`version++` | — | 约 0.01ms |
| t=0–16ms | 继续渲染上一帧 | 取任务、meshing 16³ 块 | 后台 1.4–4.1ms |
| t=16ms | 收到 transfer 的 TypedArray，`setGeometryAt` | — | 上传 ≈37KB ≈0.03ms |
| t=16–32ms | 下一帧已见洞 | 空闲 | draw call 不变 |

边界情况（挖在 `x%16===0`）会让 2–4 个块变脏：Worker 侧 4×2ms = 8ms（4 个 worker 并行约 2–4ms 墙钟），主线程上传 4×0.03 = 0.12ms。**仍然是「一帧内看不见卡顿」的量级**，因为重活全在 Worker，主线程只做 slot 替换。

真正会卡的是「一次编辑触发整块 64³ 重合并」：64 个 16³ 块 × 2ms = 128ms meshing + 0.5ms 上传，如果同步做就是 128ms 的掉帧。**所以 BatchedMesh 的 `setGeometryAt` 必须支持「只替换一个 16³ 子块」，而不是「替换整个 64³ 渲染块」**——如果实测发现它只能整块替换，就把渲染粒度退回 16³、draw call 用「可见块合并」补，这是 11.4.1 方案 B 的退路，必须提前留好。

### 11.4.3 帧预算表

| 项 | 预算 | 依据 |
|---|---|---|
| Worker meshing（后台） | 不占主线程 | 16³ 块 1.4–4.1ms/块，4 worker 并行 |
| 主线程上传 | ≤2ms/帧 | 11.3.4 |
| 脏块重建装配 | ≤4ms/帧 | 本节 |
| 渲染 | 余下 ≈10ms | 60fps 帧预算 16.6ms |
| 紧急上限 | 单帧 ≤8ms | 超了就是可感卡顿 |

### 11.4.4 体素 LOD：距离决定「面要不要出」

| 距离 | 策略 | 面数比例 |
|---|---|---|
| ≤32m | 完整 greedy 网格，保留 AO 与细节面 | 100% |
| 32–96m | 合并 2×2 面（2m 粒度），去掉 AO | ≈45% |
| 96–192m | 合并 4×4 面（4m 粒度），只留剪影 | ≈18% |
| >192m | 不出体素，交给地形/远景 impostor | 0% |

这条 LOD 与现有 `LodManager` 的 `near/mid/far/impostor` **不是同一套**，必须用独立的名字与独立的阈值表，避免 11.1.5 说的命名撞车。体素 LOD 的切换点是「屏幕像素」而不是绝对距离更好，但第一版用距离即可，像素级切换标「待优化」。

## 11.5 内存

### 11.5.1 现状：1.83–1.86GB 是 `heapEnd`，真峰值是 2.30–2.62GB

先把三条口径钉死（同 11.1.7）：

- **`heapEnd` 1.83–1.86GB**：载入结束瞬间的 `usedJSHeapSize`。它是本项目最常被引用的数，但**不是峰值**。
- **常驻 1.37–1.39GB**：GC 后稳定值，已达 ≤1.5GB。
- **真峰值 2.30–2.62GB**：载入期 40ms 采样最大值，**未达标**。

体素预算必须加在**真峰值**上，不是 `heapEnd` 上。加在 `heapEnd` 上会低估 0.5–0.8GB。

### 11.5.2 体素数据怎么压

| 方案 | 每体素 | 1 万块 | 100 万块 | 4.19M 块（256×256×64） | 适用 |
|---|---|---|---|---|---|
| 稠密 8bit 调色板 | 1B | 9.8KB | 0.95MB | 4.0MB | 通用，最简单 |
| 稠密 4bit 调色板（≤16 型） | 0.5B | 4.9KB | 0.48MB | 2.0MB | 方块类型 ≤16 时 |
| RLE（游程） | 0.05–0.4B | 2–6KB | 0.02–0.4MB | 0.2–1.6MB | 地形/实心体，编辑后需重编码 |
| 位平面（solid/air 1bit + 类型层） | 0.125B + 类型 | ≈3KB | ≈0.2MB | ≈0.8MB | 地表薄壳 |
| 稀疏编辑（只存改动） | 16B/次编辑 | 160KB/万次 | 16MB/百万次 | — | 叠加在基线世界上，不单独用 |

选择：**基线世界用 4bit 调色板 + 分块 RLE，玩家编辑用稀疏覆盖层**。

- 基线（生成出来的地形/建筑）压缩率高，RLE 足够；
- 玩家编辑是稀疏的（1 万次编辑 × 16B = 160KB），没必要重编码整块；
- 读取时「基线 + 覆盖」合并，写时只写覆盖层。这避免「每挖一块就重压整块」。

具体编码（定长、可随机访问，不做变长流）：

```
块头 16B：paletteId u16 | runCount u16 | nonAirCount u32 | version u32 | crc32 u32
调色板：≤16 项 × u32（ARGB 或 blockId），最多 64B
体素段：4bit/体素，4096 体素 = 2048B；按 y→z→x 线性排，解压时按索引取半字节
RLE 段（可选）：run = (count u16, value u8) × 3B；run 数 > 2048 时不启用，
                因为 3B/run 已经比 2B/体素的稠密表示更差
稀疏覆盖：哈希表，key = (chunkKey u64, localIndex u16)，value = blockId u8 + meta u8
          每条 16B（含哈希桶开销），1 万次编辑 = 160KB
```

这套格式的三个性质是刻意的：**定长块头**让 `chunkAt(x,y,z)` 是 O(1) 而不是扫流；**调色板 ≤16** 让 4bit 索引永远够用；**RLE 只在 run 数 ≤2048 时启用**，否则退回稠密——编码器要自己判断「压了反而更大」，不能无条件压。解压一个 16³ 块的成本约 0.05–0.1ms，远低于 meshing 的 1.4–4.1ms，可以忽略。

### 11.5.3 估算：数据是噪声，网格才是钱

| 规模 | 体素数据 | 网格 @92B/面 | chunk 头 + 索引 | **合计** | 占现有常驻 1.37GB |
|---|---|---|---|---|---|
| 1 万（薄壳） | 6KB | 2.0MB | 4KB | **≈2.0MB** | +0.15% |
| 10 万（薄壳） | 60KB | 20MB | 40KB | **≈20MB** | +1.5% |
| 100 万（实心） | 0.5MB | 5.5MB | 0.4MB | **≈6.4MB** | +0.5% |
| 100 万（地表） | 0.5MB | 119.6MB | 4MB | **≈124MB** | **+9.1%** |
| 419 万（256×256×64 薄壳） | 0.8MB | 7.8MB | 1MB | **≈9.6MB** | +0.7% |

读法：

1. **体素数据压缩的收益上限是「几 MB」**。把 1B/块压到 0.125B/块，100 万块只省 0.9MB——在 1.37GB 面前是 0.07%。**为压缩算法投入的每一天，都不如去优化一个面的字节数。**
2. **网格才是钱**。同样 100 万块，实心 5.5MB、地表 120MB，差 22 倍。决定内存的是「暴露面数」，不是「方块数」。
3. **合批期峰值要按 2× 算**（11.1.7 的模板）。120MB 网格 → 峰值 +240MB → 2.54–2.86GB。这是 100 万地表方块真正的死因，不是常驻。

### 11.5.4 给体素的内存预算

本节 MB 一律按 **1MiB = 1,048,576B** 计，与 `probe-mem.mjs` 的 `bytes / 1048576` 同口径；换口径会让「能买多少面」差 4.8%。

| 项 | 预算 | 理由 |
|---|---|---|
| 常驻增量 | **≤64MB** | 1.37GB → ≤1.43GB，仍在 1.5GB 内 |
| 峰值增量 | **≤128MB** | 2.30–2.62GB → ≤2.43–2.75GB，离 3.3GB 悬崖 ≥0.55GB |
| 64MB 能买多少面 | 64MiB / 92B ≈ **72.9 万面** | 按薄壳 1.3 面/块 ≈ **56.1 万块** |
| 128MB 能买多少面 | ≈**145.9 万面** | 按薄壳 ≈ **112.2 万块**（但峰值会顶到 2.75GB） |

**结论：在「峰值增量 ≤128MB」的纪律下，体素薄壳的安全上限约 56 万块（取整说 50 万更稳）；100 万块要占用全部预算且没有余量。**

## 11.6 必须回答：12s 红线 + 一个实例不删，体素玩法可行吗

### 11.6.1 结论先说

**全量体素化不可行；局部沙盒可行；100 万方块只在「实心/低暴露面 + 载入后流式」这一个窄条件下可行。**

这不是保守，是四道约束里任意一道都足以单独否决全量方案。

### 11.6.2 四道约束，逐条算

**约束一：用户硬指令「一个实例都不许删」。**
全量体素化意味着把现有 696,220 个盒体、10.59M infill 面、4496 个角色所依赖的烘焙几何替换成体素。替换就是删除原有实例。**这一条不需要算性能，它直接违反指令。** 唯一不违规的做法是「烘焙世界保留，体素只作为叠加的局部沙盒」——这已经把答案限定成局部。

有人会问：能不能「保留烘焙几何，同时把同一块区域也体素化」？那样两套几何同时存在，静态面不是替换而是相加：13.35M + 体素面，内存也是相加。它没有绕开约束，只是把「删实例」换成了「双倍成本」。而且两套几何会发生 Z-fighting、阴影互相遮挡、碰撞二义——玩家看到的是两层皮，不是更真实的世界。**几何层面没有第三条路：要么替换（违反指令），要么叠加（双倍成本），要么隔离（局部沙盒）。** 局部沙盒是唯一同时满足指令与预算的形态。

**约束二：静态面。**
13.35M 现状 + 100 万地表方块的 2.6M 面 = **15.95M**，超过 15.09M 的记录上限，更超过 13.5M 的裁定目标。即使按最乐观的 greedy 把 2.6M 压到 1.3M，也到 **14.65M**，仍超 13.5M。**没有一种 100 万地表方块的排布能塞进 0.15M 的余量。**

**约束三：draw call。**
最坏帧 608，预算 600，**余量是 −8**。100 万方块按 16³ 块、每块一 draw = +245；按 64³ 渲染块 = +4（但需要 BatchedMesh 或额外合并）。**只有「64³ + BatchedMesh」这一条路能不加 call；任何「每 chunk 一 Mesh」的实现都会把最坏帧推到 850+。**

**约束四：内存。**
100 万地表方块 +120MB 常驻、+240MB 峰值 ⇒ 真峰值 **2.54–2.86GB**。历史 GC 悬崖是 3.3GB（`SPEC-总账.md` 记录「堆到 3.3GB 触发 GC 悬崖」）。余量 0.44–0.76GB，一次载入期的临时缓冲就可能吃掉。**这不是「可能超」，是「已经在悬崖边」。**

### 11.6.3 三档判断

| 方案 | 静态面增量 | 常驻增量 | 峰值增量 | draw call | 载入增量 | 判定 |
|---|---|---|---|---|---|---|
| 全量体素化（改造三界） | +2.6M～+12M | +120～+553MB | +240MB～+1.1GB | +245～+1024 | 不可控 | ❌ **不可行**，且违反「不删实例」 |
| 局部沙盒 1 万块 | +0.02M | +2MB | +4MB | +1 | ≈10ms | ✅ **可行，立刻可做** |
| 局部沙盒 100 万（实心 100³） | +0.12M | +6.4MB | +13MB | +4 | ≈0.5s | ✅ **可行**（但玩法上「实心块」没什么可挖的） |
| 局部沙盒 100 万（地表薄壳） | +2.6M | +124MB | +248MB | +4～+245 | ≈0.8–1.2s | ⚠️ **有条件可行**，见 11.6.4 |

### 11.6.4 局部沙盒可行，但有六个前提

1. **空间隔离**：沙盒有独立原点、独立材质、独立渲染根节点；网格不叫 `city_*`，不进 `compactStatic`，不参与静态合批。
2. **规模上限**：第一版 **≤5 万块**（面数 ≤0.1M、内存 ≤10MB）；验证通过后再谈 50 万。**不许第一版就上 100 万。**
3. **单一图集**：所有方块类型走一张 `DataArrayTexture` 或图集，全局 **1–2 个材质**；禁止「一种方块一个材质」。
4. **greedy + 面剔除**：暴露面/块 ≤2.2（薄壳典型值），greedy 后 ≤1.0；达不到就不扩规模。
5. **数据压缩**：4bit 调色板 + 分块 RLE + 稀疏编辑层；常驻 ≤8MB。
6. **载入后流式**：沙盒在 `__loadEndAt` 之后生成，**不进 12s 关键路径**；首次进入只生成脚下 3×3 块（≈18ms），其余后台排队。

满足六条时，1 万块的实测预期是：载入 +10ms 内、常驻 +2MB、峰值 +4MB、draw call +1、帧率无可测变化。**这是可以写进验收断言的数字，不是愿望。**

### 11.6.5 如果一定要 100 万地表方块

必须同时做到：

- 先把最坏帧 draw call 从 608 压到 **≤350**，给体素留 250 的余量（来源：静态合批再合并、远景 impostor 化、阴影 pass 减组）；
- 把真峰值从 2.30–2.62GB 压到 **≤2.2GB**，给 +240MB 留出空间；
- 体素网格必须走 BatchedMesh，**不得**每 chunk 一 Mesh；
- 沙盒必须在载入后流式，**不得**进 12s；
- greedy 比例 ≥2.5×（1.3M 面 → ≤0.52M 面）。

这五条里任意一条做不到，100 万地表方块就不可行。**当前项目一条都不满足。** 所以正确的路线是：先做 1 万，再逐步扩到 5 万、20 万，每扩一档重跑一次本卷的全部断言；而不是先立 100 万的目标再倒推。

## 11.7 可执行验收断言

每条都给测量方式与阈值。**「PASS/BLOCK + 退出码」是唯一承认的形式**；口头「优化了」不算。

| # | 断言 | 探针 / 命令 | 阈值 | 口径 |
|---|---|---|---|---|
| A1 | 静态面不回归 | `node scripts/probe-mem.mjs --runs 3` | `staticTris ≤ 13,500,000` | 三次中位数；`assetAudit` 口径 |
| A2 | 载入不破 12s | `node scripts/verify-packaged.mjs <exe>` ×3 | `navToEngineMs + engineMs ≤ 12,000` | 三次中位数；打包态 |
| A3 | 体素常驻增量 | 新增 `probe-voxel-mem.mjs`，载入后/进沙盒后各读一次 `usedJSHeapSize` | `Δ ≤ 64MB` | 同构建、feature on/off 对照；不是绝对值 |
| A4 | 体素峰值增量 | `probe-voxel-mem.mjs` 40ms 采样序列 | `Δpeak ≤ 128MB`，且 `peak < 2,900MB` | 三次中位数；绝对值仍红，故用双重判据 |
| A5 | draw call 峰值 | `node scripts/probe-calls-sweep.mjs` | `maxCalls ≤ 600` | 六机位逐帧 max，不用单点 |
| A6 | 16³ 块 meshing 时延 | 新增 `probe-voxel-mesh.mjs`，Worker 内 1000 块取 p95 | `p95 ≤ 4ms` | 单 worker；4 worker 并行的墙钟另记 |
| A7 | 单帧上传预算 | `probe-voxel-stream.mjs` 记录每帧 `renderer.info.memory.geometries` 与上传字节 | `≤4MB/帧` 且 `≤2ms/帧` | 进入沙盒后连续 300 帧 |
| A8 | 破坏后帧稳定 | `probe-voxel-edit.mjs`：连续 100 次破坏，记录 `frameMs` | `p95 ≤ 25ms`，`max ≤ 50ms` | 硬件光栅；单帧 >50ms 即 BLOCK |
| A9 | 脏块队列排空 | 同上，记录队列长度与最老任务等待 | `≤500ms` 排空，队列 `≤64` | 100 次编辑后 1s 内 |
| A10 | 破坏可见性 | 射线从相机到被破坏块中心 | 命中空气；相邻块新面可见（像素差 >8/255） | 固定机位、固定块坐标 |
| A11 | 碰撞一致性 | 玩家胶囊推进测试 | 未破坏块不可穿；破坏后可穿 | `probe-voxel-edit.mjs` 子项 |
| A12 | 离开沙盒不泄漏 | 进出沙盒 3 次，读 `renderer.info.memory.geometries` | 回到基线 ±5% | 三次；`dispose` 后 2s 读 |
| A13 | 确定性 | 同 seed 生成两次，chunk 网格 SHA-256 | 两次哈希相同 | Node 端跑 mesher，不进浏览器 |
| A14 | 材质数不膨胀 | `renderer.info.memory.textures` 与材质计数 | 体素材质 ≤2，纹理 ≤+2 张 | 进入沙盒前后对比 |

其中 A1–A5 是**回归门**（现有构建也必须绿），A6–A14 是**新功能门**。两组的区别：回归门红了，说明体素改动破坏了现有体验，必须先修；新功能门红了，说明体素方案本身没达标，可以缩规模而不是硬上。

测量协议（不遵守的读数一律作废）：

1. **同一构建内做 A/B**：体素功能用 URL 参数 `?vox=0|1` 开关，A/B 必须来自同一次 `vite build`、同一个 exe、同一条启动路径。跨构建比数字会把「别的改动」算进体素账上。
2. **三次取中位数**：`calls`、`heap`、`load` 都至少三次。本项目已经因为单点采样误判过四次（`toPlayableMs` 当载入、`__loadStartAt` 取到 undefined、堆 2923MB 当泄漏、`calls 597` 当回归），**第五次不许再犯**。
3. **固定机位**：draw call 与帧率用 `probe-calls-sweep.mjs` 的六机位，不用自由飞行。相机每帧不同，读数就没有可比性。
4. **绝对值与增量分开报**：A1/A2/A5 报绝对值（因为它们是现有红线），A3/A4 报增量（因为绝对值已经红了，报绝对值只会得到「一直红」的结论）。增量断言必须写清基线构建号，否则「Δ」没有意义。
5. **探针要能自证**：每个新 probe 必须有 `--self-test`，用构造的正/负样本证明「该 BLOCK 的时候真的 BLOCK」。一个永远 PASS 的探针比没有探针更坏，因为它会给出假绿。
6. **失败要留现场**：BLOCK 时把 `calls` 曲线、堆采样序列、队列长度、构建号写进 `artifacts/probe-<name>-<build>.json`，否则下一轮只能靠记忆复现。

这六条不是流程洁癖。本项目历史上每一次「优化了但没效果」或「回归了但找不到」，追到最后都是这六条里缺了一条。

## 11.9 超预算时的降级阶梯

体素玩法最大的工程风险不是「一开始就慢」，是「在某些机器/某些视角下突然慢，然后没有人知道该关什么」。所以降级必须是**预设的四档**，每档有明确触发条件、明确动作、明确可见标记，不许临场拍脑袋。

| 档 | 触发 | 动作 | 玩家可见变化 | 恢复 |
|---|---|---|---|---|
| **L0 正常** | 默认 | 全部开启，视距 128m，voxLod 全档 | 无 | — |
| **L1 降视距** | `frameP95 > 25ms` 连续 30 帧 | 视距 128→96→64m；voxLod 提前一档（32m 细节档缩到 24m） | 远处体素先消失，近处不变 | 连续 10s `frameP95 < 20ms`，升一档 |
| **L2 降更新率** | L1 后仍超，或脏块队列 >64 | 每帧重建预算 4→2ms；合并窗口 120→250ms；暂停非编辑块的流式预取 | 挖掘后洞穴边缘延迟约 0.25s 才补面 | 队列 <16 且 10s 稳定，升一档 |
| **L3 停用编辑** | L2 后仍超，或 `peak > 2.8GB` | 体素转为只读：`vox_*` 仍渲染，但 `destroy/place` 返回失败并提示；停止所有 meshing worker | HUD 明确显示「体素编辑已暂停（性能保护）」 | 需玩家手动在设置里恢复，不自动升档 |

四条纪律：

1. **降级必须可观测**：每次换档写一条 `console.warn('[voxel] degrade L2: queue=83 p95=31ms')`，并累加 `window.__voxDegrade` 计数。没有日志的降级等于没发生，事后无法归因。
2. **不许静默降级**：L3 必须在 HUD 上明说，不许让玩家以为「这块石头挖不动是 bug」。这是本项目「三重零容忍」里「零降级」的具体落地——降级可以，隐瞒不行。
3. **恢复要滞回**：升级阈值比降级阈值严 5ms/10s，否则会在边界反复跳档，比一直慢更难受。
4. **每档都要有机检**：`probe-voxel-degrade.mjs` 用 `?voxdegrade=L1|L2|L3` 强制指定档位，断言「该档的动作确实生效」（例如 L1 下 `voxLod` 的远档距离从 192 变 96），而不是只看帧率有没有变好。帧率变好可能是别的原因，档位生效才是因果。

## 11.10 待验证清单

以下不是「已知」，是「必须实测后才能写进结论」：

1. `BatchedMesh.setGeometryAt` 在 245 个 geometry slot 下的实际重上传成本——**未实跑**。
2. 45–47M/帧的精确分解（可见静态 / 实例 / 阴影 pass 各占多少）——**未拆解**。
3. 15.09M 与 13.35M 的 1.74M 差额来源——**未归因**。
4. 原生 `DataArrayTexture` 在 Electron/ANGLE 下的采样开销——**未测**。
5. 4bit 调色板 + RLE 在「频繁编辑」下的重编码成本——**未测**。
6. 移动端/集显上的体素填充率——**未测**，本卷所有数字只对桌面独显负责。
