# V3 · 方块与材质系统

> 卷次 V3 / 16 ｜ 上游：V2（体素世界 × 烘焙世界）｜ 下游：V4（采矿冶炼合成）、V5（建造）、V11（性能）
>
> V2 已经定死了「在哪里放体素、放多大、怎么合并、每帧多少预算」。本卷不重复这些结论，只接手它留下的三块空白：**放什么方块**（注册表与行为）、**方块长什么样**（材质组与图集）、**一个非立方构件怎么塞进 1 米格里而不丢形制**（形制编码）。
>
> **诚实边界**：凡引自仓库代码的事实都带文件与行号；凡标「估算」的是按字节数与面数推出来的预算，**没有在真机跑过**；凡标「待实测」的是必须先跑一次才能写进验收的项。三类不混写。

## 0. 与 V2 的分工

先把边界写死，否则两卷会互相改数字，验收时对不上账。

| 项目 | V2 已定（本卷服从） | V3 负责（本卷新增） |
|---|---|---|
| 区块 | 16×16×16 = 4,096 体素，`Uint16Array` 8,192 B | 区块内每个 id 的语义与状态位 |
| 沙盒 | 48 区块/沙盒（4×4×3，64×64×48 m），5 个沙盒，共 240 区块 | 沙盒内的方块调色板与可用集 |
| 合并 | 每（沙盒 × 材质组）一个 Mesh，`addUpdateRange` 局部上传，draw call +30 | 材质组如何承载 62 种方块而不增 draw call |
| 预算 | 4 ms/帧，单区块 0.8–1.6 ms，一帧 2–4 块 | 单块的 mesher 规则与 UV 语义 |
| 顶点 | 32 B（位置 12 + 法线 6 + 颜色 6 + UV 8） | 每个字段填什么值 |
| 材质 | 克隆 6 组（`wood/wall/earth/roof/ground/ash`） | 克隆后 `map` 换成什么、UV 怎么改 |

**一处必须当场说明的分歧**：V2 §1.2 说「体素区必须克隆材质」，理由是 `WardInfill` 给 `infill.ts` 的材质挂了三个 `onBeforeCompile` 补丁（`plasterHook`、`roofFluteHook`、`roofEmissiveTint`），这些补丁按世界 Y 做勒脚与墙帽色带，1 米方块抬高两米就会换一种颜色。V2 的判断是对的，但理由只说了一半——**克隆之所以能解决，是因为 `Material.copy()` 根本不复制 `onBeforeCompile` 这个自有属性**。本卷实测过：

```
原材质 Object.hasOwnProperty('onBeforeCompile') → true
克隆后 Object.hasOwnProperty('onBeforeCompile') → false
克隆后 onBeforeCompile.toString() → 'onBeforeCompile( /* shaderobject, renderer */ ) {}'
```

也就是说，克隆体自动回到原型上的空实现，补丁不会被继承。这条不是文档承诺，是 `three` 当前版本的实现事实（`node_modules/three/src/materials/Material.js` 的 `copy()` 未复制该属性），所以它需要一个回归断言（见 §6 的 A7）：升级 three 后如果 `copy()` 开始复制钩子，体素方块会集体变色，而这个 bug 极难从画面上归因。

反过来还有一条更容易踩的坑：**克隆体与原体共享同一张贴图实例**。实测 `clone().map === original.map` 为 `true`。所以 V3 换图集时必须**给克隆体赋一张新贴图**，不能就地改原贴图的 `repeat/offset`——那会把整座烘焙城市的墙面一起改掉。这条同样进断言。

## 1. 方块注册表

### 1.1 数据结构

新建 `src/voxel/blocks.ts`。这个文件**不 import three**，只导出纯数据与纯函数，这样它能被 vitest 直接单测，也能被 Node 侧的配方校验脚本直接读——现有 `tests/bakeQuant.test.ts` 就是「纯数据 + 逐位断言」的写法，沿用同一套路。

```ts
export type BlockCat = 'natural' | 'build' | 'craft' | 'func' | 'decor';
export type FaceFamily = 'opaque' | 'cutout' | 'translucent' | 'emissive';
export type ModelKind = 'cube' | 'panel' | 'post' | 'beam' | 'bracket' | 'tile' | 'sculpt';

export interface BlockDef {
  id: number;            // 1..255；0 恒为空气；高 8 位留给状态
  key: string;           // 'qing_zhuan'，存档与配方只认 key，不认 id
  name: string;          // '青砖'
  cat: BlockCat;
  bgroup: BGroup;        // 14 组之一；决定它进哪个克隆材质
  family: FaceFamily;    // 渲染语义：不透明/裁切/半透/自发光
  model: ModelKind;      // 几何形态：立方/薄板/柱/梁/斗栱/瓦/雕塑
  hex: number;           // 基准色，写进顶点色
  hexTop?: number;       // 顶面异色（草皮、瓦面、台面）
  hardness: number;      // 空手基准秒
  tier: 0 | 1 | 2 | 3 | 4;   // 需要的工具等级，见 §1.3
  flammable: boolean;
  craftable: boolean;
  drop: string;          // 掉落物 key；空串表示不掉
  atlas: number;         // 图集格号 0..255
  solid: boolean;        // 是否挡路（窗棂不挡，栏杆挡）
  opacity: number;       // 遮光等级 0..15，用于室内亮度
}
```

字段看起来多，但每一个都在下游有明确消费者：

- `bgroup` 决定它进哪个克隆材质，进而决定 **draw call 归属**——这是 V2 的账，V3 不能自造第 15 组。
- `family` 决定它进哪个渲染队列。`cutout` 要 `alphaTest`，`translucent` 要排序，`emissive` 要 `MeshBasicMaterial`，三者的渲染状态不同，不能靠一个材质开关糊过去。
- `model` 决定 mesher 走「6 面立方」还是「构件模板」，见 §4。
- `solid` 与 `opacity` 是给 AI 与光照用的：窗棂不挡路但挡光 3 级，灯笼不挡路但发光。

`id` 之所以只给 8 位，是因为 V2 定的存储是 `Uint16Array`，高 8 位要放状态（见 §1.5）。方块总数 62，8 位够用到 255 种，留了 4 倍余量。

### 1.3 工具与采集时长

工具分五级：手 0、木 1、石 2、铜 3、钢 4。采集时长：

```
t = hardness × toolMul(tier)
toolMul: 手 1.0 / 木 0.5 / 石 0.25 / 铜 0.167 / 钢 0.1
若 toolTier < block.tier → toolMul 取 1.0 且 drop 为空（挖得动，但不掉件）
```

举三个具体值：青砖（硬度 2.4，tier 1）空手 2.4 s、木器 1.2 s、石器 0.6 s；汉白玉（2.8，tier 2）空手 2.8 s、石器 0.7 s；钢块（4.4，tier 3）铜器 0.73 s、钢器 0.44 s。这些数字必须与 UI 上的「预计耗时」逐条一致，否则玩家会觉得进度条在骗人——所以它们进断言（A3）。

**为什么用乘法而不是减法**：减法在高硬度端会归零（4.4 − 4 = 0.4 s），低硬度端会变负；乘法在任何档位都保持「工具越好、边际收益递减」的形状，且不会出现负时长。

### 1.4 掉落：宋式构件是可拆的

这条是「中式」与 Minecraft 默认行为最不一样的地方，必须单独写。

Minecraft 的默认语义是「挖掉方块 → 掉这个方块」。宋式木构则相反：**榫卯结构的构件本来就是可拆装的**，一根额枋从梁架上取下来仍是那根额枋，不会变成「额枋碎片」。所以：

- `斗栱 / 额枋 / 檐柱 / 格子门 / 直棂窗 / 寻杖栏杆` 掉落**整件**，哪怕用错工具。理由写在明面上：这些是榫卯件，不是整料。
- `青砖 / 城砖 / 方砖 / 条石 / 汉白玉` 用低于 `tier` 的工具砸，掉落**碎料**（配方里的「碎石」），不掉整砖。理由：烧结砖与石材是整体受力，砸开就废。
- `瓦当 / 滴水 / 鸱尾 / 脊兽` 用错工具掉「碎瓦」，用对工具掉整件。这条直接对应现实：瓦当是屋面最容易被完整取下的构件，也是文物里存世最多的一类。
- `树叶 / 稻草 / 茅草顶` 掉落自身 1 个，但**不传播**（不做 Minecraft 的叶子 decay）。

这套规则的意义不只是「拟真」，它还决定了 V4 的经济：如果拆房能无成本地回收整砖，玩家就会把城市当矿场拆。所以还要加一条硬约束：**烘焙城市的几何不可拆**（V2 §0 的 `city_*` 隔离），可拆的只有玩家自己放的方块与 V4 的矿洞。

### 1.5 状态位

`Uint16Array` 的高 8 位：

| 位 | 含义 | 取值 |
|---|---|---|
| 0–3 | 朝向 | 0..15，绕 Y 每 22.5° 一档；构件类只用 0/4/8/12 四向 |
| 4–5 | 变体 | 瓦当四纹样、砖四色差、木四纹理偏移 |
| 6 | 含水 | 0/1，影响是否导电（V5 红石等价物）与重量 |
| 7 | 预留 | 现阶段恒 0，留给「附着物」（如墙上的灯） |

朝向为什么给 16 档而不是 4 档：栏杆与格扇需要 8 向（斜院墙、八角亭），斗栱需要 4 向加转角特例。16 档一次给够，避免以后改存储布局——**存储布局是最贵的技术债**，改一次要迁移所有存档。


### 1.6 放置规则与朝向推断

方块放置不是「点哪放哪」，有四条规则必须先定，否则同一套方块在不同玩家手里会拼出完全不同的东西。

**朝向推断**。水平朝向取玩家视线反方向最近的 90°；构件类（栏杆、额枋、寻杖）优先沿相邻同类方块的轴向吸附，没有邻居才用玩家朝向。这条决定了「沿着已有栏杆继续接」是自然的，而不是每放一段就转一次向。斗栱另按所在柱头的主轴取 4 向，转角铺作取变体位。

**依附规则**。瓦当、滴水必须「下方是屋面且前方临空」；窗棂必须「左右或上下有墙/框」；灯笼必须「上方有支撑」；匾额必须「背后是墙」。不满足时放置失败并给出一句具体提示（「瓦当只能放在檐口」），而不是静默失败——静默失败会让玩家以为是按键没响应。

**支撑检查**。放置承重类方块（台基、檐柱、额枋）时向下做一次 8 格支撑查询，无支撑则拒绝。V5 的结构完整性会做更严格的版本（含悬挑与倾覆），V3 只做这一层最低保障，避免两卷各写一套互相打架的规则。

**禁止区**。`protected` 的烘焙几何、矿脉生成器保留的区块、POI 半径 2 m 内，一律不可放置。这条与 V2 §0 的所有权隔离是同一件事的两面：V2 保证体素不会进合并，V3 保证玩家不会把方块糊到地标脸上。

**快速连放**。按住 Shift 沿视线连续放置同种方块，步长 1 m，单次最多 8 格，遇到不合法位置即停。上限 8 是为了防止一次误操作铺出几百个方块后无法撤销。

### 1.7 与既有系统的接口

- **与 V4**：配方产出的是 `key`，不是 `id`。放置时用 `key` 查 `BLOCKS`，这样存档跨版本仍可读——`id` 会随表调整而漂移，`key` 不会。
- **与 V5**：蓝图只存 `key + state`，不存世界坐标以外的任何东西；蓝图粘贴时逐格走一遍 §1.6 的四条规则，不合法的格子跳过并在 UI 上计数。
- **与 V8**：`solid=false` 的方块（窗棂、灯笼）不参与寻路阻挡；`opacity` 参与室内亮度，灯笼的 15 级光会覆盖 5 m 半径。
- **与 V11**：体素 mesher 的单块耗时必须进性能预算表，与 `bake.ts` 的 flush 耗时并列记账，不能混在「其他」里。

## 2. 材质组容量：62 种方块如何不撑爆 14 个组

### 2.1 先把 V2 的账接过来

V2 §1.3 定了合并策略 A3：每（沙盒 × 材质组）一个 Mesh，预分配大缓冲，脏区块用 `addUpdateRange` 局部上传。按 5 沙盒 × 6 克隆组算，体素层的 draw call 增量是 **+30**，与方块种类数无关。

这句话是本卷最重要的一句：**draw call 的增长维度是「沙盒 × 材质组」，不是「方块种类」。**

所以「上百种方块会不会炸 draw call」的正确答案是：不会，只要它们仍然落在这 6 个材质组里。真正会炸的是另外两条路——每种方块一个材质（62 × 5 = 310 个 draw call），或者按空间再分桶（沙盒内再切 16 m 桶，48 区块 × 6 组再乘桶数）。这两条都必须否决。

### 2.2 四个方案

| 方案 | 做法 | draw call | 62 种方块能否区分 | 代价 |
|---|---|---|---|---|
| A 每方块一材质 | 62 个材质实例 | 62 × 5 = 310 | 能 | 状态切换爆炸，直接否决 |
| B 组内分桶 | 每组再按 16 m 切 | 30 × 桶数（约 4）≈ 120 | 不能 | 桶把同材质拆碎，`addUpdateRange` 的连续段假设失效 |
| C 顶点色 + 单一贴图 | 沿用 Baker 现状，只靠顶点色 | 30 | 只能区分颜色，不能区分纹样 | 砖缝、瓦当纹、窗棂格心全部丢失 |
| **D 6 组 + 图集 + 状态位** | 每组一张图集，UV 改为格内采样 | **30（不变）** | 能 | 显存 +5.3 MB；UV 语义改变 |

**A 否决**：310 个 draw call 是当前峰值 527 的 59%，只为一个可有可无的「每方块独立材质」——而独立材质能提供的，图集全都能提供。

**B 否决**：V2 的 A3 依赖「每个区块在缓冲里占一段连续区间」，分桶会把同一区块的顶点拆到不同桶里，`addUpdateRange(start, count)` 的 `count` 就不再是「这一区块的面数」，局部上传退化成整体上传。**这是与 V2 的直接冲突，不是偏好问题。**

**C 否决**：Baker 现状确实是 `vertexColors: true` + 每组一张世界平铺贴图，但它的 UV 是 `scaleGeoUV(geo, 0.24, dims)`（`bake.ts:773`），即每 0.24 m 一个纹理周期。1 米方块的顶面只采到 0.24 个 UV 单位，砖缝永远不会落在方块边界上；更硬的是 `leaf/trunk/water/glow` 四组连 uv 缓冲都没有（`bake.ts:591` 的 `UV_GROUPS`），树叶方块想用 alpha 裁切都做不到。

### 2.3 方案 D 的具体形态

**图集**：1024×1024，16×16 格，每格 64 px，四周留 4 px padding，实际内容 56 px。62 种方块占 62 格，留 194 格给后续扩展。只做 albedo，不做 normal——1 米方块的棱角由面法线本身给出，再叠法线贴图在 4 px/m 的采样率下只会产生噪点。

**UV 语义**：从「世界平铺」改为「格内采样」。每个面取该方块 `atlas` 格的四角，内缩 4 px：

```
u0 = (col * 64 + 4) / 1024, u1 = ((col + 1) * 64 - 4) / 1024
v0 = (row * 64 + 4) / 1024, v1 = ((row + 1) * 64 - 4) / 1024
```

代价是**同一材质内的纹理不再连续**：一堵青砖墙由 20 个方块拼成，每块都从格子的左上角重新开始，砖缝会在方块边界处断开。这在 Minecraft 里是常态，但在本项目的写实基调下会显得「一块一块」。处理办法不是回到世界平铺，而是**让图集内容本身对齐方块边界**：青砖格画 4 皮砖、每皮 8 块，正好 1 米见方；筒瓦格画 4 垄，正好 0.25 m 一垄。这样断开处正好是砖缝/瓦缝，视觉上反而更整齐。这条要求写进图集规范，由 A6 断言检查「每格内容的边界像素必须是缝或纯色」。

**材质克隆**：沿用 V2 的 6 组克隆，但每个克隆体做两件事——`map` 换成图集（**新实例，不共享**），`vertexColors` 保持 `true`。这样：
- 顶点色仍承担每块的明度抖动（±6%）与顶/侧面差（顶面 ×1.06，侧面 ×1.0，底面 ×0.82），62 种方块不会看起来像 62 张复制贴图。
- `map` 是新实例，不与 Baker 共享，改 `repeat/offset` 不会污染全城。
- `onBeforeCompile` 因克隆自动回到空实现，`plasterHook` 的按 Y 色带不会作用在方块上。

**四族与六组的关系**必须说清，否则会以为我在推翻 V2。`family` 是渲染语义（要不要 `alphaTest`、要不要排序、要不要 `Basic`），`bgroup` 是材质归属（进哪个克隆）。两者是多对一：`opaque` 覆盖 `wall/earth/ground/wood/metal/ceramic/ash`，`cutout` 覆盖 `leaf/wood`（窗棂），`translucent` 覆盖 `water`，`emissive` 覆盖 `glow`。**一个 bgroup 内可以同时有 opaque 与 cutout 方块**（木组既有木板壁也有窗棂），这时按 `family` 把同一区块的几何拆成两个 draw range，而不是新增材质。

### 2.4 代价

| 项 | 数值 | 说明 |
|---|---|---|
| 显存 | +5.3 MB | 1024² RGBA = 4 MB，含 mipmap ×1.33 |
| UV 语义 | 世界平铺 → 格内采样 | 砖缝需重新对格，见上 |
| 图集生成 | 约 40 ms（估算，未实测） | 62 格 canvas 绘制；超 80 ms 挪 Worker |
| draw call | 不变（+30） | 这是方案 D 相对 A/B 的核心优势 |
| 材质数 | +6（克隆） | 与 V2 一致，未新增 |

**一个必须承认的损失**：图集让「同一材质的连续表面」失去纹理连续性。对砖墙、瓦面可以用「图集内容对齐边界」补救；对夯土墙这种本来就没有规律缝线的材质，补救不了，只能靠顶点色抖动掩盖。这是方案 D 的真实代价，不写在纸面上就会在验收时被当成 bug。


### 2.5 六组材质的关键参数必须逐字段复刻

体素方块与烘焙墙体经常并置（玩家在城墙边砌一段砖），如果两边的材质参数不同，接缝处会出现一条明显的「亮度台阶」。下面六个值抄自 `bake.ts:1467-1493`，克隆时必须原样保留，只换 `map`：

| 组 | 材质类 | 必须复刻的参数 |
|---|---|---|
| wall | MeshLambertMaterial | `emissive: 0x3a3d48`（夜景补光，漏掉后新墙在夜里发黑） |
| roof | MeshStandardMaterial | `DoubleSide`、`roughness: 0.93`、`emissive: 0x171b22`、`emissiveIntensity: 0.55` |
| ground | MeshStandardMaterial | `roughness: 0.96`、`metalness: 0` |
| wood | MeshStandardMaterial | `roughness: 0.82`、`metalness: 0.03` |
| earth | MeshStandardMaterial | `roughness: 0.96`、`metalness: 0` |
| ash | MeshStandardMaterial | `roughness: 0.95`、`metalness: 0.02` |

其中 `wall` 的 emissive 最容易漏：它不是装饰，是给夜景补的最低亮度。实测现象是「白天看不出、夜里新墙比老墙黑一截」。这条由 A7 的扩展断言覆盖——克隆体的 `emissive.getHex()` 必须与原体相等。


### 2.6 图集的打包、压缩与远处降级

**打包顺序**按 `bgroup` 聚簇，而不是按 `cat`。原因是将来若图集扩到 2048²（256 格 → 1,024 格），同一组的方块必须尽量落在同一页里；一个木组的窗棂被挤到第二页，就意味着木组要多一个材质实例，draw call 从 30 变 36。现在 62 格远没到上限，但打包顺序要一次定对，否则扩容时得重排。

**不做纹理压缩**。项目约束是零外部资产、可离线运行，图集由 canvas 在运行时生成，没有离线 KTX2/Basis 工具链；硬上压缩只会引入一个新的构建依赖。代价是显存按 RGBA8 计（4 MB + mipmap），而不是压缩格式的 1 MB 级。这个代价在 62 种方块下可接受，扩到 300 种时再谈。

**不做 2048²**。2048² 的显存是 1024² 的四倍，而 62 格只用了 1024² 的 24%。升到 2048² 的唯一理由是「每格要更细」，但 1 米方块在 4 px/m 的屏幕采样率下，64 px 的格子已经过剩。

**远处降级**。距离超过 64 m 时，整个沙盒切换到「无图集」材质（只有顶点色，没有 `map`）。这不是逐方块降级，是**整沙盒**降级——因为逐块换材质会打断合批，而整沙盒本来就是独立 mesh，换材质不增加 draw call。副作用是远处方块变成纯色块，但 64 m 外的 1 米方块在 1080p 下不到 10 px，纹理本来也读不出来。这条同时解决了 mipmap 渗色：远处根本不采样图集。

## 3. 破坏/放置的几何重建

### 3.1 与 V2 A3 的关系

V2 已经把「重建粒度 = 16³ 区块 + 边界标 6 邻」「单区块 0.8–1.6 ms」「4 ms/帧、2–4 块」定完了。V3 不再重复，只补三件 V2 没写的：**面剔除时每个面填什么**、**一次编辑的完整状态变更序列**、**存档里怎么只存改动**。

### 3.2 面剔除与每个面的数据

对每个非空体素，检查 6 个方向；邻居为空（或为 `cutout/translucent` 且不遮挡）则产出一个 quad。每个 quad 6 个顶点（两个三角），每个顶点 32 B：

| 字段 | 类型 | 值 |
|---|---|---|
| position | Float32×3 | 世界坐标，先算区块内局部再整体平移 |
| normal | Int16×3 normalized | 6 个轴向之一，量化误差 < 1/32767 |
| color | Uint16×3 normalized | `hex` × 面系数 × 每块抖动，量化误差 < 1/65535 |
| uv | Float32×2 | 该面在图集格内的四角，见 §2.3 |

**面系数**是让方块有体积感的最低成本手段：顶面 1.06、侧面 1.00、底面 0.82。它替代了 AO——V2 的预算里没有逐顶点 AO 的位置，而 1 米方块在 4 px/m 的采样率下，AO 的渐变本来也读不出来。

**邻居判定要区分三种遮挡**：

- `solid=true` 的不透明方块：完全遮挡，不产面。
- `cutout`（窗棂、树叶）：**不遮挡**，两侧都要产面，否则透过窗棂会看到空洞。
- `translucent`（水、冰）：水面与水面相邻时不产面（避免水下看到一层内壁），水面与空气相邻时产面。

这三条如果写成「非空即遮挡」，窗棂会变成实心板、水面会出现内壁；如果写成「非空即不遮挡」，实心墙内部会多出成倍的面。它们进 A2 断言，用三个最小场景逐条验。

### 3.3 单区块的面数与字节

V2 给的实测口径是「平均 300–900 quad」，V3 补上界：

```
全实心区块的暴露面 = 6 × 16² = 1,536 quad = 3,072 tri
顶点 = 1,536 × 6 = 9,216
字节 = 9,216 × 32 = 294,912 B ≈ 288 KB
```

典型地表区块（上半空、下半实）约 256（顶）+ 4×16×8（侧）= 768 quad，即 V2 区间中段。玩家搭的薄壳建筑（墙、顶、地板）约 300–900 quad，与 V2 一致。

一个沙盒满配 48 区块全部按 900 quad 计：48 × 900 × 6 × 32 = 8.29 MB，与 V2 的「单沙盒预分配 8.45 MB」基本吻合（V2 按材质差异化分配，总数略高）。两卷的数字能对上，说明预算没有各说各话。

### 3.4 一次编辑的完整序列

```
1. 命中判定：射线 → 体素坐标 → 读 BlockDef
2. 合法性：目标非 protected；工具 tier 达标，否则只掉碎料（榫卯件例外，见 §1.4）
3. setBlock(x,y,z,0)：写 blocks，count--
4. markDirty(自身区块)
5. 若 lx/ly/lz ∈ {0,15}：额外标对应的面邻居（角点最多 4 块）
6. 掉落物进背包（整件或碎料，见 §1.4）
7. 若方块是容器（箱柜）：先弹出内容物，再删方块
8. 若方块承重（V5 结构完整性）：触发一次支撑检查
9. 队列：被编辑块走同步快路径，其余进帧预算队列
10. 存档：该区块标 dirty，`VoxSave.flush()` 时只序列化 dirty 区块
```

第 5 步的「最多 4 块」是 V2 的结论（角点最坏 4 块），V3 补一个容易漏的例外：**斜向相邻不影响面剔除**，因为面剔除只看 6 邻，不看 26 邻。所以 `(0,0,0)` 角点标的 4 块是「自身 + 3 个面邻居」，不是 7 块。

### 3.5 队列与帧预算

V2 定 4 ms/帧、单块 0.8–1.6 ms、一帧 2–4 块。V3 补优先级与积压处理：

```ts
// src/voxel/remesh.ts
interface Job { key: number; dist2: number; seq: number }
// 排序键：先按「是否被编辑」（同步快路径），再按 dist2，再按 seq（防饿死）
```

- **同步快路径**：玩家刚敲的那一块当帧重建，不走队列。理由是手感——延迟一帧（16.7 ms）在连续敲击时会被感知为「粘手」。单块 0.8–1.6 ms 在 4 ms 预算内。
- **队列**：其余脏块按到相机距离升序，每帧消耗剩余预算（4 ms − 已用）。队列空时不分配对象。
- **积压**：连续爆破（V5 的炸药等价物）一帧可能脏 30+ 块。此时**不降级、不跳帧**，而是把队列上限设为 64，超出部分合并为「整沙盒重建」一次（V2 的 A2 路径，40–80 ms），并在 UI 上显示一次进度。这是「宁可卡一下，不要卡每帧」的取舍。
- **饿死保护**：`seq` 递增，距离排序里对 `seq` 超过 120 帧的作业强制提前，避免远处一直不重建导致玩家回头看见空洞。

### 3.6 碰撞与行走面

`walkSurfaceY()`（`src/actors/behaviors.ts:137`）读的是烘焙期建好的 4 m 网格 `WS_GRID`，体素编辑后这张表就过期了。V2 没有展开这一条，V3 给出改法：

查询顺序改为「体素覆写 → 烘焙网格」。覆写层只维护玩家 64 m 内的 `Map<4m格, y>`，`setBlock` 时同步更新该格与 8 邻格的最高实心面。代价是人群 AI 每帧数千次调用各多一次 Map 查找——必须先测 `walkSurfaceY` 的调用频次与单次成本，若 >0.05 ms/千次就改按区块 `Uint8Array` 直接索引。

**这条是待实测风险，不是已解决项。** 写在这里是为了让 V11 在性能评审时能直接找到它。

还有一条容易漏的：**放置方块会改变行走面，但不会改变导航图**。`buildNav()` 生成的路网是烘焙期的静态数据，玩家在路中间砌一堵墙，AI 仍会撞上去。V3 不解决导航重算（那是 V8 的题目），但要求放置方块时若与导航边相交，给该边打 `blocked` 标记，AI 走到时按「贴墙滑动」处理（`behaviors.ts:947` 已有该分支）。

### 3.7 存档：只存改动

体素数据不能全量存。一个沙盒满配 48 区块 × 8 KB = 384 KB，5 个沙盒 1.88 MB，超过 localStorage 的常规配额（约 5 MB）里能接受但没必要。

方案：只序列化 `count > 0` 且 `dirty` 的区块，键 `cq_vox_<sandboxId>`，值是一段 RLE：

```
[chunkIndex:uint8][runCount:uint16][(runLength:uint16, value:uint16)...]
```

未编辑的区块不写盘，读档时按 V4 的矿脉/地形重新生成。这意味着**读档后的世界 = 种子生成的基线 + 玩家改动**，与 Minecraft 的「区块差异存档」是同一套思路，也与 V2 §6 的确定性契约一致。

代价：如果玩家在矿洞里挖了一条长巷道，改动区块可能有几十个，单次存档约 20–60 KB（估算），可接受。但如果玩家把整个沙盒挖空，48 区块全 dirty，单沙盒约 384 KB × 压缩比 5–20 = 19–77 KB，仍在可接受范围。


### 3.8 破坏反馈：粒子、音效与高亮

破坏如果没有反馈，玩家会怀疑「到底挖没挖动」。三层反馈都要做，但都要压预算：

- **碎屑粒子**：每次破坏 8–12 个，用 `InstancedMesh` 池（沿用 `actors/pools.ts` 的 `InstSet` 思路），寿命 0.6 s，重力 −9.8，落地即回收。同时存在上限 200 个，超出按最旧回收。粒子**不参与阴影**——一旦进阴影相机，每次破坏都要重绘一张阴影图，成本远超收益。
- **音效**：石、木、土、金属四类，每类 3 个变体，走 `audio/scape.ts` 的 WebAudio 合成，不引入外部音频文件（项目零外部资产的约束不能破）。
- **高亮**：准星 0.08 s 收缩 + 目标方块 1 px 线框。线框用 `LineSegments` 单独一个对象复用，不为每次破坏新建几何。

代价：粒子与线框合计增加 2 个 draw call，已计入 V2 的 +30 预算余量。若实测超出，先砍粒子数量，不砍音效——声音是判断「挖的是什么材质」最快的通道。

## 4. 中式方块：非立方构件的五个案例

方块化的本质矛盾是：**模数化 ≠ 均质化**。宋式建筑的力量感来自「材分」这套比例系统，不是来自每个构件都是正方体。五个案例的公共解法是——**方块只做定位与碰撞，形制靠「构件模板 + 朝向状态」在方块内叠加子几何**，子几何仍进同一区块 Mesh，不增 draw call，只增面数。

### 4.1 斗栱（铺作）

不能丢的形制：栌斗坐斗、华栱出跳、昂嘴下斜、耍头收头。宋式以「材」为模数，材广 15 分、厚 10 分、栔广 6 分、足材 21 分（**通行说法，具体条文待检索核实《营造法式》卷四**）。

做法：`model='bracket'`，占 1×1×1，内部三层——栌斗收分台体 8 面、华栱十字梁 12 面、耍头斜切 6 面，共 26 面，是普通方块的 4.3 倍。状态位存 4 向，转角铺作另用 1 个变体位。

代价与降级：一朵铺作 26 面，一座三开间厅堂檐下约 20 朵，即 520 面对比整栋 3,000–6,000 面，占 9%–17%。距离 >48 m 时 `model` 降为 `cube`，只保留外轮廓色块——降级由区块 LOD 统一控制，不在 mesher 里写距离分支。

### 4.2 瓦当 + 滴水

不能丢的形制：瓦当是**圆**头不是方头，滴水是**下尖舌片**不是平口。这两件事是宋檐最容易被认出的剪影。

做法：`model='tile'`，前表面加 8 段半圆柱（8 面）+ 圆心凸点（1 面），底面加三角垂片（1 面）。只在檐口一圈出现：20 m 面宽约 80 构件 × 9 面 = 720 面，占整栋的 12%–24%。

失效模式：如果允许铺满整个屋面，面数立刻翻倍，视觉上也会变成「满身疙瘩」。**必须由放置规则限制**——瓦当只能放在「上方无方块且前方临空」的檐口位，这条写进 A6。

### 4.3 寻杖栏杆

不能丢的形制：望柱头、寻杖的「细」、华板/蜀柱的「疏」。栏杆的美全在细杆与空当，一旦做成实心矮墙就全毁。

做法：拆三种方块——望柱 10 面、寻杖 `beam` 断面 0.12×0.12 m 共 6 面、华板 `panel` 厚 0.06 m 共 4 面。3 m 一段 = 2 望柱 + 3 寻杖 + 2 华板 = 46 面，对实心 3 个方块 36 面只多 28%，但形制差别是「栏」与「墙」。

### 4.4 窗棂

不能丢的形制：直棂、冰裂纹、步步锦、一码三箭四种辨识符。做法：`model='panel'` + `family='cutout'`，**一个方块两个三角面**，图案全交给图集 alpha。这是全表性价比最高的一类：2 面承载最大视觉信息。

代价：`alphaTest: 0.5` + 4 px padding + `anisotropy: 4` 防 mipmap 闪烁；窗棂必须 `solid=false`、`opacity=3`，否则室内全黑、AI 也过不去。这三条写进 `BlockDef`，不靠材质全局设置。

### 4.5 鸱尾 / 脊兽

不能丢的形制：鸱尾向内卷的鱼尾、脊兽蹲坐剪影，纯剪影识别，细节可省轮廓不可错。做法：`model='sculpt'`，占 2×1×1，顶点偏移表存 `src/voxel/sculpt.ts`（24 顶点 × 3 偏移），一件约 20 面。

代价：偏移烘在局部系，不能实时旋转，4 向各存一份表，内存 ×4；全城脊饰 <200 件，可接受。>64 m 换深灰 `cube`，剪影交给脊线本身。

**公共结论**：非立方构件不是「把方块做成立方体再贴图」。宋式檐下是**透空**的，透空必须真几何；用贴图假装立体，斜视角立刻穿帮。


### 4.6 形制编码的两种做法与取舍

非立方构件在数据上只有两条路：

- **微网格**：每个方块存 16³ 的位掩码（4,096 位 = 512 B），mesher 按 3D 填充生成面。自由度最高，任何形状都能雕。代价是单块 mesher 的邻居检查从 6 次变成 24,576 次（与 V2 的单区块检查同量级），一块斗栱的成本等于重建一个区块。
- **模板**：每种 `model` 一份共享顶点表，实例只存朝向与变体。斗栱 26 面 = 156 顶点 × 32 B ≈ 5 KB，62 种方块里只有 6 种需要模板，合计不到 30 KB。代价是形状固定，不能任意雕。

选**模板**。理由是 V2 把单块预算压在 0.8–1.6 ms，微网格会让非立方块的 mesher 成本翻 8 倍，直接把「一帧 2–4 块」打到「一帧 0–1 块」。形制自由度的损失用「多几个模板」补，而不是用「每块都能雕」补——前者是加数据，后者是加一个数量级的运行时成本。

`sculpt` 用的是偏移表（24 顶点 × 3 偏移），本质仍是模板族：顶点数固定，只是坐标可调。它不能实时旋转，所以 4 向各存一份，内存 ×4，但全城脊饰不到 200 件，这点内存可以忽略。

## 5. 冲突与代价

| 冲突 | 表现 | 代价 | 处理 |
|---|---|---|---|
| 静态城市 vs 可破坏 | 烘焙几何一次性合并，砸一块留洞且无法局部重建 | 全量重跑一次装配约 0.6 s（`bake.ts:1302` 实测 flush 0.63 s） | 城内烘焙几何标 `protected`，可拆的只有玩家方块与矿洞 |
| 材质补丁 | `infill.ts` 的三个 `onBeforeCompile` 按世界 Y 做色带 | 1 m 方块会继承墙基/墙帽色 | 用克隆（副本不带钩子，已实测），并加 A7 回归 |
| 贴图共享 | `clone()` 与原体共享 `map` 实例 | 改贴图会污染全城 | 克隆体赋新图集实例，禁止就地改原贴图 |
| UV 语义 | Baker 0.24/m 世界平铺 vs 图集格内采样 | 砖缝在方块边界断开 | 图集内容对齐方块边界，A6 检查边界像素 |
| 面数 | 非立方构件 20–26 面/块 | 三开间檐下 +520 面，占整栋 9%–17% | 远距离降 `cube`，由区块 LOD 统一控制 |
| 内存 | 顶点预分配 42.2 MB（V2 口径） | 占现有 1.1 GB 的 3.8% | 沿用 V2 的差异化容量表，不额外加 |
| 载入 | 首屏 8.3–9.7 s 逼近 12 s | 体素层若进首屏必超 | 懒加载：首次进入沙盒才初始化，首屏 +0 |

**一句总结**：V3 没有增加一个 draw call，也没有增加一个材质组。它做的是把「62 种方块」压缩进 V2 已经买过单的 6 个克隆材质里，代价是 5.3 MB 显存与一处纹理连续性的损失。
