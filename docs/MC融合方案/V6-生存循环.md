## 0. 先纠正三处路径与事实

写之前必须先对齐，否则整卷会建在错误前提上。

**0.1 任务书写的 `src/actors/player.ts` 不存在。** 玩家的实际文件是 **`src/game/player.ts`**（431 行）。`src/actors/` 下只有 `actions.ts / behaviors.ts / crowd.ts / heroes.ts / pools.ts / types.ts`。本卷所有对「玩家」的改动都落在 `src/game/player.ts`。

**0.2 昼夜时钟默认是停的。** `TimeOfDay.paused = true`（`src/core/palette.ts:36`），`speed = 1/420`（`:35`，一昼夜 7 分钟）。开局停在黄昏（`phase = 0`）。这意味着**任何挂在 `phase` 上的生存结算都不会走**——饥饿、天气、作物全都推不动。

**0.3 `speedScale` 每帧被 world 覆盖。** `world.ts:1271` 在 `update()` 里无条件写 `this.player.speedScale = near ? 0.55 : 1;`。任何状态效果若也写 `speedScale`，会在同一帧被抹掉。这是本卷最容易踩的坑，第 5 节给解法。

## 1. 四维：生命 / 饥饿 / 体力 / 精神

### 1.1 存储：整数千分位

```ts
// src/survival/Vitals.ts
export interface Vitals {
  hp: number;       // 0–1000
  hunger: number;   // 0–1000
  stamina: number;  // 0–1000
  spirit: number;   // 0–1000
  /** 界域附加维：天宫用香火，地府用阴寿，人间恒 0 */
  extra: number;
}
export const FULL = 1000;
export const toPct = (v: number): number => Math.round(v / 10);
```

不用 `0–100` 浮点，用 `0–1000` 整数，理由有三条，都不是洁癖：

1. **确定性存档**。V10 要求跨平台 lockstep。浮点最后一次舍入在 x86 与 ARM 可能差 1 ULP，`hunger = 0.0000001` 与 `0` 会让「饿死」在两台机器上差一帧，进而在多人局里分叉。整数没有这个问题。
2. **显示精度够**。`toPct()` 给 UI，一位小数，肉眼看不出和浮点的差别。
3. **状态效果的百分比乘法可逆**。`×0.85` 用 `Math.round(v * 0.85)`，千分位下最大误差 0.5/1000，叠十层也不到 0.5%，不会出现「吃了三口饭还是 0」。

### 1.2 消耗与恢复曲线

单位：**每秒**，千分制。一昼夜按 `TimeOfDay.speed = 1/420` 即 **420s** 折算。

| 维 | 静止 | 步行 | 奔跑 | 游泳 | 骑乘 | 睡眠 |
|---|---|---|---|---|---|---|
| 饥饿 | −0.95 | −1.52 | −2.47 | −2.85 | −0.60 | −0.20 |
| 体力 | +70 | −4 | −35 | −60 | −5 | +110 |
| 精神（昼） | +1.5 | +1.5 | +1.5 | +1.5 | +1.5 | +12 |
| 精神（夜） | −3.4 | −3.4 | −3.4 | −3.4 | −3.4 | +12 |

几处刻意的对齐：

- **饥饿满→空 = 1053s ≈ 2.5 昼夜**（1000 / 0.95）。跑起来 405s 就空。这个节奏让「出门带干粮」成为真需求，但不至于走两条街就要吃。
- **精神整夜刚好掏空**。夜间时长 = `(0.86 − 0.16) × 420 = 294s`，`294 × 3.4 = 999.6`。这不是巧合，是按 `crowd.isNight` 的判定区间（`world.ts:1257`，`phase > 0.16 && phase < 0.86`）反算的：**熬一整夜 = 精神见底**，睡一觉（+12/s × 60s = 720）能补七成。
- **体力满→空 = 28.6s 全速跑**（1000 / 35）。`RUN_SPEED = 8.2`（`player.ts:34`），28.6s 跑 235m——正好是虹桥到州桥一个来回。站着回满 14.3s。这个「跑得动但跑不远」是设计的核心手感。

### 1.3 阈值分档与惩罚

| 维 | 区间 | 档名 | 效果 |
|---|---|---|---|
| hp | > 0 | 存活 | — |
| hp | = 0 | 倒下 | 进入第 4 节死亡流程 |
| hunger | ≥ 850 | 饱食 | 体力恢复 ×1.5 |
| hunger | 200–849 | 正常 | — |
| hunger | 1–199 | 饥饿 | 体力恢复 ×0.5，`hp −0.05/s` |
| hunger | = 0 | 饿殍 | `hp −0.5/s`，`speedScale ×0.7` |
| stamina | > 200 | 正常 | — |
| stamina | 1–200 | 疲乏 | 跳跃初速 ×0.7（7.5 → 5.25，跃高 1.28m → 0.63m） |
| stamina | = 0 | 力竭 | `speedScale ×0.44`（即强制走路：`3.6 / 8.2 = 0.439`） |
| spirit | > 200 | 正常 | — |
| spirit | 1–200 | 恍惚 | 相机抖动 0.05rad，交互半径 ×0.7 |
| spirit | = 0 | 崩溃 | 强制睡眠 20s，醒来 `spirit = 300` |

跳跃那一条要解释：`player.ts:347` 写死 `this.vy = 7.5`，重力 `22`（`:343`），跃高 `v²/2g = 7.5²/44 = 1.28m`。乘 0.7 后 `5.25²/44 = 0.63m`——刚好跨不过一格台阶（`WS_STEP_UP = 0.95`，`behaviors.ts:47`）。**这是有意的**：疲乏时连台阶都要绕，玩家才会珍惜体力。

### 1.4 三界差异化

不是换皮，是**每界换一套规则**。

| | 人间（y≈0） | 天宫（y≈2150） | 地府（y≈−260） |
|---|---|---|---|
| 生命 | hp 0–1000 | 仙体完整度，同名不同义 | hp 仍存在，但**阴寿**才是真血条 |
| 饥饿 | 正常消耗 | **冻结**（仙体不饥） | 冻结，但饥饿值保留原数，回人间继续 |
| 体力 | 正常 | 消耗 ×0.5（仙体轻） | 消耗 ×1.3（阴气重） |
| 精神 | 正常 | 夜 −1.4（有仙光庇护） | 夜 −6.1（阴气侵体） |
| 附加维 | 无 | **香火** 0–1000，−0.5/s | **阴寿** 600s 倒计时 |
| 核心压力 | 谋生 | 戒律 | 业力 |
| 死亡后果 | 昏迷、掉钱 | 贬谪、扣香火 | 魂散、阴德清零 |

**天宫：仙体不饥，但受戒律。** 饥饿冻结意味着天宫没有「吃饭」这个循环，取而代之的是**香火**——每 2000s（4.8 昼夜）耗尽，靠供奉（瑶池、南天门香炉）补充。香火耗尽不是死，是「金光黯淡」：`hp` 上限降到 600，且无法使用天宫传送。戒律是第二条：在天宫说谎（对话选项）、杀生、偷供品，各记一次，累计 3 次触发「贬谪」直接送回人间。**天宫的生存压力是行为约束，不是数值约束。**

**地府：阴寿是倒计时，不是血条。** 进入地府自动获得 600s：受击 −30s、击杀亡魂 −60s、掉入忘川 −120s。阴寿归零 = 魂散。这个设计的关键差别是——**在地府里，你不能靠「回血」活着，只能靠「少挨打」**。玩家会自然地从「战斗」转向「潜行」，这正是地府该有的玩法。

**业力**是只增不减的 0–9999 计数：杀亡魂 +3、毁坏冥器 +5、超度 −20。业力 ≥ 100 时挂「业障」状态（第 2 节 19 条），商人加价 50%，掉落翻倍。业力**不随死亡清零**——这是三界里唯一一个「死了也不会变好」的数值，也是地府叙事的支点。

### 1.5 一昼夜的资源曲线

把昼夜相位与精神收支放在同一张表上，才能看出节奏对不对。一昼夜 420s（`palette.ts:35`），按 `crowd.isNight` 的判定区间（`world.ts:1257`）切成五段：

| 时段 | phase | 时长 | 精神净值 | 场景 |
|---|---|---|---|---|
| 黄昏 | 0.00–0.16 | 67.2s | +100.8 | 开局，全城最亮，适合赶路与采买 |
| 夜 | 0.16–0.42 | 109.2s | −371.3 | 夜市、瓦子、酒楼开门 |
| 深夜 | 0.42–0.68 | 109.2s | −371.3 | 只剩更夫与鬼祟，地府压力最大 |
| 黎明 | 0.68–0.86 | 75.6s | −257.0 | 天色转亮，摊贩回场 |
| 暮归 | 0.86–1.00 | 58.8s | +88.2 | 回到黄昏，循环闭合 |

整夜（0.16–0.86）共 294s，精神净 −999.6 —— **恰好一管**。这不是巧合，是按 `isNight` 的区间反算出来的设计常数；若哪天 `isNight` 的边界改了，这个「刚好见底」就会失准，所以 A6-2 把它固化成了断言。

一日总账：

```
昼 126s × (+1.5) = +189
夜 294s × (−3.4) = −999.6
净 −810.6/昼夜（不睡）
```

睡眠 +12/s，因此：

| 睡眠时长 | 回复 | 一昼夜净变化 | 可持续性 |
|---|---|---|---|
| 0s | 0 | −811 | 1.23 昼夜后崩溃 |
| 60s | +720 | −91 | 约 11 昼夜后见底，需茶馆补 |
| 90s | +1080 | +269 | 可持续 |

**结论：每天睡 90 秒是可持续线，睡 60 秒是慢性消耗。** 这个差值只有 30 秒，但它制造了一个真实的选择：省下 30 秒去多跑一趟货，还是老实睡够。玩家会在第三天感觉到差别（精神条开始发黄），而不是当场被惩罚——这是「渐进压力」而非「突然死亡」，符合生存类游戏的基本节奏。

饥饿的账更宽松：静止 1053s（2.5 昼夜）、步行 658s（1.57 昼夜）、奔跑 405s（0.96 昼夜）。也就是说**只要在城里正常逛，一天吃两顿就够**；跑长途才需要带干粮。这个梯度让「食物」是补给品而不是每五分钟一次的打扰。

## 2. 状态效果

### 2.1 状态机

```ts
// src/survival/Status.ts
export interface StatusDef {
  id: string; name: string; realm: 'any' | 'renjian' | 'tiangong' | 'difu';
  dur: number;            // 秒；0 = 永久直到解除
  maxStack: number;       // 1 = 不可叠
  exclusive?: string[];   // 互斥 ID
  mod: Partial<VitalsMod>; // 速度/恢复/上限/伤害
  cure: string[];         // 解除途径：'time' | 'herb' | 'sleep' | 'pray' | 'ritual'
}
export interface StatusInst { id: string; until: number; stacks: number }
```

四条规则，缺一条就会出 bug：

1. **同名刷新不叠加时长**：再次触发只把 `until` 推到 `now + dur`，不累加。否则玩家连喝三碗姜汤能获得 15 分钟的湿寒免疫，直接把系统玩坏。
2. **可叠层的只叠数值**，上限 `maxStack`。叠层只影响 `mod` 的系数，不影响 `dur`。
3. **互斥对必须硬拦**：`湿寒 × 上火`、`羽化 × 业障`、`惊悸 × 超度`。互斥不是「不显示」，是**后触发的直接失败并提示**。理由：湿寒与上火同时挂在 HUD 上，玩家会认为系统坏了。
4. **解除优先级**：药 > 仪式 > 睡眠 > 时间。有药时按 E 直接解，不等待自然结束。

覆盖任务点名的六个：**上火（4）、湿寒（5）、惊悸（9）、中邪（10）、羽化（13）、业障（19）**。

三处需要说明的设计意图：

- **湿寒与风寒是两级，不是两条并列**。单次淋雨只得湿寒；湿寒叠两层才转风寒。这给了玩家一个明确的「该烤火了」的窗口，而不是一淋雨就重病。
- **中邪有前置条件（精神 < 300）**。它不惩罚谨慎的玩家，只惩罚熬夜的玩家。这条把「精神」这一维和「事件」缝合起来，而不是让精神只是个数。
- **贬谪是状态不是传送**。它先给 600s 的「不能回天宫」，再触发传送；直接传送会让玩家觉得被系统踢出，而不是「被贬」。

### 2.3 状态之间的连锁

单条状态只是数值，**链才是玩法**。系统必须让状态互相触发，否则 24 条只是 24 个互不相干的减益。

| 链 | 条件 | 结果 |
|---|---|---|
| 雨 → 病 | 淋雨 120s 得湿寒 → 湿寒未解再淋 120s（叠 2） | 转风寒（600s，hp −0.12/s） |
| 夜 → 邪 | 夜间 + 精神 < 300 + 经过纸马铺 30m 内 | 中邪（600s） |
| 酒 → 火 | 醉酒期间再吃炙/炸类 | 上火（180s），且醉酒时长 +60s |
| 摔 → 悸 | 坠落 > 20m 落地 | 惊悸（90s）+ 骨折（若 > 7m） |
| 火 → 寿 | 地府内被鬼火命中 | 磷火附体（180s）→ 暴露 → 更易被围 → 阴寿加速 |
| 业 → 障 | 业力跨过 100 | 业障（永久至业力 < 100），商人加价 50% |

六条链里有三条是**跨系统**的，这是刻意的：

- **「夜 → 邪」把精神、时间、地点三个条件相乘**。玩家不能靠「白天多逛纸马铺」或「夜里待在家」单独规避，必须同时管理三者。这条链让「熬夜」从「数值下降」变成「有具体后果的风险」。
- **「火 → 寿」把地府的三条独立机制缝起来**：鬼火（环境）、阴寿（资源）、围殴（战斗）。玩家一旦被磷火点着，正确的反应是**跳进忘川**（解除条件），而忘川又会触发「忘川迷雾」。这是一个「两害相权」的决策，不是一个「按 E 解除」的按钮。
- **「业 → 障」是唯一一条不可逆的链**。业力只增不减，业障一旦挂上，除非做超度仪式（业力 −20）否则永久生效。它给地府一个「你做过的事会跟着你」的叙事重量，而不是又一个可刷的 buff。

反例也要写清：**不做「饥饿 → 暴怒」这类链**。它看起来合理（饿了脾气差），但会让玩家在低饥饿时同时承受三种惩罚（体力恢复减半、hp 掉、命中下降），叠加后不可玩。状态链的设计原则是**每条链最多两个负面效果**，第三个必须是正面或中性（如「醉酒 +60s」只是延长，不是新增减益）。

### 2.4 状态与既有系统的接缝

`player.applyDisorient(k)` 已经存在（`player.ts:100`），它做的事恰好就是「失向」：把 `speedScale` 压到最低 0.6、写 `fadeHint`。**不要重写它**，只在 `Status` 里给 12 号挂一个 `onApply: () => player.applyDisorient(1)`、`onExpire: () => player.applyDisorient(0)`。

同理，望乡台的「乡愁」已经是硬编码的 `speedScale = 0.55`（`world.ts:1271`），**也不要改写成状态**——它是关卡威胁，不是生理状态，混进状态表会让「解除」语义变得荒谬（玩家会问：吃碗面能不能解乡愁）。

### 2.5 数值的单一真相源

24 条状态 × 4 个字段 ≈ 100 个常数。若散落在各文件，V12 的调参阶段每改一次都要 grep 全仓，且必然漏改。

## 3. 天气与昼夜

### 3.1 与 `palette.ts` 的字段级对齐

`TimeOfDay`（`src/core/palette.ts:33`）暴露的字段：

```
phase  speed  paused
neon  bloom  ambient
skyTop skyMid skyBot fogColor fogDensity
sunColor  sunI  hemiI  fillI
```

天气**只读**这组值，**绝不写回**。原因：`apply(p)` 每次 `update()` 都会用 `STOPS` 重新算一遍全部字段（`palette.ts:49`），写回去等于同帧被覆盖，且会污染 `jump()` 之后的状态。

所以天气是一个**后置乘子**：

```ts
// src/survival/Weather.ts
export interface WeatherMod {
  fog: number;      // 雾密度乘子
  sun: number;      // 主光强度乘子
  hemi: number;     // 半球光乘子
  amb: number;      // 环境光乘子
  exposure: number; // 曝光乘子
  wet: number;      // 0–1，决定湿寒累积速率
  wind: number;     // m/s，影响粒子与帆
  tint: number;     // 雾色偏移色（十六进制）
}
```

### 3.2 八种天气

| 天气 | 界 | fog× | sun× | hemi× | amb× | 曝光× | wet | wind |
|---|---|---|---|---|---|---|---|---|
| 晴 | 人间 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 0 | 0.2 |
| 阴 | 人间 | 1.35 | 0.72 | 1.10 | 1.05 | 0.96 | 0.1 | 0.6 |
| 雨 | 人间 | 1.85 | 0.50 | 1.18 | 1.08 | 0.90 | 1.0 | 1.2 |
| 雪 | 人间 | 1.55 | 0.62 | 1.28 | 1.10 | 1.04 | 0.5 | 0.8 |
| 雾 | 人间 | 3.20 | 0.45 | 1.15 | 1.06 | 0.98 | 0.4 | 0.1 |
| 沙尘 | 人间 | 2.60 | 0.68 | 1.05 | 1.02 | 0.88 | 0 | 3.0 |
| 罡风 | 天宫 | 0.55 | 0.95 | 1.00 | 1.00 | 1.00 | 0 | 6.0 |
| 阴风 | 地府 | 1.90 | 0.55 | 0.85 | 0.90 | 0.90 | 0.2 | 1.6 |

数值不是随手填的。三条约束把它们钉住：

1. **雨天的 `hemi × 1.18 > 1`**：阴天不能只压主光。`applyLighting` 的半球光 `hemiI` 在黄昏是 0.68（`palette.ts:24`），若只压主光不抬半球光，建筑背光面会整片死黑。抬 18% 是把「阴天的漫射光变多」翻译成数字。
2. **雾天 `fog × 3.2`**：`fogDensity` 在街面已经被 `×2.4` 放大过一次（`world.ts:961`），基准值 0.00009 × 2.4 = 0.000216。再 ×3.2 = 0.00069，对应可视距离约 1450m——正好让虹桥看不清对岸，但仍能看见桥本身。**这个数是从「要遮住 1.5km」反推的，不是拍的。**
3. **罡风 `fog × 0.55`**：天宫本来就被 `×0.14` 收敛过（`world.ts:966`）。罡风要「吹散云」，所以是唯一一个小于 1 的雾乘子。

### 3.3 插入点：只有一处

这是本卷最容易做错的地方。`applyLighting`（`world.ts:930`）内部对 `fog.density` 有**四次**赋值：

- `:944` 基准值
- `:961` 按相机高度 ×2.4→1
- `:966` 天宫高度 ×1→0.14
- `:996` 天宫分支 `lerp(fog.density, 0.00006, sf)`
- `:1030` 地府分支 `lerp(fog.density, 0.0046, uf)`

如果在函数内部任何一处乘天气系数，**后面三处会把它覆盖掉**。特别是 `:996` 与 `:1030` 用的是 `lerp(当前值, 常数, 系数)`，天气的影响会随 `sf/uf` 增大而衰减到 0——表现为「在天宫/地府里天气失效」。

**唯一正确的插入点**是 `world.update()` 里 `applyHellDepth()` 之后：

```ts
// src/world.ts:1247-1249 现状
this.applyLighting(t);
this.applyHellDepth();
this.applySkyDomeTint();

// 改为
this.applyLighting(t);
this.applyHellDepth();
this.weather.applyPost(this);      // ← 新增一行，位置不可动
this.applySkyDomeTint();
```

`applyPost` 做的事：

```ts
applyPost(w: World): void {
  const m = this.cur.mod;
  const fog = w.engine.scene.fog as THREE.FogExp2;
  fog.density *= m.fog;
  fog.color.lerp(_tint.setHex(m.tint), 0.35 * (1 - m.sun));
  w.sun.intensity *= m.sun;
  w.hemi.intensity *= m.hemi;
  w.ambientLight.intensity *= m.amb;
  w.engine.renderer.toneMappingExposure *= m.exposure;
}
```

放在 `applyHellDepth()` 之后，是因为地府纵深黑场（`world.ts:1077`）会把雾密度压到接近 0；若天气在它之前乘，会被抹平。放在 `applySkyDomeTint()` 之前，是因为后者只改穹顶 uniform，不动雾与光——顺序上互不干扰，但先天气后天穹更符合「天气改世界色、天穹做最终调色」的层次。

### 3.4 天气对四类对象的影响

**雾与光照**：见 3.2/3.3。

**NPC 行为**：`Crowd` 已有 `isNight` 字段（`crowd.ts:1100`），并在 `ctx()` 里打包成 `BehCtx`（`behaviors.ts:215`、`crowd.ts:1538`）。天气接同一根管子：

```ts
// behaviors.ts:215
export interface BehCtx { nav: NavGraph; spots: SpotRegistry; isNight: boolean; weather: WeatherKind; camPos: THREE.Vector3; t?: number }

// behaviors.ts:803 之后追加
if (ctx.weather === 'rain' || ctx.weather === 'snow') {
  w.trade *= 0.35; w.chat *= 0.5; w.work *= 0.6; w.rest *= 1.8;
}
if (ctx.weather === 'dust') { w.trade *= 0.2; w.work *= 0.3; w.rest *= 2.2; }
```

代价：`crowd.ts:1538` 的 `ctx()` 返回值要加一个字段，`BehCtx` 是结构类型，加字段不会破坏既有调用点（TS 会要求所有构造处补齐，实际只有一处）。

**作物**：本仓库**现在没有作物系统**。`infill.ts:3718` 的注释写明「原四段稻田带已清空，只剩裸土」。所以这一条是**新增**，不是接入：

```ts
// src/world/fields.ts（新文件）
export interface Field { x: number; z: number; w: number; d: number; crop: 'rice' | 'wheat'; growth: number }
export const WEATHER_GROWTH: Record<WeatherKind, number> = {
  clear: 1.0, overcast: 0.8, rain: 1.25, snow: 0.0,
  fog: 0.7, dust: 0.3, gangfeng: 1.0, yinfeng: 1.0,

```

生长只改**着色器 uniform**（`uGrowth` 控制高度缩放与颜色插值），**不换几何**。理由：换几何要走 Baker 重烘，一次 200 块田会让载入时间突破 12s 红线；用 uniform，一块田 2 个三角，代价为零。

**传送与 POI**：见第 4 节。

### 3.5 「paused = true」这个坑

`TimeOfDay.paused = true`（`palette.ts:36`）是美术基线：全部色阶是在 `phase = 0`（黄昏）下调的，注释写明「默认停在黄昏，玩家可开启循环」。

生存循环一旦上线，**必须**在开局把它打开（`time.paused = false`），否则饥饿不走、天气不换、作物不长，整套系统静默失效——而且没有任何报错，探针若只读「饥饿值是否下降」会误判成「实现正确但玩家没动」。

代价是真实的：一开循环，玩家在 7 分钟里会经历夜→深夜→黎明，而**夜景的调色是按静态黄昏调的**。`STOPS` 里的夜间档（`palette.ts:25-26`）只有 `neon 1.12/1.22`，是否足够亮、地标在深夜是否读得出来，**未做视觉验证**。这是本卷最大的一处未验证风险，V11 必须补测。

折中方案（写进实现备注）：默认 `speed = 1/420` 保持，但提供「生存模式」开关；开关打开才 `unpause`，关闭时所有生存结算按 `phase` 的**名义进度**（一个独立累加器）走，视觉仍停在黄昏。这样纯观光玩家不受影响，生存玩家承担昼夜风险。

### 3.6 天气的渲染预算

天气必须便宜，否则它会成为压垮帧率的最后一根稻草——静态面已经 13.35–15.09M，没有余量给几十万个雨滴。

| 天气 | 粒子数 | 三角面 | draw call | 实现 |
|---|---|---|---|---|
| 雨 | 3000 | 6000 | 1 | 单 `InstancedMesh`，细长四边形，绕相机 40m 盒内循环 |
| 雪 | 2500 | 5000 | 1 | 同上，但带正弦横摆 |
| 沙尘 | 1800 | 3600 | 1 | 同上，更大更慢，色偏沙黄 |
| 雾 | 0 | 0 | 0 | 纯 `fog.density`，不加几何 |
| 罡风 | 0 | 0 | 0 | 复用云海位移 + 角色布料摆动 |
| 阴风 | 0 | 0 | 0 | 纯雾色 + 磷火粒子（已有 `GLOW_MAT`） |

四条纪律：

1. **只用一个 `InstancedMesh`**。每个粒子一个 Mesh 会在 3000 个时产生 3000 次 draw call，直接帧率归零。实例化后是 1 次。
2. **盒内循环，不生成/销毁**。粒子位置对 40m 盒取模，永远在相机周围；离相机超过 40m 的粒子直接 `mod` 回来，不做可见性剔除。
3. **40m 而不是全场**。雨天若铺满 5km 城区，需要几十万粒子；40m 盒配合雾（雨天的雾 ×1.85）已经把远处遮住，玩家看不出来。
4. **粒子不投影**。`castShadow = false`。雨滴投影在物理上就几乎不可见，开了只是白烧一遍 shadow pass。

音效接 `Audio/sc`（`src/audio/scape.ts`）的既有总线：`scape.update(dt, neon)` 每帧已经在跑，天气只需额外给一条雨声/风声的 gain，按 `wet / wind` 线性映射到 0–0.35。**不要新建 AudioContext**——浏览器对同时存在的 AudioContext 数量有限制，而 `scape.ts` 已经占了一个。

## 4. 死亡与重生

### 4.1 三界死亡规则

| | 人间 | 天宫 | 地府 |
|---|---|---|---|
| 判定 | `hp = 0` | 仙体完整度 = 0，或戒律 3 次 | 阴寿 = 0 |
| 前摇 | 昏迷 8s（黑屏渐入） | 金光溃散 3s | 魂不附体 3s |
| 去处 | 最近医馆 / 客栈 | 南天门 | 人间出生点 |
| 掉落 | 铜钱 10%（向下取整） | 香火 −50% | 阴德 −20 |
| 保留 | 装备、阴德、蟠桃点 | 装备、业力 | 装备、铜钱 |
| 附加 | 无 | 600s 内不得再入天宫 | 600s「还阳虚弱」（全属性 ×0.8） |

三条设计理由：

- **人间掉钱不掉装备**。掉装备会让玩家在死亡后回到「一无所有」，惩罚过重且读档冲动强；掉 10% 铜钱是「疼但能承受」，且铜钱是可再生资源（V4 有打工）。
- **天宫不掉东西，掉权限**。天宫的资源是香火与准入资格，扣这两样比扣钱更符合「被贬」的叙事。
- **地府掉阴德**。阴德是单向货币（`interact.ts:19`，只能烧纸获得），扣它等于扣「阳间亲人给你烧的钱」，情感重量最大。

### 4.2 重生锚点表

**不能复用 `POIS`**。理由：`interact.ts:255` 用 `distanceToSquared` 做三维判距，而 `world.ts:1325` 把所有 61 个交互点注册在 `y = 0.1`。若拿交互点当重生点，天宫的「瑶池青鸾架」（`POINTS` R5，x=150, z=34）会把人送到人间地面 y=0.1 的同一个 x/z 上——**这是本仓库真实存在的坐标复用**（天宫瑶池 POI 是 `heavenPoint(150, 208.26, 20)`，与 R5 的 x/z 接近但不同 y）。

所以重生锚点单开一张表，**必须带 `realm` 与 `y`**：

```ts
// src/survival/Respawn.ts
export interface Anchor { key: string; realm: 'renjian' | 'tiangong' | 'difu'; x: number; y: number; z: number; label: string }
export const ANCHORS: Anchor[] = [
  { key: 'spawn',    realm: 'renjian', x: -20, y: 0,  z: 58,  label: '汴京·州桥' },
  { key: 'clinic',   realm: 'renjian', x: 168, y: 0,  z: 64,  label: '赵太丞家' },
  { key: 'inn',      realm: 'renjian', x: 340, y: 0,  z: 64,  label: '久住王員外家' },
  { key: 'nantian',  realm: 'tiangong', x: 0,  y: 0,  z: 0,   label: '南天门' },   // y/x/z 由 heavenPoint 填
  { key: 'bridge',   realm: 'difu',    x: 0,  y: -258, z: -60, label: '奈何桥' },
];
```

`nantian` 的坐标不能写死。`heavenPoint(0, 203.12, -80)` 会返回 `[0, 2150.25, -176]`（`heavenFrame.ts:29`：`x*z × 2.2`、`y = 2129 + (y−196) × 2.2`）。硬编码这三个数会在 `HEAVEN_LIFT` 或 `HEAVEN_SCALE` 改变时静默失效——而这两个常数在项目历史上**已经改过一次**（从 200m 抬到 2150m）。所以 `ANCHORS` 里天宫项必须在模块初始化时用 `heavenPoint()` 计算，表里只存「缩放前坐标」。

`spawn` 取 `-20, 0, 58`，与 `world.ts:655` 的 `new THREE.Vector3(-20, 0, 58)` 逐字一致。这是玩家真正的出生点，不是 `POINTS` E1 茶坊的 `(-36, 62)`。

### 4.3 与 `PORTALS` 的兼容

现状：`player.ts:357-359` 每帧遍历 `PORTALS`（`:428`，只有 2 条：人间→地府 `(470,0,24)→(0,-260,-130)`，地府→人间 `(0,-260,-124)→(472,0,28)`），命中即调 `private usePortal(pt)`（`:375`）。

死亡重生需要「带黑屏的传送」，而 `usePortal` 已经实现了这件事：设 `fadeEl.style.opacity = 1` → `setTimeout(460ms)` → 改坐标 → toast → 淡出 → `busyUntil = now + 1000`。

**不要复制这段逻辑。** 把 `usePortal` 提成一个公共方法：

```ts
// player.ts:375，改签名
private usePortal(pt: PortalDef): void { this.teleportWithFade(pt.to, pt.label); }

/** 带黑屏的定点传送：死亡重生、剧情传送、传送门共用 */
teleportWithFade(to: [number, number, number], label: string): void {
  if (!this.fadeEl) { this.actor.pos.set(...to); bus.emit('ui:toast', label); return; }
  this.fadeEl.style.opacity = '1';
  window.setTimeout(() => {
    this.actor.pos.set(...to);
    this.vy = 0;
    // 关键：跨界必须同步 realmY，否则化身被钉在上一界的平面
    this.realmY = to[1] > 120 || to[1] < -120 ? to[1] : null;
    bus.emit('ui:toast', label);
    this.fadeEl!.style.opacity = '0';
  }, 460);
  this.busyUntil = performance.now() + 1000;
}
```

**`realmY` 这一行是必须的**，也是现有 `usePortal` 的一个潜在缺陷：`realmY` 只在 `toggleMode()`（`player.ts:116`）里按相机高度设置。传送后若 `realmY` 还是旧值，`update()` 的 `if (this.realmY !== null) { p.y = this.realmY; }`（`:338-340`）会把化身钉在旧的界域平面上——从地府传回人间，人会悬在 y=−260 而不是落地。

**这条缺陷现在没暴露，是因为两条 `PORTALS` 的落点 y 分别是 0 与 −260，而 `realmY` 在两个落点上恰好都是 `null` 或恰好匹配**。一旦加入天宫重生（y≈2150），缺陷立刻显形。所以 `teleportWithFade` 必须自己管 `realmY`。

### 4.4 死亡流程

```
hp → 0
 ├ 若 realm = 人间：昏迷 8s（fadeEl opacity 0→1 用 2s）→ 选锚点 → teleportWithFade
 ├ 若 realm = 天宫：金光溃散 3s → 扣香火 → 南天门 → 挂「贬谪」
 └ 若 realm = 地府：魂不附体 3s → 扣阴德 → 人间 spawn → 挂「还阳虚弱」
```

昏迷期间 `busyUntil` 锁死（复用 `player.ts:61` 的 `busyUntil` 字段，`update()` 里已有 `const busy = now < this.busyUntil` 判断，`:216`），玩家不能移动、不能交互。**不需要新的输入锁**。

### 4.5 掉落物的去向

死亡掉落分两类，处理方式必须分开，否则会互相打架。

| 类型 | 例子 | 处理 |
|---|---|---|
| **数值型** | 铜钱、阴德、香火 | 直接从计数器扣，不生成实体。生成实体意味着玩家有「捡回来」的可能，那 10% 惩罚就形同虚设 |
| **实体型** | 工具、药材、蓝图卷轴 | 在死亡点 3m 内生成掉落物，5 分钟后消失 |

实体型的三条规则：

1. **拾回窗 5 分钟**（游戏内时间，不是真实时间）。这个长度刚好是「跑一趟回来」的量级，且短于一个昼夜（7 分钟），不会让掉落物跨夜还在原地。
2. **再次死亡则旧掉落立即消失**。这条是防滚雪球：否则玩家会「死一次捡一次」，把风险转成刷子。消失前 30s 掉落物闪烁提示。
3. **掉落物不进 Baker**。走 V3 定义的掉落物池（`InstSet`，与 `src/city/vehicles.ts` 的同一设施），最多同时存在 64 个，超出则最旧的立即消失。

地府与天宫的死亡**不产生实体掉落**——那两界的惩罚是「权限」与「阴德」，不是「东西掉了」。这条差异要写进 UI 提示，否则玩家会在地府死后满地图找自己的剑。

### 4.6 三界资源不许互通

现有三币已经是一套单向兑换：铜钱（人间）、阴德（地府，只能烧纸获得，`interact.ts:19`）、蟠桃点（天宫，赏赐后单向兑铜钱，`interact.ts:88-96` 的 `burnpaper` / `peachgrant` 特判）。

生存资源**必须**遵守同一套单向律，否则会立刻出现套利：

| 资源 | 界 | 获得 | 消耗 | 能否跨界 |
|---|---|---|---|---|
| 食物（饱食） | 人间 | 购买/烹饪（V4） | 饥饿 | **否**。天宫/地府的食物不回复饥饿 |
| 香火 | 天宫 | 供奉 | 时间 −0.5/s、破戒 | **否**。不可兑铜钱，也不可兑蟠桃点 |
| 阴寿 | 地府 | 入界自动 600s | 受击/杀生/落水 | **否**。不可购买、不可补充 |
| 阴德 | 地府 | 烧纸（铜钱→阴德，单向） | 死亡 −20 | 只进不出 |
| 蟠桃点 | 天宫 | 蟠桃宴赏赐 | 兑铜钱（单向） | 只进不出（对铜钱） |

三条「否」是这张表的全部意义：

- **食物不能跨界的理由**：若天宫也能吃东西回复饥饿，那饥饿冻结就失去意义，玩家会带一背包干粮上天宫，把「仙体不饥」变成「仙体可以吃」。若地府能吃，阴寿的压力会被食物抵消一半。
- **香火不能兑钱的理由**：香火是「信仰」，一旦可兑，玩家会把它当矿挖（反复供奉再兑换），天宫的稀缺性立刻归零。
- **阴寿不能买的理由**：它是**唯一一个只能靠「少犯错」延长的资源**。一旦可买，地府就退化成「有钱就能横着走」，与业力系统的叙事直接冲突。

这条规则与 V4 的经济是强耦合的：V4 定价时必须假设「食物只在人间流通」，否则所有价格表都要重算。

## 5. 与既有系统的接线

### 5.1 `src/game/player.ts`

三处改动：

**(a) 新增 `statusScale`，绕开 `speedScale` 被覆盖的问题。**

```ts
// player.ts:50 附近
speedScale = 1;
statusScale = 1;   // 新增：状态效果专用，world 不写这个字段

// player.ts:85
effectiveSpeed(run: boolean): number {
  return (run ? RUN_SPEED : WALK_SPEED) * this.speedScale * this.statusScale;
}
```

`world.ts:1271` 继续写 `speedScale`（望乡台 0.55），生存系统只写 `statusScale`，两者相乘。**这是最小侵入**：不改 world，不改既有探针（`probe-threat.mjs` 断的是 `speedScale` 线性关系，仍然成立）。

**(b) 饥饿影响奔跑资格。**

`vitals` 由 `world` 注入，玩家本身不持有生存逻辑：

```ts
// player.ts 新增公开字段
vitals: Vitals = { hp: FULL, hunger: FULL, stamina: FULL, spirit: FULL, extra: 0 };
// world.init() 里：this.player.vitals = this.survival.vitals;
```

于是判定只读两个数：

```ts
// player.ts:326 附近
const run = (k.has('ShiftLeft') || k.has('ShiftRight'))
         && this.vitals.stamina > 0
         && this.vitals.hunger > 0;
```

不满足时 `effectiveSpeed(true)` 退化成走路速度。注意这里改的是**输入判定**而不是速度公式，所以「速度 = 基准 × 系数」的可断言性不变。

**(c) 坠落伤害。**

`update()` 的落地分支在 `:343`：`if (p.y > target + 0.05) { this.vy -= 22 * dt; ... }`。落地瞬间在 `:344` 的 `else { p.y = target; this.vy = 0; }`。在此处取 `|vy|`：

```ts
const impact = Math.abs(this.vy);
if (impact > 9) this.onFall?.(impact);   // 9 m/s 对应约 1.84m 自由落体
```

`impact > 9` 换算成坠落高度：`h = v²/2g = 81/44 = 1.84m`。这个阈值太低（跳一下就触发），实际取 **`impact > 14`（h ≈ 4.5m）**，对应「从一层屋顶跳下会崴脚，从二层跳下会骨折」。伤害 `dmg = round((impact − 14) × 12)`：4.5m 摔落 0 伤，10m 摔落（impact 21）伤 84。

### 5.2 `src/game/physics.ts`

`ImpactSystem.apply(tier, target, dir, force)`（`physics.ts:77`）已经把冲击分成五档：`stagger / knockdown / launch / shatter`，阈值是 `0.8T / 1.6T / 3.2T / 6T`（`:35-41`）。

接线只需在 `apply()` 开头加一次转发，**不改任何既有分支**：

```ts
// physics.ts:77 之后
if ((target.data?.code ?? '') === 'player') this.onPlayerImpact?.(tier, force);
```

`onPlayerImpact` 由 `world` 注入，映射到伤害：

| tier | 伤害 | 附加状态 |
|---|---|---|
| stagger | 40 | 无 |
| knockdown | 90 | 惊悸（90s） |
| launch | 180 | 惊悸 + 若落地 impact > 14 则骨折 |
| shatter | 350 | 骨折 |

依据：`profileOf()`（`physics.ts:20`）把玩家判为「平民」，`toughness = 9`。`tierOf` 的 `knockdown` 下界是 `1.6 × 9 = 14.4` 的力。一辆 `mass × speed` 的车（`vehicleSweep`，`:147`）很容易打到 20–40，即 knockdown；巨灵神斧（`bus.emit('impact:giant')`，`:56`）直接把玩家 `launch`。所以 **180 伤的 launch 是「被神佛打飞」的常规后果**，玩家挨两下就得跑——这与现有 `launch` 的 4000ms 硬直是一致的强度设计。

### 5.3 `src/world.ts` 的 `applyLighting`

如 3.3 所述，**不改 `applyLighting` 内部任何一行**，只在 `update()` 的 `:1248` 与 `:1249` 之间插一行 `this.weather.applyPost(this)`。

这一条要在文档里写死，因为「把天气塞进 applyLighting」是最自然的错误直觉，而它会在天宫/地府静默失效。

### 5.4 `crowd` 与 `HUD`

- `crowd.weather: WeatherKind` 新字段，每帧由 `weather.update()` 写。
- HUD 四维条：复用 `src/ui/ui.ts` 的面板设施，`bus.emit('vitals:change', v)`，HUD 只读事件。**不要每帧 DOM 写入**——现有 `coins:change` 就是事件驱动（`interact.ts:52`），照抄这套。

### 5.5 HUD 与提示

生存 HUD 是唯一一个「每秒都在变」的 UI，写不好会把主线程拖死。

**布局**（桌面）：左下角四条竖条，每条 6px 宽、间距 4px、总高 120px，颜色分别为朱（hp）、土黄（hunger）、青（stamina）、紫（spirit）。条上方一行状态图标，最多 8 个，超出折叠成 `+N`。天气图标与 `phaseName`（`world.ts:260` 的 `phaseName` 字段）并排放在右上。

**四条节流规则**：

1. **差值阈值**：千分位变化 > 1 才写 DOM。`hp` 每秒掉 0.05 千分位，意味着 20 秒才够触发一次——这是对的，玩家不需要看到心跳级的抖动。
2. **只写 `style.transform`，不写 `style.width`**。`transform: scaleY()` 走合成层，`width` 会触发重排。四条 × 每秒 60 次 = 每秒 240 次重排，足以在低端机上掉 10 帧。
3. **不重建 DOM**。状态图标用固定 8 个槽位，切换时改 `background-image` 与 `display`，绝不 `innerHTML`。`interact.ts` 的 `makePanel` 每次 `innerHTML` 重建是可以的（面板不常开），HUD 不行。
4. **离屏暂停**。`document.hidden` 时停掉计时器——后台标签页里饿死玩家是最容易引起投诉的 bug。

**无障碍**：不能只靠颜色区分四维。每条条左侧加一个汉字（生 / 食 / 力 / 神），状态图标用形状而非纯色（圆=增益、方=减益、三角=异常）。色盲玩家占男性约 8%，这不是可选项。

**移动端**：竖条改横条置于屏幕顶部（`@media (max-width: 720px)`），否则会被虚拟摇杆（`engine.touchMove`）挡住。

## 6. 可执行验收断言

与 V5 同规矩：`scripts/probe-*.mjs`，`PASS`/`BLOCK` + 退出码，读 `window.__qingming`，不模拟键鼠。

**A6-1 饥饿线性**：`probe-vitals-hunger.mjs`
静止站立 60s（用 `engine.time` 冻结、只推进 `Survival.update(dt)`），断言 `hunger` 下降 `57 ± 1`（0.95 × 60）。跑动 30s 断言下降 `74 ± 2`（2.47 × 30）。两条都要过。

**A6-2 精神一夜见底**：`probe-vitals-spirit.mjs`
把 `time.phase` 设为 0.16、每次 `+0.01` 推到 0.86，断言 `spirit` 落在 `[0, 30]`。这直接验证 `3.4 × 294 ≈ 1000` 这个设计常数，若实现者写成 `0.34` 会立刻红。

**A6-3 状态互斥**：`probe-status-exclusive.mjs`
先挂湿寒，再挂上火，断言 `Status.has('上火') === false` 且返回了 `rejectedByExclusive` 原因。反向再来一次。**负样本必测**：把 `exclusive` 表清空后必须变红。

**A6-4 天气不污染 TimeOfDay**：`probe-weather-purity.mjs`
在 `clear` 与 `rain` 两种天气下，各读一次 `time.skyTop / fogColor / sunI / hemiI / fogDensity`，断言**逐字段完全相等**。这是防「天气写回 `TimeOfDay`」的唯一硬门——一旦写回，美术基线会被玩家的一次下雨永久改掉，且重开游戏不复原（`TimeOfDay` 没有序列化）。

**A6-5 天宫/地府天气不失效**：`probe-weather-realm.mjs`
相机分别置于 y = 2150 与 y = −260，切到 `rain`，断言 `scene.fog.density` 相对 `clear` 的比值 ≥ 1.7（人间是 1.85，两界允许 8% 偏差）。若插入点放进 `applyLighting` 内部，天宫比值会掉到 1.0 左右，必红。

**A6-6 传送重置 realmY**：`probe-teleport-realm.mjs`
人间（realmY=null）→ 天宫锚点 → 断言 `player.realmY` 落在 `[2149, 2152]`；再传回人间 → 断言 `realmY === null` 且 `2s` 后 `actor.pos.y` 落在 `[−0.1, 0.1]`。第二条是为了抓「人悬在半空」这个症状。

**A6-7 坠落伤害曲线**：`probe-fall-damage.mjs`
从 4.5m 落下断言 `hp` 不变；从 10m 落下断言 `hp` 减少 `84 ± 8`；从 30m 落下断言挂「骨折」。三条覆盖阈值、线性段、状态触发。

**A6-8 死亡掉落守恒**：`probe-death-drop.mjs`
人间设 `coins = 1000`，触发死亡，断言 `coins === 900`。再设 `coins = 15`，断言 `coins === 14`（扣除 `Math.floor(15 × 0.1) = 1`）。探针里的期望值写成 `coins - Math.floor(coins * 0.1)` 而不是硬编码 900/14——规则一改就应自动跟随，硬编码会让探针在调参后假红。

**A6-9 三界不串味**：`probe-realm-isolation.mjs`
在人间把 `hunger` 打到 100，进天宫断言 `hunger` **不再下降但也不回升**（冻结 ≠ 清零）；出天宫断言 `hunger` 仍是 100。这一条防的是「天宫直接把饥饿设成满」。

### 手工验收：探针覆盖不到的三件事

机检能断数值链，断不了观感。以下三条必须人看，写在这里是为了不让它们被忘掉：

1. **雨夜的虹桥**。机位 `(0, 14, 60)` 朝桥，天气 `rain`、`phase = 0.45`。判据：桥体轮廓可辨、雨丝有前后层次（近处粗、远处被雾吃掉）、无整屏灰白。机检可以量平均亮度，但「像不像下雨」只能看。
2. **无灯的地府走 60 秒**。从 `POIS['mengpo']`（−40, −258, −132）走到 `POIS['naihe']`（0, −258, −60）。判据：全程能分辨路面与墙体的边界，不出现「一片纯黑只能靠小地图」。`applyHellDepth`（`world.ts:1077`）已经做了纵深黑场，加天气后可能过黑，这条专门抓它。
3. **天宫罡风**。机位在南天门。判据：云海有位移方向、角色衣摆/披风有摆动、但建筑不抖。「风」的可见性全靠次级运动，若只改雾不改动，玩家感觉不到。

## 8. 本卷最弱的三处

1. **夜景没有视觉证据。** 3.5 说「一开昼夜循环，夜景调色未验证」——这是本卷最大的空白，而且它会连带影响所有天气（雨夜、雪夜的曝光是两套乘子叠出来的，没有任何一张截图）。我只能证明数值链是自洽的，不能证明画面成立。

2. **24 条状态的数值全是设计值，没有一条经过试玩校准。** 尤其是「上火 180s」「中邪 600s」这类时长，是按「一昼夜 420s」的比例拍的，不是从玩家行为数据里回归出来的。真实上线后大概率要整体重调，而重调会连带影响 UI 提示、食物定价（V4）、药材产出，牵一发动全身。

3. **天气对 NPC 的影响只有权重，没有行为。** 3.4 给的是「雨天少摆摊」，但 NPC 不会真的**跑进屋檐下避雨**——`behaviors.ts` 的 `planStep` 没有「找遮蔽」这个动作，`SpotRegistry` 也没有「屋檐下」这类场所。要真做，得给每个建筑标可避雨面，是另一个量级的工程。本卷只做了权重，明确承认这是降级实现。
