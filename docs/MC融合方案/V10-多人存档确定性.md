# V10 · 多人 · 存档 · 确定性

> 本卷回答三个问题：① 这个项目现在到底有多确定？② 要联机「同结果」还缺什么、代价多少？③ 存档、Electron 打包、回放验证怎么落地而不和现有架构打架。
>
> 结论先给：**单机可复现只差一层固定步 + 种子化**；联机同结果差的是**一整套确定性仿真**，不是加个 WebSocket 就能解决。本卷把两者分开写，不混为一谈。

---

## 0. 现状盘点：已有的确定性纪律

本项目不是「完全随机」，它已经有一半的确定性基础设施。先列清楚哪些是真的：

| 机制 | 代码位置 | 现状 | 判定 |
|---|---|---|---|
| 种子随机 | `src/core/rng.ts:2-20` | mulberry32；`next()` 用 `Math.imul` 与 `>>>`，纯 32 位整数运算 | ✅ 可复现 |
| 主世界种子 | `src/world.ts:277` | `new RNG(20260905)`，全城生成共用一条序列 | ✅ 但只覆盖 baker 侧 |
| 独立子种子 | `src/world.ts:352` | `new RNG(0x5e7a1)` 给街屋内饰，避免扰动主序列 | ✅ 做法正确 |
| 角色卡外观 | `src/actors/crowd.ts:391-420` | `cardLook(id)` 是纯函数：同一卡 id 恒定同一外观 | ✅ 跨会话稳定 |
| 角色 id | `src/actors/crowd.ts:1227` | `id: this.idSeq++`，按 spawn 顺序单调递增 | ✅ 前提是 spawn 顺序稳定 |
| 天宫换算 | `src/sky/heavenFrame.ts:22-29` | `heavenY/heavenPoint` 是纯函数，只含 `+ - *` | ✅ 唯一真相源 |
| 渲染时间 | `src/core/engine.ts:752` | 可变步长 `dt = min(0.1, now-last)` | ❌ 不可复现 |
| 玩法随机 | 15 个文件、127 处 `Math.random` | 见 §1.2 | ❌ 每次刷新都不同 |
| 墙体时钟 | `src/game/player.ts:216`、`src/game/physics.ts:80` | `performance.now()` 直接进玩法状态 | ❌ 不可回放 |

**一句话总结**：世界**几何**基本可复现（baker 走种子），世界**角色**与**战斗**不可复现（`spawnActor` 与 `boss.rollMove` 走 `Math.random`）。V10 的重点不是「从零建确定性」，而是「把已经确定的部分守住，把不确定的部分逐条关掉」。

还要先纠正一个常见误解：确定性不是「联机才需要」的额外成本。它是三件事的共同前置——**单机存档**（读档后 NPC 不能换一批）、**回放**（bug 复现）、**视觉回归**（同 seed 截图可比）。即使永远不做多人，P0（固定步 + 种子 + 去墙钟）也应该做；联机只是把 P1/P2 的收益放大。反过来，如果只做联机不做单机确定性，会得到一个「能连、但读档就崩、bug 复现不了」的系统——那不是联机，是把不确定性扩散到两个人。

## 1. 确定性盘点：五个破口

### 1.1 破口一：`Math.random` 的 127 处分布

用 `grep -rn "Math.random" src/ --include=*.ts | wc -l` 实测为 **127 处**，分布如下：

| 文件 | 次数 | 性质 | 处理 |
|---|---|---|---|
| `src/actors/behaviors.ts` | 43 | 行人行为/停留时长/转向 | 必须种子化（联机同步） |
| `src/actors/crowd.ts` | 28 | 出生外观/速度/相位/朝向 | 必须种子化（角色初始状态） |
| `src/city/bake.ts` | 18 | 烘焙期的纹理/构件微差 | 可保留（初始化一次，种子已固定） |
| `src/fx/vfx.ts` | 9 | 粒子速度/寿命 | 可分流：视觉流不参与对账 |
| `src/audio/scape.ts` | 8 | 环境音随机 | 可保留（不影响状态） |
| `src/world/terrain.ts` | 6 | 地形散点 | 应种子化（地形是碰撞面） |
| `src/city/pavement.ts` | 4 | 铺装色斑 | 可保留（纯视觉） |
| `src/sky/expansion.ts` | 3 | 云团/浮岛微差 | 可保留（纯视觉） |
| `src/actors/heroes.ts` | 2 | 名将小动作 | 应种子化（演员状态） |
| `src/world.ts` | 1 | 凌振炮击落点 `:1431` | 必须种子化（伤害判定） |
| `src/sky/heavenStair.ts` | 1 | 台阶微差 | 可保留 |
| `src/sky/havoc.ts` | 1 | 雷部落点 `:256` | 必须种子化（战斗演出会碰到玩家） |
| `src/game/interact.ts` | 1 | 骰子 `:143` | 应种子化（经济结果） |
| `src/game/boss.ts` | 1 | 选招 `:86` | **必须**种子化（Boss 行为） |
| `src/city/mounts.ts` | 1 | 坐骑微差 | 可保留 |

结论：**必须改的约 83 处**（behaviors 43 + crowd 28 + boss 1 + havoc 1 + world 1 + interact 1 + terrain 6 + heroes 2 = 83，其中 terrain 的 6 处若只影响视觉可降级），**可保留的约 44 处**。不要一刀切全改：烘焙期随机已经在种子 RNG 下稳定，改成另一套只会让全城外观漂移。

分类原则不是「随机就是坏」，而是「这次随机的结果是否进入对账状态」。同一个 `Math.random()`，在 `bake.ts` 里决定一块瓦的色差，只影响画面，保留；在 `boss.ts` 里决定下一招是横扫还是擒拿，直接改变玩家血量与站位，必须换。用这条尺子量，127 处里真正危险的是 83 处，而不是全部。剩下的 44 处如果也强行种子化，收益为零、视觉回归风险却很高——尤其是 `bake.ts` 的 18 处，它们已经共享 `world.ts:277` 的种子序列，改流会让全城纹理与构件微差重新洗牌，等于把已有的视觉验收作废。

还有一个容易被忽略的中间态：`src/fx/vfx.ts` 的 9 处、`src/audio/scape.ts` 的 8 处。它们不影响 HP/位置，但会影响**玩家看到的同一帧画面**。联机时不要求两端粒子一致，回放时也不把粒子纳入哈希；但如果特效代码顺手调用了 `combat` 流，就会间接改变 Boss 选招。所以它们的正确处理不是「保留 `Math.random`」，而是「接到独立的 `vfx`/`audio` 流」，既不影响对账，也不影响观感。

### 1.2 破口二：`crowd.spawnActor` 的初始状态

这是最严重的一处，也是最容易被忽略的：

```ts
// src/actors/crowd.ts:1228-1237（原样）
yaw: o.yaw ?? Math.random() * Math.PI * 2,
speed: job ? job.speed[0] + Math.random() * (job.speed[1] - job.speed[0]) : 1,
action: o.action ?? 'stand', actT: Math.random() * 100, timer: Math.random() * 4,
seed: card ? card.seed : Math.random() * 1000,
scale: o.scale ?? (o.occ === 'kid' ? 1 : (job?.scale
  ? job.scale[0] + (card ? card.r : Math.random()) * (job.scale[1] - job.scale[0])
  : 0.9 + (card ? card.r : Math.random()) * 0.24)),
hat: o.hat ?? (card ? pickWeighted(job ? job.hats : CARD_HAT_DEFAULT, card.v) : pickHat(job ? job.hats : [1, 3, 3, 2])),
cloth: new THREE.Color(o.cloth ?? (card ? card.color : (job ? job.cloth[Math.floor(Math.random() * job.cloth.length)] : 0x6a6a6a))),
pants: new THREE.Color(o.pants ?? (job ? job.pants[Math.min(job.pants.length - 1, ((card ? card.x : Math.random()) * job.pants.length) | 0)] : 0x3a3a3a)),
skin: new THREE.Color(o.skin ?? (card ? (card.w < 0.34 ? 0xd8b090 : card.w < 0.67 ? 0xc8a080 : 0xb89070) : (Math.random() < 0.34 ? 0xd8b090 : Math.random() < 0.5 ? 0xc8a080 : 0xb89070))),
```

即使世界几何逐字节相同，**4000+ 个角色的朝向、速度、相位、身高、衣服颜色、帽子、肤色**每次刷新都不同。后果：
- 同一 seed 下截图不可对比（视觉回归失效）；
- 联机时两名玩家看到的街面不同（状态同步直接失败）；
- 存档里的 NPC 位置无法复现（读档后人群换了一批）。

修法：把 `spawnActor` 的所有 `Math.random()` 换成 `this.rng.next()`，`Crowd` 构造时接收一个 `RNG` 流（默认 `new RNG(worldSeed ^ 0x9e3779b9)`）。改造后的关键行：

```ts
// src/actors/crowd.ts:1110 的构造签名 + 1228 起的关键行
constructor(private scene: THREE.Scene, readonly nav: NavGraph, private rng: RNG) {
  // 其余初始化不变
}

const r = this.rng;
yaw: o.yaw ?? r.range(0, Math.PI * 2),
speed: job ? job.speed[0] + r.next() * (job.speed[1] - job.speed[0]) : 1,
actT: r.range(0, 100), timer: r.range(0, 4),
seed: card ? card.seed : r.range(0, 1000),
scale: o.scale ?? (job?.scale
  ? job.scale[0] + (card ? card.r : r.next()) * (job.scale[1] - job.scale[0])
  : 0.9 + (card ? card.r : r.next()) * 0.24),
hat: o.hat ?? (card ? pickWeighted(job ? job.hats : CARD_HAT_DEFAULT, card.v) : pickHat(job ? job.hats : [1, 3, 3, 2])),
cloth: new THREE.Color(o.cloth ?? (card ? card.color : job ? job.cloth[Math.floor(r.next() * job.cloth.length)] : 0x6a6a6a)),
```

注意 `card` 分支仍走 `cardLook(id)` 的纯函数值，不消耗 RNG；只有「无卡」路径才取随机。这样既有卡角色（108 将、神佛）的外观不变，只有街面路人的分布变。**代价**：现有 4000+ 街面角色的外观会整体换一次，用户可能察觉「人变了」。缓解：先用当前构建跑一次 `probe-crowd-snapshot`，把外观哈希存为 baseline；改造后逐项对比，只允许「可解释的差异」（例如原来随机的帽子分布现在按 seed 分布）。

### 1.3 破口三：可变步长

`src/core/engine.ts:752` 的 `dt` 来自 rAF 间隔，30fps 与 144fps 下：

| 量 | 30fps（dt=33.3ms） | 144fps（dt=6.94ms） | 差异 |
|---|---|---|---|
| 跳跃顶点高度（v0=7.5，g=21） | ≈1.214m（半隐式欧拉，误差 `v0·dt/2`） | ≈1.313m | ≈0.10m |
| Boss 3.2s 计时器递减次数 | 96 次 | 461 次 | 阶段切换最多差 33ms |
| 一次 100ms 卡顿（任何帧率，dt 被钳到 0.1） | 跳过 6 个 60Hz 逻辑帧 | 跳过 6 个 | 钳制把帧率差异抹平，但状态跳步仍发生 |
| `actionT` 每帧增量 | 0.0333 | 0.00694 | 动作相位不同步 |

上表的跳跃高度是**解析估算**（半隐式欧拉的高度误差约为 `v0·dt/2`），不是实测；它说明的是「同一按键在不同帧率下跳得不一样高」，这正是回放对不上的根源。修法：固定 60Hz（见 §2.1）。**代价**：高刷屏上要么多 1 帧延迟，要么做插值；低帧率时最多补 4 步，超出丢弃，表现为「卡顿时慢动作」而不是「瞬移」。

### 1.4 破口四：`performance.now()` 进玩法

全仓 `grep -rn "performance.now()" src/ --include=*.ts | wc -l` 实测 **61 处**，其中约 20 处直接或间接进入玩法状态；下表列 6 个代表：

| 位置 | 用法 | 后果 |
|---|---|---|
| `src/game/player.ts:215-216` | `now = performance.now()`；`busy = now < busyUntil \|\| now < actor.impactUntil` | 读档/回放时 `busyUntil` 是过去的时间戳，行为不同 |
| `src/game/player.ts:385` | `busyUntil = performance.now() + 1000` | 传送锁定依赖墙钟 |
| `src/game/physics.ts:80` | `impactUntil = performance.now() + 3600` | 硬直时长不可复现 |
| `src/game/physics.ts:115` | `respawn.push({at: performance.now()+26000})` | 亡魂重生时机不可复现 |
| `src/game/physics.ts:215-219` | `now = performance.now()`；`if (now > L.until)` | 击飞结束时机不可复现 |
| `src/actors/crowd.ts:1984` | `now >= a.impactUntil` | 同上 |

其余 41 处是加载计时（`world.ts` 8 处、`engine.ts` 6 处）、渲染统计（`infill.ts` 11 处）、烘焙计时（`bake.ts` 4 处）与界面动画（`hells.ts`/`flora.ts`/`expansion.ts` 各 1 处），它们不写 sim 状态，可以保留；但要在 lint 里区分「允许的计时用途」与「禁止的 sim 用途」，否则新代码会以「只是计时」为名把墙钟带进玩法。

修法：全部改成 `simTick`（整数帧）。`impactUntil` → `impactUntilTick`，`busyUntil` → `busyUntilTick`；渲染层要毫秒时用 `tick * 16.6667` 换算。**代价**：`Actor` 接口改字段名，涉及 `types.ts`、`crowd.ts`、`player.ts`、`physics.ts`、`world.ts` 五处；旧存档里的毫秒时间戳要迁移（V10 的 v2→v3 迁移顺带处理）。

### 1.5 破口五：浮点超越函数与跨引擎差异

`+ - * /` 与 `Math.sqrt` 在 IEEE-754 下是正确舍入的，跨引擎一致（`sqrt` 的 ECMAScript 规范写的是 implementation-approximated，但主流引擎都走硬件 `sqrtsd`，需实测确认）。**`Math.sin/cos/atan2/hypot/pow` 不保证**：V8、JSC、SpiderMonkey 的实现可以差最后 1–2 个 ulp。

本项目在这些地方用了超越函数：
- `src/game/boss.ts:73` `Math.hypot(b.x-p.x, b.z-p.z)` 算距离；
- `src/game/player.ts:224` `Math.hypot(ix, iz)` 归一化输入；
- `src/actors/behaviors.ts` 多处 `Math.sin/cos` 做步态；
- `src/actors/actions.ts` 全表 `Math.sin/cos` 做姿态（纯视觉，可不改）。

修法：仿真层禁用 `hypot/atan2/sin/cos`。距离用 `Math.sqrt(dx*dx+dz*dz)`；朝向用查表（1024 项 `sin/cos` LUT，线性插值）或整数角度。**代价**：`Math.sqrt` 仍是浮点，若要**跨机器**逐位一致，最终要走到定点（§2.3）。

## 2. 联机也要同结果：需要补什么

### 2.1 固定步与命令缓冲

```
SIM_HZ = 60
每个 tick 的输入 = { tick, moveX, moveZ, yaw, pitch, buttons, seq }
```

客户端在 tick N 采样输入，带 `seq` 发给服务器/主机；服务器在 tick N+delay 执行。所有玩家必须在**同一 tick** 执行同一组输入，顺序按 `playerId` 升序，不按到达时间。这是 lockstep 与权威服务器共同的前提。

命令缓冲的实现落点：`src/game/sim/command.ts`，`CommandBuffer.push(cmd)` 按 `tick` 排序，`step()` 取出 `tick === simTick` 的命令，缺命令时用「空输入」补齐（不阻塞，避免一人卡顿拖死全队）。

### 2.2 RNG 流分区

一条全局 RNG 在联机下会被「谁先调用」影响。必须按系统分叉，而且**分叉本身不能消耗父流**：

```ts
class RNG {
  fork(label: string, index = 0): RNG {
    let h = 2166136261;
    for (const ch of label) { h ^= ch.charCodeAt(0); h = Math.imul(h, 16777619); }
    h = Math.imul(h ^ index, 16777619) >>> 0;
    return new RNG((this.seed ^ h) >>> 0);   // 从 seed 派生，不调用 this.next()
  }
}
```

**为什么不能用 `this.next()` 派生**：如果 `fork('crowd')` 与 `fork('combat')` 的调用顺序在某次重构中互换，`this.next()` 会把父流推进一格，后续所有流整体错位；表面上「代码等价」，结果全变。用 `seed ^ hash(label)` 则每个流与调用顺序无关，这是联机确定性的硬要求。

流清单（每条独立、互不消耗）：

| 流 | 用途 | 是否参与对账 |
|---|---|---|
| `world` | 地形/建筑/植被 | 是（初始化一次） |
| `crowd` | 角色外观/初始状态 | 是 |
| `behavior` | 行人决策 | 是 |
| `combat` | Boss 选招/暴击/掉落 | 是 |
| `loot` | 掉落品质 | 是 |
| `vfx` | 粒子 | 否（纯视觉） |
| `audio` | 环境音 | 否 |
| `ui` | 提示抖动 | 否 |

关键纪律：**视觉流不得调用玩法流**。`vfx.ts` 要随机数就从 `vfx` 流取，不能顺手 `Math.random()`，否则「特效多放了一次」会改变 `combat` 流的消耗位置，导致对账漂移。这条比「禁用 Math.random」更细，也更难守；用 lint 规则 + `grep` 门禁双保险。

**流的分叉时机必须固定**：`World.init()` 里先 `fork` 出全部流，再按固定顺序交给各系统；不允许 `Baker` 在构造时顺手 `fork('bake')`——那样「先建 baker 还是先建 crowd」会改变流 id。正确写法是 `const streams = makeStreams(worldSeed)` 一次建齐，作为参数传入。

这不是洁癖：`src/world.ts:277` 的 `new RNG(20260905)` 被约 35 个 load task 共用（共享约束 §五已把这条列为跨卷口径），任何一个新系统在初始化时多取一个随机数，下游地形/建筑/植被的随机序列就会整体错位。所以新系统必须 `fork` 独立种子，不得直接 `import` 主 RNG；V9 的武器掉落、V8 的生物生成、V3 的方块纹理都要遵守同一条。

### 2.3 定点化：什么时候必须做

| 方案 | 精度 | 跨引擎 | 改动量 | 适用 |
|---|---|---|---|---|
| 纯浮点 + 同构建 | 双精度 | 同引擎同版本可 | 0 | 单机回放/同机验证 |
| 浮点 + 量化哈希 | 位置 1mm、角度 1mrad | 容差内可 | 小 | 联机容错对账 |
| 全定点（mm/mrad） | 整数 | 完全一致 | 大（~1500 行） | 严格 lockstep/PvP |

**建议**：先做「浮点 + 量化哈希」，把 `probe-replay` 跑通；只有当跨机器对账连续失败，才上全定点。理由：全定点要重写 `player.ts` 的移动、`physics.ts` 的积分、`boss.ts` 的距离判定，且会让现有手感（3.6/8.2 m/s、7.5 跳跃）全部重新调参，风险远大于收益。

这里要避免一个常见的工程误区：把「定点」当成「更正确」。定点不是更正确，它只是**更可对账**——同样的输入在任何机器上得到同样的整数。代价是精度损失（毫米级位置、毫弧度角度）与手感重调。对本项目这种以漫游/演出为主、战斗为辅的游戏，毫米级误差玩家感知不到，但「跳跃高度差 0.10m」是能感知的。所以顺序应该是：先固定步消除帧率差异，再量化哈希消除末位差异，最后才考虑定点；而不是一上来就把所有 `Vector3` 换成整数。

### 2.4 状态哈希

```
H(tick) = FNV1a32(
  tick,
  player: {x_mm, y_mm, z_mm, yaw_mrad, hp, stamina, yang, karma, weaponIdHash},
  entities sorted by id: {id, x_mm, y_mm, z_mm, yaw_mrad, hp, state}
)
```

- 位置量化到毫米：`Math.round(x * 1000) | 0`；角度量化到毫弧度。
- 实体必须**按 id 升序**，不能按 `Map` 插入顺序或 `crowd.actors` 数组顺序（后者会因隐藏/密度裁剪而变化）。
- 每 60 tick 在内存里算一个轻量 hash（用于逐段对账），每 600 tick 才写一个 checkpoint 进 replay 文件（用于断点恢复）；对账时从最后一个相同 checkpoint 开始逐 tick 二分，第一次分叉的 tick 就是 bug 现场。
- FNV-1a 32 碰撞率约 1/2³²；90 个内存 hash 下误报概率约 2×10⁻⁸，够用。**不要**用它做反作弊（可碰撞、可伪造），反作弊用 SHA-256。

哈希本身也会骗人，三个反例必须提前堵住：

1. **只哈希玩家**：Boss 的 HP/位置没进哈希，玩家被击退到同一位置但 Boss 已经换了招，哈希仍然相等。必须把「参与战斗的全部实体」纳入，按 id 排序。
2. **哈希了视觉量**：把 `actionT`、粒子数、相机位置纳入，两端画面本来就不要求逐帧一致，哈希永远对不上。视觉量不进哈希，是纪律不是偷懒。
3. **量化太粗**：位置量化到 0.1m，两个实体差 5cm 被判相同，desync 被吞掉。量化精度要小于「一次命中的最小位移」（击退 1.6m/s × 16.7ms ≈ 2.7cm），所以 1mm 是安全下限。

### 2.5 联机前必须清掉的禁止项

| 禁止项 | 现状 | 替代 |
|---|---|---|
| `Math.random` 进玩法 | 83 处 | `RNG.fork(label)` |
| `performance.now()` 进状态 | 6 处 | `simTick` |
| `Date.now()` 进状态 | 未发现（`grep` 为空） | — |
| `for...in` 遍历实体 | `world.ts:1060` 的 `POIS`、`hellPoiShield` | 改成显式 key 数组或排序 |
| `Set/Map` 迭代顺序依赖 | `Havoc.once`、`Physics.launches` | 按 id 排序后再遍历 |
| `async/await` 进 sim | `world.init` 有 35 步 async | 初始化可分帧；**战斗循环内禁止 await** |
| DOM 读取进 sim | `boss.ts` 的 `syncHud` 读 DOM | HUD 抽成事件订阅，sim 不碰 DOM |

### 2.6 分阶段落地

| 阶段 | 内容 | 产出 | 人日 |
|---|---|---|---|
| P0 | 固定步 + `simTick` + `Math.random` 替换（玩法路径） | `probe-determinism` 通过 | 8 |
| P1 | RNG 流分区 + 命令缓冲 + 哈希 | `probe-replay` 同机通过 | 6 |

P0 是单机收益（视觉回归、存档复现），即使不做联机也该做；P1/P2 是联机前置；P3 是 PvP 前置。

## 3. 存档格式

### 3.1 与 `.acs/task-state.json` 的边界

必须写死：**游戏存档与 `.acs/task-state.json` 没有任何关系**。

| 维度 | 游戏存档 | `.acs/task-state.json` |
|---|---|---|
| 所有者 | 玩家/游戏进程 | agent 工作流 |
| 路径 | `%APPDATA%/CyberQingming/saves/` | 仓库根 `.acs/` |
| 生命周期 | 玩家可删、可云同步 | 任务结束即归档 |
| schema | `SaveV4`（本卷定义） | ACS 1.1.0 契约 |
| 读写者 | Electron main + renderer | ACS 门禁脚本 |
| 失败后果 | 读档失败/回退备份 | 门禁 BLOCK |

游戏运行时**不得**读 `.acs/`；ACS 门禁**不得**读游戏存档。两者共用「JSON + 版本号 + 校验和」的形式是巧合，不是耦合。

### 3.2 SaveV4 schema

```json

    "levelOrderVersion": 1
  },

```

字段纪律：
- id 命名规则：武器用 `拼音_拼音`（`tie_jian`/`qingfeng_jian`/`dao_gang`），护甲用 `套装_slot`（`pijia_head`），符箓用 `拼音_fu`（`huo_fu`），铭刻用 `拼音`（`pijun`）。这些 id 必须与 §2 武器表、§3.1 护甲表、§3.2 效果表一一对应；上面 JSON 里的 id 是 schema 样例，不是新增物品。
- `magic` 必须是 `CQSV`；不是则拒绝，不尝试修复。
- `schema` 是**存档自身的版本**；`minReader` 是「低于此版本的 reader 必须拒绝」。
- `checksum` 覆盖「除 `checksum` 外的所有字段」，用规范化 JSON（键按字典序、无空白）计算。
- 位置用米（float），不存量化值；量化只用于哈希，不用于存档（存档要可读、可手改调试）。
- `inventory` 上限 300 条；超出时按 `count` 合并同类，仍超出则拒绝保存并提示「背包已满」。

**逐字段不变量**（`validateSave()` 按此表机检，失败即拒绝读档，不做「尽力修复」）：

| 字段 | 类型 | 范围/约束 | 失败处理 |
|---|---|---|---|
| `magic` | string | 严格 `"CQSV"` | 拒绝 |
| `schema` | int | 1–`CURRENT_SCHEMA`（当前 4） | >4 走 §3.5 协商 |
| `minReader` | int | 1–`CURRENT_SCHEMA` | 缺失按 1 |
| `worldSeed` | uint32 | 0–4294967295 | 拒绝 |
| `playTicks` | uint32 | ≥0 | 拒绝 |
| `realm` | enum | `renjian/tiangong/difu` | 回退 `renjian` 并记 warning |
| `player.pos` | float[3] | `\|x\|,\|z\| ≤ 20000`，`y ∈ [-300, 2500]`，全 finite | 拒绝 |
| `player.hp` | int | 0–`maxHp`（100） | 夹取并记 warning |
| `player.stamina` | int | 0–100 | 夹取 |
| `player.yang` | int | 0–100 | 夹取 |
| `player.karma` | int | -100–100 | 夹取 |
| `player.wanted` | int | 0–5 | 夹取 |
| `equipment.weapon` | string | `WEAPONS` 的 id 或 `fist` | 回退 `fist` 并记 warning |
| `equipment.armor.*` | string\|null | `ARMOR` 的 id 或 null | 回退 null |
| `inventory[].count` | int | 1–999 | 拒绝 |
| `inventory[].durability` | int | 0–`spec.durability` | 夹取 |
| `inventory[].temper` | int | 0–5 | 夹取 |
| `inventory[].inscribe` | string\|null | `RUNES` 的铭刻 id 或 null | 回退 null |
| `progress.objectives` | object | 键 ∈ `LEVEL_ORDER`；每项 `{done:boolean,at:uint32,source:'live'\|'legacy'}` | 未知键移 `legacyObjectives` |
| `economy.coins/yinde/peach` | int | ≥0 | 夹取到 0 |
| `checksum` | string | `^fnv1a32:[0-9a-f]{8}$` | 拒绝 |

这张表的意义：读档失败时，玩家得到的是「哪一行坏了」而不是「存档损坏」四个字。`validateSave` 返回 `{ok, errors[], warnings[]}`，UI 只展示前 3 条。

### 3.3 原子写与备份环

```
saves/
  slot.0.json          // 当前
  slot.1.json          // 上一版
  slot.2.json          // 上上版
  slot.0.bak           // 写入前快照
  slot.tmp             // 写入中
  index.json           // { activeSlot, lastGoodChecksum, updatedAt }
```

写流程（Electron main）：
1. `JSON.stringify(save)` → 计算 checksum → 写 `slot.tmp`；
2. `fs.fsyncSync(fd)` → `fs.closeSync(fd)`；
3. 若 `slot.0.json` 存在，`fs.copyFileSync(slot.0, slot.0.bak)`；
4. `fs.renameSync(slot.tmp, slot.0.json)`（同分区原子）；
5. 轮转：`slot.1 → slot.2`、`slot.0.bak → slot.1`；
6. 写 `index.json`（先写 tmp 再 rename）。

**失败语义**：任一步失败，`slot.0.json` 保持旧内容；`slot.tmp` 残留由下次启动清理。绝不「先删旧档再写新档」。

为什么不用 `fs.writeFileSync(path, json)`：它只保证「数据交给了操作系统」，不保证「已经落盘」。断电时可能出现「文件长度已更新、内容还是旧块」的半写状态，读出来是合法 JSON 但字段被截断。`open → write → fsync → close → rename` 的组合保证：要么看到旧档，要么看到完整新档，不存在中间态。`rename` 必须在同一分区，否则是复制+删除，不是原子操作；因此 `slot.tmp` 与 `slot.0.json` 必须同目录。

备份环的意义不是「多存几份」，而是「任意一次写入失败都能退回上一个已知良好状态」。三个 slot 对应「当前、上一次自动存档、上一次手动存档」；`index.json` 里的 `lastGoodChecksum` 是最后的仲裁者：读档时若 `slot.0` 校验失败，自动尝试 `slot.1`，再失败尝试 `slot.2`，三者都坏才提示玩家「存档损坏」。这条链必须写进 `probe-save-atomic.mjs` 的断言，不能只写在文档里。

### 3.4 三次破坏性迁移

| 迁移 | 旧 → 新 | 破坏点 | 兼容策略 |
|---|---|---|---|
| v1→v2 | `localStorage` 三键 → `SaveV2` | 旧档没有位置/任务/背包，只有 `cq_coins/cq_yinde/cq_peach` 与 `playerWeapon.mult` | 位置默认 `(-20,0,58)`（`world.ts:655` 的出生点）；任务空；`mult 2.5 → dao_gang`，`1 → fist`；`migrationReport.losses` 记 `position/quests/inventory` |
| v2→v3 | `inventory: string[]` → `items: {id,count,durability,temper,inscribe}[]` | 旧字符串没有耐久/淬炼/铭刻 | 同名堆叠；`durability = round(spec.durability × 0.6)`，`temper=0`，`inscribe=null`；`migrationReport.estimated` 逐条记 `durability` |
| v3→v4 | `quests: Record<string,boolean>` → `objectives: {done,at,source}` | 旧档没有完成时间 | `at=0`、`source='legacy'`；不在 `LEVEL_ORDER` 的键移入 `legacyObjectives`，**不删除**；新增 `rng.streams/playTicks/realm/yang/karma/wanted` |

三次迁移都遵循同一条纪律：**只增不删、先备份再迁移、迁移结果写 `migrationReport`**。破坏性指的是「信息无法完全恢复」，不是「静默丢数据」。

`custom_mod_zone` 这种不在 `LEVEL_ORDER` 的键必须保留：它可能是玩家装的 mod 或旧版本节点，删掉等于毁档。UI 不显示它，但读档不报错。

**迁移函数签名**：

```ts
type Migration = (old: unknown) => { save: SaveV4; report: MigrationReport };
const MIGRATIONS: Record<number, Migration> = { 1: v1ToV2, 2: v2ToV3, 3: v3ToV4 };
export function migrate(raw: unknown): SaveV4 {
  let s = raw as { schema?: number };
  while ((s.schema ?? 1) < CURRENT_SCHEMA) {
    const step = MIGRATIONS[s.schema ?? 1];
    if (!step) throw new SaveError('NO_MIGRATION_PATH');
    const r = step(s); s = r.save; report.merge(r.report);
  }
  return validate(s);
}
```

迁移必须**幂等**：同一份 v1 跑两次得到同一份 v4（`migrationReport` 除外，带时间戳）。测试用固定 fixture 跑两次逐字段对比。

### 3.5 版本协商与前向兼容

| 读到的 `schema` | 当前 build 行为 |
|---|---|
| `< 4` | 依次迁移；迁移失败则**不写回**，让玩家选择「用备份 / 放弃」 |
| `= 4` | 校验 checksum 后直接读 |
| `> 4` 且 `minReader ≤ 4` | 只读兼容模式：忽略未知字段，**不回写**（避免降级丢字段） |
| `> 4` 且 `minReader > 4` | 拒绝，提示「存档来自更新版本，请升级游戏」；不覆盖、不删除 |

### 3.6 容量与性能预算

- 单档 < 256KB（300 件物品约 36KB + 任务/图鉴约 8KB + 元数据 2KB）。
- 写入 < 10ms（含 fsync）；读档 + 校验 < 50ms。
- 自动存档每 60s 一次，且在「传送/进 Boss/退出」三个事件点强制存；**不在战斗帧内存档**。
- 云同步时压缩：`zlib.gzipSync`（Electron main），压缩后约 8–20KB；checksum 对**未压缩** JSON 计算，避免压缩实现差异。

## 4. 多人架构选型

### 4.1 三条路线

**路线 A：权威服务器 + 客户端预测**
- 服务器 60Hz 跑 sim，20Hz 下发快照；客户端本地预测，收到快照后回滚重放未确认输入。
- 适合 PvP、需要防作弊的场景。
- 成本：服务器、匹配、反作弊、运维；8–12 人周。

**路线 B：房主权威（host-authoritative）**
- 一名玩家当 host，跑完整 sim；其他客户端只发输入、收快照；host 迁移时选新房主。
- 适合 2–4 人 co-op；host 有延迟优势，但可接受。
- 成本：WebRTC/WS 中继、NAT 穿透、host 迁移；4–6 人周。

**路线 C：确定性 lockstep**
- 所有客户端跑同一 sim，只同步输入；每 60 tick 对哈希，分叉即暂停。
- 带宽最省，但对确定性要求最高；任何 `Math.random`/浮点差异都会 desync。
- 成本：确定性改造 4–6 人周 + 网络 3–4 人周；6–10 人周。

### 4.2 代价对比

| 维度 | A 权威服务器 | B 房主权威 | C lockstep |
|---|---|---|---|
| 下行带宽/客户端 | ~5.8KB/s（20Hz 增量） | ~5.8KB/s | ~3.4KB/s（只收输入） |
| 上行带宽/客户端 | ~0.5KB/s（输入） | ~0.5KB/s | ~0.5KB/s |
| 服务器/主机上行 | 8 人 × 5.8 = 46.4KB/s | host 上行 8 × 5.8 = 46.4KB/s | 3.8KB/s 广播 |
| 感知延迟 | 150–200ms（100ms 插值缓冲） | 80–150ms（host 0） | 100–250ms（等最慢输入） |
| 作弊面 | 低（服务器裁决） | 中（host 可改内存） | 高（客户端可注入，只能事后对账） |
| 断线恢复 | 服务器保留状态，重连快 | host 掉线需迁移 | 任一人掉线全队暂停 |
| 开发量 | 8–12 人周 | 4–6 人周 | 6–10 人周 |
| 与本项目冲突 | 需拆 `SimWorld`/`RenderWorld` | 低（host 跑完整客户端） | 高（全量确定性改造） |

**带宽算法**（可复算）：单实体快照 `id u16 2B + pos 3×i32 12B + yaw i16 2B + hp u16 2B + state u8 1B + flags u8 1B = 20B`；48 实体 = 960B/快照；20Hz = 19.2KB/s；增量 30% = **5.8KB/s**。输入 `buttons u16 + yaw i16 + pitch i16 + move u8 + seq u8 = 8B`；60Hz = 480B/s。这些是**估算**，实际要 `probe-bandwidth` 实测。

### 4.3 推荐与分期

1. **先做单机 P0/P1**（固定步 + 种子 + 回放）。没有这一步，联机一定是「看起来同步、实际各跑各的」。
2. **co-op 走路线 B**（2–4 人）。理由：host 跑完整客户端，不需要拆 `SimWorld`，与现有 13.35M 面数的渲染架构兼容；代价是 host 优势与作弊面，但 co-op 可接受。
3. **PvP 才上路线 A**。那时再拆 `SimWorld`，把碰撞/伤害/掉落放服务器，渲染留客户端。
4. **路线 C 只用于回放验证**，不作为首发联机方案。它的收益（带宽）在本项目不是瓶颈，风险（desync）却是最高的。

为什么对 lockstep 这么保守：它的前提是「所有客户端逐位一致」，而本项目的仿真里有 4000+ 角色、127 处 `Math.random`、6 处墙钟、可变步长、5 类超越函数。任何一处没清干净，desync 不会立刻报错，而是「两个人看到的 Boss 血量差 3 点」——这种 bug 的定位成本远高于它的带宽收益（本项目 8 人满负载也就 5.8KB/s，而 13.35M 面数的渲染才是真瓶颈）。lockstep 适合「小状态、强确定、竞技」的场景；本项目是「大世界、弱确定、漫游」，用它是拿最贵的工程换最不缺的带宽。

反过来，路线 B 的代价是明确的：host 有 0 延迟优势，客户端多 80–150ms；host 可以改内存作弊。co-op 场景下这两个代价可接受，因为玩家是朋友而不是对手。若未来做 PvP，再按路线 A 拆服务器；那时 P0/P1 的确定性工作也不会白做——服务器同样需要固定步与种子。

### 4.4 与 13.35M 面数的冲突

服务器不能渲染 13.35M 三角形，也不需要：联机只同步**状态**（位置/HP/状态机），不同步几何。但当前 `World` 把 sim 与 render 绑死：
- `src/world.ts:589` 的 `spawnCrowd` 同时创建 Actor 与实例矩阵；
- `src/actors/crowd.ts:741` 的 `writeActor` 每帧写 `InstancedMesh` 矩阵；
- `src/actors/pools.ts:106` 在模块级 `document.createElement('canvas')` 建纹理，**无 DOM 环境直接崩**。

所以路线 A 的服务器不能直接 `import World`。两条路：
- **B 路线绕过**：host 是完整客户端，不需要 headless；
- **A 路线必须先拆**：`SimWorld`（无 Three.js、无 DOM） + `RenderWorld`（读 SimWorld 状态画）。这是 3–4 人周的架构改造，且会触碰 `pools.ts` 的模块级 DOM 依赖（`creatures.ts:7` 的注释已经警告过这个问题）。

## 5. 与 Electron 打包的关系

### 5.1 现状

`electron/main.cjs` 只有 28 行：`BrowserWindow` + `loadFile(dist/index.html)`，`contextIsolation: true`、`nodeIntegration: false`，**没有 preload、没有 IPC、没有存档目录**。渲染进程只能用 `localStorage` 存三个键（`src/game/interact.ts:31-33`）。

`package.json` 的 `build.directories.output` 仍写 `release-v11`，而仓库已有 `release-v94`。这是打包配置漂移：每次 `npm run dist:win` 都会往旧目录写，产物版本号靠 `artifactName` 里的 `${version}` 区分，但目录不区分。V10 建议改成 `release-v${version}` 或统一 `release/`，并在打包脚本里断言「产物路径含当前版本」。

### 5.2 preload / IPC 设计

新增 `electron/preload.cjs`：

```js
const { contextBridge, ipcRenderer } = require('electron');
contextBridge.exposeInMainWorld('cqSave', {
  read: (slot) => ipcRenderer.invoke('save:read', slot),
  write: (slot, json) => ipcRenderer.invoke('save:write', slot, json),
  list: () => ipcRenderer.invoke('save:list'),
  remove: (slot) => ipcRenderer.invoke('save:remove', slot),
});
```

`main.cjs` 增加 `preload: path.join(__dirname, 'preload.cjs')`，并注册四个 handler。安全边界：
- `slot` 只允许 `0/1/2/autosave`，不接受任意路径；
- `json` 长度 ≤256KB，先 `JSON.parse` 再校验 `magic/schema/checksum`；
- 写入走 §3.3 的原子流程；
- 渲染进程永远拿不到 `fs`/`path`，只能通过这四个方法。

handler 的校验骨架（`electron/save-ipc.cjs`，由 `main.cjs` 注册）：

```js
const SLOTS = new Set(['0', '1', '2', 'autosave']);
const MAX_BYTES = 256 * 1024;

function assertSlot(slot) {
  if (!SLOTS.has(String(slot))) throw new Error('E_SLOT');
}

function parseSave(text) {
  if (Buffer.byteLength(text, 'utf8') > MAX_BYTES) throw new Error('E_TOO_LARGE');
  const s = JSON.parse(text);
  if (s.magic !== 'CQSV') throw new Error('E_MAGIC');
  if (!Number.isInteger(s.schema) || s.schema < 1 || s.schema > 4) throw new Error('E_SCHEMA');
  if (typeof s.checksum !== 'string' || !/^fnv1a32:[0-9a-f]{8}$/.test(s.checksum)) throw new Error('E_CHECKSUM');
  if (fnv1a32(canonicalJson(s, ['checksum'])) !== s.checksum) throw new Error('E_CHECKSUM_MISMATCH');
  return s;
}

ipcMain.handle('save:write', async (_e, slot, text) => {
  assertSlot(slot);
  const save = parseSave(text);          // 先校验，后落盘
  return writeAtomic(path.join(SAVE_DIR, `slot.${slot}.json`), JSON.stringify(save));
});
```

三个细节：
- `canonicalJson()` 必须按键名字典序输出，且排除 `checksum`；否则同一份存档在不同 V8 版本下 checksum 不同。
- `writeAtomic()` 用 `fs.openSync(tmp,'w')` → `writeSync` → `fsyncSync` → `closeSync` → `renameSync`；不要用 `fs.writeFileSync`（它不保证 fsync）。
- `save:read` 返回 `{ok, save, errors}`，不抛异常给渲染进程；渲染进程根据 `ok` 决定是否进「坏档恢复」流程。

**与现有 `contextIsolation: true` 的兼容**：preload 用 `contextBridge` 暴露白名单方法，不需要关掉隔离；`nodeIntegration` 保持 `false`。这条不能妥协——关掉隔离等于把整个文件系统交给页面。

### 5.3 单机存档目录

- Windows：`app.getPath('userData')` → 通常是 `%APPDATA%/CyberQingming/`，存档在 `saves/`。
- macOS：`~/Library/Application Support/CyberQingming/saves/`。
- Linux：`~/.config/CyberQingming/saves/`。
- **portable exe**：electron-builder 的 `portable` 目标会把程序解压到临时目录；`userData` 仍走 `%APPDATA%`，**不随 exe 走**。若希望「U 盘带走存档」，需读 `process.env.PORTABLE_EXECUTABLE_DIR` 并把 `saves/` 放旁边——这条**待验证**（不同 electron-builder 版本行为可能不同），不要先写进承诺。

### 5.4 云同步与冲突解决

云同步是可选层，不阻塞单机。目录：

```
saves/
  cloud/
    sync.json           // { deviceId, lastSync, files: { slot.0: {hash, updatedAt, playTicks} } }
    remote/             // 云端拉下来的副本（只读镜像）
```

冲突规则（按顺序）：

1. 本地 hash == 远端 hash → 跳过。
2. 本地 `parentHash` == 远端 hash → 远端是祖先，本地快进上传。
3. 远端 `parentHash` == 本地 hash → 本地是祖先，拉取远端。
4. 否则**分叉**：写 `slot.0.conflict.<deviceId>.<timestamp>.json`，两份都保留，弹窗让玩家选；**绝不自动合并** `inventory/economy/objectives`。
5. `codex` 可以取并集（只增不减），但仅作为「展示」，不写回主档；主档仍以玩家选择为准。

**为什么不做自动合并**：`economy` 合并可被刷（两边各买一次再合并）；`objectives` 合并会让「没打过的 Boss」变成已完成。单人游戏的云同步，正确性优先于便利性。

举一个真实会发生的冲突：玩家在台式机把巨灵神打到 50%，存档 A 的 `updatedAt` 是今天 10:00；晚上在笔记本离线玩到 30%，存档 B 的 `playTicks` 更大但 `updatedAt` 是昨天。按 `updatedAt` 取 A，B 的两小时白玩；按 `playTicks` 取 B，A 的 Boss 进度倒退。两个指标都不能单独做仲裁，所以只能保留两份、让玩家选。UI 不能只写「存档冲突」，要给出可比较的信息：

```
A：巨灵神 50% · 天宫将台 · 今天 10:00 · 游玩 2h14m
B：巨灵神 30% · 人间虹桥   · 昨天 22:40 · 游玩 4h02m
[用 A] [用 B] [都保留]
```

「都保留」写 `slot.0.conflict.*.json`，不覆盖主档；玩家选完后主档才更新。这条流程的价值不是技术，而是**不替玩家做不可逆的决定**。

### 5.5 打包验收

- `npm run dist:win` 后，产物路径含当前 `version`；
- 启动打包版，写一次存档，`%APPDATA%/CyberQingming/saves/slot.0.json` 存在且 checksum 通过；
- 删除 `slot.0.json`，启动后能从 `slot.1.json` 恢复；
- 断网启动，云同步失败但单机可玩（不得阻塞启动）。

## 6. 回放与验证

### 6.1 ReplayV1 格式

```json
{
  "magic": "CQRP",
  "version": 1,
  "worldSeed": 20260905,
  "simHz": 60,
  "startTick": 0,
  "endTick": 5400,
  "build": "1.2.0+20261103",
  "inputs": [
    { "t": 0, "moveX": 0, "moveZ": -1, "yaw": 1.57, "buttons": 1 },
    { "t": 17, "moveX": 1, "moveZ": 0, "yaw": 1.57, "buttons": 0 }
  ],
  "checkpoints": [
    { "t": 600, "hash": "0x8f2c1a44" },
    { "t": 1200, "hash": "0x1a2b3c4d" }
  ],
  "result": { "playerHp": 42, "bossHp": 0, "codex": ["juling"], "hash": "0xdeadbeef" }
}
```

- `inputs` 只在**输入变化**时记录，不是每 tick 一条；回放时按 tick 插值/保持。
- `build` 必须匹配，否则拒绝回放（不同构建的物理常量可能不同）。
- `checkpoints` 每 600 tick（10s）一个；对账从最后一个相同 checkpoint 开始。

「只在变化时记录」有一个必须写清的细节：`yaw` 是连续量，鼠标每帧都可能变。若每帧都记，5400 tick 的 replay 会有 5400 条输入，文件约 300KB，回放 IO 本身就会影响计时；若只记「变化超过 1mrad」的采样，文件降到 10–30KB，但回放时会丢失亚毫弧度的微调。V10 取折中：**按键/按钮变化必记，视角按 1mrad 量化后变化才记**，并在 `inputs` 里存量化值而不是原始浮点。这样回放与实时输入的差异不超过 1mrad（约 0.057°），玩家感知不到，文件又足够小。

回放文件不放 `world` 全量快照：5400 tick 的世界状态 JSON 约 3–8MB，且与 `worldSeed` 重复。正确做法是「种子 + 输入 + 每 600 tick 的哈希」，需要中间状态时用 `checkpoint` 重新跑——这也是为什么固定步与种子必须先做，否则 replay 只是一段「看起来像」的录像，不是可验证的证据。

### 6.2 哈希规范化

```ts
function hashState(w: SimWorld): number {
  let h = 2166136261;
  const feed = (n: number) => { h ^= n & 0xff; h = Math.imul(h, 16777619) >>> 0; };
  feed(w.tick);
  feed(w.player.hp); feed(w.player.stamina);
  feed(Math.round(w.player.pos.x * 1000)); // 量化到 mm
  feed(Math.round(w.player.pos.z * 1000));
  feed(Math.round(w.player.yaw * 1000));
  const ids = [...w.entities.keys()].sort((a, b) => a - b);
  for (const id of ids) {
    const e = w.entities.get(id)!;
    feed(id); feed(Math.round(e.pos.x * 1000)); feed(Math.round(e.pos.z * 1000));
    feed(e.hp); feed(e.state);
  }
  return h >>> 0;
}
```

三条纪律：
- **排序**：实体按 id 升序，不按数组/Map 顺序。
- **量化**：位置 mm、角度 mrad；浮点末位差异不应导致误报。
- **不含视觉**：粒子、动画相位、相机不参与哈希（否则永远对不上）。

### 6.3 `probe-replay.mjs` 流程

复用现有探针模式（`puppeteer-core` + `CHROME` + `waitForFunction(()=>!document.getElementById('loading'))`）：

1. 启动 preview，等 `window.__qingming` 就绪。
2. `world.loadReplay(fixture)`：重置 sim 到 `startTick`，加载 `worldSeed`，清空输入。
3. 循环 `world.runTicks(60)` 90 次；每次对比 `hashState()` 与 `checkpoints`。
4. 结束时对比 `result.hash`。
5. **同一页面重跑一次**（捕获全局状态泄漏）。
6. **刷新页面再跑一次**（捕获模块级单例泄漏，如 `pools.ts` 的纹理、`behaviors.ts` 的 `WS_GRID`）。
7. 任一次不一致 → 输出第一个分叉 tick + 实体 diff，退出码 1。

**现有阻塞**：`Engine.start()` 是 rAF 驱动，`world.update(t,dt)` 直接跑；回放需要 `engine.stop()` + `world.runTicks(n)` 的纯 sim 循环，且 `player.update` 里不能读 `performance.now()`。P0/P1 不做完，回放一定失败——这不是探针的问题，是仿真本身不确定。

探针核心循环（节选，沿用 `scripts/probe-boss.mjs` 的 `page.evaluate` 模式）：

```js
// scripts/probe-replay.mjs
const page = await browser.newPage();
await page.goto(PREVIEW_URL, { waitUntil: 'networkidle2' });
await page.waitForFunction(() => !document.getElementById('loading') && !!window.__qingming);

const out = await page.evaluate((fixture) => {
  const w = window.__qingming.world;
  window.__qingming.engine.stop();          // 停 rAF，改为手动 tick
  const bad = [], runs = [];
  for (let run = 0; run < 2; run++) {
    w.loadReplay(fixture);                  // 重置 sim / seed / 输入 / tick
    for (let t = 0; t < fixture.endTick; t += 60) {
      w.runTicks(60);                       // 60 个固定步，不渲染
      const want = fixture.checkpoints.find((c) => c.t === t + 60);
      if (want && w.hashState() !== want.hash) {
        bad.push({ run, t: t + 60, got: w.hashState(), want: want.hash });
        break;
      }
    }
    runs.push(w.hashState());
  }
  return { bad, runs, final: w.hashState() };
}, fixture);
```

### 6.4 回放分级：L0 / L1 / L2

「回放通过」是一句需要拆开的话，不同级别证明不同的东西：

| 级别 | 做法 | 能捕获 | 不能捕获 | 是否可作为联机证据 |
|---|---|---|---|---|
| L0 | 同一页面跑两次 | 全局变量/单例泄漏、`loadReplay` 未清干净 | 模块初始化顺序、DOM 依赖 | 否 |
| L1 | 刷新页面再跑 | 模块级单例（`pools.ts` 纹理、`behaviors.ts` 的 `WS_GRID`）、初始化顺序 | 跨引擎浮点差异 | 否 |
| L2 | 两台机器/两个 Electron 版本跑同一 replay | 浮点超越函数差异、引擎版本差异 | 网络抖动、作弊 | **是**（同结果的最低证据） |
| L3 | 跨游戏版本跑旧 replay | 常量漂移、迁移破坏 | — | 否（只作回归） |

V10 的验收只要求 L1；L2 作为「联机前置」单独立项，L3 不承诺。把 L1 说成「联机没问题」是虚假汇报，报告里必须写明级别。

### 6.5 回放能证明什么、不能证明什么

**能证明**：
- 同一构建、同一机器，同一输入序列得到同一状态（checkpoint hash 一致）；
- 修 bug 后旧 replay 仍能跑通（回归）；
- 存档读回后继续跑，状态与不读档一致（读档不污染）。

**不能证明**：
- 跨机器一致（浮点超越函数差异，见 §1.5）；
- 玩家看到的画面一致（渲染插值、粒子、相机不在哈希里）；
- 反作弊（FNV 可伪造）。

这三条要分开写进验收报告，不能拿「回放通过」冒充「联机没问题」。

**回放失败时怎么定位**：不要从第 0 tick 重新单步——那要跑几千次。正确流程是「从最后一个相同 checkpoint 二分」：

1. 取最后一个 `hash` 相同的 checkpoint `C`，从 `C` 的存档快照恢复；
2. 每次推进 1 tick，比较 `hashState()`，找到第一个不同的 tick `T`；
3. 在 `T` 导出实体 diff：`{id, field, a, b}`，按 id 升序，只列不同的字段；
4. 按四类常见原因排查：① 某个视觉系统偷用了 `combat` 流；② 某处仍读 `performance.now()`；③ 实体遍历顺序变了（`Set/Map` 插入顺序）；④ 新加字段没进哈希（看起来相同，实际状态不同）。

这四类的排查顺序不能反：先查流，再查时钟，再查顺序，最后查漏字段。因为前三类会伪装成「随机 desync」，第四类才是「哈希没覆盖」。把 diff 写进 `artifacts/replays/<fixture>.diff.json`，下次回归直接对比，不用重新猜。

1. **P0 会暴露隐藏耦合**。把 `performance.now()` 换成 `simTick` 时，会发现 `impactUntil` 同时被 `player.ts`、`physics.ts`、`crowd.ts` 三处读写，且语义不同（一个是「输入锁定」、一个是「硬直」、一个是「动画时间线」）。拆语义比换字段慢，通常多 2–3 天。
2. **存档迁移要跑旧档**。仓库里没有 v1/v2 的真实旧档，只能从 `localStorage` 三键反推；反推出来的 fixture 是否覆盖真实玩家状态，需要人工构造 3–5 份，测试成本被低估。
3. **视觉回归不可省**。`spawnActor` 种子化会让 4000+ 角色外观变一次；如果只跑单测不跑截图，玩家会先发现「人变了」。至少要留 2 天做前后对比与局部回退。

所以 33 人日是「顺利路径」，加 30% 缓冲约 **43 人日 ≈ 8.6 人周**；如果要做联机路线 B，再加 20–30 人日与联调时间，整体接近 12–14 人周。这个量级不应该由一个人扛，至少拆成「确定性」「存档/Electron」「回放/探针」三条线并行。

## 9. 未决与待验证

- **跨引擎浮点一致性**：V8/JSC 对 `Math.sqrt` 是否逐位一致，未实测；`Math.sin/cos/atan2` 已知不保证。P2 的「跨机器同 hash」需要两台不同浏览器/Electron 版本实测后才能承诺。
- **`crowd.spawnActor` 种子化的视觉影响**：会影响 4000+ 角色的外观分布；需要一次「改造前/后」截图对比，确认不是「全城换了一批人」的不可接受回归。
- **portable exe 的 `userData` 行为**：electron-builder 版本相关，需在目标机实测 `PORTABLE_EXECUTABLE_DIR` 与 `app.getPath('userData')` 的实际值。
- **路线 B 的 NAT 穿透**：WebRTC 在部分企业网/校园网需要 TURN 中继；中继带宽成本未估算。
- **路线 A 的 `SimWorld` 拆分**：`pools.ts:106` 的模块级 `document.createElement('canvas')`、`creatures.ts:7` 的注释都表明当前代码不能无 DOM 运行；拆分工作量是 3–4 人周的**下限**，实际可能更高。
- **存档容量 256KB**：按 300 件物品估算；若未来加「每件物品的词条历史」，会超。需要时改成 gzip + 分片，不要先放大上限。
- **回放的渲染验证**：本卷只验证 sim 哈希，不验证画面；要做「画面回放」，需另存相机轨迹与 VFX 随机流，成本另算。
- **手改存档与 mod 的边界**：玩家手改 `legacyObjectives`、塞未知物品 id 不应导致崩溃。校验器对未知字段只记 `warning` 不拒绝，写回时保留原字段；但 `magic/schema/checksum` 三项仍严格——手改后 checksum 失效的档，进「只读恢复」而不是「静默覆盖」。
