# V2 体素世界 × 烘焙世界

> 卷次 V2 / 12 ｜ 上游：V1（总纲与可玩性支柱）｜ 下游：V3（方块与材质）、V5（建造）、V11（性能）、V12（验收）
>
> 本卷只回答一个问题：**一个烘焙的、静态的、有限的世界，如何容纳一块可破坏、可放置、可增长的体素区域，而不把现有 13.35–15.09M 面与 8.3–9.7s 载入一起拖垮。**

## 0. 冲突的精确表述

先把两个世界的差别写成可对账的数字，而不是形容词。

| 维度 | 烘焙世界（现状） | 体素世界（要加的） |
|---|---|---|
| 数据形态 | 顶点缓冲，非索引三角面 | 定长整数数组，每格一个 id |
| 几何来源 | `Baker.push()` 逐构件累积（`bake.ts:771`） | `ChunkMesher.build()` 逐区块面剔除生成 |
| 生命周期 | 构建期一次性写入，运行期只读 | 运行期任意时刻可写，写后需重建 |
| 空间组织 | 无（`compactStatic()` 后按材质合并） | 16³ 区块，按沙盒分组 |
| 面数量级 | 13.35–15.09M（全场景） | 单沙盒上限 40,960 tri |
| 内存形态 | 40.06M 顶点 × 约 28B ≈ 1.1GB | 240 区块 × 8KB ≈ 1.97MB |
| 载入 | 35 个 task + 36 次 `flush` + 1 次 `compactStatic`（task 数按 `world.ts` 的 tasks 数组实测；文件内旧注释「33 步」为历史值） | 按需，零预载 |

数字对账之后，冲突只剩三条，且都不是「性能」这种笼统说法：

**冲突一：所有权。** `compactStatic()`（`world.ts:710`）把同材质的 `city_*` 网格合并成 ≤48MB 的批次。合并之后，「这栋楼在哪一段顶点里」这个信息**不存在了**。体素区如果要能被单独重建，它的几何就必须**不进入**这次合并——但同一个场景里又要和合并后的烘焙体共存。

**冲突二：生命周期。** `Baker.flush()`（`bake.ts:1297`）只会追加新 Mesh，从不删除。现有代码里没有任何一处 `scene.remove(mesh)` 针对城市几何。体素区需要「删旧几何、建新几何」，这是一条现有代码从未走过的路径。

**冲突三：预算。** 烘焙世界的预算是**一次性**的：载入时花掉 8.3–9.7s，之后每帧只付渲染成本。体素世界的预算是**持续**的：玩家每敲一下都要付一次重建成本。两种预算不能混在一个账本里，否则「载入没超」和「操作不卡」会互相掩盖。

还有一条被忽视的冲突，它不出现在任何设计文档里，但会直接让方案失败：

**冲突四：命名空间即协议。** 现有代码有两处按 `name` 前缀做全局操作，且都在 `world.ts` / `sky/expansion.ts` 里：

- `compactStatic()`：`if (!m.isMesh || !m.name.startsWith('city_')) return;`（`world.ts:716`）
- `scaleHeavenGeometry()`：`if (!(m.name.startsWith('city_') || m.name.startsWith('sky_cloudSheets'))) return;`，随后对 `y >= HEAVEN_Y_MIN(150)` 且 `|x|,|z| < 1500` 的顶点做 `x*s, HEAVEN_BASE_LIFTED + (y-196)*s, z*s`（`sky/expansion.ts:294`、判定在 `:300`）

这意味着：**体素网格只要被命名为 `city_vox_*`，就会被天宫 2.2× 缩放二次变形，然后被 `compactStatic` 合并掉，从此不可重建。** 命名不是风格问题，是协议问题。本卷所有方案统一使用 `vox_` 前缀。

## 1. 路线 A：局部体素沙盒 + 烘焙背景（推荐）

一句话：烘焙世界一格不动，体素区作为**独立的几何命名空间**叠在指定位置。

### 1.1 数据结构

**区块尺寸 16×16×16 = 4,096 体素。** 三条理由，都可验证：

1. `Uint16Array(4096)` 正好 8,192 字节，一个区块的存储是常量，便于做内存预算。
2. 坐标到区块的换算是位运算：`cx = wx >> 4`、`lx = wx & 15`，没有除法与取模。
3. 重建一个区块要检查 `4,096 × 6 = 24,576` 次邻居。32³ 区块是 `32,768 × 6 = 196,608` 次，单次重建成本涨 8 倍，而玩家一次只能改一格——粒度太粗会造成明显卡顿。

**存储布局**：每个沙盒一个扁平数组，不做 `Map`。

```
chunksPerSandbox = 4 × 4 × 3 = 48        // 64/16, 64/16, 48/16
index(cx, cy, cz) = (cy * 4 + cz) * 4 + cx   // 0..47
sandbox.chunks: (Uint16Array | null)[48]
```

用扁平数组而不是 `Map<string, Chunk>` 的理由是热路径：面剔除时每个体素要查 6 次邻居，其中边界体素要跨区块。`Map` 的字符串键在这个频率下会产生大量临时字符串。扁平数组的下标是纯算术，且天然支持「空区块 = `null`」的稀疏表示——玩家没去过的地方一个字节都不分配。

**索引与调色板**：`Uint16Array` 存的是 `BlockDef.id`，全局唯一，不是每区块调色板。原因是方块种类预计在 60–120 之间（V3 定），远小于 65,535，不值得为省 2 字节引入一层间接。如果 V3 的方块数超过 4,000，再引入每区块调色板。

**压缩**：三档，按需启用。

| 档 | 手段 | 压缩比（估算） | 何时启用 |
|---|---|---|---|
| 0 | 空区块 `null` | ∞ | 默认 |
| 1 | 全同区块折叠为 `{fill: id}` | 2,048:1 | 地形/岩层批量生成 |
| 2 | RLE（行内游程） | 5–20:1 | 存档落盘时 |

运行期只用 0 与 1；档 2 只在 `VoxSave.flush()` 时对序列化流做，不改变内存布局。这样热路径永远是 O(1) 数组索引。

**内存账**：

```
单区块          8,192 B
单沙盒满分配    48 × 8,192 = 393,216 B ≈ 384 KB
5 个沙盒满分配  240 × 8,192 = 1,966,080 B ≈ 1.88 MiB
```

对比现有场景：`bake.ts` 注释记录的顶点量化后约 28B/顶点、40.06M 顶点。体素数据只占其 **0.17%**。这也是为什么路线 A 敢说「内存不是瓶颈」——瓶颈在网格，不在体素。

### 1.2 与 Baker 管线如何共存

共存的核心是**三条隔离**，每条都对应一个具体的代码事实。

**隔离一：命名空间。**

```
city_*  → 参与 compactStatic 合并、参与天宫 2.2× 缩放
vox_*   → 两者都不参与
sky_cloudSheets → 只参与缩放，不参与合并
```

体素网格统一命名 `vox_<sandboxId>_<group>`。这条隔离必须配一条断言（见 §7 的 A7），因为它是隐式的——没有任何类型系统能阻止你把名字写成 `city_vox`。

**隔离二：材质实例。**

`Baker.materialSet()`（`bake.ts:1468`）把 14 个材质缓存在 `this.mats`，全局唯一。更要紧的是 `WardInfill` 的构造函数（`infill.ts:2813`）在材质上挂了三个 `onBeforeCompile` 补丁：

- `plasterHook(BODY)`：按世界 Y 做勒脚/墙帽/夯土横纹的着色带
- `roofFluteHook(ROOF)`：瓦垄条纹
- `roofEmissiveTint(ROOF)`：夜间按瓦色着色

这些补丁假设几何是「建筑」，世界 Y 对应「地面到屋檐」的高度。方块如果共用同一批材质实例，一个 0.5m 的方块会继承按米尺度定义的色带，颜色随高度突变——同一个方块在地面是墙基色，抬高两米变成墙帽色。

因此体素区必须**克隆**材质。克隆的粒度建议是「每材质组一份」，不是「每方块一份」：

```
voxMats = { wood, wall, earth, roof, ground, ash }  // 6 份克隆
```

不克隆 `glow / water / leaf / trunk / ceramic / metal / fabric / lacquer` 的理由：这 8 组在体素场景里的用量要么极少（lacquer、ceramic、fabric 是陈设级细节），要么适合走实例化（leaf、trunk、glow），要么需要单独的水面 pass（water）。用不到就不克隆，少 8 个材质 = 少 8 次状态切换。

**隔离三：加载时序。**

`world.init()` 的顺序是：35 个 task → 每 task 后 `await baker.flush(scene)` → `await compactStatic()`（`world.ts:821`）→ 之后才做云海切分等后处理。

体素沙盒必须在 `compactStatic()` **之后**创建。理由不是「怕被合并」（`vox_` 前缀已经排除了），而是**场景遍历成本**：`compactStatic` 会对全场景 `scene.traverse`，如果此刻场景里已经有 240 个 `vox_` 网格，遍历会白白多走 240 个节点。它们在 `startsWith('city_')` 处就被 `return` 掉、不会进入分桶 `Map`（`world.ts:716`），但遍历本身仍要付，且这 240 个节点之后还要被 `LodManager` 再遍历一次。

正确时序：

```
... 35 tasks → flush → compactStatic → 云海切分 → [新建] 体素沙盒 → 注册 LOD → start
```

代价是体素沙盒的构建时间**加在载入末尾**，无法与前面的 task 并行。这段成本必须计入 12s 红线（见 §7 的 A6）。

### 1.3 破坏/放置时的增量重建

这是整卷最核心的工程问题。先定粒度，再定合并策略，最后算 draw call。

**重建粒度：16³ 区块，边界标 6 邻。**

一次破坏的影响范围不是一格，是「这一格所在区块」+「如果这一格在区块边界，则相邻区块」。原因是面剔除：`(15, y, z)` 被挖空后，`(0, y, z)` 那个区块的 −X 面从「被遮挡」变成「暴露」，必须重建。只标本区块会留下一个永久性的洞——因为没有任何后续事件会再触发那个区块的重建。

```
dirty(chunk)            → 重建 1 个区块
if (lx == 0 || lx == 15 || ly == 0 || ly == 15 || lz == 0 || lz == 15)
  → 额外标 6 邻中实际相邻的那几个
```

最坏情况一次破坏标 4 个区块（角点），平均 1.24 个（估算：边界体素占比 = 1 - (14/16)³ ≈ 33%，其中角/棱占少数）。

**单区块重建成本**：

```
邻居检查   4,096 × 6            = 24,576 次
可见面     平均 300–900 quad（玩家建筑薄壳）
顶点产出   900 × 6 verts        = 5,400 verts
字节产出   5,400 × 32 B         = 172,800 B ≈ 169 KB
```

顶点 32B 的构成：position 12 + normal 6（Int16 量化）+ color 6（Uint16 量化）+ uv 8。这与 `bake.ts` 的 `QBuf` 口径一致（该文件头注写「28B/顶点」，其分项相加为 24B、加 UV 为 32B，文件内的减法与分项差 4B，本卷按 32B 计并标注**待核对**）。

**每帧预算**：4ms。按单区块 0.8–1.6ms（估算，24,576 次邻居检查 + 缓冲写入）计算，一帧可重建 2–4 个区块。玩家单次操作通常只脏 1–2 个区块，因此不会掉帧；连续爆破（如 TNT 等价物）会积压，需要队列 + 上限。

**合并策略：三选一，推荐 A3。**

| 策略 | 做法 | draw call | 重建 CPU | 问题 |
|---|---|---|---|---|
| A1 | 每区块一个 Mesh | 240 × 材质组数 ≈ 最多 1,440 | 最低（只重建 1 个） | draw call 爆炸，直接否决 |
| A2 | 每沙盒每材质一个 Mesh，脏了就整块重建 | 5 × 6 = 30 | 最高（重建整个沙盒） | 一次破坏重算 48 个区块，约 40–80ms |
| A3 | 每沙盒每材质一个 Mesh，预分配大缓冲 + `addUpdateRange` 局部上传 | 5 × 6 = 30 | 低（只重算脏区块，写入固定槽位） | 需要容量管理与空洞整理 |

A3 的具体做法：

```
每个 (sandbox, group) 维护：
  capacityQuads   预分配上限（例如 40,960）
  geometry        BufferGeometry，position/normal/color/uv 各 capacityQuads*6 个顶点
  slotMap         chunkIndex → { start, count }（该区块在缓冲里的段）
  freeList        空洞链表

破坏时：
  重建脏区块 → 得到 newCount 个 quad
  if (newCount <= oldCount) 原地写，多余段清零并回收
  else 追加到缓冲末尾，旧段回收
  geometry.attributes.position.addUpdateRange(start * 6 * 3, count * 6 * 3)
  ... 其余属性同理
  geometry.attributes.position.needsUpdate = true
```

`addUpdateRange(start, count)` 在 three 0.180.0 的 `BufferAttribute` 上确实存在（`node_modules/three/src/core/BufferAttribute.js:178`），配合 `updateRanges` 数组可以只上传改动段，避免每帧重传整个 40MB 缓冲。两个细节必须注意：① 渲染器上传后会自动清空 range 列表（`node_modules/three/src/renderers/webgl/WebGLAttributes.js:146` 的 `attribute.clearUpdateRanges()`），不需要手动清；② 但 `needsUpdate = true` 仍然必须设——它递增 `version` 才会触发 `update()`，只改 range 不设 `needsUpdate` 等于没传。

A3 的代价是**内存预分配**：每沙盒每材质按上限分配。若 6 个材质各预分配 40,960 quad，单沙盒的顶点缓冲是：

```
40,960 quad × 6 verts × 32 B = 7.86 MB
× 6 材质 = 47.2 MB
× 5 沙盒 = 236 MB
```

这个数字太大，不能接受。所以预分配必须**分材质差异化**：`earth/wall/wood/roof` 给大容量，`ash/ground` 给小容量。按经验配比（估算）：

| 材质组 | 容量（quad） | 字节 |
|---|---|---|
| wall | 12,000 | 2.30 MB |
| wood | 10,000 | 1.92 MB |
| roof | 8,000 | 1.54 MB |
| earth | 8,000 | 1.54 MB |
| ground | 4,000 | 0.77 MB |
| ash | 2,000 | 0.38 MB |
| **单沙盒合计** | **44,000** | **8.45 MB** |
| **5 沙盒合计** | — | **42.2 MB** |

42MB 相对现有约 1.1GB 的顶点数据是 +3.8%，可以接受。但这是**静态预分配**，与 §1.1 的「体素数据只占 0.17%」不是同一本账——前者是网格，后者是数据。两本账必须分开记，否则会得出「体素很便宜」的错误结论。

**面数代价**：

```
单沙盒实心壳上限  2×(64×64) + 2×(64×48) + 2×(64×48)
                = 20,480 quad = 40,960 tri
5 沙盒上限        = 204,800 tri
玩家薄壳         20,000 块 × 3 面 = 60,000 quad = 120,000 tri / 沙盒
5 沙盒实战        = 0.20M ~ 0.60M tri
```

占现有 13.35–15.09M 的 **1.3%–4.5%**（按 0.20–0.60M 计）；上限按 5 × 204,800 = 1.02M 计，占 **6.8%**。这个量级不会触碰性能红线，但也意味着**体素区不能成为主玩法**——它只有 5 个盒子，玩家 90% 的时间仍在烘焙世界里。

这一点必须写清楚，否则会在验收时产生预期错位：**路线 A 买到的是「可改变」，不是「可改变整个世界」。**

**与 V11 的交叉引用（重要）**：`V11-性能与工程.md` §11.3 给出了另一条更激进的实现——16³ 数据块 + 64³ 渲染块 + `BatchedMesh` + Worker 异步 meshing，把 draw call 压到 16–25，并把单块 meshing 交给 Worker 池。两者不矛盾，是**基线**与**优化**的关系：

| | 本卷 A3（同步基线） | V11 §11.3（异步优化） |
|---|---|---|
| 重建线程 | 主线程，4ms/帧预算 | Worker 池，主线程只上传 |
| 渲染合批 | 每沙盒每材质一个缓冲 | 64³ 渲染块 + BatchedMesh |
| draw call | +30 | +16–25 |
| 首次进入 | 载入期全建（190–380ms） | 只建脚下 3×3，其余后台排队 |
| 代码量 | ≈6,500 行 | 更高（Worker + 传输协议 + BatchedMesh 接入） |

裁决权在 V11：如果 V11 的 Worker 路线先落地，本卷的「4ms 预算 / 30 draw call」应替换为 V11 的数值，本卷只保留「必须是局部有界沙盒」这一前提。反过来，如果 V11 的方案因 Worker/`BatchedMesh` 集成风险被推迟，本卷的同步基线可以作为第一版直接实现。两卷不冲突的判据是：**无论走哪条，`vox_` 命名隔离、坐标契约、种子契约三条都不变。**

### 1.4 路线 A 的代价汇总

### 1.5 五个沙盒落在哪：选址判据与候选点

V1 定了「人间 3 / 天宫 1 / 地府 1」。这一节把「落在哪」写成可检查的条件，而不是感觉。

**四条选址判据**，缺一不可：

1. **不与行走面表重叠。** `walkSurfaceY` 的 4m 哈希表（`behaviors.ts:45`）覆盖了 `beltRoomSpecs()`、`riverRoomSpecs()`、`STREET_HOUSE_SLOTS` 三张表的所有房屋。沙盒若压在这些矩形上，玩家会在既有建筑的墙里放方块，视觉上就是「新砖长进老墙」。
2. **不在地标禁入区。** `layout.ts:12` 的 `LANDMARK_KEEPOUT` 有 4 个矩形（孙羊正店、十千脚店、府衙大堂、漕运仓场），这些是 B1 可进入内饰的承载，任何改动都会破坏室内外一致性。
3. **在近档可达范围内。** 沙盒要么在玩家常规动线上（虹桥—御街—城门），要么有 POI 直达。孤立的沙盒等于不存在。
4. **有叙事理由。** 人间是「营造场」（工地、料场），天宫是「炼形台」（仙造），地府是「孽镜台」（改判）。位置要能解释「为什么这里可以动土」。

候选点如下，**全部标注「待验证」**，因为本卷没有跑 AABB 求交：

| ID | 界 | 候选位置（世界坐标） | 叙事理由 | 风险 |
|---|---|---|---|---|
| H1 | 人间 | 城东外郭内空地，`x≈700, z≈52` 北街东段南侧 | 城门内的「官营料场」 | 邻近城门与御廊，需验 `LANDMARK_KEEPOUT` |
| H2 | 人间 | 南岸河滩，`x≈300, z≈-120` | 卸货码头旁的堆场 | 邻近河岸坡，需验 `waterAt` 与岸线 |
| H3 | 人间 | 城外旷野，`x≈-6200, z≈2400` | 远离城市的「野筑」试验区 | 地形 `terrainHeight` 非零，需按坡地找平 |
| T1 | 天宫 | 星宿九府外缘，`heavenPoint` 反算的设计坐标待定 | 仙匠的「炼形台」 | 天宫几何密布，重叠概率最高 |
| D1 | 地府 | 丰都鬼城外围，`UNDER.y + 2` 基准，`x≈540, z≈85` 附近 | 孽镜台旁的「改判所」 | 十八狱环占位密集 |

**验证方式**（写进 A12）：对每个候选点，取沙盒的 XZ 包围盒，与 ①`walkSurfaceY` 的全部矩形、②`LANDMARK_KEEPOUT` 的 4 个矩形、③`POIS` 里 radius > 20 的地标圆，三者求交。交集非空即换点。这项检查必须在写第一行体素代码之前跑完——选址错了，后面所有代价估算都要重算。

天宫那个点最麻烦：`scaleHeavenGeometry` 会把 `y > 150` 且 `|x|,|z| < 1500` 的 `city_*` 顶点整体放大 2.2×（`expansion.ts:294`），天宫的实际占地比设计坐标大 2.2 倍。选址时必须用**世界坐标**去查重叠，不能用设计坐标——这是 `heavenFrame.ts` 文件头记录过的那类漂移。

## 2. 路线 B：分块烘焙 + 增量重建

一句话：不引入体素，把现有烘焙输出按空间块切开，破坏时重跑那一块的 builder。

这条路线值得写，因为它是「最省美术」的方案——网格还是原来的网格，只是切小了。但它有一个**结构性障碍**，必须先讲清楚。

### 2.1 数据结构

沿用 `Baker` 的 14 材质组与非索引三角面，但给 `Baker` 加一个作用域概念：

```ts
baker.beginChunk(key: string): void;   // 之后 push 的所有几何归入该块
baker.endChunk(): void;                // 结束该块，装配为一个 Mesh
```

块的划分建议 64m × 64m × 全高。城区 10km × 10km，若只切有人区（里坊 920–4880），块数约：

```
(4880 - 920) / 64 = 61.9 → 62
62 × 62 ≈ 3,844 块
```

这 3,844 块每块一个 Mesh，draw call 直接涨到 3,844（未计材质组再分）。必须再做一层「同材质合并」，但合并后又回到「不可单独重建」的原点——这正是路线 A 要解决的问题，路线 B 只是把它推迟了一步。

### 2.2 与 Baker 管线如何共存

`beginChunk/endChunk` 本身不难，难的是**builder 不是纯函数**。

`world.ts:324` 的注释写得很明确：

> 「拆分只按『调用点』切，调用顺序与共享 rng 消耗顺序逐字不变，因此世界逐值可复现。」

这句话是现有的确定性保证，也是路线 B 的死穴。现有 35 个 task 共享一个 `new RNG(20260905)`（`world.ts:277`），所有 builder 按固定顺序从这个实例取值。如果为了重建某个 64m 块而单独重跑该块的 builder：

1. 该 builder 会从共享 rng 里取走一批数；
2. 后续所有 builder 拿到的数全部错位；
3. 整座城除了被重建的那一块，其余全部变化。

要修这个问题，必须把「每块独立种子」下沉到**每一个 builder 函数**。现有 builder 数量按 `world.ts` 的 tasks 与 `infill.ts` 的 `fillWard`/`fillCourt` 估算在 30 个以上，逐一改造 rng 注入点的成本，与重写一遍生成层相当。

这不是「工作量略大」，是「路线 B 的前提不成立」——它要求先完成一次全仓的确定性重构，而这次重构的收益只在路线 B 里兑现。

### 2.3 增量重建的粒度与成本

假设前提已经解决（每块独立种子），单块重建的成本是：

```
单块 64m × 64m，约等于 1/3,844 的全城 builder 工作量
全城 builder 自报耗时约 14s（world.ts:785 注释）
单块 ≈ 3.6ms（估算，且不含 flush 与 compactStatic）
```

3.6ms 看起来可接受，但它**只重建了方块被破坏的那一块**——而破坏一堵墙会让相邻块的接触面变化，必须连带重建邻块。一次破坏实际重建 1–4 块，13–15ms 的峰值卡顿。

更麻烦的是：重跑 builder 会重建整块里的**所有**建筑，包括没被碰过的那几栋。这不仅浪费，还会让同一栋楼在「被重建」与「没被重建」两种状态下出现细微差异（浮点累加顺序不同），玩家能看出来。

### 2.4 路线 B 的代价汇总

| 项 | 代价 | 备注 |
|---|---|---|
| 面数 | 不变（13.35–15.09M） | 最大优势 |
| 内存 | 基本不变（顶点数据没变） | 优势 |
| 载入 | 不改善，可能更慢（块作用域遍历） | 劣势 |
| draw call | +数百到数千 | 硬伤 |
| 代码 | ≈8,000–12,000 行（含确定性重构） | 估算 |
| 结构障碍 | builder 非纯函数，需全仓 rng 重构 | 可能否决 |

**判定：路线 B 不适合作为破坏方案。** 它唯一有价值的场景是「远景承载」——把远处 2–4km 的烘焙体按 256m 块切开，做更激进的裁剪。但现有的 `LodManager` 四档（`engine.ts:150`）已经用「可见子集切换」解决了同一问题，不需要再切块。

## 3. 路线 C：全量体素化

先算，再判。

**地表一层的面数下界**：

```
城区外郭 ±5000（infill.ts:3330 注释）→ 10,000 m × 10,000 m = 1e8 m²
1m 体素：1e8 个地表体素，每个至少 1 个朝上可见面
       = 1e8 quad = 2e8 tri
0.5m 体素：4e8 个地表体素 = 4e8 quad = 8e8 tri
```

对比当前 13.35–15.09M：

```
2e8 / 15.09e6 ≈ 13.3 倍（1m 体素，只算地面）
8e8 / 15.09e6 ≈ 53.0 倍（0.5m 体素，只算地面）
```

这还**没有算建筑立面**。当前 `WardInfill` 单独贡献 10,589,198 面（`infill.ts:62` 注释台账），全部要重建成方块；举折曲面的 86 面/栋（`infill.ts:1120`）在体素化后退化成阶梯状，要维持观感必须把体素降到 0.15m 以下，面数再翻一个量级。

**内存下界**：1e8 个体素 × 2B = 200MB，仅地表一层；含高度 150m 的体积是 1.5e10 格，即便 99.9% 为空、只存表面，也是 GB 级。

**载入**：现有 35 步管线全部作废，需要重写为流式生成。12s 红线不可能守住。

**判定：否决。** 它同时违反「一个实例都不许删」（方块化等于删掉所有精细构件）与「12s 红线」两条硬约束。

## 4. 三条路线对照

| 维度 | A 局部沙盒 | B 分块烘焙 | C 全量体素 |
|---|---|---|---|
| 可破坏 | 是（5 个盒子内） | 是（全城，但卡） | 是（全城） |
| 面数 | +0.2–0.6M | 0 | +2e8 以上 |
| 内存 | +44 MB | ≈0 | +GB 级 |
| 载入 | +0.3–0.9s | 不改善 | 不可估 |
| draw call | +30 | +数百至数千 | 不可估 |
| 代码 | ≈6,500 行 | ≈8,000–12,000 行 | ≈34,000 行 |
| 结构障碍 | 无 | builder 非纯函数 | 全仓重写 |
| 判定 | **推荐** | 否决（可作远景备选） | 硬否决 |

选 A 不是因为它最好，是因为**只有它在 12s 红线内、且不需要先重构确定性层**。B 和 C 都能提供更大的可破坏范围，但都要先付一笔与收益无关的架构债。

## 5. 区块流式

### 5.1 区块尺寸：16³，理由已在上文，这里补两条边界条件

**边界一：与 `camera.near = 0.5` 的关系。** `engine.ts:488` 的近裁剪面是 0.5m。人间方块边长 0.5m，意味着相机贴到方块表面时，方块会被近裁剪面切掉一半。这不影响玩法（玩家不会把头埋进墙里），但会影响「贴脸看纹理」的截图验收。建议：体素区验收机位的最小距离设为 1.5m，或在 V11 评估把 `near` 降到 0.2（需检查对数深度缓冲的精度）。

**边界二：区块边长与方块边长的耦合。** 16 格 × 0.5m = **8m** 一个区块。这个尺寸决定了重建粒度：8m 见方的改动范围。如果一个玩家在 8m 范围内连续放置 20 块，会触发 20 次区块重建——需要合并队列，把同一帧内的多次写入合并成一次重建。

### 5.2 加载半径

路线 A 的沙盒是**离散且极小**的：单沙盒 32m × 32m × 24m（64×64×48 格 × 0.5m）。相机站在沙盒中心，到最远角的距离是：

```
√(16² + 16² + 12²) ≈ 25.6 m
```

远小于 `LodManager` 的近档阈值 120m（`engine.ts:38` 的 `LOD_ENTER[0]`）。所以**路线 A 不需要流式加载**——整个沙盒永远在近档内。这是路线 A 相对「开放体素世界」的最大简化。

但如果 V11 决定扩大沙盒（例如 96×96×64 格 = 48m × 48m × 32m），对角距离升到 71m，仍在 120m 内，依然不需要流式。**只有当沙盒边长超过 200m 时才需要引入流式**，那已经超出本卷范围。

作为对照，如果未来要做连续体素世界，本卷给出参考参数（**待验证**）：

| 参数 | 取值 | 依据 |
|---|---|---|
| 区块 | 16³ = 8m（0.5m 方块） | 同 §5.1 |
| 加载半径 | 12 区块 = 96m | 地面雾密度最高 0.00432（`world.ts:961`，`lerp(2.4,1,y/130)` × 0.0018），可见度 ≈ 231m；96m 在雾内 |
| 卸载半径 | 16 区块 = 128m | 与加载半径留 4 区块滞回，避免边界抖动 |
| 每帧预算 | 2 区块 | 与 §1.3 的 4ms 预算一致 |

### 5.3 卸载策略

路线 A 的卸载分两层：

| 层 | 数据 | 策略 |
|---|---|---|
| 体素数据 | `Uint16Array(4096)` × 48 | **永不卸载**。5 沙盒共 1.88 MiB，卸载的收益小于管理成本 |
| 网格几何 | BufferGeometry（预分配 8.45 MB/沙盒） | 离开 200m 后 `visible = false`；离开 600m 后 `geometry.dispose()` 释放显存，数据保留，回来时重建 |

不卸载数据的理由是可算的：1.88 MiB 相当于一张 1024² RGBA 贴图（4 MiB）的一半。为省这点内存引入「重新生成区块」的路径，只会增加 bug 面。

卸载几何的理由同样可算：5 沙盒 × 8.45 MB = 42.2 MB 的顶点缓冲常驻显存，在集显机器上是实打实的压力。600m 的阈值取的是「远于沙盒对角 25.6m 的 23 倍」，此时沙盒在屏幕上不超过几十像素。

### 5.4 与 `infill.ts` 的 tier LOD 关系

这是最容易写错的一节，因为项目里有**两套** LOD，语义完全不同：

| 系统 | 位置 | 阈值 | 语义 | 切换方式 |
|---|---|---|---|---|
| 构建档 tier 0–3 | `infill.ts:65-67` | 1200 / 2400 / 3600 m | **构建时**决定这块坊用多少面 | 不同的几何，构建期定死 |
| 运行时档 near/mid/far/impostor | `engine.ts:38` | 120 / 400 / 1200 m（进），150/470/1350（出） | **运行时**决定哪批 Mesh 可见 | 同一批 Mesh 的 `visible` 子集 |

两套不能混用：tier 是「这块地方值多少面」，LOD 是「现在看不看」。体素沙盒属于后者。

**正确接线**：把沙盒注册为 `LodGroupSpec`（`infill.ts:21` 的接口），只填 `near`：

```ts
registerInstancedLod({
  id: 'vox_human_1',
  cx, cy, cz, hx: 16, hy: 12, hz: 16,
  tiers: { near: [voxMeshWall, voxMeshWood, ...], mid: [], far: [emptyGroup], impostor: [] },
  card: null,
});
```

**这里有一个必须写下来的陷阱。** `LodManager.applyVisibility()`（`engine.ts:342`）按档选集合：

```ts
const set = g.tier === 0 ? g.near : g.tier === 1 ? g.mid : g.tier === 2 ? g.far : LOD_EMPTY;
for (const m of g.meshes) m.visible = set.has(m);
```

而 `isReady()`（`engine.ts:316`）要求 `g.mid.size > 0` 才算 mid 档就绪：

```ts
if (t === 1) return g.ready.mid && g.mid.size > 0;
```

如果 `mid` 是空数组，那么相机退到 120m 外时：

1. `want = 1`（mid）；
2. `isReady(g, 1)` 返回 `false`（`mid.size === 0`）；
3. `g.blocked++`，**保留上一档**（注释原文：「目标档未就绪 → 保留上一档（禁止隐藏）」）；
4. tier 停在 0，`visible` 保持 `true`。

结果：**沙盒永远不会隐藏**。这不是 bug，是现有 LOD 的设计选择（宁可糊，不能空），但它与「我想让体素区在远处消失」的意图相反。

解法：给 `far` 塞一个**空的 `THREE.Group()`**，让 `far.size === 1`。这样 `isReady(g, 2)` 为真，`applyVisibility` 切到 far 档，`near` 的网格全部 `visible = false`，空 Group 本身不占 draw call。这条解法必须在实现时写进注释，否则下一个人会把空 Group 当垃圾删掉。

### 5.5 与传送 / POI 系统的集成

项目里已经有一套 POI 传送（`world.ts` 的 `POIS`，以及 `interactPoints.ts` 的 61 个交互点）。玩家点一下就能跨 2km 移动到天宫或地府，中间没有过场。

这对体素区提出一条硬要求：**落点必须在传送完成的同一帧就可站立。**

现有传送的实现是「设置相机/角色位置」，没有「等待几何加载」这一步。如果沙盒几何是懒加载的，玩家会经历：传送 → 落地 → 高度图还没建好 → `walkSurfaceY` 返回 0 → 角色从 2150m 掉到人间。

三条处置，按优先级：

1. **载入期全建。** 5 个沙盒共 240 区块，按 §1.3 的 0.8–1.6ms/区块估算，全建一次 190–380ms。这笔钱一次付掉，之后永不重付。这是推荐方案——它把「传送一致性」变成一个静态属性，而不是运行时要处理的状态机。
2. **传送前置钩子。** 如果沙盒数量增长到 20 个以上，全建成本超过 1s，就需要在 POI 传送前插一个 `await sandbox.ensureBuilt(id)`。代价是传送出现可感知的停顿（100ms 量级），需要加载指示。
3. **兜底：传送落点抬高 1m。** 无论哪种方案，落点都应该比目标面高 1m，给高度图一个「已经生效」的容错窗口。这一条是防御性的，不替代前两条。

同时，§5.3 的「离开 600m 释放 geometry」必须加一条例外：**玩家在沙盒内时永不释放**。判据是相机到沙盒 AABB 的距离，不是玩家在哪个界——因为相机在附身模式下跟着角色走。

## 6. 种子与确定性

### 6.1 现有纪律：三条，且都是硬约束

**纪律一：单一 RNG 实例、单序列。**

`world.ts:277` 只有一个 `const rng = new RNG(20260905)`，35 个 task 共享。`world.ts:324` 的注释把这条写成契约：

> 「拆分只按『调用点』切，调用顺序与共享 rng 消耗顺序逐字不变，因此世界逐值可复现。」

**纪律二：能用坐标 hash 就不用 rng。**

`infill.ts:139` 的 `h01(a, b, c)` 是三条整数混合的哈希，返回值域 `[0,1)`：

```ts
function h01(a: number, b: number, c: number): number {
  let t = (Math.imul(a + 1, 0x27d4eb2d) ^ Math.imul(b + 1, 0x165667b1) ^ Math.imul(c + 1, 0x9e3779b1)) >>> 0;
  t = Math.imul(t ^ (t >>> 15), 0x85ebca6b) >>> 0;
  t = Math.imul(t ^ (t >>> 13), 0xc2b2ae35) >>> 0;
  return ((t ^ (t >>> 16)) >>> 0) / 4294967296;
}
```

它的两个性质正是体素世界需要的：**与调用顺序无关**（纯函数）、**不消耗共享 rng**。`infill.ts:213` 的注释明确写着「随机性全部由坐标 hash（h01）与连续低频场 fieldN 承担，不消耗共享 rng」。

**纪律三：RNG 是 mulberry32，种子 `>>> 0`。**

`core/rng.ts` 的 `RNG` 构造是 `this.seed = seed >>> 0`，`next()` 用 `Math.imul` 做 32 位混淆。它是确定性 PRNG，但不是密码学 PRNG，也不保证跨版本稳定（未来如果换实现，历史种子会失效）。

### 6.2 种子 → 世界的确定性契约

体素世界不能接进上面那条单序列。必须自建三层，且**每一层都是纯函数**：

```
worldSeed                       // 唯一外部输入，例如 20260905
  └─ realmSeed(realm) = h01(worldSeed, 0x5245_414C, realmIndex)   // 'REAL'
       └─ chunkSeed(realm, cx, cy, cz) = h01(h01(...), ...)        // 三段哈希
            └─ new RNG(chunkSeed * 2^32)                            // 每区块独立实例
```

**契约五条**（每条都要有对应断言）：

| # | 契约 | 违反后果 | 断言 |
|---|---|---|---|
| 1 | 同 `worldSeed` + 同代码版本 → 同 blockId 序列，逐字节相同 | 存档读回后地形变形 | A5 |
| 2 | 区块生成顺序无关：任意顺序生成，结果一致 | 流式加载顺序影响地形 | A5（乱序生成对照） |
| 3 | 玩家改动是**差分**，不进种子 | 改一格导致整块重算 | A5（差分重放对照） |
| 4 | 同 seed + 同操作序列 → 同最终状态 | 多人/回放不可用 | A5（双进程对照） |
| 5 | 生成路径禁止 `Math.random()` / `Date.now()` / `performance.now()` | 不可复现 | 静态扫描 + CI |

契约 3 是最容易被误解的一条。玩家放置一个方块，**不应该**改变该区块的生成种子——否则「挖了再填回去」会得到不同的区块，玩家会发现世界记不住他的撤销。正确模型是：

```
最终状态 = generate(chunkSeed) ⊕ diff(playerOps)
```

`generate` 是纯函数、缓存友好；`diff` 是有序操作日志。两者分离，才能同时满足「撤销」与「确定性」。

### 6.3 与 `heavenFrame` 的换算契约

天宫沙盒的坐标必须走唯一真相源 `src/sky/heavenFrame.ts`，不能手抄常数。

```ts
export const HEAVEN_SCALE = 2.2;
export const HEAVEN_BASE_Y = 196;
export const HEAVEN_LIFT = 1935;
export const HEAVEN_BASE_LIFTED = 196 + 1935;   // 2131

export function heavenY(y: number): number {
  return HEAVEN_BASE_LIFTED + (y - HEAVEN_BASE_Y) * HEAVEN_SCALE;
}
```

体素坐标 → 世界坐标的完整公式：

```
worldX = originX + lx * BLOCK_SIZE
worldY = originY + ly * BLOCK_SIZE
worldZ = originZ + lz * BLOCK_SIZE
```

其中天宫的 `origin` 必须由 `heavenPoint()` 产出，而不是手写 `(0, 2150, 0)` 之类的近似值。

**方块边长在三界不同，这是设计决定，不是妥协：**

| 界 | BLOCK_SIZE | 理由 |
|---|---|---|
| 人间 | 0.5 m | 宋式砖材常见 0.3–0.5m；与 `architecture.ts` 的构件尺寸同量级 |
| 地府 | 0.5 m | 与人间一致，便于「人间的砖搬到地府」的叙事 |
| 天宫 | **2.2 m** | 天宫几何整体被 `scaleHeavenGeometry` 放大 2.2×；1 设计米 = 2.2 世界米。若天宫也用 0.5m，方块相对仙宫建筑会小 4.4 倍，玩家在 240m 面阔的凌霄殿前像蚂蚁 |

天宫 2.2m 的代价：同一块「砖」在人间与天宫尺寸差 4.4 倍，**方块物品不能直接跨界搬运**。解法是物品层记录「设计尺寸」而非「世界尺寸」，放置时按目标界的 `BLOCK_SIZE` 换算——这与现有 `heavenPoint` 的设计米口径一致。

**换算断言**：对任意天宫设计坐标 `(dx, dy, dz)`，体素世界坐标 `w` 必须满足

```
|w.y - heavenY(dy)| < 1e-6
|w.x - dx * HEAVEN_SCALE| < 1e-6
|w.z - dz * HEAVEN_SCALE| < 1e-6
```

这条断言的作用是防止「手抄 2.2」——`heavenFrame.ts` 的文件头注释已经记录过一次漂移事故（`palace.ts` 手抄 2.2/196 导致改一处必漂移）。

### 6.4 与全局 RNG 的解耦验证

体素子系统**不得**触碰 `world.init()` 里的那个 `rng`。验证方式不是「代码 review 时注意一下」，而是一条可执行的断言：

```ts
// 在 world.init() 全部 task 结束后，全局 rng 的序列位置应停在基线常量上。
// RNG.s 是私有字段，探针用「连续取 8 个值的指纹」间接定位序列位置：
const fingerprint = Array.from({ length: 8 }, () => rng.next());
// 与改造前（尚未引入体素）记录的 fingerprint 基线逐值比对。
// 任一位不同 = 有代码在 init 期间偷用了全局 rng，且用量可以被差值反推。
```

这条断言的巧妙处在于：它不要求体素代码「声明」自己不碰 rng，而是从**结果**上证明序列没被推进。基线在改造前录一次，之后每次 CI 重跑都比。代价是 `fingerprint` 会消耗掉 8 个随机数，因此必须放在全部 task 结束之后——现有 `world.ts` 的任务序列以「名牌图鉴」收尾（`world.ts:679`），该 task 及其后代码不再读 `rng`，位置安全。若后续新增 task 又用了 `rng`，这条断言会立刻变红，正好起到看门作用。

更稳妥的做法是把 `RNG` 改成可派生的（`rng.fork(label)`），但这会改动 `core/rng.ts` 这个全局基础设施，风险高于收益。本卷的建议是：**体素代码在类型层面就拿不到那个 rng 实例**——`buildVoxelSandboxes(worldSeed, ...)` 的签名里不出现 `RNG` 参数，从源头断掉。

## 7. 可执行验收断言

十条，每条给出**测量方式**与**阈值**。全部按 `probe-*.mjs` 的既有格式输出 `PASS` / `BLOCK` + 退出码（0/1），与项目现有 80+ 个 probe 一致。

### A1 区块内存

- **测量**：`VoxelStore.bytesAllocated()` 返回值；或 `performance.memory.usedJSHeapSize` 在分配 240 个空区块前后的差值。
- **阈值**：`≤ 240 × 8,192 = 1,966,080 B`（1.88 MiB），允许 ±5% 的数组开销。
- **判据**：超过即说明存在每区块的额外对象（如 `Map` 包装、调色板副本）。

### A2 单区块重建耗时

- **测量**：`performance.now()` 包裹 `ChunkMesher.build()`，连续 200 次破坏取 p95。
- **阈值**：p95 ≤ 4.0 ms；p99 ≤ 8.0 ms。
- **判据**：超过 4ms 说明邻居检查没有走扁平数组，或顶点写入触发了数组扩容。

### A3 draw call 增量

- **测量**：`engine.renderer.info.render.calls`，在进入沙盒前 / 站在沙盒中心时各取一次（同一机位、同一朝向）。
- **阈值**：增量 ≤ +30（5 沙盒 × 6 材质组）。
- **判据**：超过 +30 说明网格没有按材质组合并，退化成「每区块一个 Mesh」。

### A4 破坏的可见延迟

- **测量**：注入一次 `vox.break` 后，同一帧内读取 `walkSurfaceY(x, z, y+2)` 的返回值；同时截图像素比对（破坏点前后各一张，比较该点 32×32 像素块的平均亮度差）。
- **阈值**：`walkSurfaceY` 在 **1 帧内**返回新面高（误差 < 0.01m）；像素亮度差 > 8/255。
- **判据**：画面变了但 `walkSurfaceY` 没变 = 玩家站不上去；`walkSurfaceY` 变了但像素没变 = 几何没重建。

### A5 确定性

- **测量**：两个独立进程，同 `worldSeed`，对同一组 1,000 次操作（500 放置 + 500 破坏，固定坐标序列）执行后，序列化全部区块数据，取 SHA-256。
- **阈值**：两个哈希**完全相同**。另外做两组对照：① 区块按随机顺序生成；② 操作序列重放两次。三组结果必须一致。
- **判据**：任何不一致都说明生成路径里有顺序依赖或未受控的随机源。

### A6 载入增量

- **测量**：`performance.now()` 从 `navigationStart` 到 `#loading` 元素被移除（`probe-load.mjs` 的现有口径），基线跑 5 次取中位数，改造后再跑 5 次取中位数。
- **阈值**：增量 ≤ 0.9s；**绝对值 ≤ 12.0s**（红线）。
- **判据**：绝对值超红线即 BLOCK，无论增量多少。

### A7 命名空间隔离

- **测量**：`scene.traverse` 统计 `name.startsWith('city_vox')` 的 Mesh 数量；同时统计 `vox_` 前缀 Mesh 的 `geometry.attributes.position.count` 是否与 `compactStatic` 前一致。
- **阈值**：`city_vox*` 数量 **必须为 0**。
- **判据**：出现即说明命名违规，该网格已被 `compactStatic` 合并或已被 `scaleHeavenGeometry` 缩放，不可重建。

### A8 天宫坐标

- **测量**：对天宫沙盒的 100 个采样点（角、棱中点、面心、随机点），比较体素世界坐标与 `heavenPoint()` 的输出。
- **阈值**：三个轴的绝对误差均 < 1e-6 m。
- **判据**：超过即说明有手抄常数或缩放次序错误。

### A9 行走面一致性

- **测量**：在沙盒内放置一个 0.5m 方块于 `(x, y, z)`，1 帧后调用 `walkSurfaceY(x, z, y + 2)`。
- **阈值**：返回值 == `y + 0.5`，误差 < 0.01。
- **判据**：返回 `null`（被墙带挡住）或返回 0（落回街面）都说明体素高度图没有接进 `walkSurfaceY`。

### A10 面数上限

- **测量**：`engine.renderer.info.render.triangles`，站在沙盒中心朝最密方向，与进入沙盒前同机位对比。
- **阈值**：增量 ≤ 1.02M（V1 §2.2 的上界）；单沙盒 ≤ 40,960 tri（实心壳上限）时不允许告警。
- **判据**：超过 1.02M 说明玩家建造量超出预算，需要触发「沙盒已满」的 UI 提示而不是静默卡顿。

### A11 长时稳定性（10,000 次操作）

- **测量**：脚本连续执行 10,000 次「破坏 + 放置」（固定坐标序列，覆盖 5 个沙盒），每 1,000 次采样一次 `renderer.info.memory.geometries`、`renderer.info.render.calls`、`performance.memory.usedJSHeapSize`。
- **阈值**：`geometries` 增量 ≤ 0（不允许每次重建都 `new BufferGeometry` 而不 dispose）；`calls` 波动 ≤ ±2；堆增长 ≤ 5 MB。
- **判据**：`geometries` 单调上升 = A3 的 `dispose()` 漏了；堆持续上升 = 顶点数组每次 `new` 而没有复用预分配缓冲。

### A12 沙盒选址无重叠

- **测量**：对 §1.5 的 5 个候选点，取 XZ 包围盒，与 ①`walkSurfaceY` 矩形全集、②`LANDMARK_KEEPOUT`（`layout.ts:12`）、③`POIS` 中 `radius > 20` 的地标圆求交。
- **阈值**：交集面积 **必须为 0**；若无法为 0，允许 ≤ 4 m² 的边缘擦碰，但必须列在白名单里并写明理由。
- **判据**：任何未登记的重叠都是 BLOCK——它意味着玩家会在既有建筑内部放方块。

## 8. 冲突与代价总表

| # | 冲突 | 现有事实 | 路线 A 的处置 | 残余代价 |
|---|---|---|---|---|
| 1 | 几何所有权 | `compactStatic()` 后无逐块句柄（`world.ts:710`） | `vox_` 前缀隔离，永不进入合并 | 体素区无法享受烘焙的 draw call 优化，固定 +30 |
| 2 | 生命周期 | `Baker.flush()` 只追加（`bake.ts:1297`） | 自建 Mesh 池，`geometry.dispose()` + 重建 | 需要自己管内存，无现成回收机制 |
| 3 | 预算账本 | 载入一次性（8.3–9.7s） | 沙盒在 `compactStatic` 后建，成本计入载入尾部 | 载入 +0.3–0.9s，压缩了后续卷的余量 |
| 4 | 命名即协议 | `startsWith('city_')`（`world.ts:716`、`expansion.ts:300`） | `vox_` 前缀 + A7 断言 | 靠纪律而非类型，需要 CI 兜底 |
| 5 | 材质补丁 | `plasterHook` 等按世界 Y 着色（`infill.ts:2813`） | 克隆 6 个材质组 | +6 个材质实例，状态切换略增 |
| 6 | 天宫缩放 | `scaleHeavenGeometry` 改顶点（`expansion.ts:294`） | `vox_` 不被扫到；改用 2.2m 方块边长 | 方块尺寸三界不一致，物品不能直接跨界 |
| 7 | LOD 兜底 | `isReady` 要求 `mid.size > 0`（`engine.ts:316`） | `far` 塞空 `Group` 骗过 `isReady` | 依赖一个「看起来像垃圾」的空对象 |
| 8 | 确定性单序列 | 35 task 共享 `RNG(20260905)`（`world.ts:277`） | 体素自建三层哈希种子，签名里不出现 `RNG` | 需要一条静态扫描防止误用 |

八条里，第 4、7、8 条是「靠纪律维持」的，不是类型系统能保证的。它们必须在 V12 的验收矩阵里各自挂一条 probe，否则会在某次重构中悄悄失效。

### 8.1 三本账必须分开记

本卷所有代价最后要落到三本独立的账上，混在一起会得出错误结论：

| 账本 | 什么时候付 | 本卷的量 | 对应断言 |
|---|---|---|---|
| **载入账** | 一次，启动时 | +0.3–0.9s（沙盒构建） | A6 |
| **常驻账** | 全程，占内存/显存 | 体素数据 1.88 MiB + 网格 42.2 MB | A1、A11 |
| **每帧账** | 玩家操作时 | 单区块 0.8–1.6ms，预算 4ms/帧 | A2、A3 |

三本账的失败模式完全不同：载入账超了是发布阻塞，常驻账超了是中低端机崩溃，每帧账超了是手感变差。现有代码把三者混在一条 `console.log` 里（`world.ts` 的逐步日志同时打印 task 耗时、`__flushMs`、面数台账），这在烘焙世界里够用，因为三本账都是「一次付清」；体素世界引入了持续付费，必须拆开。

拆账的具体做法：给 `SandboxManager` 加三个累计计数器 `loadMs` / `residentBytes` / `frameMsPeak`，由 `probe-vox.mjs` 分别读取，各自对应一条断言。不要用一个总分代替三个分项——总分合格掩盖不了某一项超标。

## 9. 结论

**结论一**：选路线 A（局部体素沙盒 + 烘焙背景）。三条路线的对照显示，只有 A 能在 12s 红线内落地，且不需要先重构现有确定性层。

**结论二**：区块 16³、0.5m 方块（天宫 2.2m）、每沙盒 48 区块、5 沙盒共 240 区块、体素数据 1.88 MiB、网格预分配 42.2 MB、draw call +30、面数 +0.2–0.6M。

**结论三**：重建粒度是区块，边界标 6 邻；合并策略是「每沙盒每材质一个大缓冲 + `addUpdateRange` 局部上传」，不是「每区块一个 Mesh」。

**结论四**：三条确定性契约不变量——生成顺序无关、玩家改动是差分、种子三层纯函数。天宫坐标必须走 `heavenFrame.ts`，方块边长按界不同。

**结论五**：真正的工程量不在体素算法本身，而在**与现有四套隐式协议的对接**：命名前缀、材质补丁、LOD 兜底、RNG 单序列。这四条都不在类型系统里，只能靠断言与 probe 守住。

移交给 V3 的两个问题：① 方块注册表如何保证每个方块都落到 14 个 `BGroup` 之一（`BlockDef.group` 的类型约束）；② 方块贴图是共用 `createCityTextures()` 的 9 张，还是新建一套图集——前者省显存但 UV 对不齐，后者对齐但要重新生成 1024² 贴图并计入载入时间。
