# SPEC · 大型 3D 网页游戏的载入 / 渲染 / 互动分级体系（本项目落地版）

> 目的：把「怎么回事，加载卡住 / 掉帧 / 一进去就糊」这类**不可诊断**的问题，变成**可测量、可分级、可预算**的工程流程。
> 本文分两部分：§1 业界通行做法（规则/方法/标准/流程），§2 本项目怎么落（已做 / 待做）。

---

## §1 业界通行做法

### 1.1 启动（Boot）—— 四段式
| 段 | 目标 | 判据 |
|---|---|---|
| **S0 Shell** | HTML/CSS/JS 外壳可交互 ≤ 1s | 出现 loading UI、可点、可取消 |
| **S1 Manifest** | 资源清单与版本号到位，能算出总进度 | 清单 JSON < 50KB，带 hash |
| **S2 Critical Path** | 只加载「首帧必须可见」的资产 | 首帧可见 ≤ 3–5s（4G/中端机） |
| **S3 Interactive** | 输入可用、相机可控、可取消加载 | 可操作 ≤ 8–10s |

**铁律**：
- **主线程永不整段阻塞**：单次占用 ≤ 50ms（人眼可感阈值），理想 ≤ 16.6ms；
- **每一步可测量**：每段有 `performance.mark/measure`，超预算在控制台点名；
- **进度必须真实**：进度 = 已完成权重 / 总权重，不能是假动画；
- **可取消**：用户切走/返回时能中止并释放。

### 1.2 载入（Loading）—— 分级 / 分层 / 分区 / 预载
**分级（Tier）**——按「离首帧多远」分：
| 级 | 内容 | 时机 | 预算 |
|---|---|---|---|
| **T0 阻塞** | 引擎、输入、着色器、UI | S0–S2 | 一次性 ≤ 2s |
| **T1 首屏** | 玩家 200m 内的地形/地面/近景建筑 | S2 | ≤ 3s |
| **T2 视距** | 200–1200m 建筑与树、LOD 中档 | S3 后空闲 | 分片，每片 ≤ 50ms |
| **T3 远景** | 1.2–5km 剪影、地标、天宫/地府 | 空闲 / 首次接近时 | 按需 |
| **T4 惰性** | 室内、器物、特效、声景 | 触发时 | 按需 |

**分层（Layer）**——按「系统职责」分：
`L0 引擎与输入` → `L1 地形与水` → `L2 城市骨架（地坪/街/坊）` → `L3 近景城市（建筑/树/人）` → `L4 远景与异界` → `L5 后处理与特效`。
**规则**：低层先于高层；同层内按「离玩家距离」排序；高层不得依赖高层。

**分区（Zone）**——空间分块，按需流式：
- 网格边长按「玩家步行 30s」定（本项目 ≈ 200m）；
- 每区有状态：`未载 / 骨架 / 完整 / 休眠`；
- 进场预取 **1 环**，出场释放 **2 环外**；
- 关键地标（虹桥、城门、凌霄殿）常驻，不参与卸载。

**预载入（Preload）**：
- **首帧前置**：只预取 T1；
- **后台预取**：T2 在 `requestIdleCallback` 里分片；
- **方向预取**：按相机朝向与速度，预取前方 1 区；
- **纹理由粗到精**：先 1/4 分辨率占位，空闲时换全分辨率。

### 1.3 渲染（Rendering）—— 预算制
| 项 | 中端机目标 | 本项目当前 |
|---|---|---|
| 帧时间 | ≤ 16.6ms（60fps） | 桌面 ~120fps，未知移动端 |
| Draw call | ≤ 600 | 340–640 |
| 三角面/帧 | ≤ 500 万 | **4500–4700 万**（远超） |
| 阴影 | 1 盏主光，级联 ≤ 2 级 | 1 盏，未见级联 |
| 后处理 | Bloom + 色调映射 | Bloom + ACES |
| 实例化 | 同类同材质必须 Instanced | 已大量使用 |

**规则**：
1. **先剔除再减面**：视锥 → 距离 LOD → 遮挡；
2. **LOD 三档**：近（细节）/ 中（剪影）/ 远（图块），切换点按**屏幕像素**而非绝对距离；
3. **阴影预算独立**：阴影相机只覆盖玩家周围 120m；
4. **后处理降级**：检测到帧时间 > 20ms 连续 30 帧 → 关 Bloom / 降分辨率比例。

### 1.4 互动（Interaction）
- 输入 → 视觉反馈 ≤ 100ms；
- 相机永不因单帧卡顿跳变（用固定时间步 + 插值）；
- 任何 > 200ms 的操作必须有**即时反馈**（进度/音效/界面）。

## §2 本项目落地

### 2.1 已落地（本轮，含实测数字）
| 项 | 做法 | 位置 | 实测 |
|---|---|---|---|
| **几何缓冲改定长** | 顶点缓冲 `number[]` → 可增长 `Float32Array`（`FBuf`，含 `take()/reset()`，`.length` 兼容旧断言）。每面占用 ~320B → ~132B，且不再产生可回收临时对象 | `city/bake.ts` | 全城 11.2M 面 |
| **分批落盘（关键修复）** | 新增 `Baker.flush(scene)`：把当前缓冲烘成 mesh 后清空；**每个加载步结束调用一次**。材质/贴图由 `materialSet()` 缓存，只建一次 | `bake.ts` + `world.ts` | 峰值堆 3.34GB → **1.7GB**；载入由「永不完成」→ **15.9s LOADED** |
| **加载可测量** | 每步 `performance.now()` 计时 + 累计三角面 + `usedJSHeapSize` + 面数前四组；> 1200ms 点名；结果挂 `window.__loadTimings` | `world.ts` init 循环 | 33 步全表可见 |
| **步数细分** | 21 步 → 33 步：只按调用点切，调用顺序与共享 rng 消耗顺序逐字不变（世界逐值可复现） | 同上 | 最慢单步 2.36s → **1.85s** |
| **每步让帧** | 每个任务前后 `await raf()` | 同上 | 主线程不连续占用 |
| **池容量硬约束** | `MAX_HUMANS` 1400 → 1600（守卒 +164 曾撑爆池，`alloc` 抛错**静默打断初始化**） | `actors/pools.ts` | live 1423 |
| **渲染过曝治理** | `glow` 改走 ACES；Bloom 阈值 0.8 → 1.05；白玉 `0xfff8ef → 0xc9c4b8` | `bake.ts` / `engine.ts` | — |
| **打包版验证** | `verify-packaged` 走真 GPU | `scripts/verify-packaged.mjs` | `PACKAGED_BOOT=PASS`，1045 draw calls，errors NONE |

**根因结论（本轮最大教训）**：症状是「加载卡死」，但不是死循环——CDP `Debugger.pause` 也停不下来、冻结位置每次不同，是 **JS 堆吃到 3.3GB 后进 V8 GC 悬崖**。判据：`baker.stats()` 累计 10.4M 面时 `usedJSHeapSize` 正好 3.34GB，之后任何几何分配都会把线程拖死。

### 2.2 待落地（按优先级）
| 项 | 现状 | 目标 |
|---|---|---|
| **① 步内时间切片** | 已按调用点拆到 33 步、每步落盘，但**步内仍是同步**：最慢 5 步 1.1–1.9s（山河·地形 1851ms / 皇城·宫城 1643ms / 筑城·街屋群 1300ms / 皇城·里坊民居 1173ms / 云海·宫阙群 1105ms） | 把 `buildTerrain` / `buildImperialCity` / `buildAllCityBuildings` / `WardInfill` / `buildSkyExpansion` 改写成 `function*`，在对象循环里 `yield`，驱动端按 16ms 预算消费 |
| **② 三角面预算超标 10 倍** | 4500 万/帧 | 引入屏幕像素 LOD：远景总面数压到 500 万以内，近景保持 |
| **③ 分区流式** | 无分区，全部常驻 | 200m 网格分区 + 1 环预取 / 2 环释放 |
| **④ 阴影预算** | 全场景投影 | 阴影相机裁到玩家 120m |
| **⑤ 自适应画质** | 有 `applyDensity()`，但只按设备初判 | 连续 30 帧 > 20ms 自动降档（Bloom/分辨率/阴影） |
| **⑥ 预载 UI 反馈** | 只有进度百分比 | 加「当前在做什么」（已由 task 标签提供）+ 可取消 |

### 2.3 诊断纪律（本轮教训）
1. **`tsc` 绿 ≠ 能跑**：池溢出、主线程卡死、上下文丢失都只在运行时暴露；
2. **任何"卡住"必须先测量再改**：本轮通过 `[加载] xxx 超预算` 直接定位到具体 builder；
3. **二分别猜**：关树 → 仍卡；关坊墙 → 仍卡；关商铺 → 仍卡；说明需要打点而不是继续删；
4. **打包版验证不可省**：`verify-packaged` 用真 GPU 跑，能区分「软件渲染慢」与「CPU 侧挂死」。

## §3 验收口径（每条可执行）

> 当前实测（release-v31 / 真 GPU 打包版 + 无头 SwiftShader 双跑）：
> 1 ❌ 5 步超 1200ms（1851/1643/1300/1173/1105ms），总时长 15.9s（目标 12s）；
> 2 ✅ 载入期可交互（每步前后让帧）；3 ⚠ 未测 p95；4 ❌ 1120 万面 / 1045 calls（目标 800 万 / 600）；
> 5 ✅ `PACKAGED_BOOT=PASS`、errors NONE；6 ✅ 超预算必告警。

1. `window.__loadTimings` 全部步 ≤ 1200ms，总时长 ≤ 12s（桌面）；
2. 首帧可交互 ≤ 5s；
3. 帧时间 p95 ≤ 20ms（桌面 1080p）；
4. draw call ≤ 600，三角面/帧 ≤ 800 万（近景全开时）；
5. `PACKAGED_BOOT=PASS`，19 机位 0 控制台错误；
6. 任一加载步超预算 → 控制台告警，且**不允许**静默通过。

## §4 诊断工具（本轮新增，可复用）

| 脚本 | 用途 |
|---|---|
| `scripts/probe-load.mjs [url] [ms]` | 逐步打印 `[加载] ▶/✔`、累计面数、`usedJSHeapSize`、面数前四组；判定 `MAIN_THREAD: alive/BLOCKED` |
| `scripts/probe-hang.mjs [url] [ms]` | 冻结取证：`Debugger.enable` 必须在导航前开启，冻住后 `Debugger.pause` 触发 V8 中断并打印调用栈 |

**判据速查**：若冻结位置逐次漂移、`Debugger.pause` 返回的栈停在随机分配点、`usedJSHeapSize` 逼近 3GB → 是堆/GC 悬崖，不是死循环，改数据结构或分批落盘；若栈稳定指向同一行 → 才是逻辑死循环。
