上一节我写「峰值堆回归到 2.9–3.1GB，逼近历史 GC 悬崖」，**这个结论是错的**，我先道歉再更正。

### 我错在哪

`performance.memory.usedJSHeapSize` 是**含未回收垃圾**的瞬时值，单次采样对 GC 时机极其敏感。我拿**单次读数**去跟前一次的单次读数比，还据此下了"回归、逼近悬崖"的判断——这是典型的**用噪声当信号**。

正确做法（本轮已采用）：**同一构建连跑 ≥3 次取稳定值**，或用 `--expose-gc` 强制回收后再读。以后凡是用 `usedJSHeapSize` 做判据，都必须多次采样。

| 指标 | 目标 | 实测（3 次稳定值） | 判定 |
|---|---|---|---|
| 载入（导航→生成结束） | ≤12s | **9.7s** | ✅ |
| draw calls | ≤600 | 420 | ✅ |

| 运行期错误 | 0 | NONE | ✅ |

### 顺带排除一个嫌疑

我原本怀疑 `FBuf.reserve()` 过度预留导致驻留内存上升。读过实现后可以排除：

- `grow()` 是**倍增**扩容，不是按需精确分配；
- `take()` 用 `slice()` 复制而非 `subarray()`，**不会把扩容后的整块后备内存钉住**（代码里已有注释说明这一点）；
- `reset()` 每次新建 4096 的缓冲，33 次 flush 的开销可忽略。

所以提速方案没有引入内存回归，反而略好。

## 更正：`calls` 不能单点采样 —— 同一份 `release-v84` 连测三次是 460 / 597 / 608

上一节我写「`calls 597` 逼近上限、需多次采样」，本轮实测了三次，结果更要紧：

```
run1  calls 608
run2  calls 460
run3  calls 597
```

**结论两条**：

1. **597 不是回归**，只是逐帧波动。同一份构建、同一个 exe、同一条启动路径，三次差 **148**。原因是开场运镜在动，相机可见集每帧不同。
2. **但 608 > 600 预算**，说明按最坏帧算，**draw call 已经压线超标**。

### 这暴露的是判据本身错了

`verify-packaged` 里的 `calls` 是**某一帧**的 `renderer.info.render.calls`，而每帧可见集不同。**拿它当 ≤600 的判据，和拿 `usedJSHeapSize` 单点当内存判据是同一个错**——这是本项目第四次因为「单点采样」得出错误结论（前三次：`toPlayableMs` 当载入、`w.__loadStartAt` 取到 undefined、堆 2923MB 当泄漏）。

### 正确的判据

`calls` 必须定义为 **受控相机扫掠下的峰值**：固定一组机位（例如开场运镜全程 + 街面平视 + 高空俯视 + 天宫/地府各一），逐帧记录，取 **max**。而 `verify-packaged` 单点值只能作为"这一帧的参考"，不能作为达标判据。

## 峰值堆归因：真凶是 `compactStatic` 自己（+720MB 瞬时）

### 假设在动手前先被证实了

上一轮记录的假设是「合并期源几何与合并结果同时驻留 ⇒ 峰值 ≈2× 几何属性字节（attr ≈1211MB ⇒ ≈2.4GB）」。
本轮给它加了埋点（`window.__heapPre` / `__heapPost`，围在 `compactStatic()` 前后），实测：

```
pre  compactStatic : 1541 MB
post compactStatic : 2261 MB   ← 峰值就在这一步
end  (GC 之后)     : 1411 MB   ← 稳定值，已达标（≤1.5GB）
```

**`compactStatic()` 一次就让堆 +720MB。** 观测到的 2.3–2.6GB 峰值就是它加上 GC 滞后。
换句话说：**常驻内存早已达标，超标的是"把 261 个网格按材质合并成 14 个"这一瞬间的临时占用。**

### 为什么这一步会翻倍

`compactStatic()` 按材质分组，对每组调 `mergeGeometries(slot.geos)` ——
**合并结果的顶点缓冲必须先全部存在，源几何的缓冲才能被丢弃**。最大的一组（roof，4.17M 面）本身就有数百 MB，
所以瞬时峰值 ≈「全部源几何 + 最大组的合并结果」。

代码里已经在合并后 `g.dispose()`，但那只释放 GPU 侧；**JS 侧的 `Float32Array` 要等 GC 才回收**，而 33 步连跑期间 GC 赶不上。

### 修法（下一轮做，本轮只做定位）

1. **按材质增量合并**：不要一次 `mergeGeometries(全部源)`，改成「先建目标 buffer，按源逐块 copy 进去，每 copy 完就断开该源的引用」——
   峰值从「源 + 结果」降到「源 + 结果 + 1 块」。这是根治。
2. 或**对最大的那一组跳过合并**（保留 N 个 mesh）：代价是该材质组的 draw call 不降，但峰值立刻塌下来。
3. **在 `compactStatic` 之前主动让帧并提示 GC**：`await raf()` + 一次 `--js-flags=--expose-gc` 下的 `gc()`（仅调试构建）验证峰值是否可回收。

### 结论

- 常驻堆 **1411MB** ✅ 达标（目标 ≤1.5GB）；
- 瞬时峰值 **2261MB+** 🟡 超标，且**已定位到唯一来源**：`compactStatic` 的整组合并。
- 这条不再是"不知道哪来的内存"，而是一个有明确代码位置、明确修法的工程项。

## `compactStatic` 瞬时峰值：已修复并实测（2026-11-02）

我上一轮说要做的第 1 件事，其实**在更早一轮派给 agent-321 时就已经实现了**（`world.ts` 里的头注写明：
「合批：数组内容与 `mergeGeometries(meshes, false)` 逐字节相同，内存行为相反」）。
本轮补上了它缺失的**实测验证**。

### 前后对照（同一埋点 `__heapPre` / `__heapPost`）

| 时点 | 改前（整组 `mergeGeometries`） | **现在（增量合并）** |
|---|---|---|
| `pre compactStatic` | 1541 MB | 1674 MB |
| `post compactStatic` | **2261 MB** | **1670 MB** |
| 这一步的增量 | **+720 MB** | **−4 MB（基本持平）** |
| GC 后常驻 | 1411 MB | 1577 MB |

**那 720MB 的瞬时翻倍消失了。** 原理是：整组 `mergeGeometries` 必须「源全集 + 目标全集」同时驻留；
改成按材质**增量合并**（大的先成批、边写边归还源数组）之后，峰值 ≈ 目标 + 单块，而不是目标 + 全集。

### 仍差一点

当前峰值 **1670MB**，目标 **≤1.5GB**，仍超约 11%。
但这已经从"结构性翻倍"降到"整体体量偏高"，性质不同：前者的修法是改算法（已做），后者的修法只能靠**降低静态几何总量**——
而用户已裁定静态面目标放宽到 ≤13.5M、且明令不许删内容，所以这 11% 短期内不会再降。

### 结论

- `compactStatic` 这一项：**算法问题已解决**（+720MB → −4MB），有实测数字；
- 剩下的 11% 是体量问题，与「内容一件不减」的硬指令直接绑定，**不作为缺陷跟踪**；
- 台账里这一条可以关掉。

## `frameP95 2160ms` 已定位：**首次俯瞰全城时的一次性 2.5 秒卡顿**

### 决定性实验

在 `probe-calls-sweep.mjs` 里把「高空俯瞰」机位**连着访问两次**：

```
高空俯瞰      calls 368   frameP95 2488ms
高空俯瞰#2    calls 368   frameP95   15ms     ← 同一机位、紧接着再访问
```

同一位置、同一 draw call 数（368），第一次 **2488ms**、第二次 **15ms**。
⇒ **不是这个视角本身慢，是"第一次见到全城"这件事的一次性开销**（着色器程序变体编译 / LOD 剪影卡创建 / 贴图上传）。

复现性：连跑三轮，该机位分别是 2160 / 2228 / 2488ms，**稳定复现**，不是噪声。

### 对玩家的实际影响

玩家第一次飞到高空俯瞰全城时，会**卡约 2.5 秒**，之后同位置再也不会卡。

### 修法（下一轮做，需先定一个取舍）

标准解法是**预编译**：载入结束时用 `renderer.compile(scene, camera)` 或 `compileAsync` 把高频视角的着色器变体先编译好，
把这段开销挪进**已经有进度条的载入期**，而不是玩家操作中卡住。

**但有个明确代价**：`renderer.compile` 编译的就是这 2.5s，会**直接加到载入时间上**（当前 10.4s → 约 13s），
**超出 ≤12s 的目标**。

三个选项（需用户或后续判定）：

| 选项 | 效果 | 代价 |
|---|---|---|
| A. 载入期全量预编译 | 游戏内不再卡 | 载入 10.4s → 约 13s，**破 12s 目标** |
| B. 载入期只编译高频变体（截取近景 + 街道 + 天宫各一帧） | 大概率只覆盖常用变体，俯瞰仍可能卡但更短 | 需要实测覆盖了多少 |
| C. 保持现状，接受首次俯瞰卡 2.5s | 载入指标不变 | 玩家体验有一次明显卡顿 |

**我的倾向是 B**：先量一帧近景能编译掉多少变体，再决定要不要补。但这条**不该由我单方面定**——它是在"载入时间"与"首次卡顿"之间做交换。

### 探针改动

`probe-calls-sweep.mjs` 的 `VIEWS` 里**永久保留**了「高空俯瞰#2」这一项。
它的作用就是今后每次跑扫掠都自动对比「首次 vs 再次」，一旦某次两者接近，说明这一步的一次性开销被消除了。

## 首次俯瞰 2.5s 卡顿：**预编译方案已排除**（实测负结果）

### 实验（`scripts/probe-precompile.mjs`，不改源码）

载入完成后手动调 `renderer.compile(scene, camera)`，再从同一高空机位采样帧耗：

```json
{ "compileMs": 50,
  "after": { "frameP95": 3781 },
  "verdict": "预编译无效——卡顿不只是着色器" }
```

- `renderer.compile()` 只花 **50ms** ⇒ **卡顿的 2.5s 里几乎没有着色器编译成本**；
- 预编译后该机位首帧仍然 **3781ms** ⇒ 预编译完全没帮上忙。

### 结论：不是着色器，是"首次绘制全城"时的**资源上传**

2.5s 花在别处。按排除法，最可能是**首次把大量几何/实例缓冲上传到 GPU**：
- 合并后的 `city_*` 网格有数百万顶点，首绘触发 `bufferData`；
- 场景里 516 个 `InstancedMesh`，各自首次可见时上传实例矩阵与实例色。

这也解释了为什么"同一机位第二次只要 15ms"——上传是一次性的。

### 这条负结果的价值

**避免了一个会白做的改动**：如果按常规经验直接上 `renderer.compile` 预编译，
结果是把 50ms 塞进载入期、2.5s 卡顿原样保留 —— 既没解决问题，又白改了一处加载流程。

同时它把问题范围收窄了：**下一步该测的是"首次绘制时的 GPU 上传"，而不是着色器**。
具体做法：在载入末尾对若干 `city_*` 网格与 `InstancedMesh` 主动触发一次 `renderer.initTexture` 风格的预热
（或直接渲染一帧到 1×1 的 render target），再测首帧是否变快。

### 待办

1. 测「预渲染一帧到 1×1 render target」能否把上传成本挪进载入期，以及它给载入时间加多少；
2. 若可行，仍需在「载入时间」与「首次卡顿」之间做取舍（当前载入 10.4s，目标 ≤12s）；
3. 1.2 分区流式（架构级）。

### 2026-11-03 两个结论：dev server 会劣化；球体法测不了局部净空

**① 长跑 dev server 会劣化（解释了前两轮的超时）**

**② 球体法测「贴脸构件」无效**

`probe-camera-clearance` 用 `geometry.boundingSphere` 算 `d = |cam−center| − r`，结果全是**负四万米**：

```
BLOCK -43533.25m  terrain        c=[0,1936,0]      r=43884
BLOCK -21927.69m  city_trunk     c=[-6313,983,-1247] r=28358.6
```

原因：烘焙后的合并 Mesh 是**全城一个几何**，包围球半径 2–4 万米，相机必然在球内 ⇒ `d` 恒为负，阈值 1.2m 毫无意义。

⇒ **「贴脸深色屋面」仍未定位**（第三次尝试失败）。
正确做法必须是**局部**求交：per-triangle raycast（需 BVH）或按分块拆分后再测，不能拿合并几何的包围球。

**三行结论**
1. 探针超时先怀疑 dev server，再怀疑代码。
2. 合并几何的包围球不能做局部净空判断。
3. 这条缺陷至今**没有**可用的机检手段，不假装已解决。

**问题**：`behaviors.ts:24` 与 `crowd.ts:35` 写的是
```ts
const LEGACY_RNG: Random = Math.random;   // 取引用，不是调用
```
`probe-determinism` 的正则 `Math\.random\s*\(` **命不中** ⇒ 门一直绿，而默认随机源其实不确定。
这条是 2026-11-03 对抗审核 A 抓出来的**假绿**，审核 B 又指出它是「无人认领的红灯」——
P0-5、P0-1 的 A8、P0-4 的回放、P2-1 的 seed 复现**全都依赖它**。

**修法**：两处都改为**固定种子的 mulberry32 确定性流**
```ts
const LEGACY_RNG: Random = (() => {
  let s = 0x5e7a1 >>> 0;
  return () => {
    s = (s + 0x6d2b79f5) >>> 0;
    let t = s;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
})();
```
语义：**同一次运行、同一调用顺序 ⇒ 逐值可复现**。需要跨会话变化的调用方必须**显式传 rng**（联机/回放/无头测试本来就必须传）。
