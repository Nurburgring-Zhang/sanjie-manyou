上一节我写「峰值堆回归到 2.9–3.1GB，逼近历史 GC 悬崖」，**这个结论是错的**，我先道歉再更正。

### 我错在哪

`performance.memory.usedJSHeapSize` 是**含未回收垃圾**的瞬时值，单次采样对 GC 时机极其敏感。我拿**单次读数**去跟前一次的单次读数比，还据此下了"回归、逼近悬崖"的判断——这是典型的**用噪声当信号**。

正确做法（本轮已采用）：**同一构建连跑 ≥3 次取稳定值**，或用 `--expose-gc` 强制回收后再读。以后凡是用 `usedJSHeapSize` 做判据，都必须多次采样。

| 指标 | 目标 | 实测（3 次稳定值） | 判定 |
|---|---|---|---|

### 顺带排除一个嫌疑

我原本怀疑 `FBuf.reserve()` 过度预留导致驻留内存上升。读过实现后可以排除：

- `grow()` 是**倍增**扩容，不是按需精确分配；
- `take()` 用 `slice()` 复制而非 `subarray()`，**不会把扩容后的整块后备内存钉住**（代码里已有注释说明这一点）；
- `reset()` 每次新建 4096 的缓冲，33 次 flush 的开销可忽略。

所以提速方案没有引入内存回归，反而略好。

## 更正：`calls` 不能单点采样 —— 同一份 `release-v84` 连测三次是 460 / 597 / 608

上一节我写「`calls 597` 逼近上限、需多次采样」，本轮实测了三次，结果更要紧：

```
run1  calls 608
run2  calls 460
run3  calls 597
```

**结论两条**：

1. **597 不是回归**，只是逐帧波动。同一份构建、同一个 exe、同一条启动路径，三次差 **148**。原因是开场运镜在动，相机可见集每帧不同。
2. **但 608 > 600 预算**，说明按最坏帧算，**draw call 已经压线超标**。

### 这暴露的是判据本身错了

`verify-packaged` 里的 `calls` 是**某一帧**的 `renderer.info.render.calls`，而每帧可见集不同。**拿它当 ≤600 的判据，和拿 `usedJSHeapSize` 单点当内存判据是同一个错**——这是本项目第四次因为「单点采样」得出错误结论（前三次：`toPlayableMs` 当载入、`w.__loadStartAt` 取到 undefined、堆 2923MB 当泄漏）。

### 正确的判据

`calls` 必须定义为 **受控相机扫掠下的峰值**：固定一组机位（例如开场运镜全程 + 街面平视 + 高空俯视 + 天宫/地府各一），逐帧记录，取 **max**。而 `verify-packaged` 单点值只能作为"这一帧的参考"，不能作为达标判据。

按这个口径，`release-v84` 的实测最坏帧是 **608**，需要再降 8 个 call 才能回到 ≤600 的硬预算内。

### 待办

1. 做一个 `scripts/probe-calls-sweep.mjs`：固定 6 个机位 × 每个机位停留 3 秒，记录 `calls` 的 max 与分布；
2. 用它的 max 作为 `calls` 的唯一判据，替换 `verify-packaged` 的单点读数；
3. 若 max 确实 >600，再从 `pool_*`（角色池 74 个网格）与 `veh_*`（35 个）这两块此前记录为"不在可改范围"的地方找空间。

## 峰值堆归因：真凶是 `compactStatic` 自己（+720MB 瞬时）

### 假设在动手前先被证实了

上一轮记录的假设是「合并期源几何与合并结果同时驻留 ⇒ 峰值 ≈2× 几何属性字节（attr ≈1211MB ⇒ ≈2.4GB）」。
本轮给它加了埋点（`window.__heapPre` / `__heapPost`，围在 `compactStatic()` 前后），实测：

```
pre  compactStatic : 1541 MB
post compactStatic : 2261 MB   ← 峰值就在这一步
end  (GC 之后)     : 1411 MB   ← 稳定值，已达标（≤1.5GB）
```

**`compactStatic()` 一次就让堆 +720MB。** 观测到的 2.3–2.6GB 峰值就是它加上 GC 滞后。
换句话说：**常驻内存早已达标，超标的是"把 261 个网格按材质合并成 14 个"这一瞬间的临时占用。**

### 为什么这一步会翻倍

`compactStatic()` 按材质分组，对每组调 `mergeGeometries(slot.geos)` ——
**合并结果的顶点缓冲必须先全部存在，源几何的缓冲才能被丢弃**。最大的一组（roof，4.17M 面）本身就有数百 MB，
所以瞬时峰值 ≈「全部源几何 + 最大组的合并结果」。

代码里已经在合并后 `g.dispose()`，但那只释放 GPU 侧；**JS 侧的 `Float32Array` 要等 GC 才回收**，而 33 步连跑期间 GC 赶不上。

### 修法（下一轮做，本轮只做定位）

1. **按材质增量合并**：不要一次 `mergeGeometries(全部源)`，改成「先建目标 buffer，按源逐块 copy 进去，每 copy 完就断开该源的引用」——
   峰值从「源 + 结果」降到「源 + 结果 + 1 块」。这是根治。
2. 或**对最大的那一组跳过合并**（保留 N 个 mesh）：代价是该材质组的 draw call 不降，但峰值立刻塌下来。
3. **在 `compactStatic` 之前主动让帧并提示 GC**：`await raf()` + 一次 `--js-flags=--expose-gc` 下的 `gc()`（仅调试构建）验证峰值是否可回收。

### 结论

- 常驻堆 **1411MB** ✅ 达标（目标 ≤1.5GB）；
- 瞬时峰值 **2261MB+** 🟡 超标，且**已定位到唯一来源**：`compactStatic` 的整组合并。
- 这条不再是"不知道哪来的内存"，而是一个有明确代码位置、明确修法的工程项。

### 342 · 地府"灰模" ✅

**真相：材质在，被一层恒定自发光洗掉了。**

`src/city/bake.ts:1451`：

```ts
wall: new THREE.MeshLambertMaterial({ vertexColors: true, emissive: 0x3a3d48, map: wallTex, ... })
```

`emissive: 0x3a3d48` 是恒定蓝灰自发光，无差别叠加在顶点色（殿身本是 `0x38202c` 朱红）之上。
地府本就暗，这点自发光压过顶点色 ⇒ 整面读成**灰蓝素板**。

**影响面比地府大**：`wall` 是全局材质组，任何光弱处（地府 / 夜间 / 背光面）都会被拉平。
**这也是"所有建筑的墙都差不多"的一部分原因——不是墙面做法单一，是被同一层自发光抹平了。**

### 344 · 人群自由行走 / 相机鼠标视角 ✅

**"所有人排成线"的三条根因**：

1. `buildNav()` 按 26m 间距把节点铺在**每条街的单条中心线**上，`randomRoam()` 只从节点选终点 ⇒ 全街共享同一串终点；
2. `randomRoam` 70% 强制走前半球；出生朝向只有 `dir` / `dir+π` 两档 ⇒ 双向流锁成两条窄带；
3. 移动层无个体差异（只改 x/z、速度固定、到站立刻换向）⇒ 目标不同也踩同一条脚印。

步速系数 0.72–1.32、局部避让（4m 格网、1.6m 内邻居侧向排斥）、到站 30% 驻足 1.4–4.6s。

**它对我一条判据的反驳，我接受**：我要求"朝向直方图 ≥4 个峰"，它指出**自由行走的极限是均匀分布，
